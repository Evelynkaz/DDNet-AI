## 2. Харнесс

Каталог `~/aiddnet/data/research/harness/` (импортирует модули репо по абсолютному пути, переменная `DDNET_AI_SRC` может его переопределить):

| файл | что делает |
|---|---|

### 2.1. Как харнесс повторяет live-бота

- **Конфиг планировщика = дефолтный live** (`bot.ts`: `plannerCfgNow()` = `{ budgetMs: LIVE_BUDGET_MS=18, explain: true, ...LIVE_PLANNER_CFG }`,
  `LIVE_PLANNER_CFG = { thirdTeeExposure: 0, memoryTrust: 0.9, frozenThrow: 3 }`, остальное — `PLANNER_DEFAULTS`: steps 9 × planStep 3 = горизонт
  27 тиков (0.54 с), population 20, iterations 2, elite 6, opponentModel "hold", shield on, commitDecisions 1). Мозг «p» (по умолчанию в `start.mjs`),
  не `--low-cpu`, не `--strong`, не «bold». WB-оверрайды (`WB_PLAN_OVERRIDES`) включаются только внутри WB-зала при «удержании» WB — в харнессе их нет.
- **Каденс**: решение на каждом снапшоте = каждые 2 тика (25 снапшотов/с, `SNAPSHOT_PERIOD_MS = 40`), вход держится 2 тика. Оба бота решают по одному и тому же состоянию, затем 2 шага мира.
- **Синхронизация (режим `snapshot`, по умолчанию)** — как `DdnetBot.planAction`: отдельный `SimWorld` планировщика с двумя ти, каждое решение
  `syncPlanningWorld()` (`applyTeeState` из `TeeState`-снапшота, `setHeldInput`, прокрутка на `lag` тиков входами «в полёте»), `enemyInputFromSnapshot(target)`
  как модель соперника, `setTravelGoal(pathGoal)` (копия логики `bot.ts pathGoal/pathAhead`: при дистанции < 420 px и чистой линии — `null`, иначе `findRoute`),
  `setLiveTick(world.tick)`, затем `planner.decide()`. Режим `direct` (`--a planner-direct`) отдаёт в `decide()` сам «настоящий» мир (планировщик делает save/restore) — идеальная информация.
- **Скриптовый бот** — `scriptedAction()` из `src/env/scripted.ts` как есть (свой `Rng` на партию). Вариант `scripted-guard` добавляет щит
  `escapeExists/saferInput`, которым live-бот оборачивает скриптового (`DdnetBot.guard`).
- Сиды: партия `g` → `seed = seed0 + g`; спавн из `Rng(seed·2654435761)`, на нечётных партиях стороны меняются местами; `planner.setSearchSeed(seed)`
  (в live этого нет — там seed всегда 1), скрипт `Rng(seed·7919+17)`.

### 2.2. Чем харнесс НЕ является (отличия от live)

- Нет сети и квантования снапшотов сверх того, что уже делает `SimWorld.quantize()`; `lag = 0` по умолчанию (есть `--lag`).
- Нет всей логики `bot.ts` вокруг планировщика: выбор цели, навигация/трек, WB-удержание, спасение друзей, `/kill` при застревании, rescue, эмоции, `ropeCatches`-фильтр по «пощажённым».
- `FreezeMemory = null` (в live на новой карте она тоже пустая; `memoryWeight = 0`, так что влияет только `memoryTrust` через `safety()`), dead-zone не задаётся (её веса по умолчанию 0).
- Мир «сервера» — тот же TS `SimWorld` (не настоящий DDNet), поэтому это проверка планировщика в его собственной физике.
- Планировщик всегда id 0, соперник id 1. В `SimWorld` последний добавленный ти идёт первым в `order` (B обрабатывается раньше A в каждом тике); стороны спавна чередуются.

## 3. Определение победы

Исход решается на **первом тике, когда какой-то ти «выбывает»**: начало фриза (`frozen` false→true) или смерть.
- выбыл только B → **W** (победа A), только A → **L**, оба в один тик → **D**;
- никто не выбыл за 1500 тиков (30 с игрового времени) → **T** (ничья по таймауту; в таблицах считается отдельно от D).

Вторичные признаки (для победы):
- **credited** — жертву за ≤ 50 тиков до фриза касался победитель (держал крюком или ударил молотком) — ровно как live-статистика `blocks`
  (`bot.ts onFreezeOnset`, `BLOCK_CREDIT_TICKS = 50`). `credited = false` значит «соперник заморозился сам» (упал/зашёл во фриз без касания).
- **held** — игра продолжается ещё 150 тиков (3 с); held = жертва в конце всё ещё во фризе/мертва и победитель за это окно ни разу не выбыл.

Плюс: повтор целых серий в отдельных процессах под другой нагрузкой — b0: 20/20 и 20/20 партий с идентичными хэшами решений обоих ботов
(platform, CLB); live: 1/20. `budgetMs: 1000` (никогда не срезает) даёт тот же хэш, что `budgetMs: 0`.

Источник недетерминизма — ровно один: `Planner.decideOnce()` проверяет дедлайн по стеночным часам
(`planner.ts:1107` `deadline = Date.now() + budgetMs`, проверка `(i & 3) === 3 && Date.now() > deadline` в цикле популяции, строка 1167;
`hardMs`/`overCap()` — только в `--low-cpu`, по умолчанию 0). Срез уменьшает число вызовов `samplePlan()`, а `Rng` планировщика один на всю
партию → после первого же среза сдвигается весь дальнейший поток случайных чисел и расходятся все следующие решения (первое расхождение —
3–10-е решение, из-за холодного JIT). `Math.random` нигде в `core/plan/env/nn/map` не используется; `Date.now()` ещё только в `lastInfo.ms` (информационно).

**Режим фиксированных итераций уже существует**: `budgetMs: 0` (и `hardMs: 0`) в конфиге → population × iterations без срезов. Правка кода не нужна,
копии/патчи файлов не понадобились. Если для эталонных трасс нужен «бюджет, но детерминированный», минимальная правка — заменить часы на счётчик
оценок в `decideOnce()`, например:
```diff
-    const deadline = Math.min(this.cfg.budgetMs > 0 ? Date.now() + this.cfg.budgetMs : Infinity, hardline);
+    const evalCap = this.cfg.maxEvals > 0 ? this.cfg.maxEvals : Infinity;   // новое поле PlannerConfig
 ...
-        if (deadline !== Infinity && (i & 3) === 3 && Date.now() > deadline) {
+        if ((i & 3) === 3 && candidates + scored.length >= evalCap) {
```
(не применялось; для baseline достаточно `budgetMs: 0`).

Замечание для Rust-порта: физика TS считается в `double` (ни одного `Math.fround`), тогда как DDNet — во `float`; из трансцендентных в `core/`
используются `Math.atan2`, `atan`, `pow` (velramp), `sin`, `cos`, `sqrt`; в планировщике ещё `log/sin/cos` (Гаусс в `Rng`), `hypot`.
Для побитового совпадения с TS-трассами нужны реализации, совпадающие с V8 (fdlibm-порт `ieee754::*`), а не системная libm.

## 8. Что удивило / наблюдения о поведении

1. **Недетерминизм live-конфига** (см. §7): одна и та же позиция в двух запусках даёт разные партии (разброс длины 87–264 тика на одном сиде).
2. **Щит — не редкая страховка, а постоянный фильтр**: подменяет выбор поиска в 10–17 % решений на платформе против скрипта и в 35 % в зеркальном матче.
3. **Планировщик «выманивает»**: на платформе он часто висит на крюке за краем, а скрипт бежит за ним прямо во фриз — 16–19 из 30 побед без касания.
   Против скрипта со щитом побед без касания меньше, партии вдвое длиннее.
4. **Крюк по замороженному врагу**: в трассе `platform seed 2 b0` (t≈160) планировщик зацепил уже замороженного B на дне озера и поднял его
   с y≈26.5 до ≈17.4 тайла, после чего отпустил обратно. Причина — бонус `hookHoldWeight` за удержание врага и `noThawRope: false` по умолчанию
   (в WB-оверрайдах `noThawRope: true`). Риск «разморозить» жертву. (`held = false` на CLB в 2 из 20 побед — причину по трассам не разбирал.)
5. **Зеркальный матч не сходится**: 39/40 таймаутов — два одинаковых осторожных планировщика не рискуют.
6. **Горизонт короткий** (27 тиков = 0.54 с) при шаге плана 3 тика и решениях каждые 2 тика; `warmShiftElapsed: false` → тёплый старт
   сдвигается на 1 шаг (3 тика), хотя прошло 2.
7. **`setSearchSeed` не используется в live** → в live seed всегда 1; `reset()` пересоздаёт `Rng` только при пересоздании planSim/смене карты.
8. Модель соперника по умолчанию `"hold"`: соперник на весь горизонт держит направление/крюк/прицел из снапшота; `scriptedAction` как модель соперника включается только при `opponentModel: "react"` / `opponentMix`.
9. `planSim.tick` в live никогда не синхронизируется с серверным тиком (растёт только на `lag` за решение); `applyTeeState` использует его для `freezeStart`/`attackTick` — харнесс это воспроизводит как есть.
10. «Холодный» старт: первые ~100 решений процесса в 1.3–2 раза медленнее, отдельные — до 200 мс; с бюджетом 18 мс именно они срезаются первыми.

## 9. Для следующего шага (генератор эталонных трасс)

- Использовать `budgetMs: 0` (детерминированно; совпадает с live, когда тот не срезан).
- `trace.mjs --json` уже пишет по каждому решению позиции/скорости/фриз/крюк/входы обоих ботов; `runGame()` считает sha1-хэш потока решений
  каждого бота (`hashA/hashB`) — удобно как контрольная сумма для сравнения с Rust.
- Хэши решений b0 стабильны между процессами и под нагрузкой (Node 24.21 / V8) — эталон можно фиксировать по `(арена, сид, конфиг) → hash`.
