# Форматы файлов и протоколов: rawmap v1, scenario v2, trace v1, `.flyg` v1, протокол 0.6+DDNet

Этот документ описывает три бинарных формата, которыми обмениваются Rust (`crates/ddai-trace`)
и C++-оракул (`tools/ddnet-oracle`), и каноничный потиковый хэш состояния. Все три формата —
собственные, не связаны с форматом карт DDNet (`.map`/datafile v4): цель — минимальный, точно
специфицированный формат, который легко читать и писать на обеих сторонах, а не совместимость
с реальными картами (та потребуется позже, отдельной задачей).

Все целые и float — little-endian. `f32`/`f64` хранятся как raw IEEE-754 биты (не текст, не
округление): `f32::to_bits()`/`from_bits()` на стороне Rust, `memcpy` через `uint32_t`/`uint64_t`
на стороне C++. Строки — префикс длины (`u16` или `u32`, см. каждый формат) + UTF-8 байты без
терминатора и без паддинга. Нет сжатия, нет опциональных полей за пределами явно описанных
битовых масок/тегов.

Rust-реализация (источник истины наравне с этим документом, при разногласии смотреть тесты):
`crates/ddai-trace/src/{rawmap,scenario,trace,io}.rs`. C++-реализация (`oracle_core.cpp`) —
независимый ридер для rawmap и scenario (только читает эти два формата, никогда не пишет их) и
единственный писатель trace (пишет, но не читает обратно — trace читает только Rust).

**Версии.** rawmap — v1 (не менялась). trace — v1 (не менялась). scenario — **v2** (v1
заменена по итогам ревью раунда 1, находка F3 — «прицел», §2.1): читатели обеих сторон
отклоняют файл с `version != 2` как неподдерживаемый — старый v1-файл не пройдёт молча,
он просто перестанет парситься.

## 1. rawmap v1

Плоское бинарное представление `ddai_physics::map::MapData` — данные тайловых слоёв карты,
без логики коллизий. Компактнее и проще, чем настоящий DDNet `.map` (datafile v4 + zlib): нет
сжатия, нет произвольных «item»/«data» индексов — только то, что нужно [`CLayers::Init`] /
[`CCollision::Init`].

```
magic            [4]     "RMP1" (ASCII, без нуль-терминатора)
version          u32     1
width            u32     ширина в тайлах
height           u32     высота в тайлах
present          u8      битовая маска присутствующих опциональных слоёв:
                            бит 0 (0x01) — front
                            бит 1 (0x02) — tele
                            бит 2 (0x04) — speedup
                            бит 3 (0x08) — switch
                            бит 4 (0x10) — tune
                          (game присутствует всегда, в маске не участвует)

game             [Tile; width*height]           всегда
front            [Tile; width*height]           если present & 0x01
tele             [TeleTile; width*height]       если present & 0x02
speedup          [SpeedupTile; width*height]    если present & 0x04
switch           [SwitchTile; width*height]     если present & 0x08
tune             [TuneTile; width*height]       если present & 0x10

settings_count   u32
settings[i]      { len: u32, bytes: [u8; len] }  UTF-8, settings_count раз
```

Порядок тайлов в каждом слое — row-major: индекс `y * width + x`, `x` — быстрее меняющийся
(как `CLayers`/`CCollision` ожидают от `IMap::GetData`).

Байтовый макет записей — точная копия полей и порядка `mapitems.h` DDNet 20.1 (см.
`crates/ddai-physics/src/map.rs`, там же — док-комментарии с точными ссылками на `mapitems.h`):

| Тип         | Байты | Поля (в порядке) |
|-------------|-------|------------------|
| `Tile`      | 4     | `index:u8, flags:u8, skip:u8, reserved:u8` (= `CTile::m_Index/m_Flags/m_Skip/m_MustBe0`) |
| `TeleTile`  | 2     | `number:u8, kind:u8` (= `CTeleTile::m_Number/m_Type`) |
| `SpeedupTile` | 6   | `force:u8, max_speed:u8, kind:u8, reserved:u8(=0), angle:i16` (= `CSpeedupTile::m_Force/m_MaxSpeed/m_Type/m_MustBe0/m_Angle`) |
| `SwitchTile`| 4     | `number:u8, kind:u8, flags:u8, delay:u8` (= `CSwitchTile::m_Number/m_Type/m_Flags/m_Delay`) |
| `TuneTile`  | 2     | `number:u8, kind:u8` (= `CTuneTile::m_Number/m_Type`) |

`SpeedupTile` в Rust (`ddai_physics::map::SpeedupTile`) не хранит поле `reserved`
(`m_MustBe0` у DDNet) — оно всегда 0 и не несёт информации, поэтому вынесено из структуры, но
байт зарезервирован и в файле присутствует (нулевой), чтобы длина записи (6 байт) была
предсказуемой и совпадала с `sizeof(CSpeedupTile)`.

Settings (строки настроек карты, аналог DDNet `Settings`-слоя) есть в формате для полноты, но ни
один из четырёх синтетических рецептов (§3) их не использует — везде `settings_count = 0`.
Оракул A их не парсит (не нужны core-уровню).

## 2. scenario v2

Ссылка на карту + мировые флаги + tuning-переопределения + список персонажей (id и спавн) +
явные потиковые вводы на каждого персонажа. Персонажи не спавнятся/не умирают в течение
сценария (Oracle A — только core, без DDRace) — список персонажей и их позиции фиксированы
на весь прогон.

```
magic              [4]   "SCN1"
version            u32   2
map_ref_tag        u8    0 = Recipe (имя рецепта), 1 = RawmapFile (путь к .rawmap-файлу)
map_ref_string     { len: u16, bytes: [u8; len] }   имя рецепта или путь (UTF-8)
map_sha256         [32]  sha256 rawmap-байт карты, на которую ссылается map_ref
no_weak_hook       u8    0/1, аналог sv_no_weak_hook (см. §5.3)

tuning_override_count  u32
tuning_overrides[i]    { name: {len:u16, bytes}, value_x100: i32 }   tuning_override_count раз

character_count    u32
characters[i]      { id: u32, spawn_x: i32, spawn_y: i32 }   character_count раз

tick_count         u32
inputs[t][c]        ScenarioInput   tick_count * character_count раз, в порядке
                                    «внешний цикл — тик по возрастанию, внутренний — c
                                    по индексу в characters[] (НЕ по id)»
```

`ScenarioInput` — *хранимый* рецепт ввода (11 полей `i32`, 44 байта), не готовый
`CNetObj_PlayerInput` — см. §2.1, почему. В этом порядке:

```
direction, target_x, target_y, aim_slot, jump, fire, hook, player_flags, wanted_weapon, next_weapon, prev_weapon
```

Все поля, кроме `aim_slot`, — как у `CNetObj_PlayerInput` (`generated/protocol.h`); `aim_slot`
вставлен между `target_y` и `jump` (см. §2.1). Применённый («resolved») ввод — `PlayerInput`,
ровно 10 полей `CNetObj_PlayerInput` в исходном порядке (без `aim_slot`) — именно он попадает в
`CCharacterCore::m_Input` и именно он — «применённый ввод» в trace-файле (§6): `aim_slot` там
уже не существует, он есть только в scenario.

### Проверки при чтении (`Scenario::read_bytes` / `ParseScenario` + `ValidateScenario`)

И Rust, и C++ ридер отклоняют файл (с ошибкой, не молча) если:

- `version != 2` (в т.ч. старый v1-файл — раунд 1, находка F3, сменил формат несовместимо);
- у какого-то персонажа `id >= MAX_CLIENTS` (`128`, `engine/shared/protocol.h`) — иначе запись
  в `CWorldCore::m_apCharacters[Id]` (массив ровно `MAX_CLIENTS` элементов) ушла бы за границу
  (раунд 1, находка F5: `id` из файла ранее не проверялся вовсе — ASan это не поймал на `id=100`,
  так как `100 < 128`, реальная граница выше, чем ожидал ревьюер, см. пояснение в отчёте);
- два персонажа делят один `id` (`World.m_apCharacters[Id]` был бы перезаписан вторым, первый
  стал бы недостижим для `m_apCharacters`, хотя всё ещё тикался бы — тихая, путающая порча
  данных, не крэш);
- у какого-то ввода `aim_slot` не равен `-1` и не является валидным индексом персонажа
  (`0..character_count`).

### 2.1 «Режим прицела» (`aim_slot`) и `resolve_input`

**История (раунд 1, находка F3).** В scenario v1 прицел каждого персонажа на каждый тик был
готовым абсолютным вектором `(target_x, target_y)`; генератор `random-v1`, целясь «в напарника»,
считал этот вектор один раз — от СВОЕЙ и ЕГО позиции СПАВНА — и хранил его. Поскольку персонажи
двигаются, а спавн статичен, векторы почти всегда быстро «расходились» с реальным напарником —
замеры на 200 сценариях (1.8М ти-тиков): событий захвата хука на игроке всего 1 886 (против
15 666 у эталонного «живого» прицеливания — ×8.3), доля тиков захвата всего 3.1% (против 26%).
Золотые фикстуры (§7, по 600 тиков) почти не содержали игрового взаимодействия хуком (37 событий
на все 8 фикстур, у `freeze_102` — 0).

**Решение.** `ScenarioInput` хранит НЕ готовый вектор, а *рецепт* его вычисления на каждый тик,
заново, от РЕАЛЬНОЙ (на тот тик) позиции цели:

- `aim_slot == -1`: `(target_x, target_y)` — явная («explicit») цель, используется как есть
  (ровно старое поведение v1).
- `aim_slot == k` (`0 <= k < character_count`): цель — `(pos[k] − pos[self]) + (target_x,
  target_y)`, где `pos[..]` — позиции персонажей ПОСЛЕ `Quantize()` предыдущего тика (на тике 0
  нет предыдущего тика — используется позиция спавна), а `(target_x, target_y)` теперь читается
  как небольшой целочисленный шум прицеливания, добавленный к «живому» вектору. Если результат
  РОВНО `(0, 0)` (цель точно в той же точке, что и `self`, и шум её не сдвигает) — откат на
  `(target_x, target_y)` как есть, то есть ровно на поведение `aim_slot == -1` (`CNetObj_
  PlayerInput` запрещает целиться точно в центр — генератор гарантирует, что этот запасной
  вектор сам никогда не `(0, 0)`).

Вся арифметика — целая `i32` (никогда float): каждая позиция, участвующая в вычислении, всегда
точно целая (позиция спавна, либо `m_Pos` после `Quantize()`, которая округляет до целого
пикселя) — округлению float здесь просто нечего испортить между Rust и C++.

Реализации — ОДНА в Rust (`crates/ddai-trace/src/scenario.rs::resolve_input(input, self_slot,
prev_positions)`, `pub`, будущая задача 1.3 должна звать её прямо, а не переизобретать) и
независимая эквивалентная в C++ (`oracle_core.cpp::ResolveInput`). У оракула `prev_positions`
не отдельный массив с копированием — после `Move()`+`Quantize()` очередного тика он просто
кэширует `(int32_t)Cores[slot].m_Pos.{x,y}` в `PrevPositions[slot]`, которое как раз и служит
«предыдущей позицией» для СЛЕДУЮЩЕГО тика; на тике 0 `PrevPositions` инициализирован позициями
спавна из `Scenario::Characters`.

Генератор `random-v1` (§4): «прицел» персонажа теперь либо `aim_slot` фиксированного «напарника»
(следующий по списку персонаж, с шумом ±30 по каждой оси, перерисовывается той же логикой, что и
раньше — раз в 10..50 тиков + 1/10 в тик во время хука), либо (без напарника, либо 1/3 случаев)
явный случайный вектор длины 1000, как в v1. `aim_slot` персонажа НЕ меняется между
перерисовками прицела — только сам шум/явная цель — то есть между перерисовками персонаж
продолжает целиться в того же «напарника», а РЕЗУЛЬТАТ (`resolve_input`) при этом сам собой
обновляется каждый тик по его текущей позиции, без каких-либо изменений в самом сценарии.

**Результат после исправления** (тот же 200-сценарийный замер, arena, seed=5, 500 тиков × 3
персонажа — см. отчёт о билде): 15 событий захвата хука на игроке и 454/1500 (30%) тиков с
захваченным игроком — на порядок больше, чем до исправления, сравнимо с «живым» экспериментом
ревьюера.

### Tuning-переопределения

`value_x100` — то же представление, что и внутри `CTuneParam` у DDNet (`m_Value = (int)(v *
100.0f)`): фиксированная точка ×100, целое. Формат хранит именно это целое (не float), чтобы
байты сценария не зависели от того, как какой-то писатель округлил float в текст и обратно.
`name` — строчное имя параметра из `src/game/tuning.h` (`ScriptName`, например `"gravity"`,
`"hook_length"`, без учёта регистра — оракул ищет через `CTuningParams::Name`/`str_comp_nocase`,
как и `CTuningParams::Set(const char*, float)`). Оракул применяет переопределение НЕ через
`CTuningParams::Set` (это привело бы к двойному округлению: `Set` сам умножает переданный float
на 100 — `(int)((value_x100/100.0f) * 100.0f)` не гарантированно равно `value_x100` из-за
ошибки округления float), а напрямую в `CTuningParams::NetworkArray()[index]`, что даёт точно
заданное целое без промежуточного float. См. `ApplyTuningOverrides` в `oracle_core.cpp`.

Генератор `random-v1` (§4) сам по себе всегда строит `no_weak_hook = false` и пустой список
tuning-переопределений — это параметры сценария, а не генератора. CLI (`ddnet-ai trace
gen-scenario`) добавляет `--no-weak-hook` (переключает флаг после генерации) и повторяемый
`--tune name=value_x100` (дописывает переопределения) — раунд 1, находка F8: без этого пути
`no_weak_hook=true` и любые tuning-переопределения никогда не попадали ни в bulk-корпус, ни в
золотые фикстуры, хотя §5.3/оракул этот путь поддерживают с самого начала. `bulk_run.sh` и
`gen_fixtures.sh` теперь включают такие сценарии (см. §7) — раунд 2, находка F11: изначально
`bulk_run.sh` задавал ОБА флага в одном слайсе (`--no-weak-hook --tune gravity=0`), так что
«обычный» `no_weak_hook` (с обычной гравитацией) в bulk-корпусе не встречался вовсе (только в
одной фикстуре `arena_nwh_201`), а `gravity=0` гасил любое падение персонажей друг на друга —
хук игрока по игроку в этом слайсе не происходил ни разу. Теперь `bulk_run.sh` гоняет два
отдельных слайса — только `--no-weak-hook` (обычный тюнинг) и только `--tune ...` (обычный
`no_weak_hook=false`, нетривиальные, но реалистичные переопределения) — и `gen_fixtures.sh`
даёт `arena_tune_202` такие же реалистичные переопределения вместо гасящего взаимодействие
`gravity=0`.

## 3. Синтетические карты (`ddai_trace::synthetic`)

`synthetic::build(name) -> Option<MapData>`, детерминированные чистые функции (без PRNG). Имена
— `synthetic::RECIPES`:

- **`arena`** (40×24): сплошная рамка, внутренний пол с разрывом, две платформы, потолок (часть
  — `NOHOOK`), узкий (1 тайл) вертикальный коридор.
- **`freeze`** (36×22): рамка, `NOHOOK`-стена (не на всю высоту — оставлен проход), бассейн
  `FREEZE` + примыкающий `UNFREEZE`, отдельный бассейн `DFREEZE` + `DUNFREEZE`, полоса `DEATH`.
- **`front`** (30×20): рамка + пол на game-слое; 4 отдельные группы клеток (раунд 1, находка F1
  переписала эту карту с нуля — оригинальная версия не давала хуку реально пройти через
  `THROUGH_*`, см. врезку ниже):
  - «Ряд A» (y=8): `THROUGH_CUT`, `THROUGH_ALL`, `THROUGH_DIR` во всех 4 поворотах — на
    front-слое, но КАЖДАЯ клетка стоит на `TILE_SOLID` game-слоя под собой;
  - «Ряд B» (y=10): `STOP`/`STOPS`, каждый во всех 8 байтах флагов, которые
    `GetMoveRestrictionsRaw` различает (4 «простых» поворота + 4 `YFLIP^поворот`, см.
    `ddai_physics::map::ROTATIONS_YFLIP`), плюс один `STOPA`;
  - «Ряд C» (y=13): один сплошной (`TILE_SOLID`) столб с обычным (не `THROUGH_CUT/ALL/DIR`)
    front-тайлом в центре и голым `TILE_THROUGH` на всех 4 соседних клетках;
  - «Ряд D» (y=16): голые `THROUGH_ALL`/`THROUGH_DIR` (все 4 поворота) прямо на game-слое, НЕ
    под чем-либо солидным (открытая клетка);
  - «Ряд E» (y=5, раунд 2, находка F12): `THROUGH_DIR` (все 4 поворота) на front-слое НАД
    открытым (`TILE_AIR`) game-слоем — в отличие от ряда A, где под тем же тайлом стоит
    `TILE_SOLID`. Ряд посреди большой открытой комнаты, со всех 4 сторон свободен (не примыкает
    ни к одной другой группе клеток, ни к рамке/полу).

  > **Почему так, а не проще (раунд 1, находка F1).** `CCollision::IsThrough`
  > (`collision.cpp`) вызывается из `IntersectLineTeleHook` только ПОСЛЕ того, как
  > `CheckPoint` УЖЕ нашёл солидную (`SOLID`/`NOHOOK`) game-клетку на пути хука — если клетка
  > открыта, хук там просто не «спотыкается», и `IsThrough` не вызывается вовсе. Первая версия
  > этого рецепта клала `THROUGH_CUT`/`ALL`/`DIR` на front-слой над game-слоем `AIR` — то есть
  > `IsThrough` был провably мёртвым кодом для любого сценария, который этот рецепт мог бы
  > породить (подтверждено gcov на 200 bulk-сценариях: `collision.cpp` строки внутри `IsThrough`
  > никогда не выполнялись). «Ряд A» это чинит (солид под каждой клеткой). «Ряд C» проверяет
  > ДРУГУЮ ветку той же функции — плоский солидный тайл (не `THROUGH_*`), но с голым
  > `TILE_THROUGH` на клетке в направлении движения хука (`collision.cpp`, проверка
  > `OffsetIndex`) — с тайлами на ВСЕХ 4 соседях эта ветка срабатывает независимо от того, с
  > какой стороны подошёл хук. «Ряд D» — для `IsHookBlocker`, СОВСЕМ другой функции, которая
  > смотрит на СЫРОЙ id тайла game-слоя даже когда клетка «открыта» (`GetTile()` не признаёт
  > `THROUGH_ALL`/`DIR` (66/67) солидными — они вне диапазона `[TILE_SOLID, TILE_NOLASER]` —
  > поэтому `CheckPoint` там ложный, но `IsHookBlocker` читает `m_Index` напрямую).
  >
  > **Ряд D покрывает не всю `IsHookBlocker` (раунд 2, находка F12).** `IsHookBlocker` смотрит
  > на СЫРОЙ id `THROUGH_DIR` в ДВУХ местах: сначала на game-слое (то, что даёт ряд D,
  > `collision.cpp:627-631`), а следующей же проверкой — НА FRONT-СЛОЕ той же клетки
  > (`collision.cpp:632-633`, тот же паттерн «direction ↔ поворот», что и в `IsThrough`). Ряд D
  > этой второй проверки не касается вовсе (front-слой у его клеток отсутствует), так что после
  > первой правки (раунд 1) `collision.cpp:633` — единственная строка `IsHookBlocker`, которая
  > так и не выполнялась ни на одном сценарии тогдашнего bulk-корпуса (200 main + 20
  > no_weak_hook/tune). Реальные карты кладут именно
  > `THROUGH_DIR` НА FRONT-СЛОЙ поверх открытого game-слоя как односторонний хук-блокер (хук,
  > летящий в одну сторону, «спотыкается», как о `NOHOOK`; летящий в другую — проходит, как
  > сквозь воздух). Ряд E воссоздаёт именно это: front-слой `THROUGH_DIR`, game-слой под ним не
  > трогается (остаётся `TILE_AIR`).
- **`tele-speedup`** (34×20): рамка + пол на game-слое; tele-слой — 6 номеров, покрывающих
  `TELEIN`/`TELEOUT`, `TELEINEVIL`, `TELEINHOOK`, `TELECHECK`/`TELECHECKOUT`,
  `TELECHECKIN`/`TELECHECKOUT`, `TELECHECKINEVIL`/`TELECHECKOUT`; speedup-слой — оба типа (28
  старый/29 новый) с разными `force`/`max_speed`/`angle` (включая отрицательные углы).

Каждый рецепт оставляет ≥ 4 свободных (`TILE_AIR` и в game, и во front, если он есть) клетки —
достаточно для максимума в 4 персонажа генератора (проверено тестом
`every_recipe_has_at_least_four_free_cells`).

Важно: tele/speedup/switch/tune — самостоятельные оверлейные слои DDNet, GAME-тайл в той же
клетке для их работы не нужен (проверено по `collision.cpp`: `IsTeleport`/`IsTeleportHook`/
`TileExists` читают исключительно `m_pTele[Index].m_Type`, не `GetTileIndex`). Поэтому в
`tele-speedup` game-слой в клетках тele/speedup остаётся `TILE_AIR`.

## 4. Генератор `random-v1`

`generator::random_v1(recipe, Params{seed, ticks, characters})`. Параметры — ровно четыре:
`recipe` (имя из §3), `seed: u64`, `ticks: u32`, `characters: u32` (1..=4). Один и тот же вызов
с одними и теми же параметрами даёт побайтово одинаковый `Scenario` — единственный источник
«случайности» — `SplitMix64` (см. ниже), потребляемый в порядке, который зависит только от
параметров (никогда — от итерации `HashMap`, времени, порядка потоков).

### PRNG: SplitMix64

Публичный домен (Sebastiano Vigna, <https://prng.di.unimi.it/splitmix64.c>), выбран вместо
`rand`-крейта, потому что поток вывода `rand`'а не является частью его semver-гарантий и может
измениться между версиями — это молча испортило бы байты всех уже сгенерированных сценариев.

```
state: u64   // = seed изначально
next_u64():
    state += 0x9E3779B97F4A7C15
    z = state
    z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9
    z = (z ^ (z >> 27)) * 0x94D049BB133111EB
    return z ^ (z >> 31)
```

`below(bound: u32)` — `((next_u64() as u128 * bound as u128) >> 64) as u32` (multiply-high,
Lemire), смещение ≤ `bound / 2^64` — не измеримо для используемых здесь `bound`.
`range_inclusive(lo, hi)` — `lo + below(hi - lo + 1)`. Реализация и тест на эталонные значения:
`crates/ddai-trace/src/prng.rs`.

### Спавн персонажей

Свободные клетки (game и, если есть, front — `TILE_AIR`) собираются в row-major порядке.
Первый персонаж — случайная свободная клетка. Каждый следующий — с вероятностью 1/2 в клетке на
расстоянии Чебышёва 1..=3 от уже поставленного персонажа (чтобы гарантированно происходили
столкновения игроков и хук друг в друга), иначе — независимо случайная свободная клетка;
позиции никогда не повторяются. Пиксельная позиция спавна — центр тайла (`x*32+16, y*32+16`).

### Ввод, потик, на персонажа

Каждый персонаж — независимый детерминированный конечный автомат:

- **direction** — держится 5..40 тиков, потом равновероятно `-1/0/1`.
- **jump** — нажатие 1..3 тика, затем отпущено 5..30 тиков; после отпуска — с вероятностью 2/5
  почти сразу (через 2..5 тиков) повторное короткое нажатие (имитация попытки второго прыжка в
  воздухе — генератор не моделирует физику, поэтому не гарантирует, что персонаж реально в
  воздухе, только форму ввода, которую дал бы играющий, пытающийся сделать дубль-джамп).
- **hook** — держится 1..60 тиков (по исходному требованию задачи), но ~15% удержаний вместо
  этого длятся 61..120 тиков (`rng.chance(3, 20)`), затем отпущен на 3..30 тиков. Хвост 61..120
  — сознательное отступление от буквального «1-60» (раунд 1, находка F2): отпускание клавиши
  `hook` сразу переводит хук в `HOOK_IDLE` (`gamecore.cpp`, ветка `else` у
  `if(m_Input.m_Hook)`), то есть при удержании ≤60 тиков это ВСЕГДА происходит раньше, чем
  сработает собственный внутренний таймаут ядра на захвате игрока (`HookTick >
  SERVER_TICK_SPEED + SERVER_TICK_SPEED/5` = `>60`, `gamecore.cpp` ~454-457) — эта ветка была
  доказуемо мёртвой при удержании 1..60. Тест `some_hook_holds_exceed_sixty_ticks`
  (`generator.rs`) проверяет, что хвост реально появляется.
- **прицел (`aim_slot`/шум или явная цель)** — обновляется раз в 10..50 тиков, и дополнительно с
  вероятностью 1/10 каждый тик, когда хук держится («изменения прицела во время хука»); с
  вероятностью 2/3 (если есть «напарник») — режим `aim_slot` на напарника + небольшой
  целочисленный шум (±30 по каждой оси); иначе — явный случайный угол, вектор длины 1000. Само
  хранимое поле `(target_x, target_y)` никогда `(0, 0)`; РЕЗУЛЬТАТ после `resolve_input` (§2.1)
  тоже никогда `(0, 0)` — гарантируется откатом на явную цель при точном обнулении «живого»
  вектора. Полный алгоритм режима `aim_slot` — §2.1 (раунд 1, находка F3).
- **fire** — счётчик нажатий (младший бит = «нажато сейчас», как реальный клиент), инертен для
  Oracle A (core не читает `m_Input.m_Fire` — это уровень `CCharacter::FireWeapon`, вне
  Oracle A), оставлен для честности формата и совместимости с будущим Oracle B.
- **wanted_weapon** — с вероятностью 1/20 в тик перебрасывается на случайное 0..5, иначе как
  было; **player_flags/next_weapon/prev_weapon** — всегда 0 (не влияют на core-тик).

Реализация (все константы, включая обработку «текущий тик уже считается первым тиком новой
длительности» — `hold_ticks`): `crates/ddai-trace/src/generator.rs`.

## 5. Порядок тика (Oracle A и будущий Rust-порт, задача 1.3)

Oracle A воспроизводит **только core-уровень** `CGameWorld::Tick` (`src/game/server/gameworld.cpp`)
и `CCharacter::Tick`/`PreTick`/`TickDeferred` (`src/game/server/entities/character.cpp:790-878`)
— без DDRace-логики персонажа (`DDRaceTick`, `HandleWeapons`, `DDRacePostCoreTick`,
`HandleSkippableTiles`, `HandleTiles`): нет фриза, тайловых эффектов, оружия. Это состояние
чистого `CCharacterCore`/`CCollision`/`CLayers`/`CTeamsCore`/`CWorldCore`.

### 5.1 Порядок персонажей: «новые первыми»

Сервер держит персонажей в односвязном списке, новые вставляются в ГОЛОВУ (`gameworld.cpp` —
`InsertEntity`), и `CGameWorld::Tick`/`TickDeferred` идут от головы к хвосту — то есть в порядке
«последний вставленный — первым». В `CNetObj_DDNetCharacter::m_StrongWeakId`
(`gameworld.cpp:79-92`, см. `docs/research/ddnet-physics.md` §3.B2 и `docs/DECISIONS.md` D-022)
сервер публикует именно эту позицию, и от неё зависит исход силового/слабого хука.

Сценарий Oracle A не порождает и не убирает персонажей во время прогона — все персонажи заданы
сразу, в порядке `characters[0..N-1]` (slot 0..N-1). Если считать, что они были бы «вставлены» в
этом порядке (slot 0 первым, slot N-1 последним), то порядок «новые первыми» — это ОБРАТНЫЙ
порядок по slot: **N-1, N-2, ..., 1, 0**. Этот порядок фиксирован на весь прогон (в этом
core-only оракуле нет респавнов, меняющих список) и используется для:

- обхода при вызове `Tick()`/`Tick(true, false)` (core-тик, ввод+хук+опционально
  player-vs-player);
- обхода при вызове `TickDeferred()` (отдельно, при `no_weak_hook`);
- обхода при вызове `Move()`+`Quantize()`.

Порядок строк трейса (§7) — НЕ порядок обработки тика, а порядок `characters[]` из сценария
(slot 0..N-1) — так проще сопоставлять трейсы одного сценария друг с другом и с самим
сценарием; порядок обработки — деталь реализации мира, не наблюдаемая напрямую (кроме как через
её физический эффект на состояние).

### 5.2 Без `sv_no_weak_hook` (`no_weak_hook = false`, генератор `random-v1` всегда так)

Мировой тик персонажа — это ровно вызов `m_Core.Tick(true, true)` (`CCharacter::PreTick` вызывает
`m_Core.Tick(true, !SvNoWeakHook)`, а `CCharacter::Tick` без `SvNoWeakHook` вызывает `PreTick()`
как часть себя, см. `character.cpp:790-825`). `Tick(UseInput=true, DoDeferredTick=true)`
внутри себя, если `DoDeferredTick`, сам вызывает `TickDeferred()` (`gamecore.cpp:461`) — то есть
ввод+хук+player-vs-player столкновение/влияние хука для ОДНОГО персонажа происходят одним
вызовом, и порядок обхода определяет, чьё столкновение кто «видит» уже обновлённым в этот же
тик.

```
for slot in [N-1, N-2, ..., 0]:
    Cores[slot].Tick(true, true)     // ввод, хук, player-vs-player — один вызов
for slot in [N-1, N-2, ..., 0]:
    Cores[slot].Move()
    Cores[slot].Quantize()
```

### 5.3 С `sv_no_weak_hook` (`no_weak_hook = true`)

Сервер (`gameworld.cpp:213-223`) делает отдельный проход `PreTick()` по ВСЕМ персонажам ПЕРЕД
обычным проходом `Tick()` — то есть входной/хуковый расчёт (`Core.Tick(true, false)`, без
внутреннего `TickDeferred`) для всех персонажей происходит раньше, чем чья-либо
player-vs-player-обработка; сама эта обработка (`Core.TickDeferred()`) — отдельным проходом
следом, тоже по всем персонажам в том же порядке. Это убирает зависимость силы хука от
порядка обхода (откуда и название флага):

```
for slot in [N-1, N-2, ..., 0]:
    Cores[slot].Tick(true, false)      // только ввод+хук, БЕЗ player-vs-player
for slot in [N-1, N-2, ..., 0]:
    Cores[slot].TickDeferred()         // player-vs-player, отдельно для всех
for slot in [N-1, N-2, ..., 0]:
    Cores[slot].Move()
    Cores[slot].Quantize()
```

### 5.4 Тюнинг, команды, свитчеры

Один `CTuningParams` на мир (`CTuningParams::DEFAULT` + `tuning_overrides` сценария, см. §2),
скопированный в `m_Tuning` каждого `CCharacterCore` (у DDNet на сервере per-character тюнинг
задаётся тайлом `TILE_TUNE` — DDRace-уровень, вне Oracle A; здесь один тюнинг для всех).
Все персонажи — команда `TEAM_FLOCK` (0) в одном `CTeamsCore` (сервер так и делает по
умолчанию, `g_Config.m_SvTeam` в этом харнессе нулевой — как раз не равен `SV_TEAM_FORCED_SOLO`,
единственному значению, которое имеет значение в `CTeamsCore::Reset`, — так что нулевой
дефолт эквивалентен реальному дефолту `sv_team=1` для наших целей: обычная команда, не «forced
solo»). `CWorldCore::m_vSwitchers` никогда не заполняется (оракул не вызывает `InitSwitchers`) —
двери switch-слоя всегда неактивны; это не влияет на `STOP`/`STOPS`/`STOPA` из front/game-слоя
(они безусловны, не завязаны на свитчеры) — единственное, что core-уровень реально читает из
тайлов помимо `SOLID`/`NOHOOK`/hook-through/тele-hook.

**`CWorldCore::m_pPrng` — всегда `nullptr` (раунд 1, находка F9, явно проговорено здесь, не
только в README оракула).** Единственное следствие в core-уровне —
`CWorldCore::RandomOr0(BelowThis)` (`gamecore.h`): `if(BelowThis <= 1 || !m_pPrng) return 0;` —
то есть при `!m_pPrng` (всегда так у Oracle A) `RandomOr0` ВСЕГДА возвращает `0`, независимо от
`BelowThis`. Единственный вызывающий в core — хук, летящий через `TILE_TELEINHOOK`: при
нескольких `TELEOUT` с одним номером сервер выбирает СЛУЧАЙНЫЙ индекс через `RandomOr0` (сид —
секретный, `secure_random`, недетерминируемо в принципе для стороннего наблюдателя); Oracle A
же (детерминированно, `RandomOr0 → 0`) **всегда** выходит через индекс `0` списка `TeleOuts`
этого номера. Это не баг оракула, а зафиксированное упрощение: задача 1.3 обязана
воспроизводить именно это поведение Oracle A (индекс 0), а не «настоящий» случайный выбор
сервера — иначе трейсы разойдутся на любой карте с несколькими выходами одного номера
(рецепты §3 такого не строят, но задача 1.3 не должна ломаться, если такая карта появится).

### 5.5 `m_MoveRestrictions`: как оракул его получает

`CCharacterCore::m_MoveRestrictions` — приватное поле без геттера. Оракул не патчит и не копирует
DDNet-код — вместо этого он повторяет тот же (чистый, `const`) запрос сразу после прохода
`Tick()`/`TickDeferred()`, но до `Move()`:

```cpp
CapturedMoveRestrictions[slot] = Collision.GetMoveRestrictions(Cores[slot].m_Pos);
// (nullptr-callback + Distance=18.0f + OverrideCenterTileIndex=-1 — те же дефолты, что и
//  внутренний вызов `Tick()`: m_pCollision->GetMoveRestrictions(UseInput ? IsSwitchActiveCb :
//  nullptr, this, m_Pos)`)
```

Корректность: `Tick()` вычисляет `m_MoveRestrictions` в самой первой строке, по `m_Pos` на
момент начала тика; `m_Pos` не меняется ни в `Tick()`, ни в `TickDeferred()` (обе трогают только
`m_Vel`/хуковые поля) — меняет его только `Move()`. Значит, повторный запрос ЛЮБОЙ момент между
началом `Tick()` и началом `Move()` даёт то же самое `m_Pos`, а следовательно и тот же результат.
Callback свитчеров: внутренний вызов передаёт `IsSwitchActiveCb` (не `nullptr`), но эта функция
безусловно возвращает `false`, когда `m_vSwitchers` пуст (§5.4) — то есть блок `if(pfnSwitchActive)`
в `GetMoveRestrictions` либо не выполняется (`nullptr`), либо выполняется и ничего не добавляет
(реальный callback, всегда `false`) — результат `Restrictions` идентичен в обоих случаях.

### 5.6 Инициализация полей, не установленных `CCharacterCore::Reset()`

`Reset()` НЕ устанавливает `m_ActiveWeapon`, `m_Colliding`, `m_LeftWall`, `m_MoveRestrictions`,
`m_Id`, `m_Reset` — на реальном сервере они получают значения из другого кода (создание
`CCharacter`, `CCharacter::SetWeapon` и т.д.), которого в core-only харнессе нет. Оракул явно
обнуляет каждый `CCharacterCore` перед `Reset()`/`Init()` (`std::vector<CCharacterCore>(N)` —
value-initialization для класса с неявным конструктором по умолчанию zero-инициализирует все
POD-поля, см. комментарий в `oracle_core.cpp`), так что стартовое значение всех этих полей —
`0`/`false`. Это определяет контракт для задачи 1.3: Rust-порт должен начинать с тех же
значений (`active_weapon = 0`, `colliding = 0`, `left_wall = false`, ...).

## 6. trace v1

Пишет только оракул; читает Rust (`trace::Trace::read_bytes`, CLI `trace diff`/`trace hashes`).

```
magic              [4]   "TRC1"
version            u32   1
metadata_len        u32
metadata_json        [u8; metadata_len]     UTF-8 JSON, см. §6.1
character_count     u32
character_ids[i]     u32                     character_count раз, порядок = порядок
                                              characters[] сценария (см. §5.1)
tick_count           u32
rows[t][c]           TraceRow                tick_count * character_count раз, тот же порядок
                                              обхода (t по возрастанию, c по character_ids)
```

`TraceRow` = `PlayerInput` (10×`i32`, формат как в §2 — «применённый на этом тике ввод») +
`CharacterCoreState` (§6.2, «состояние ПОСЛЕ тика», то есть после `Move()`+`Quantize()`).

### 6.1 metadata JSON

```json
{
  "producer": {"name": "ddnet-oracle-a", "version": "1"},
  "ddnet": {"tag": "20.1", "commit": "c9d208138f85755521f16a0096b6fe036c5c8698"},
  "map_sha256": "<64 hex>",
  "scenario": {
    "generator": "random-v1",       // опционально: только если оракулу передали --generator
    "seed": 42,                     // опционально: только если оракулу передали --seed
    "scenario_sha256": "<64 hex>"   // всегда — sha256 байт файла сценария, который был прочитан
  },
  "input_schema": [["direction","i32"], ...],   // 10 пар, см. §2
  "state_schema": [["pos_x","f32"], ...]         // 28 пар, см. §6.2, порядок = порядок записи
}
```

`generator`/`seed` — не более чем аннотация: оракул им не пользуется для выбора карты/сценария
(он их вообще не резолвит, только читает готовые rawmap+scenario файлы — резолвинг рецепта в
`MapData` целиком на стороне Rust, см. `ddnet-ai trace export-map`). `scenario_sha256` — всегда
присутствует и достаточен сам по себе для проверки того, что за сценарий трассировался, даже
если `generator`/`seed` не переданы.

`Trace::read_bytes` (раунд 1, находка F4) проверяет `input_schema`/`state_schema` файла ПОСЛЕ
парсинга JSON — если они не совпадают байт-в-байт с тем, что реально ожидает жёстко заданный
макет тела файла (`input_schema()`/`state_schema()` в `trace.rs`), чтение отклоняется с
`FormatError::SchemaMismatch`, а не молча декодируется по неверному макету. Невалидный JSON в
`metadata_json` — отдельная ошибка, `FormatError::InvalidJson` (раньше репортилась как
`InvalidUtf8`, что технически неверно: байты там были валидным UTF-8, просто не валидным JSON).

Байтовый макет ряда: 10×`f32` (по 4 байта, raw IEEE-754 биты) затем 18×`i32` (по 4 байта) — 112
байт на `CharacterCoreState`, плюс 40 байт на `PlayerInput` = 152 байта на `(тик, персонаж)`.

**Почему пропущен `m_AttachedPlayers`.** Это `std::set<int>` — множество ID персонажей, которые
сейчас держат ХУК НА ЭТОМ персонаже (`SetHookedPlayer` заносит/убирает `this.m_Id` из
`pCharCore->m_AttachedPlayers`, см. `gamecore.cpp:709-730`). Значит,
`attached_players(X) = { Y : state(Y).hooked_player == X }` на этом же тике — множество
целиком выводится из уже записанного поля `hooked_player` каждого персонажа; отдельное поле
только продублировало бы эту информацию (и плохо ложится на фиксированную по ширине схему —
переменный размер множества). Схема task-спеки помечает этот пункт вопросом («attached
players?») — здесь он сознательно опущен по этой причине.

**Почему пропущены оружие (кроме `active_weapon`)/ниндзя/телеган/фриз/остальные DDNet-флаги
(раунд 1, находка F6 — выбран путь «документировать», не «расширить схему сейчас»).** Задача
явно исключает оружие и фриз из Oracle A («no freeze/tiles/weapons — that's Oracle B later»);
следующие поля `CCharacterCore` (`gamecore.h`) core-only тик никогда НЕ ЗАПИСЫВАЕТ, они остаются
на значении `Reset()`/zero-init на любом тике этого оракула:

- `m_aWeapons[...]`, `m_Ninja.*` — оружие/ниндзя, вне охвата (Oracle B);
- `m_HasTelegunGun/Grenade/Laser` — телеган, вне охвата;
- `m_FreezeStart`, `m_FreezeEnd`, `m_IsInFreeze`, `m_DeepFrozen`, `m_LiveFrozen` — фриз, вне
  охвата;
- `m_Jetpack`, `m_Invincible`, `m_EndlessJump`, `m_HammerHitDisabled`, `m_GrenadeHitDisabled`,
  `m_LaserHitDisabled`, `m_ShotgunHitDisabled` — DDNet-флаги персонажа, устанавливаются только
  через `CCharacterCore::ReadDDNet(CNetObj_DDNetCharacter*)`, которую Oracle A никогда не
  вызывает (нет сети, нет `CCharacter`);
- `m_Reset` (`bool`) — устанавливается кодом `CCharacter`/`CGameWorld` вне core (например, при
  застревании после телепорта), которого здесь нет.

Важное уточнение по `m_Super`: в отличие от списка выше, `m_Super` РЕАЛЬНО ЧИТАЕТСЯ (не только
пишется) внутри самого `gamecore.cpp` — влияет на хук игрока, столкновение игроков и
`TickDeferred` (проверено построчно в текущем дереве: условия вида `if(!(m_Super ||
pCharCore->m_Super) && ...)` встречаются несколько раз в `Tick()`/`TickDeferred()`/`Move()`).
Но поскольку `m_Super` тоже устанавливается ТОЛЬКО через `ReadDDNet` (никогда — самим ядром),
он у Oracle A всё равно навсегда `false` — как `active_weapon` уже в схеме (константа, но
проверяемая константа). Добавление `super` (и остальных флагов выше) в схему сейчас не дало бы
НОВОЙ информации ни в одной трассе, которую этот оракул может произвести — это заготовка для
Oracle B, когда у флагов появится реальное ненулевое значение для сравнения; тогда её нужно
будет добавить и синхронно обновить каноничный хэш (§6.3), `STATE_F32_COUNT`/`STATE_I32_COUNT`/
`STATE_BYTES` (`trace.rs`) и `StateFields`/`state_schema` (`oracle_core.cpp`).

### 6.3 Канонический потиковый хэш состояния

FNV-1a 64 (стандартные offset basis `0xcbf29ce484222325` и prime `0x100000001b3`, вариант
XOR-затем-умножение) по конкатенации байт `CharacterCoreState` (§6.2, порядок как в таблице,
little-endian) КАЖДОГО персонажа тика, в порядке `character_ids` (= порядок `characters[]`
сценария, §5.1), одним хэшем на весь тик (не по персонажу отдельно):

```
h = 0xcbf29ce484222325
for c in character_ids (в порядке трейса):
    for field in CharacterCoreState-поля персонажа c (в порядке §6.2):
        for byte in little_endian_bytes(field):
            h ^= byte
            h *= 0x100000001b3   // (mod 2^64, wrapping)
tick_hash = h
```

Вход хэша — ТОЛЬКО state-поля (не `PlayerInput`). **Этот хэш вычисляет только Rust**
(`crates/ddai-trace/src/hash.rs`, `Fnv1a64`; потребитель — `Trace::tick_hashes()` / CLI
`ddnet-ai trace hashes`) — оракул (C++) его вообще не считает, он только пишет `CharacterCoreState`
в trace-файл в задокументированном порядке байт; Rust читает этот файл и хэширует. (Уточнение к
раунду 1, находка F9: более ранняя редакция этого раздела читалась так, будто C++ тоже вычисляет
FNV — нет, только Rust; алгоритм здесь специфицирован настолько точно, что задача 1.3 сможет
реализовать РАВНО ТОТ ЖЕ хэш поверх состояния своей Rust-физики и сравнить числа напрямую, без
участия C++ на этом шаге.) Задача 1.3 будет сравнивать хэши Rust-физики с этими значениями как
первый, дёшевый уровень проверки (полное потиковое `diff`, §6.4 — второй, подробный).

### 6.4 `diff`

`ddai_trace::trace::diff(a, b)` / CLI `ddnet-ai trace diff <a> <b>`: сравнивает два трейса
поле за полем (сначала форма — число тиков, число и порядок `character_ids`, иначе — ошибка
формы без попытки посравнивать поля; затем на каждом (тик, персонаж) — все 10 полей ввода, потом
все 28 полей состояния, в порядке схемы). Сравнение `f32` — побитовое (`to_bits()`, то есть
`+0.0 != -0.0`, `NaN` с одинаковой битовой начинкой равны) — то, что нужно для проверки паритета
физики, а не поведение IEEE `==`. Отчёт — первое несовпадение (тик, id персонажа, имя поля, оба
значения) и общее число несовпадений по всему трейсу.

## 8. `.flyg` v1 — подграф мухи

Задача 6.3. Крейт `ddai-flyg` (без `arrow`, без зависимости на `ddai-connectome`) определяет типы,
чтение/запись и валидацию; крейт `ddai-connectome` (модуль `subgraph`) — сам алгоритм выбора
подграфа из полного коннектома и сборку `.flyg`. Файл — вход для модели мухи (фаза 7).

### Хранение на диске

`postcard` (компактная бинарная сериализация без схемы) → `zstd` уровень 3, тот же приём, что и у
`connectome.tables` (см. `ddai_connectome::tables::save_tables`/`load_tables`). Запись атомарна:
во временный файл рядом + `rename`. `ddai_flyg::save`/`ddai_flyg::load` — единственный код,
который умеет читать/писать этот формат; `load` сразу проверяет `header.format_version` и гоняет
полную структурную валидацию (`ddai_flyg::validate`), так что повреждённый или собранный вручную
файл никогда не долетает до потребителя как «вроде бы нормальные» данные.

### `header: FlygHeader`

| поле | тип | смысл |
|---|---|---|
| `format_version` | `u32` | версия формата (сейчас `1`, `FLYG_FORMAT_VERSION`) |
| `source_tables_sha256` | `String` (hex) | sha256 файла `connectome.tables`, из которого выбран подграф |
| `config_sha256` | `String` (hex) | sha256 байтов конфига выбора (`configs/fly/S.toml`/`M.toml`) |
| `generator_version` | `String` | версия крейта `ddai-connectome`, для справки (не участвует в валидации) |

### `neurons: Vec<FlygNeuron>`

Плотный индекс = позиция в массиве (0-based) — это то, что везде дальше называется
«dense/local index». Сортировка — по `bodyId` возрастанию (это гарантирует и
`ddai_connectome::tables`: плотный индекс в `connectome.tables` уже отсортирован по `bodyId`, а
подмножество отсортированного множества индексов остаётся отсортированным).

| поле | тип | смысл |
|---|---|---|
| `body_id` | `i64` | исходный `bodyId` MaleCNS |
| `type_index` | `u32` | индекс в `types` (см. ниже) |
| `role` | `NeuronRole` | `InputVisual` \| `InputAscending` \| `Hidden` \| `Output` |
| `side` | `Side` | `L` \| `R` \| `M` \| `Unknown` (из `somaSide`; `Unknown`, если в исходных данных стороны нет вообще — не путать с `M`) |
| `group_id` | `Option<i64>` | исходная колонка `group` (билатеральный гомолог), если задана |
| `rf` | `Option<ReceptiveField>` | **только** для `role == InputVisual`; всегда `None` для остальных ролей |

`ReceptiveField { azimuth_deg: f32, elevation_deg: f32, is_fallback: bool }` — центр рецептивного
поля в градусах игровой лучевой сетки (азимут 0 = прямо вперёд, отрицательный = левый глаз,
положительный = правый; элевация 0 = экватор глаза, положительная = дорсально). `is_fallback`
— `true`, если суммарная (прямая + однохоповая производная) гекс-опора нейрона ниже
конфигурируемого `rf.min_hex_support` и центр посчитан запасным способом (см.
`crates/ddai-connectome/README.md` §RF и модуль `subgraph::rf` — точная линейная карта,
однохоповое распространение гекс-координат и запасной путь).

### `types: Vec<FlygType>`

Только типы, у которых в этом подграфе есть хотя бы один нейрон. Индекс — позиция в массиве,
сортировка — по имени типа (детерминированно и читаемо).

| поле | тип | смысл |
|---|---|---|
| `name` | `String` | имя типа MaleCNS v1.0 (точное написание) |
| `superclass`, `class` | `String` | из аннотаций (первого по индексу нейрона этого типа в подграфе) |
| `nt_class_used` | `NtClassUsed` | какой NT-класс лёг в основу знака (`Acetylcholine`/`Glutamate`/`Gaba`/`Histamine`/`Modulatory`/`Unknown`) |
| `sign` | `Sign` | `Excitatory`(+1) \| `Inhibitory`(−1) \| `Neutral`(0) |
| `nt_confidence` | `f32`, `[0, 1]` | `1.0`, если знак взят из курированного `consensus_nt`; иначе — доля голосов победившего NT-класса среди **проголосовавших нейронов типа** (не среди суммы весов — иначе один нейрон всегда даёт «уверенность» 1.0 независимо от его собственной `predicted_nt_confidence`, см. `subgraph::signs`) |
| `uncertain` | `bool` | `nt_confidence` ниже конфигурируемого порога, либо NT неизвестен/`unclear` |
| `neuron_count` | `u32` | сколько нейронов **этого подграфа** (не всего коннектома) имеют этот тип |

Знак: ACh → +1, GABA/Glu/гистамин → −1 (все конфигурируемы), дофамин/серотонин/октопамин →
`Modulatory` → 0 по умолчанию (конфигурируемо). Тирамин как отдельный класс в файле
нейромедиаторов MaleCNS v1.0 не предсказывается (см. `docs/research/fly-data.md` §1.4) — правило
спецификации «тирамин → 0» для этого датасета не применяется ни к одному типу.

### `edges: FlygEdges` — CSR по постсинаптическому нейрону

| поле | тип | смысл |
|---|---|---|
| `row_start` | `Vec<u32>`, длина `neurons.len()+1` | `row_start[i]..row_start[i+1]` — диапазон в `pre_index`/`synapse_count`/`type_pair_index` для нейрона `i` как **поста** |
| `pre_index` | `Vec<u32>` | плотный индекс пресинаптического партнёра; внутри одной строки строго по возрастанию |
| `synapse_count` | `Vec<u32>` | `N_ij` — число синапсов в этом подграфе (после порога `θ_edge`) |
| `type_pair_index` | `Vec<u32>` | индекс в `type_pairs` |

Автапсы исключены (их и не было в `connectome.tables`). Индуцированный подграф: ребро попадает
в `.flyg`, если оба конца выбраны И вес ≥ `θ_edge`.

### `neuron_input_totals: NeuronInputTotals` — параллельно `neurons`

| поле | смысл |
|---|---|
| `full_connectome: Vec<u64>` | `N_i^in` — весь входящий счёт синапсов нейрона в **полном** коннектоме (не только в подграфе); нормировка `Z_i` модели (`γ` **не** применяется здесь — только сырое число, FLY.md §4) |
| `in_subgraph: Vec<u64>` | входящий счёт синапсов **внутри** подграфа (сумма `synapse_count` по строке CSR); всегда `<= full_connectome[i]` |

### `type_pairs: Vec<TypePair>`

Одна строка на различимую пару (тип-пре, тип-пост), встретившуюся среди рёбер подграфа. Сортировка
— по `(pre_type, post_type)` (индексы в `types`).

| поле | смысл |
|---|---|
| `pre_type`, `post_type` | индексы в `types` |
| `total_synapses: u64` | сумма `N_ij` по этой паре типов **в подграфе** |
| `shared_param_id: u32` | какой обучаемый параметр силы связи разделяет эта пара. Пары с `total_synapses >= weak_pair_threshold` (из конфига) получают свой уникальный id; более слабые пары делят один id на каждую комбинацию (знак типа-пре, superclass типа-пре, superclass типа-пост) |

`Flyg::summary.shared_param_count` — число **различных** `shared_param_id` (не число строк
`type_pairs`).

### `input_channels: Vec<InputChannelMapping>`

Только для визуальных входов (`role == InputVisual`) — какие игровые каналы луча (FLY.md §5,
например `"opponent_position"`) идут в этот тип. `type_index` — индекс в `types`. Восходящие
(проприоцептивные) входы сюда не попадают: их типы в MaleCNS v1.0 почти всегда не несут
функционального имени (см. `crates/ddai-connectome/README.md`), поэтому канальная карта для них не
формат-специфицирована.

### `output_groups: Vec<OutputGroup>`

`action` (например `"direction_left"`, FLY.md §6) → список `OutputMember { neuron_index: u32,
side: Side }`, `neuron_index` — индекс в `neurons` (обязательно `role == Output`).

### `summary: Summary`

Снимок статистики, посчитанный один раз при сборке (числа нейронов по ролям, число типов/рёбер/
пар типов, число различных `shared_param_id`, распределение знаков, число «неуверенных» типов,
число визуальных входов с запасным РП). Не пересчитывается заново при загрузке, но
`ddai_flyg::validate` перепроверяет каждое поле против остальных данных файла — расхождение здесь
означает испорченный или собранный не тем кодом файл.

### Валидация (`ddai_flyg::validate`)

Останавливается на первой найденной проблеме (после первого нарушения инварианта дальнейшие
проверки по тем же данным уже не говорят ничего нового, см. комментарий в коде). Проверяется: все
индексы (`type_index`, `pre_index`, `type_pair_index`, `pre_type`/`post_type`,
`output_groups[].members[].neuron_index`) в допустимом диапазоне; CSR корректен (`row_start`
монотонен, длины массивов согласованы, внутри строки `pre_index` строго по возрастанию, без
автапсов, без нулевого `synapse_count`); нет `NaN` (в `ReceptiveField`, в `nt_confidence`);
`nt_confidence ∈ [0, 1]`; `rf.is_some()` тогда и только тогда, когда `role == InputVisual`;
`in_subgraph <= full_connectome` на каждый нейрон; `input_channels`/`output_groups` ссылаются на
нейронов подходящей роли; `summary` согласована с остальными полями файла.

### Детерминизм

Сборка (`build-subgraph`) — чистая функция от `connectome.tables` + конфига: нет обхода
`HashMap` без сортировки на выходе (только `BTreeMap`/`BTreeSet`, или `Vec` с явной сортировкой),
нет системного времени/случайности в содержимом файла (только в отчёте, который отдельный файл).
Повторный запуск с тем же входом даёт байт-идентичный `.flyg` — проверено на реальных `S`/`M`
(см. отчёт задачи 6.3).

## 9. Протокол 0.6+DDNet: низкий уровень

Задача 2.2a, крейт `crates/ddai-net`. Реализован **только** клиентский путь 0.6+DDNet (TKEN);
0.7/sixup и ванильный (без TKEN) хендшейк — вне охвата (см. `<constraints>` задачи).

### 1. Заголовок пакета (`src/packet.rs`, ориг. `network.h:20-111`, `network.cpp`)

UDP-датаграмма ≤ `NET_MAX_PACKETSIZE` = 1400 байт. Для пакетов «с соединением» (не connless) —
3-байтный заголовок:

```
byte0 = (flags << 2) | ((ack >> 8) & 0b11)
byte1 = ack & 0xff
byte2 = num_chunks
```

`flags` (6 бит; в 0.6+DDNet используются только 3):

| бит | имя | смысл |
|---|---|---|
| `1<<2` | CONTROL | пакет несёт одно control-сообщение (§3), 0 чанков |
| `1<<4` | RESEND | «перешли мне все неподтверждённые vital-чанки» |
| `1<<5` | COMPRESSION | тело пакета (после заголовка, до общего хвоста-токена) сжато Huffman'ом (§2) |

Остальные биты (`UNUSED`, `TOKEN`, `CONNLESS`) — 0.6.5/0.7/connless, не наш путь; `CONNLESS`
детектируется отдельно (`packet::unpack_packet` возвращает `Connless`-ошибку, connless-кадры
разбирает `unpack_connless_packet`).

Валидность (`is_valid_connection_oriented_packet`, ориг. `network.cpp:134-155`): флаги — только из
множества выше; control ⇒ `num_chunks == 0` и `data_len > 0` и не сжат; иначе `num_chunks ≥ 1`,
кроме случая с флагом RESEND, где допустимо 0 (пакет — «голая просьба на resend»).

Сжатие Huffman'ом применяется к полезной нагрузке (чанки **и** уже приклеенный хвост-токен, см.
§4) целиком, и только если результат короче исходного — иначе пакет уходит несжатым (control-пакеты
никогда не сжимаются).

### 2. Huffman (`src/huffman.rs`, ориг. `huffman.cpp`)

Фиксированное (не адаптивное) дерево из таблицы частот 257 символов (256 значений байта + EOF=256);
дерево строится один раз (`Huffman::new`) тем же жадным алгоритмом слияния (`stable_sort` по
частоте, каждый раз сливаем два наименьших), что и `CHuffman::ConstructTree`. Побитово совпадает с
оригиналом — 5 тест-векторов из `src/test/huffman_test.cpp` (конкретные байты) перенесены в
`huffman::tests` и проходят точно. Дополнительно сверено с `libtw2-huffman` (MIT/Apache,
dev-зависимость) на ≥100k случайных входов (`tests/oracle_libtw2.rs`) и **с реальным выводом
сервера DDNet 20.1** — decompress→recompress по каждому сжатому пакету из захвата даёт побайтово
тот же результат (`tests/capture.rs`).

`decompress` ограничен по размеру буфера входа/выхода и никогда не зацикливается на испорченном
входе (в отличие от старого TS-бота, который на этом висел, — см. `<goal>` задачи 2.2a):
- сжатие использует `u64`-аккумулятор бит (как `Bits` в C++), безопасный побайтовый вывод;
- разбор LUT (10 бит) + при необходимости побитовый спуск по дереву — спуск идёт по индексам узлов,
  которые всегда строго убывают при движении к листу (дерево строится «снизу вверх»), поэтому спуск
  гарантированно завершается за ≤ `NUM_NODES` (513) шагов независимо от содержимого входа; счётчик
  бит специально допускает wraparound (`wrapping_sub`) на этом участке — как и в оригинале
  (`unsigned Bitcount` в C++), но у нас это не UB, а явный, откомментированный факт.

### 3. Пакер/варинт (`src/packer.rs`, ориг. `compression.{h,cpp}`, `packer.{h,cpp}`)

Целые — variable-length int: `[ext:1][sign:1][6 бит]`, затем `[ext:1][7 бит]` × до 4 байт (максимум
5 байт на int). Знак — через `!value` (побитовое НЕ) при кодировании и `value ^= -sign`-эквивалент
при декодировании; нет отдельного «-0». Сверено с `libtw2-packer` на ≥100k случайных `i32`
(включая границы `i32::MIN/MAX`) — байт-в-байт то же самое кодирование в обе стороны
(`tests/oracle_libtw2.rs`).

Строки — NUL-terminated UTF-8; на невалидном UTF-8 (как и `str_utf8_decode` в C++) один недопустимый
байт заменяется на U+FFFD, без потери прогресса. Санитайзинг (`SANITIZE`/`SANITIZE_CC`/
`SKIP_START_WHITESPACES`) — как в `CUnpacker` (`packer.h:61-66`). `Unpacker` «отравляется»
(`error()` становится `true`) при первой ошибке и дальше возвращает нейтральные значения без
дальнейшего чтения — так же, как оригинальный `CUnpacker`.

### 4. Control-сообщения и рукопожатие TKEN (`src/control.rs`, ориг. `network_conn.cpp`,
`network_server.cpp:513-522`)

```
KEEPALIVE:      [00]
CONNECT:        [01] 'T' 'K' 'E' 'N'                (+ хвост-токен, изначально UNKNOWN=0xffffffff)
CONNECTACCEPT:  [02] 'T' 'K' 'E' 'N'                (+ хвост-токен = токен, который сервер выдаёт клиенту)
ACCEPT:         [03]                                (+ хвост-токен, теперь известный)
CLOSE:          [04] <причина: NUL-terminated string>?  (+ хвост-токен, если уже известен)
```

Причина `CLOSE` обрезается до 255 байт (как в C++ `char aStr[256]`, заполняемый `str_copy`,
`network_conn.cpp:411`) — байты после этого предела отбрасываются ещё до поиска NUL-терминатора.

**Хвост-токен** — отдельные 4 байта (big-endian), которые дописываются к телу пакета *до* сжатия
Huffman'ом на **любом** неconnless-пакете, если токен для этого соединения не «не поддерживается»
(`NET_SECURITY_TOKEN_UNSUPPORTED=0`) — включая control-пакеты (`network.cpp:217-223`). Это отдельный
слой от собственно control-байтов и реализован в `packet::build_packet`
(параметр `security_token: Option<u32>`), а не в `control.rs`.

Рукопожатие 0.6+DDNet (без sixup/ванильного anti-spoof пути — не наша задача):

```
C→S  CONTROL CONNECT       ["TKEN"]     (+ хвост = UNKNOWN, 0xffffffff)
S→C  CONTROL CONNECTACCEPT ["TKEN"]     (+ хвост = свежий токен, который сервер сгенерировал)
C→S  CONTROL ACCEPT        []           (+ хвост = тот же токен)
C→S  … далее каждый пакет …             (+ хвост = тот же токен)
```

**Важно, проверено на реальном захвате (§7):** токен передаётся **один раз**, как обычный
хвост-токен. Более раннее предположение (в т.ч. в `docs/research/ddnet-protocol.md` §1.3), что
`CONNECTACCEPT` несёт токен *дважды* — как данные сообщения **и** как хвост — не подтвердилось:
`network_server.cpp:519` вызывает `SendControl(Addr, CONNECTACCEPT, SECURITY_TOKEN_MAGIC, 4, Token)`
— в данных сообщения передаётся только магия `"TKEN"` (4 байта), сам `Token` уходит только как
аргумент `SecurityToken` в `SendPacket`, т.е. как хвост. Итоговый пакет: заголовок(3) +
`[02,'T','K','E','N']`(5) + хвост(4) = 12 байт — ровно то, что видно в захвате
(`tests/fixtures/local-capture-20260927.dat`, запись 1).

Клиент может прочитать этот хвост как «данные», потому что в момент получения `CONNECTACCEPT` его
собственный `security_token` ещё `Unknown` — а хвост-токен строго/снимается только когда токен уже
`Known` (`conn::SecurityToken::should_verify`). Поэтому 4 байта сразу после `"TKEN"` — это ровно то
значение, которое стоит запомнить как токен; так это и реализовано в `Connection::feed`
(`src/conn.rs`), а не в `control::decode` (у которого для `CONNECTACCEPT` есть только
`has_tken_magic: bool`, без значения токена — см. doc-комментарий модуля `control` для полного
разбора).

### 5. Заголовок чанка (`src/packet.rs::ChunkHeader`, ориг. `network.h:156-165`, `network.cpp:443-469`)

2 байта (не-vital) или 3 байта (vital, есть sequence):

```
b0 = (flags & 0b11) << 6 | (size >> split) & 0x3f
b1 = size & ((1 << split) - 1) | [если vital] (seq >> 2) & ~((1 << split) - 1)
b2 = seq & 0xff                                [только если vital]
```

`split = 4` для 0.6 (в 0.7/sixup — 6, не реализовано). `size ≤ 1023` (10 бит), `seq` — 10 бит,
пространство последовательностей `NET_MAX_SEQUENCE = 1024` (wraparound по модулю). Побитово сверено
с 5 тест-векторами `src/test/chunk_header_test.cpp` (`packet::tests::chunk_header_seq*`).

`flags`: `VITAL` (доставляется надёжно, с ack/resend), `RESEND` (информационный — чанк послан
повторно; получатель не обрабатывает его иначе).

### 6. Соединение (`src/conn.rs`, ориг. `network_conn.cpp`)

Sans-IO стейт-машина `Connection` — без сокета, без обращения к системным часам (`now: Duration`
передаётся вызывающим кодом на каждый вызов). Состояния: `Offline`, `Connecting` (роль клиента),
`Pending` (роль сервера — у DDNet это ветвится вне `CNetConnection::Feed`, у нас — один тип на обе
роли, см. doc-комментарий модуля), `Online`, `Error(причина)`.

Отличия от прямого порта C++ (осознанные, см. D-029 — своя безопасная реализация, не вендоринг):

- нет привязки к адресам (демультиплексация датаграмм по адресу — задача вызывающего слоя, задача
  2.3);
- `feed()` никогда не шлёт данные немедленно (в C++ control-сообщения уходят синхронно из `Feed`);
  вместо этого они складываются во внутреннюю очередь и отдаются следующим вызовом `flush()`;
- `flush(now)` всегда сливает накопленные vital/non-vital чанки (а не только по 500-мс таймеру, как
  `Update()` в C++) — таймеры остаются только для keepalive/resend/timeout/повтора хендшейка;
- переполнение resend-буфера (`NET_CONN_BUFFERSIZE` = 32 КиБ) — это **ошибка**
  (`SendChunkError::ResendBufferFull` + `State::Error`), а не тихий пропуск с надеждой, что чанк не
  понадобится повторно (как в C++, `network_conn.cpp:187-191`);
- переходы в `State::Error`, которые обнаруживает не `feed()` (timeout, too weak connection,
  переполнение resend-буфера), а `flush()`/`send_chunk()`, тоже наблюдаемы как событие — через
  `Connection::take_events()` (отдельная внутренняя очередь, `feed()` продолжает возвращать свои
  события напрямую, как и раньше); ровно одно событие на переход, не на каждый вызов;
- `queue_chunk_bytes` (внутренний, вызывается и `send_chunk`, и путём resend внутри `flush`) сам
  отказывается класть что-либо в очередь, если состояние уже `Offline`/`Error` — как
  `QueueChunkEx` в C++ (`network_conn.cpp:145-146`); без этой проверки один и тот же вызов
  `flush()`, который только что обнаружил timeout, мог бы всё равно отправить уже накопленные до
  этого данные — нашли и исправили во втором раунде ревью.

Ack/seq wraparound, правила resend (переслать все неподтверждённые при флаге RESEND, ограниченно по
`conn_resend_requests_per_second`), «too weak connection» и «timeout» — порт правил
`CNetConnection` 1:1 (см. doc-комментарии в `conn.rs`). Как и в C++ (`network_conn.cpp:522-523`,
`State() != EState::CONNECT`), у состояния `Connecting` **нет** таймаута по бездействию — оно
ретраит `CONNECT` бесконечно, пока вызывающий код (клиентская сессия, задача 2.3) сам не решит
сдаться.

### 7. UUID расширенных сообщений (`src/uuid.rs`, ориг. `uuid_manager.{h,cpp}`, `protocol_ex*.{h,cpp}`)

UUID v3: `md5(namespace ++ имя)`, затем версия=3 (байт 6, старший ниббл = `0011`) и вариант=1
(байт 8, два старших бита = `10`) — RFC 4122. `namespace` = `e05ddaaa-c4e6-4cfb-b642-5d48e80c0029`
(фиксированный, `uuid_manager.cpp:14-16`). Таблица имён (20 штук, задача 2.2a) — в порядке
`protocol_ex_msgs.h`, id — последовательно от `OFFSET_UUID = 1<<16`. Значения UUID сверены с
независимым вычислением через Python `hashlib.md5` (см. doc-комментарий `uuid::tests`) — libtw2
этот алгоритм не реализует вовсе (только упаковку готового 16-байтного UUID), поэтому дифф-тест
против него невозможен; используется независимая реализация MD5 вместо сборки полного C++-движка.

`NETMSG_EX`: первый varint сообщения — `(id << 1) | sys`; `id == 0` ⇒ далее 16 сырых байт UUID.
Неизвестный UUID — не ошибка, просто `resolved: None` (сообщение нужно игнорировать, а не рвать
соединение) — как и в оригинале.

### 8. Захват реального трафика (тест `tests/capture.rs`)

Как получена фикстура `tests/fixtures/local-capture-20260927.dat` (< 200 КБ, два сегмента, 1405
датаграмм из полной сессии в 2778):

```bash
sudo tcpdump -i lo -w ddnet-loopback.pcap udp port 8303 &
cd ~/aiddnet/DDNet-AI && node src/bot/main.ts --server 127.0.0.1:8303 --scripted --duration 20 --no-console
# затем:
python3 tests/fixtures/extract_capture.py ddnet-loopback.pcap tests/fixtures/local-capture-20260927.dat 8303 0:40 1414:2777
```

**Правка после первого раунда ревью:** первая версия этого раздела и фикстуры ошибочно описывала
непрерывный префикс первых 400 пакетов как «хендшейк + ~2 c устоявшегося обмена снапшотами». На
самом деле все 400 пакетов — это хендшейк TKEN плюс *начало* передачи карты по протоколу (карта не
была закэширована); сама передача карты (`MAP_DATA`↔`REQUEST_MAP_DATA`) заняла **~1400 пакетов**
сессии — ни одного снапшота, ни `READY`/`ENTERGAME`, ни единого non-vital чанка в исходном диапазоне
не было вообще. Обнаружено и исправлено во втором раунде ревью.

`extract_capture.py` (без внешних зависимостей) сам разбирает Ethernet/IPv4/UDP-обёртку pcap,
оставляет только полезную нагрузку UDP-пакетов между локальным сервером и ботом, помечает
направление (клиент→сервер / сервер→клиент) и пишет компактный формат `DDCAP2` (магия `DDCAP2` +
число сегментов + на сегмент: число записей + записи `[direction:u8][len:u16 LE][payload]`; без
~42 байт заголовков Ethernet/IP/UDP на пакет, которые есть в самом `.pcap`). Взяты **два**
независимо непрерывных сегмента исходного потока (индексы — по порядку появления в pcap, только
трафик с портом 8303):

- сегмент 0 (`0..=40`, 41 запись, ~19,8 КБ) — сам хендшейк TKEN + `CLIENTVER`/`INFO`/`CAPABILITIES`/
  `MAP_DETAILS`/`MAP_CHANGE` + первые несколько циклов `REQUEST_MAP_DATA`↔`MAP_DATA` (показывают
  механизм, не оплачивая все ~1400 пакетов полной передачи карты);
- сегмент 1 (`1414..=2777`, 1364 записи, ~53,6 КБ) — от `READY` клиента через `CON_READY`,
  `Cl_StartInfo`, `ENTERGAME` и до конца сессии: устоявшийся обмен (снапшоты `SNAP`/`SNAPEMPTY`,
  `INPUTTIMING`, клиентский `INPUT`, ack'и) и собственный чистый `CLOSE` в самом конце.

Границы (в терминах ack/seq) внутри каждого сегмента согласованы сами по себе, но НЕ друг с другом —
между сегментами вырезана часть реальной сессии (передача карты), так что seq/ack-проверки в
`capture.rs` идут **по сегментам отдельно** (`check_segment`), не через границу.

Трафик — только между нашим локальным сервером и нашим ботом, наружу никогда не уходил.

Тесты в `capture.rs` проверяют (см. doc-комментарий файла): 100% декодирование, кроме **двух**
задокументированных исключений:

1. Один пакет клиент→сервер в сегменте 0 (7 байт: flags=0, num_chunks=0, без флага RESEND) —
   npm-библиотека `teeworlds`, которой пользуется старый TS-бот, один раз шлёт такой пакет; настоящий
   сервер DDNet отверг бы его по той же самой `IsValidConnectionOrientedPacket`
   (`network.cpp:150-154`: не-resend пакет обязан нести хотя бы один чанк).
2. Два пакета сервер→клиент в сегменте 1 — **connectionless** (флаг `CONNLESS`, легаси-заголовок
   `0xFF×10`, ответ `"iext"` + версия): библиотека бота параллельно с игровым соединением сама шлёт
   легаси server-browse запрос на тот же порт и получает ответ. Разбираются отдельной функцией
   (`packet::unpack_connless_packet`), не участвуют в проверках ack/seq/токена. Найдено во втором
   раунде ревью — не баг, а факт о трафике реального клиента.

Помимо декодирования: совпадение токена на всех connection-oriented пакетах после рукопожатия (в
обоих сегментах, без двух исключений выше); побайтовый Huffman-рантрип против реального вывода
сервера; в пределах каждого сегмента — последовательность vital seq строго по +1 в каждом
направлении, и **нетавтологичная** проверка ack (не «ack < 1024», это верно для любого 10-битного
поля и ничего не проверяет, а «ack не превышает старший vital seq, который эта сторона уже
отправила в этом сегменте» — как только мы увидели от неё хотя бы один vital-чанк).
