# Решения (ADR-журнал)

Формат: **D-NNN** — дата — решение. Почему. Следствия. Новые решения — в конец. Отменённые не удаляются, а
помечаются «ЗАМЕНЕНО D-xxx».

## Фаза 0 (2026-09-27)

**D-001 — Железо: AVX-512 нет, цель — x86-64-v3.** Промпт говорит «EPYC 9645 (Zen 5, AVX-512)», но гость KVM видит
модель «AMD EPYC-Rome» (family 23, model 49) с флагами до AVX2/FMA/BMI2, **без avx512***. Верим фактам: SIMD-код мухи
пишем под AVX2 (x86-64-v3); физику — без зависимостей от target-cpu. Если провайдер включит AVX-512 — это бонус,
не требование.

**D-002 — Эталон физики — C++ DDNet, не TS.** Эксперимент фазы 0 (`research/ddnet-physics.md` §0, §4): TS-порт
считает во float64 и расходится с настоящим C++ уже на 2–5 тике; даже одношагово ~40% мировых шагов отличаются.
Та же C++-логика в double совпадает с TS бит-в-бит → логика TS верна, отличие только в точности. Прототип Rust во
float32 совпал с C++ бит-в-бит на 20 сидов × 10 000 тиков × 3 ти. **Расхождение с промптом:** «паритет с TS-версией
и C++ DDNet» бит-в-бит одновременно невозможен. Решение: Rust f32 = бит-в-бит с C++ (все целые и квантованные поля);
Rust f64 в режиме совместимости с TS = бит-в-бит с TS на механиках, которые TS реализует; Rust f32 против TS — только
одношагово с допуском ±1 px / ±1/256.

**D-003 — Физика обобщена по скаляру (`f32`/`f64`) и имеет профиль совместимости.** `ddai-physics` параметризуется
типом `Real` и флагами профиля (`Ddnet` — полная механика, продакшн и обучение; `TsCompat` — отключает механики,
которых нет в TS: front-фриз, switch, tune, ehook и т.д., и повторяет квирки TS). Нужно для паритета физики с TS и для
паритета решений планировщика. Цена — дженерики в ядре; окупается проверяемостью.

**D-004 — Математика: glibc через std, без крейта `libm`.** `f32::powf/sin/cos/atan` в Rust на linux-gnu вызывают
glibc и совпали с C++ на 2 млн проб; чисто-Rust `libm` 0.2.16 расходится (powf в 9,7% проб). Порядок операций — как
в C++ (`Dir*a*(V*0.75f)`, `(vel+boost)-vel`, `round_to_int` через `f + 0.5f32`), без `mul_add` и fast-math.

**D-005 — Версия эталона DDNet: релиз 20.1** (2026-09-26, последний стабильный; master = 20.2 без тега). Между 20.0 и
master изменений в `gamecore`/`collision` нет. Оракул собирается из тега; версия/коммит пишутся в каждую трассу.
Целевые блок-серверы работают на разных базах (DDNet 18.5…20.2, моды DDNet++/F-DDrace/S-DDRaceX/Block Worlds) —
отличия модов изучаем отдельно, когда дойдём до конкретного сервера.

**D-006 — Эталонные трассы: три уровня.** (A) standalone C++-харнесс из настоящих `gamecore/collision/layers`
(прототип работает, дёшево, >10⁶ тик/с); (B) **основной эталон** — in-process сервер DDNet по образцу
`src/test/gameworld_test.cpp` (100% серверного кода, детерминированно); (C) приёмка — настоящий headless
DDNet-Server + teehistorian. TS-генератор трасс (из стенда фазы 0) — для паритета f64/TsCompat и планировщика.

**D-007 — Бот не пишет в чат ничего; `/showall` заменён на `Cl_ShowDistance`.** Старый бот при подключении слал в чат
`/showall 1`, чтобы видеть далёких игроков. В DDNet есть штатное сообщение `Cl_ShowDistance`
(`show-distance@netmsg.ddnet.tw`), которое шлёт любой клиент при отдалении камеры; сервер его не ограничивает
(`gamecontext.cpp:2777`), радиус клиппинга = ShowDistance/2 + 320 px (`player.cpp:1118-1141`). Также не шлём
`i-am-npm-package@…`, `rcon crashmeplx` и строки npm в версии.

**D-008 — Сеть: libtw2 (MIT/Apache) — вендорим/форкаем низкий уровень, сессию пишем сами.** Берём huffman, packer,
snapshot, demo как есть; форк `libtw2-net` (Connection, panic → Result, таймауты), форк `libtw2-gamenet-ddnet`
(регенерация под 20.x: `MapDetails.size/url`, новые сообщения), форк `libtw2-datafile/map` (патч «несколько game-слоёв»).
Своё: клиентская сессия (вход, INPUTTIMING/PredTick, карта in-protocol + HTTPS с sha256, REDIRECT/RECONNECT,
тюнинг, детект капчи/бана → avoid-list), мастер-сервер. Тестовый клиент на libtw2 в фазе 0 зашёл в игру на живом
сервере. Уведомления MIT/Apache сохраняются в вендорных файлах.

**D-009 — twmap и twgame (AGPL-3.0-only) не используем вообще.** Совместимость AGPL с GPL-3.0 есть (§13 обеих), но
AGPL §13 распространилась бы на весь бинарник. Даже как dev-оракул не нужен: карты и физику сверяем с C++ DDNet.
Читать их код как справку можно, копировать — нет.

**D-010 — Веб: axum + WebSocket (бинарные кадры) за Caddy.** Бот слушает только 127.0.0.1; Caddy — HTTPS (Let's Encrypt)
на `89-58-7-133.sslip.io`, ufw: 22/80/443. Вход: пароль (argon2id), сессия в cookie (HttpOnly, Secure, SameSite=Strict),
rate limit на вход, выход из сессии, проверка Origin для WS/POST, лимиты размера тел. Все команды, меняющие
состояние, — только после входа. Старый опрос JSON 25 Гц (125–390 КиБ/с) заменяется бинарным live-кадром.

**D-011 — Графика DDNet: скачивается ботом в рантайме, не коммитится.** Данные DDNet — CC-BY-SA 3.0; источник —
закреплённый коммит DDNet 20.1 (`c9d208138f85755521f16a0096b6fe036c5c8698`) на GitHub, манифест (путь, размер,
sha256) в репо, кэш `~/aiddnet/data/assets/`. Атрибуция на странице (DDNet/Teeworlds contributors, CC-BY-SA 3.0,
DejaVu, авторы скинов из `skins.json`). Скины с NC/ND/unknown — только по запросу, по умолчанию выключены.

**D-012 — Коннектом: MaleCNS v1.0 (CC-BY 4.0), минимальный набор 3 файла ≈ 566 МБ, закрепление по GCS generation +
md5 + sha256.** FlyWire (лицензия противоречива: NC vs CC-BY) — только локальная сверка, в релизы не попадает.
Чтение Feather — в Rust (крейт `arrow`, IPC+LZ4). Python-venv с pyarrow из фазы 0 — только исследовательский.

**D-013 — Модель мухи: rate-модель в стиле flyvis.** Знак × число синапсов × масштаб на пару типов, нормировка на
полный вход нейрона, ReLU с мягким потолком, экспоненциальный Эйлер Δ = 10 мс × 4 подшага на решение, параметры общие
для L/R (зеркальная симметрия), знаки ACh+/GABA−/Glu−/His−, моноамины вне быстрого пути, декодер DN с замороженной
калибровкой, голова модели мира + замороженный пробник как метрика. Детали — `FLY.md`. LIF — только отдельный
эксперимент.

**D-014 — Обучение: сначала имитация, потом RL; обязательные контроли.** BC → DAgger от планировщика → демки людей →
ES (S) / PPO (M/L). Контроли: перепроводка с сохранением степеней, перемешанные знаки, MLP/GRU того же размера.
Литература: RL с нуля через коннектом нестабилен везде; работало только «сначала имитация».

**D-015 — YouTube-ролики не используем как обучающие данные.** Владелец предложил «засунуть в муху клипы блока с
YouTube». В видео нет вводов (только картинка) → нужна отдельная CV-модель без GPU, данные шумные; скачивание роликов
запрещено правилами YouTube и задевает права авторов. Вместо этого: (1) демки DDNet (точные снапшоты); (2) записи
бота-наблюдателя на блок-серверах (точные данные, ники только локально); (3) ролики-объяснения — как источник тактик
для библиотеки сценариев и проверки награды (разбор по субтитрам/описаниям, без скачивания видео). Цель «лучше и
быстрее алгоритма» зафиксирована в метриках (F3 ≥ 50% против планировщика; инференс ≤ 5 мс против ~8 мс p50 у TS).

**D-016 — IP дата-центра и баны: никакого обхода.** В фазе 0 короткий исследовательский заход (`research-probe`,
< 20 с) получил автобан «bad ip» на 10 минут на TeeUnion и «VPN detected» на официальном DDNet-сервере. Прокси/VPN/смена
IP для обхода запрещены. Варианты для живой игры: серверы, которые принимают этот IP; серверы владельца; запуск
клиентской части бота с домашнего IP владельца (веб-панель остаётся на VPS). Решение — за владельцем (вопрос в STATUS).

**D-017 — Учитель — планировщик в режиме фиксированных итераций.** Недетерминизм TS-планировщика — только дедлайн
по часам; `{budgetMs: 0, hardMs: 0}` воспроизводим (20/20 игр). Датасеты размечаются только в этом режиме (иначе метки
зависят от загрузки CPU). `--brain planner` вживую может использовать бюджет по времени (или по числу оценок).

**D-018 — Паритет решений планировщика требует V8-совместимой математики в скоринге.** `Math.round` (половины к +∞),
`Math.hypot` (масштабирование + Kahan), `sin/cos/log` (fdlibm) отличаются от Rust std. В планировщике — модуль
`jsmath` (порт соответствующих функций V8/fdlibm, лицензия Sun/BSD-подобная с уведомлением). Скоринг планировщика
всегда в f64; физика под планировщиком — f64/TsCompat для паритета, f32/Ddnet в продакшне.

**D-019 — Модели /duo.** Билдер — Sonnet 5 (`sonnet-builder`), ревьюер — Opus 5.5 (`opus-reviewer`). Исследования
фазы 0 — субагенты на Opus. Мелкие поиски можно отдавать более дешёвым моделям.

**D-020 — Toolchain закреплён.** Rust 1.98.1 (`rust-toolchain.toml`), Node 24.21.0 (только для TS-генератора трасс).

**D-021 — Не переносим мёртвое и вредное.** `OpponentProfile` (вес 0), `routeDistance` в скоринге, `bandCost`,
подстрочное сравнение ников в friend/war (баг → точное сравнение после нормализации), автоклипы по пустым `events`
(в Rust события будут настоящими), дуэль-«auto» через `/accept` (чат).

**D-022 — Порядок персонажей (strong/weak) — из снапшота.** Сервер тикает персонажей «новые первыми» и отдаёт
позицию в `CNetObj_DDNetCharacter::m_StrongWeakId`; от этого зависит исход борьбы хуками. LiveWorld упорядочивает
мир по `m_StrongWeakId` (TS этого не делал).

**D-023 — Ввод: синхронизация PredTick по `NETMSG_INPUTTIMING`.** TS слал ввод по таймеру 20 мс и игнорировал
INPUTTIMING. В Rust — как клиент DDNet (`client.cpp`): управление intended tick по ответам сервера; модель «летящих»
вводов в LiveWorld пересчитывается от реального intended tick.

**D-024 — Серверный тюнинг и tune-зоны учитываются.** `Sv_TuneParams` (47 значений ×100) и `TILE_TUNE`/настройки
карты применяются к физике (TS использовал дефолты).

**D-025 — Автономность после фазы 0.** Владелец (2026-09-27) разрешил не ждать «ок» на план и идти по фазам дальше
без вопросов; вопросы копятся в `STATUS.md`. Разрешено тестирование на сервере «DDNet GER Block Copy Love Box» под
ником «Muha» (факт разрешения — со слов владельца).

**D-026 — Карты читаем своим безопасным ридером, а не форком libtw2-datafile/map** (2026-09-27, уточняет D-008).
В libtw2-datafile/map 58 блоков `unsafe` и устаревшие зависимости; формат datafile простой. Свой ридер (`ddai-map`) без
`unsafe`, корректность доказывается сравнением с загрузчиком самого DDNet 20.1 (`map2raw` в оракуле) на корпусе
из 2428 официальных карт + блок-карты. libtw2 остаётся кандидатом для сети/снапшотов (решение в задаче 2.2).

**D-027 — Основной сервер живых тестов — Swarfey `45.141.57.35:8308` (ник «Muha»)** (2026-09-27). Разрешение получено
владельцем; по его словам, IP VPS там не банят. Сервер работает на моде «DDFightNet fng» на базе DDNet 18.5, а наш
эталон — ванильный 20.1. Следствия: (1) до живой игры мухи измерить ошибку прогноза LiveWorld на этом сервере (фаза 2/4);
(2) при систематических расхождениях — изучить мод и/или собрать оракул под 18.5; (3) ранние вводы (изменение 19.4)
на 18.5 обрабатываются иначе — учесть в синхронизации ввода.

**D-028 — Ответы владельца по живой игре и данным** (2026-09-27). Живые тесты только на Swarfey (`45.141.57.35:8308`,
«Muha»); собственных серверов нет. Запись игры других игроков на серверах (как обычная клиентская демка) для имитации
людей разрешена владельцем; ники и сырые записи хранятся только локально (`~/aiddnet/data/demos`), в отчёты и
репозиторий не попадают. Знания о блоке (вики DDNet, гайды, ролики — без скачивания видео) собираются в
`docs/research/block-knowledge.md` и превращаются в библиотеку сценариев и проверки награды.

**D-029 — Сетевой стек пишем сами (безопасный Rust), libtw2 — эталон и dev-оракул** (2026-09-27, уточняет D-008).
В libtw2 есть `unsafe` (huffman 14, snapshot 10, gamenet 37, net 1 блок), устаревшие зависимости и один мейнтейнер; свои
правки нужны всё равно (panic → Result, таймауты, REDIRECT, DDNet 20.x сообщения). Реализуем `ddai-net` сами по исходникам
DDNet 20.1; корректность — дифференциальные тесты против libtw2 (только dev-dependency), тестовые векторы из
`src/test/*` DDNet и разбор реального трафика локального сервера. Сгенерированные сообщения/объекты — из
`datasrc/network.py` DDNet (генератор в `tools/`).

**D-030 — Награда, учебный план и оценка мухи по знаниям о блоке** (2026-09-27, `research/block-knowledge.md`).
(1) Атрибуция блока как в открытых block-модах (DDNet++, ddnet-insta): кил — «последнему коснувшемуся» (хук, молот,
толчок телом), касание сбрасывается через 3 с без фриза; для обучения — плотный вариант: вход соперника во фриз и ≥ 1 с
без спасения. Штрафы: свой фриз, разморозка соперника молотом, сближение над фризом без второго прыжка.
(2) Учебный план: выживание → атака → защита → добивание → сценарии Copy Love Box → свободная игра; 18 сценариев из
§2 документа становятся юнит-сценариями арены. (3) Боты-блокеры DDNet++ (zlib) портируются как скриптовые соперники
лиги (с уведомлением о лицензии). (4) Карта сервера Swarfey (`clb-cyber-2026-2`, 468×255, front/switch/tune) — отложенная
карта для проверки переноса; WB-координаты TS-бота к ней не подходят — WB обобщается или размечается заново.
(5) Готового легального набора записей блока нет; данные людей — свои клиентские демки на Swarfey (D-028).

**D-031 — Swarfey: физика считается ванильной, данные людей собираем сами** (2026-09-27, ответ владельца). Владелец
уверен, что мод DDFightNet физику не меняет → оракул DDNet 20.1 остаётся эталоном; при первом подключении всё равно
меряем ошибку прогноза LiveWorld на Swarfey (дёшево). Teehistorian с сервера не будет → свой пайплайн «лучших демок»:
«Muha» (единственный ник, один бот на сервере) пишет клиентскую запись 25 Гц с максимальным `Cl_ShowDistance`
(видна почти вся карта), вводы людей восстанавливаются через нашу физику (ddai-demo, фаза 8).

**D-032 — Состав подграфов мухи S/M** (2026-09-27, задача 6.3). Выходы (100 DN-клеток) одинаковы для S и M ради
сопоставимости; AN в S — 82 клетки вместо оценочных 20–40; AN выбираются по данным (топ-типы по синапсам на выходы и
партнёров VPN); рецептивные поля — гекс-координаты с выводом на один хоп и порогом опоры 10; гомологи — замыкание до
неподвижной точки, `group` только в пределах типа. Факты — `FLY.md` §3.1.

**D-033 — Скорость физики: планка 3M ти-тиков/с снята** (2026-09-27, задача 1.3). Ядро на Rust бит-в-бит совпадает с
C++ DDNet 20.1 и на тех же входах в 2–3× быстрее самого C++-оракула; смешанный ввод (ходьба+прыжки+хук) даёт ~1,5M
ти-тиков/с на ядро — ограничение самого алгоритма (попиксельные проходы `MoveBox`/`IntersectLine*`). Для планировщика
(~2,7 тыс. ти-тиков на решение ≈ 2 мс) и обучения (8 ядер) этого хватает. Дешёвые оптимизации без потери точности
делаются; менять алгоритм ради скорости нельзя (паритет важнее).

**D-034 — Инференс мухи: задержка принята, стартовый α = 2,3** (2026-09-27, задача 7.1). На этом общем VPS p99 решения
S ≈ 1,0–1,2 мс, M ≈ 5–6,5 мс (чистый счёт M ≈ 2,8–3,0 мс, хвост — шум хоста). Принимаем: обучение начинается с S;
быстрый рациональный tanh (−0,5…1 мс на M) — отдельная задача при переходе на M. Стартовый α снижен 5,0 → 2,3: сеть
успокаивается за 0,3 с (S) / 0,9 с (M) вместо ~2,4 с, при этом ~70% ответа DN на вход приходит за 2 решения и знак
L/R-асимметрии правильный уже после первого. Прогрев — до сходимости (|ΔV| < 0,01, потолок 5 с).

**D-035 — TsCompat — отдельный буквальный порт TS-мира, а не флаги в рабочей физике; `jsmath` — отдельный крейт**
(2026-09-27, уточняет D-003 и PLAN §1.1). Чтобы решения Rust-планировщика совпадали с TS на 100%, он должен
считать на физике, побитно равной TS `SimWorld`, со всеми её причудами: порядок `order.unshift`, `applyTeeState`,
`thawScratch`, тюнинг `trunc(v*100)/100` в f64, V8-математика. Все эти причуды вносить флагами в рабочий
`ddai-physics::World`, который повторяет сервер C++ побитно, — значит усложнить главный код и рисковать им. Поэтому:
(1) `ddai-jsmath` — листовой крейт без зависимостей: V8-совместимая математика и `Rng` из `src/nn/rng.ts`. На нём
стоят и TS-мир, и планировщик. (2) `ddai-tsworld` — буквальный порт `src/core/*` (плюс API `SimWorld`, которым
пользуются `src/plan` и `src/env`) в f64 с `jsmath`; нужен только для паритета с TS и не участвует в игре.
(3) Планировщик (фаза 3) обобщён по трейту мира: на `ddai-tsworld` проверяется паритет решений с TS, а на
`ddai-physics::World<f32>` планировщик работает как учитель на настоящей физике DDNet. Цена — примерно 2,6 тыс.
строк порта физики, которые дублируют логику. Это приемлемо: код тестовый, и паритет буквального порта проверить
проще, чем паритет флагов.

**D-041 — Мозг бота: муха предлагает, точный поиск на настоящей физике проверяет** (2026-09-28, владелец поручил
выбрать самому; цель — «настоящий блок»: точный расчёт, чтобы соперник попал во фриз, и защита от чужих атак даже
1 против 5). Обученная сеть сама по себе — «интуиция». Точного расчёта на много тиков вперёд она не гарантирует, а
MLP на тех же входах пока сильнее мухи. Поэтому решение принимается в два шага (как «политика + поиск» в
AlphaZero):

1. **Муха** (модель на коннектоме) за ~1 мс даёт распределение действий и несколько кандидатов-планов на ~0,5–1 с.
2. **Поиск** (порт планировщика, фаза 3) проигрывает кандидатов и их вариации на побитно точном `World<f32>` (1.6)
   из прогноза LiveWorld (2.4). Модель угроз учитывает всех соперников в радиусе (до 5+), с их вероятными вводами
   (держат ввод, скриптовая реакция, выученная модель). Выбирается план, который максимизирует гарантированный
   исход (соперник во фризе, мы — нет) при худшем разумном ответе соперников.

Муха учится на выборе поиска (BC/DAgger, фаза 8) и на людях (D-038/D-040) и со временем берёт на себя всё больше
решения. Поиск остаётся «страховкой точности»: shield/seal из старого бота. MLP/GRU — честный контроль в
отчётах, не мозг.

Это **изменяет исходное правило «планировщик никогда не играет вживую»**: поиск участвует в живых решениях.
Согласовано делегированием владельца; если он будет против — откатываем к «только муха».

Следствия для плана:
- порт планировщика (фаза 3) становится частью живого мозга, не только учителем;
- арена и лига (фаза 8) включают матчи 1v1…1v5;
- бюджет решения (~20 мс на 2 тика) делится между мухой и поиском.
**Скорость (требование владельца: «главное — чтобы было БЫСТРО»):**
- Всё живое решение укладывается в **≤ 5 мс p99 на одном ядре**: муха ~1 мс, поиск ≤ 4 мс. Решение принимается
  каждые 2 тика, то есть раз в 40 мс, поэтому остаётся запас на сеть и прогноз.
- Поиск ограничен временем: итеративное углубление с тёплым стартом от прошлого плана, при исчерпании бюджета
  отдаёт лучший найденный план. Паритет с TS проверяется в режиме с фиксированным числом итераций, живая игра —
  в режиме с дедлайном.
- Значит, скорость `World::step`/`clone` критична. Цель задачи 1.10 — ≥ 1–2 млн ти-тиков/с и `clone` ≤ 5 мкс без
  потери побитной точности; при необходимости поиск работает на упрощённом «быстром» мире с проверкой итогового
  плана на точном.


**D-042 — Бюджет живого решения: цель ≤ 5 мс p99, но сила важнее; добираем оптимизацией** (2026-09-28, ответ

близко фриз, нас держат хуком) до 15 мс, если арена (8.1) показывает, что так бот сильнее. (3) Приоритет —
скорость без потери точности: ускорение `World` (1.10b), параллельные прогоны на ядрах, отсечение кандидатов мухой.

**D-045 — Как мерить задержку решения на этой VM: счётчики работы + wall, а не CPU потока** (2026-09-28, ревью 3.2,
раунд 2; уточняет D-042). Хост режет непрерывный счёт паузами ~10 мс около 10 раз в секунду. `/proc/thread-self/schedstat`
засчитывает эти паузы как время работы потока. Пример: поиск из 48 шагов физики (~0,5 мс работы) показал 10,8 мс
«CPU» при 11,5 мс wall. Поэтому «CPU потока» из D-042 паузы от работы не отделяет. Решение: ограниченность и бюджет
решения доказываются **счётчиками работы** (шаги физики по фазам: поиск, щит, прочее; перевод в мкс по медиане
~4,5 мкс/шаг на 2 ти), а wall p50/p90/p99 публикуется рядом с базовой линией пауз машины. Цель D-042 «≤ 5 мс p99»
относится к работе. Хвост wall от пауз VM — отдельная метрика и отдельный риск; снимать его можно закреплением ядра
и выделенным хостом, но не кодом. Ревью 3.2 нашло реальный неограниченный хвост работы в щите после дедлайна
(до ~2 000 шагов, 9–20 мс). Он чинится бюджетом щита.

**D-047 — Бот кроссплатформенный: Linux и Windows, с одинаковой физикой** (2026-09-29, просьба владельца: «сразу
реализуй кроссплатформенную поддержку, чтобы и там и там было легко; на Windows у меня не дата-центр IP»). Это
реализует запасной путь D-016: клиентская часть бота работает с домашнего IP владельца.

1. Побитная точность физики держалась на математике glibc через std (D-004). На Windows std вызывает UCRT, и
   последние биты другие. Поэтому вводится **своя переносимая математика, побитно равная glibc** (sin/cos/atan/atan2/
   powf в f32 и log в f64, порты алгоритмов glibc из ARM optimized-routines и fdlibm). Она используется на всех
   платформах, так что Linux и Windows считают одинаково. Доказательство — сверка с glibc на ≥ 10⁷ проб на функцию и
   полный паритет с оракулами.
2. Unix-специфичное (права 0600, `/proc`, пути, сигналы) заменяется переносимым или ветками `cfg`.
3. В CI добавляется сборка и тесты на `windows-latest`, в том числе золотые фикстуры физики.
4. Упаковка `.exe` и простой запуск на Windows — задача 5.5b. Веб бота на Windows слушает только 127.0.0.1; мост к
   сайту на VPS обсуждается там же.

Правила живой игры не меняются, где бы ни работал клиент: только разрешённые серверы, один бот, без чата, кик/бан —
стоп.

**D-048 — Мозг владеет техниками блока, включая хук в стену и потолок для спасения** (2026-09-29, владелец: «блокер

**D-050 — Защитные ограничения входа в игру (уточняет D-037)** (2026-09-29, по итогам инцидента на Swarfey и
задачи 2.3b). Причина инцидента: мод или прокси Swarfey на каждое приветствие отвечает `reconnect@ddnet.org`, а наш
клиент молча переподключался каждый раз с нового UDP-порта. Получилось 10 сессий за 35 с; правило «5 за 20 с» при этом
соблюдалось. Теперь:
1. Все переподключения и редиректы идут с одного локального порта, как у настоящего клиента (`client.cpp:3619`).
2. До первого входа в игру — **не больше 2 попыток подключения на запуск**, по любой причине: просьба сервера,
   «сервер полон», таймаут. Дальше — CLOSE и окончательная остановка.
3. Сторож входа: не в игре за 15 с — CLOSE и стоп. Пока идут куски карты, срок продлевается, но с абсолютным
   потолком. Повторное «connected» без явного решения о переподключении — тоже стоп.
4. Каждый шаг входа и каждый служебный пакет пишется в лог на уровне info.
5. Для записи наблюдателем после потери связи в игре весь бюджет восстановления — те же 15 с. Для будущего играющего
   бота (4.1) нужен отдельный бюджет «на один обрыв», его спроектировать там.
Остановка по этим правилам (код выхода 4) — повод разбираться, а не перезапускать.

**D-051 — Swarfey: админ разрешил, переподключение — ожидаемое поведение; Windows — только локальный веб**
(2026-09-29, ответы владельца).
1. Владелец спросил админа Swarfey. Тот «всё разрешил, делай что хочешь, просто переподключайся». Значит, просьба
   сервера `reconnect@ddnet.org` при входе — задуманная защита, а не ошибка. Клиент должен переподключиться так, как
   это делает настоящий клиент DDNet: с того же порта, один раз (D-050). Наши правила всё равно остаются: один бот,
   без чата и спама, остановка при кике или бане, ники других только локально. Условие для начала игры (D-043) —

**D-055 — Гибридный мозг: устройство и мелкие решения** (2026-09-29, задача 3.5, решения билдера). (1) Гибрид живёт в
`ddai-planner` (`hybrid::*`), не в новом крейте: поиск — это и есть планировщик (те же `evaluate`/`scoreTick`, щит, скрытое
состояние), всё это приватно; отдельный крейт заставил бы открыть внутренности ради одного потребителя. `FlyProposer` —
в `ddai-fly` (реализует `Proposer` из планировщика), чтобы планировщик не тянул зависимость от мухи. (2) Радиус угроз по
умолчанию — `380 + (2·2 + лаг)·15 px = 440 px`: длина хука плюс путь, который тушка проходит сама за два решения (15
px/тик — потолок `hook_drag_speed` на ось). (3) Робастный выбор — смесь `λ·худший + (1−λ)·ожидание` по комбинациям ответов
(`hold`/`react`) соперников, λ = 0,5: чистый max-min играет слишком осторожно против бота, который всегда атакует.
Ожидание взвешено онлайн-оценкой «соперник отвечает как скриптовый бот» (видимый ввод против двух предсказаний), вес
худшего случая падает, если соперник выглядит стоящим. Комбинации строятся только по соперникам, способным действовать
(замороженная или дальняя жертва не удваивает стоимость); при > 2 таких (1v3, 1v5) пересчёт пропускается — на 4 мс он
отнимал треть кандидатов и давал больше поражений.
(4) Расширение D-042 — правило явное и журналируется: флаги опасности (≥ 2 соперников в радиусе, фриз ближе 3 тайлов, нас
держат хуком) **и** выбранный план всё ещё заканчивается нашим выбыванием при каком-то ответе; тогда до 15 мс суммарно
добираются нерассмотренные кандидаты и CEM. (5) В `PlannerConfig` добавлен `enemy_landing_bonus` (0 во всех TS-пресетах,
3,0 у гибрида): бросок молотом кладёт жертву на дугу, которая приземляется за горизонтом 27 тиков, без этого слагаемого

(6) Абсолютный прицел в плане — `ABS_AIM + угол` (`PlanStep.aim > 50`): относительный прицел CEM/книги не уходит дальше
нескольких радиан, TS-путь его никогда не порождает; хук в стену не должен «плыть» вслед за жертвой. (7) Общий код:
`PlanWorld::step_into` (без аллокаций; по умолчанию делегирует `step`), `PhysicsWorld::step` и `restore_state`/
`save_state_into` без аллокаций (`World::restore_from` вместо производного `clone_from`, которое строило новую копию мира
~105 КБ на каждый кандидат), `Planner`: `Rc` → `Arc` для полей опасности, `deterministic_thaw` (кэш `noThaw` не зависит от
порядка кандидатов и потока), `threats` (1vN, `None` на TS-пути). Паритет TS: 19 360 + 3 604 решений, 0 расхождений после

**D-063 — Бот: удержание решения до его тика, адаптивный `prediction_margin`, пощажённые тии как тела** (2026-10-01,
задача 4.1b + её ревью раунд 1: F1-F4, остаток; уточняет D-023 и D-042).
- **Удержание до намеченного тика.** Решение с `InputTag` ждёт в драйвере, пока следующий `NETMSG_INPUT` не станет для
  `tag.expected_tick`; до того уходит предыдущий ввод (его и предполагала модель «летящих» вводов бота). Опоздавшее решение
  уходит сразу, решение без тега — как раньше. Причина: слоты ввода стоят в постоянной фазе к снапшотам, а оценка времени
  решения (асимметричного, двугорбого: гибрид 6 мс, до 15 мс в опасности) раньше была сглаженным средним, и до 24% решений
  уходили на тик раньше, чем бот предсказал. Теперь «раньше» невозможно, и оценку можно делать консервативной: ошибка в
  большую сторону стоит максимум одного тика. Отвергнуто: слать готовое решение вне слота (сервер хранит ввод по
  `IntendedTick`; второй ввод на тот же тик — не предусмотренный клиентом случай, D-023).
  - Оценка готовности зажата ниже периода снапшота, чтобы тег не уходил дальше `MAX_HOLD_TICKS` (единственный путь «раньше»);
    вытесненные до своего тика решения считаются (`superseded_decisions`).

    вытеснено и не ушло, не может «просочиться» в следующее значение счётчика (`CountInput` считает все нечётные между двумя
    вводами). Нажать может только принятое решение, а каждое решение прошло вето молотка на своём тике.
- **Оценка времени решения** — скользящий p90 по последним 64 решениям (`DecisionEstimator`, `BotConfig::estimate_quantile`).
  p90 даёт больше попаданий в первый слот, p97 — больше точных попаданий в тик, но почти все решения идут во второй слот
  (цифры — `docs/formats.md` §21.6). Разброс прогонов на общей машине больше разницы между квантилями.
- **Адаптивный margin** (`ddai_client::timing::MarginController`, включён у `ddnet-ai play --bot`, если не задан
  `--prediction-margin-ms`, который остаётся фиксированным переопределением). Датчик — `time_left` из `NETMSG_INPUTTIMING`
  (D-023): скользящий p1 за 5 с, цель 2 мс запаса, зажим 3-20 мс. **Первая версия (+2 мс за каждое опоздание, 30 с
  удержания) на загруженной машине ползла к потолку 20 мс** (пауза потока даёт опоздание раз в ~10 с при любом margin) и
  сводила выигрыш к нулю; переработано: вверх только по оконному сигналу (>= 2 опоздавших ввода в окне или p1 < 2 мс при
  >= 100 отсчётах); «затык» — по задержке отправки `margin - time_left > 18 мс`, а не по сырому опозданию; отсчёты вводов,
  отправленных до последней смены, игнорируются; вниз не больше 1 мс за 3 с, при p1 >= 4 мс (гистерезис) и после 10 с без опоздавших; `StallWatch` предупреждает (раз в минуту, только доли), если затыки > 0,5% вводов. Сброс к 10 мс на новой карте и
  соединении. Чем меньше margin, тем позже после снапшота стоит слот ввода и тем больше времени у решения.
  Отвергнуто: фиксированный margin 4 по умолчанию (на реальном сервере зависит от RTT и джиттера, D-043).
- **Горизонт предсказания** `max(12, pred_tick - tick + 3)` тиков, не больше 75 (раньше фиксированные 12 недопредсказывали

**D-067 — Клипы, консольные команды без чата, выбор сервера только из разрешённых (задача 4.3, `ddai-clip`, `ddai-bot::{clipper,command,console,settings}`, `ddai-client::server_list`)** (2026-10-02; номер — следующий свободный

- **Консоль и API:** `BotCommand` (enum) → `Bot::command` → `CommandReply`; шина `CommandBus`, поток `ddai-console`. **Строка без префикса не уходит никуда**, доказано тестами (она не доходит даже до шины; перебор 20 000 строк; в e2e — 0 чатов в аудите).

- **Зависимости:** `ddai-bot` +`toml` (settings), `ddai-client` +`serde_json` (разбор мастера), `ddnet-ai` +`reqwest` (blocking, те же версия и признаки, что у `ddai-connectome`): новых пакетов в `Cargo.lock` нет, кроме нового крейта `ddai-clip` (`postcard`, `zstd`, `serde` уже в дереве).

**D-070 — Веб-управление ботом: модель безопасности канала управления (задача 5.6, `ddai-botctl`, `ddai-bot::control`, `ddai-web::http::bot`)** (2026-10-02; номер — следующий свободный на момент написания, при слиянии пересчитать; развивает D-007, D-036, D-051, D-067, D-068).

  Файл теперь пишется с `0600` (в нём настоящие ники).
