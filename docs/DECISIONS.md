# Решения (ADR-журнал)

Формат: **D-NNN** — дата — решение. Почему. Следствия. Новые решения — в конец. Отменённые не удаляются, а
помечаются «ЗАМЕНЕНО D-xxx».

## Фаза 0 (2026-09-27)

**D-001 — Железо: AVX-512 нет, цель — x86-64-v3.** Промпт говорит «EPYC 9645 (Zen 5, AVX-512)», но гость KVM видит
модель «AMD EPYC-Rome» (family 23, model 49) с флагами до AVX2/FMA/BMI2, **без avx512***. Верим фактам: SIMD-код мухи
пишем под AVX2 (x86-64-v3); физику — без зависимостей от target-cpu. Если провайдер включит AVX-512 — это бонус,
не требование.

**D-002 — Эталон физики — C++ DDNet, не TS.** Эксперимент фазы 0 (`research/ddnet-physics.md` §0, §4): TS-порт
считает во float64 и расходится с настоящим C++ уже на 2–5 тике; даже одношагово ~40% мировых шагов отличаются.
Та же C++-логика в double совпадает с TS бит-в-бит → логика TS верна, отличие только в точности. Прототип Rust во
float32 совпал с C++ бит-в-бит на 20 сидов × 10 000 тиков × 3 ти. **Расхождение с промптом:** «паритет с TS-версией
и C++ DDNet» бит-в-бит одновременно невозможен. Решение: Rust f32 = бит-в-бит с C++ (все целые и квантованные поля);
Rust f64 в режиме совместимости с TS = бит-в-бит с TS на механиках, которые TS реализует; Rust f32 против TS — только
одношагово с допуском ±1 px / ±1/256.

**D-003 — Физика обобщена по скаляру (`f32`/`f64`) и имеет профиль совместимости.** `ddai-physics` параметризуется
типом `Real` и флагами профиля (`Ddnet` — полная механика, продакшн и обучение; `TsCompat` — отключает механики,
которых нет в TS: front-фриз, switch, tune, ehook и т.д., и повторяет квирки TS). Нужно для паритета физики с TS и для
паритета решений планировщика. Цена — дженерики в ядре; окупается проверяемостью.

**D-004 — Математика: glibc через std, без крейта `libm`.** `f32::powf/sin/cos/atan` в Rust на linux-gnu вызывают
glibc и совпали с C++ на 2 млн проб; чисто-Rust `libm` 0.2.16 расходится (powf в 9,7% проб). Порядок операций — как
в C++ (`Dir*a*(V*0.75f)`, `(vel+boost)-vel`, `round_to_int` через `f + 0.5f32`), без `mul_add` и fast-math.

**D-005 — Версия эталона DDNet: релиз 20.1** (2026-09-26, последний стабильный; master = 20.2 без тега). Между 20.0 и
master изменений в `gamecore`/`collision` нет. Оракул собирается из тега; версия/коммит пишутся в каждую трассу.
Целевые блок-серверы работают на разных базах (DDNet 18.5…20.2, моды DDNet++/F-DDrace/S-DDRaceX/Block Worlds) —
отличия модов изучаем отдельно, когда дойдём до конкретного сервера.

**D-006 — Эталонные трассы: три уровня.** (A) standalone C++-харнесс из настоящих `gamecore/collision/layers`
(прототип работает, дёшево, >10⁶ тик/с); (B) **основной эталон** — in-process сервер DDNet по образцу
`src/test/gameworld_test.cpp` (100% серверного кода, детерминированно); (C) приёмка — настоящий headless
DDNet-Server + teehistorian. TS-генератор трасс (из стенда фазы 0) — для паритета f64/TsCompat и планировщика.

**D-007 — Бот не пишет в чат ничего; `/showall` заменён на `Cl_ShowDistance`.** Старый бот при подключении слал в чат
`/showall 1`, чтобы видеть далёких игроков. В DDNet есть штатное сообщение `Cl_ShowDistance`
(`show-distance@netmsg.ddnet.tw`), которое шлёт любой клиент при отдалении камеры; сервер его не ограничивает
(`gamecontext.cpp:2777`), радиус клиппинга = ShowDistance/2 + 320 px (`player.cpp:1118-1141`). Также не шлём
`i-am-npm-package@…`, `rcon crashmeplx` и строки npm в версии.

**D-008 — Сеть: libtw2 (MIT/Apache) — вендорим/форкаем низкий уровень, сессию пишем сами.** Берём huffman, packer,
snapshot, demo как есть; форк `libtw2-net` (Connection, panic → Result, таймауты), форк `libtw2-gamenet-ddnet`
(регенерация под 20.x: `MapDetails.size/url`, новые сообщения), форк `libtw2-datafile/map` (патч «несколько game-слоёв»).
Своё: клиентская сессия (вход, INPUTTIMING/PredTick, карта in-protocol + HTTPS с sha256, REDIRECT/RECONNECT,
тюнинг, детект капчи/бана → avoid-list), мастер-сервер. Тестовый клиент на libtw2 в фазе 0 зашёл в игру на живом
сервере. Уведомления MIT/Apache сохраняются в вендорных файлах.

**D-009 — twmap и twgame (AGPL-3.0-only) не используем вообще.** Совместимость AGPL с GPL-3.0 есть (§13 обеих), но
AGPL §13 распространилась бы на весь бинарник. Даже как dev-оракул не нужен: карты и физику сверяем с C++ DDNet.
Читать их код как справку можно, копировать — нет.

**D-010 — Веб: axum + WebSocket (бинарные кадры) за Caddy.** Бот слушает только 127.0.0.1; Caddy — HTTPS (Let's Encrypt)
на `89-58-7-133.sslip.io`, ufw: 22/80/443. Вход: пароль (argon2id), сессия в cookie (HttpOnly, Secure, SameSite=Strict),
rate limit на вход, выход из сессии, проверка Origin для WS/POST, лимиты размера тел. Все команды, меняющие
состояние, — только после входа. Старый опрос JSON 25 Гц (125–390 КиБ/с) заменяется бинарным live-кадром.

**D-011 — Графика DDNet: скачивается ботом в рантайме, не коммитится.** Данные DDNet — CC-BY-SA 3.0; источник —
закреплённый коммит DDNet 20.1 (`c9d208138f85755521f16a0096b6fe036c5c8698`) на GitHub, манифест (путь, размер,
sha256) в репо, кэш `~/aiddnet/data/assets/`. Атрибуция на странице (DDNet/Teeworlds contributors, CC-BY-SA 3.0,
DejaVu, авторы скинов из `skins.json`). Скины с NC/ND/unknown — только по запросу, по умолчанию выключены.

**D-012 — Коннектом: MaleCNS v1.0 (CC-BY 4.0), минимальный набор 3 файла ≈ 566 МБ, закрепление по GCS generation +
md5 + sha256.** FlyWire (лицензия противоречива: NC vs CC-BY) — только локальная сверка, в релизы не попадает.
Чтение Feather — в Rust (крейт `arrow`, IPC+LZ4). Python-venv с pyarrow из фазы 0 — только исследовательский.

**D-013 — Модель мухи: rate-модель в стиле flyvis.** Знак × число синапсов × масштаб на пару типов, нормировка на
полный вход нейрона, ReLU с мягким потолком, экспоненциальный Эйлер Δ = 10 мс × 4 подшага на решение, параметры общие
для L/R (зеркальная симметрия), знаки ACh+/GABA−/Glu−/His−, моноамины вне быстрого пути, декодер DN с замороженной
калибровкой, голова модели мира + замороженный пробник как метрика. Детали — `FLY.md`. LIF — только отдельный
эксперимент.

**D-014 — Обучение: сначала имитация, потом RL; обязательные контроли.** BC → DAgger от планировщика → демки людей →
ES (S) / PPO (M/L). Контроли: перепроводка с сохранением степеней, перемешанные знаки, MLP/GRU того же размера.
Литература: RL с нуля через коннектом нестабилен везде; работало только «сначала имитация».

**D-015 — YouTube-ролики не используем как обучающие данные.** Владелец предложил «засунуть в муху клипы блока с
YouTube». В видео нет вводов (только картинка) → нужна отдельная CV-модель без GPU, данные шумные; скачивание роликов
запрещено правилами YouTube и задевает права авторов. Вместо этого: (1) демки DDNet (точные снапшоты); (2) записи
бота-наблюдателя на блок-серверах (точные данные, ники только локально); (3) ролики-объяснения — как источник тактик
для библиотеки сценариев и проверки награды (разбор по субтитрам/описаниям, без скачивания видео). Цель «лучше и
быстрее алгоритма» зафиксирована в метриках (F3 ≥ 50% против планировщика; инференс ≤ 5 мс против ~8 мс p50 у TS).

**D-016 — IP дата-центра и баны: никакого обхода.** В фазе 0 короткий исследовательский заход (`research-probe`,
< 20 с) получил автобан «bad ip» на 10 минут на TeeUnion и «VPN detected» на официальном DDNet-сервере. Прокси/VPN/смена
IP для обхода запрещены. Варианты для живой игры: серверы, которые принимают этот IP; серверы владельца; запуск
клиентской части бота с домашнего IP владельца (веб-панель остаётся на VPS). Решение — за владельцем (вопрос в STATUS).

**D-017 — Учитель — планировщик в режиме фиксированных итераций.** Недетерминизм TS-планировщика — только дедлайн
по часам; `{budgetMs: 0, hardMs: 0}` воспроизводим (20/20 игр). Датасеты размечаются только в этом режиме (иначе метки
зависят от загрузки CPU). `--brain planner` вживую может использовать бюджет по времени (или по числу оценок).

**D-018 — Паритет решений планировщика требует V8-совместимой математики в скоринге.** `Math.round` (половины к +∞),
`Math.hypot` (масштабирование + Kahan), `sin/cos/log` (fdlibm) отличаются от Rust std. В планировщике — модуль
`jsmath` (порт соответствующих функций V8/fdlibm, лицензия Sun/BSD-подобная с уведомлением). Скоринг планировщика
всегда в f64; физика под планировщиком — f64/TsCompat для паритета, f32/Ddnet в продакшне.

**D-019 — Модели /duo.** Билдер — Sonnet 5 (`sonnet-builder`), ревьюер — Opus 5.5 (`opus-reviewer`). Исследования
фазы 0 — субагенты на Opus. Мелкие поиски можно отдавать более дешёвым моделям.

**D-020 — Toolchain закреплён.** Rust 1.98.1 (`rust-toolchain.toml`), Node 24.21.0 (только для TS-генератора трасс).

**D-021 — Не переносим мёртвое и вредное.** `OpponentProfile` (вес 0), `routeDistance` в скоринге, `bandCost`,
подстрочное сравнение ников в friend/war (баг → точное сравнение после нормализации), автоклипы по пустым `events`
(в Rust события будут настоящими), дуэль-«auto» через `/accept` (чат).

**D-022 — Порядок персонажей (strong/weak) — из снапшота.** Сервер тикает персонажей «новые первыми» и отдаёт
позицию в `CNetObj_DDNetCharacter::m_StrongWeakId`; от этого зависит исход борьбы хуками. LiveWorld упорядочивает
мир по `m_StrongWeakId` (TS этого не делал).

**D-023 — Ввод: синхронизация PredTick по `NETMSG_INPUTTIMING`.** TS слал ввод по таймеру 20 мс и игнорировал
INPUTTIMING. В Rust — как клиент DDNet (`client.cpp`): управление intended tick по ответам сервера; модель «летящих»
вводов в LiveWorld пересчитывается от реального intended tick.

**D-024 — Серверный тюнинг и tune-зоны учитываются.** `Sv_TuneParams` (47 значений ×100) и `TILE_TUNE`/настройки
карты применяются к физике (TS использовал дефолты).

**D-025 — Автономность после фазы 0.** Владелец (2026-09-27) разрешил не ждать «ок» на план и идти по фазам дальше
без вопросов; вопросы копятся в `STATUS.md`. Разрешено тестирование на сервере «DDNet GER Block Copy Love Box» под
ником «Muha» (факт разрешения — со слов владельца).

**D-026 — Карты читаем своим безопасным ридером, а не форком libtw2-datafile/map** (2026-09-27, уточняет D-008).
В libtw2-datafile/map 58 блоков `unsafe` и устаревшие зависимости; формат datafile простой. Свой ридер (`ddai-map`) без
`unsafe`, корректность доказывается сравнением с загрузчиком самого DDNet 20.1 (`map2raw` в оракуле) на корпусе
из 2428 официальных карт + блок-карты. libtw2 остаётся кандидатом для сети/снапшотов (решение в задаче 2.2).

**D-027 — Основной сервер живых тестов — Swarfey `45.141.57.35:8308` (ник «Muha»)** (2026-09-27). Разрешение получено
владельцем; по его словам, IP VPS там не банят. Сервер работает на моде «DDFightNet fng» на базе DDNet 18.5, а наш
эталон — ванильный 20.1. Следствия: (1) до живой игры мухи измерить ошибку прогноза LiveWorld на этом сервере (фаза 2/4);
(2) при систематических расхождениях — изучить мод и/или собрать оракул под 18.5; (3) ранние вводы (изменение 19.4)
на 18.5 обрабатываются иначе — учесть в синхронизации ввода.

**D-028 — Ответы владельца по живой игре и данным** (2026-09-27). Живые тесты только на Swarfey (`45.141.57.35:8308`,
«Muha»); собственных серверов нет. Запись игры других игроков на серверах (как обычная клиентская демка) для имитации
людей разрешена владельцем; ники и сырые записи хранятся только локально (`~/aiddnet/data/demos`), в отчёты и
репозиторий не попадают. Знания о блоке (вики DDNet, гайды, ролики — без скачивания видео) собираются в
`docs/research/block-knowledge.md` и превращаются в библиотеку сценариев и проверки награды.

**D-029 — Сетевой стек пишем сами (безопасный Rust), libtw2 — эталон и dev-оракул** (2026-09-27, уточняет D-008).
В libtw2 есть `unsafe` (huffman 14, snapshot 10, gamenet 37, net 1 блок), устаревшие зависимости и один мейнтейнер; свои
правки нужны всё равно (panic → Result, таймауты, REDIRECT, DDNet 20.x сообщения). Реализуем `ddai-net` сами по исходникам
DDNet 20.1; корректность — дифференциальные тесты против libtw2 (только dev-dependency), тестовые векторы из
`src/test/*` DDNet и разбор реального трафика локального сервера. Сгенерированные сообщения/объекты — из
`datasrc/network.py` DDNet (генератор в `tools/`).

**D-030 — Награда, учебный план и оценка мухи по знаниям о блоке** (2026-09-27, `research/block-knowledge.md`).
(1) Атрибуция блока как в открытых block-модах (DDNet++, ddnet-insta): кил — «последнему коснувшемуся» (хук, молот,
толчок телом), касание сбрасывается через 3 с без фриза; для обучения — плотный вариант: вход соперника во фриз и ≥ 1 с
без спасения. Штрафы: свой фриз, разморозка соперника молотом, сближение над фризом без второго прыжка.
(2) Учебный план: выживание → атака → защита → добивание → сценарии Copy Love Box → свободная игра; 18 сценариев из
§2 документа становятся юнит-сценариями арены. (3) Боты-блокеры DDNet++ (zlib) портируются как скриптовые соперники
лиги (с уведомлением о лицензии). (4) Карта сервера Swarfey (`clb-cyber-2026-2`, 468×255, front/switch/tune) — отложенная
карта для проверки переноса; WB-координаты TS-бота к ней не подходят — WB обобщается или размечается заново.
(5) Готового легального набора записей блока нет; данные людей — свои клиентские демки на Swarfey (D-028).

**D-031 — Swarfey: физика считается ванильной, данные людей собираем сами** (2026-09-27, ответ владельца). Владелец
уверен, что мод DDFightNet физику не меняет → оракул DDNet 20.1 остаётся эталоном; при первом подключении всё равно
меряем ошибку прогноза LiveWorld на Swarfey (дёшево). Teehistorian с сервера не будет → свой пайплайн «лучших демок»:
«Muha» (единственный ник, один бот на сервере) пишет клиентскую запись 25 Гц с максимальным `Cl_ShowDistance`
(видна почти вся карта), вводы людей восстанавливаются через нашу физику (ddai-demo, фаза 8).

**D-032 — Состав подграфов мухи S/M** (2026-09-27, задача 6.3). Выходы (100 DN-клеток) одинаковы для S и M ради
сопоставимости; AN в S — 82 клетки вместо оценочных 20–40; AN выбираются по данным (топ-типы по синапсам на выходы и
партнёров VPN); рецептивные поля — гекс-координаты с выводом на один хоп и порогом опоры 10; гомологи — замыкание до
неподвижной точки, `group` только в пределах типа. Факты — `FLY.md` §3.1.

**D-033 — Скорость физики: планка 3M ти-тиков/с снята** (2026-09-27, задача 1.3). Ядро на Rust бит-в-бит совпадает с
C++ DDNet 20.1 и на тех же входах в 2–3× быстрее самого C++-оракула; смешанный ввод (ходьба+прыжки+хук) даёт ~1,5M
ти-тиков/с на ядро — ограничение самого алгоритма (попиксельные проходы `MoveBox`/`IntersectLine*`). Для планировщика
(~2,7 тыс. ти-тиков на решение ≈ 2 мс) и обучения (8 ядер) этого хватает. Дешёвые оптимизации без потери точности
делаются; менять алгоритм ради скорости нельзя (паритет важнее).

**D-034 — Инференс мухи: задержка принята, стартовый α = 2,3** (2026-09-27, задача 7.1). На этом общем VPS p99 решения
S ≈ 1,0–1,2 мс, M ≈ 5–6,5 мс (чистый счёт M ≈ 2,8–3,0 мс, хвост — шум хоста). Принимаем: обучение начинается с S;
быстрый рациональный tanh (−0,5…1 мс на M) — отдельная задача при переходе на M. Стартовый α снижен 5,0 → 2,3: сеть
успокаивается за 0,3 с (S) / 0,9 с (M) вместо ~2,4 с, при этом ~70% ответа DN на вход приходит за 2 решения и знак
L/R-асимметрии правильный уже после первого. Прогрев — до сходимости (|ΔV| < 0,01, потолок 5 с).

**D-035 — TsCompat — отдельный буквальный порт TS-мира, а не флаги в рабочей физике; `jsmath` — отдельный крейт**
(2026-09-27, уточняет D-003 и PLAN §1.1). Чтобы решения Rust-планировщика совпадали с TS на 100%, он должен
считать на физике, побитно равной TS `SimWorld`, со всеми её причудами: порядок `order.unshift`, `applyTeeState`,
`thawScratch`, тюнинг `trunc(v*100)/100` в f64, V8-математика. Все эти причуды вносить флагами в рабочий
`ddai-physics::World`, который повторяет сервер C++ побитно, — значит усложнить главный код и рисковать им. Поэтому:
(1) `ddai-jsmath` — листовой крейт без зависимостей: V8-совместимая математика и `Rng` из `src/nn/rng.ts`. На нём
стоят и TS-мир, и планировщик. (2) `ddai-tsworld` — буквальный порт `src/core/*` (плюс API `SimWorld`, которым
пользуются `src/plan` и `src/env`) в f64 с `jsmath`; нужен только для паритета с TS и не участвует в игре.
(3) Планировщик (фаза 3) обобщён по трейту мира: на `ddai-tsworld` проверяется паритет решений с TS, а на
`ddai-physics::World<f32>` планировщик работает как учитель на настоящей физике DDNet. Цена — примерно 2,6 тыс.
строк порта физики, которые дублируют логику. Это приемлемо: код тестовый, и паритет буквального порта проверить
проще, чем паритет флагов.

**D-041 — Мозг бота: муха предлагает, точный поиск на настоящей физике проверяет** (2026-09-28, владелец поручил
выбрать самому; цель — «настоящий блок»: точный расчёт, чтобы соперник попал во фриз, и защита от чужих атак даже
1 против 5). Обученная сеть сама по себе — «интуиция». Точного расчёта на много тиков вперёд она не гарантирует, а
MLP на тех же входах пока сильнее мухи. Поэтому решение принимается в два шага (как «политика + поиск» в
AlphaZero):

1. **Муха** (модель на коннектоме) за ~1 мс даёт распределение действий и несколько кандидатов-планов на ~0,5–1 с.
2. **Поиск** (порт планировщика, фаза 3) проигрывает кандидатов и их вариации на побитно точном `World<f32>` (1.6)
   из прогноза LiveWorld (2.4). Модель угроз учитывает всех соперников в радиусе (до 5+), с их вероятными вводами
   (держат ввод, скриптовая реакция, выученная модель). Выбирается план, который максимизирует гарантированный
   исход (соперник во фризе, мы — нет) при худшем разумном ответе соперников.

Муха учится на выборе поиска (BC/DAgger, фаза 8) и на людях (D-038/D-040) и со временем берёт на себя всё больше
решения. Поиск остаётся «страховкой точности»: shield/seal из старого бота. MLP/GRU — честный контроль в
отчётах, не мозг.

Это **изменяет исходное правило «планировщик никогда не играет вживую»**: поиск участвует в живых решениях.
Согласовано делегированием владельца; если он будет против — откатываем к «только муха».

Следствия для плана:
- порт планировщика (фаза 3) становится частью живого мозга, не только учителем;
- арена и лига (фаза 8) включают матчи 1v1…1v5;
- бюджет решения (~20 мс на 2 тика) делится между мухой и поиском.
**Скорость (требование владельца: «главное — чтобы было БЫСТРО»):**
- Всё живое решение укладывается в **≤ 5 мс p99 на одном ядре**: муха ~1 мс, поиск ≤ 4 мс. Решение принимается
  каждые 2 тика, то есть раз в 40 мс, поэтому остаётся запас на сеть и прогноз.
- Поиск ограничен временем: итеративное углубление с тёплым стартом от прошлого плана, при исчерпании бюджета
  отдаёт лучший найденный план. Паритет с TS проверяется в режиме с фиксированным числом итераций, живая игра —
  в режиме с дедлайном.
- Значит, скорость `World::step`/`clone` критична. Цель задачи 1.10 — ≥ 1–2 млн ти-тиков/с и `clone` ≤ 5 мкс без
  потери побитной точности; при необходимости поиск работает на упрощённом «быстром» мире с проверкой итогового
  плана на точном.

**D-045 — Как мерить задержку решения на этой VM: счётчики работы + wall, а не CPU потока** (2026-09-28, ревью 3.2,
раунд 2; уточняет D-042). Хост режет непрерывный счёт паузами ~10 мс около 10 раз в секунду. `/proc/thread-self/schedstat`
засчитывает эти паузы как время работы потока. Пример: поиск из 48 шагов физики (~0,5 мс работы) показал 10,8 мс
«CPU» при 11,5 мс wall. Поэтому «CPU потока» из D-042 паузы от работы не отделяет. Решение: ограниченность и бюджет
решения доказываются **счётчиками работы** (шаги физики по фазам: поиск, щит, прочее; перевод в мкс по медиане
~4,5 мкс/шаг на 2 ти), а wall p50/p90/p99 публикуется рядом с базовой линией пауз машины. Цель D-042 «≤ 5 мс p99»
относится к работе. Хвост wall от пауз VM — отдельная метрика и отдельный риск; снимать его можно закреплением ядра
и выделенным хостом, но не кодом. Ревью 3.2 нашло реальный неограниченный хвост работы в щите после дедлайна
(до ~2 000 шагов, 9–20 мс). Он чинится бюджетом щита. **Поправка D-076 (задача 3.6):** курс часов работы теперь 1,25 мкс на ти-тик (`WORK_US_PER_TEE_TICK`, предварительно; поиск ускорен ≈ 1,75× без смены решений), прежние 2,2 мкс остались в конфигах E-003/E-007 явно.

**D-047 — Бот кроссплатформенный: Linux и Windows, с одинаковой физикой** (2026-09-29, просьба владельца: «сразу
реализуй кроссплатформенную поддержку, чтобы и там и там было легко; на Windows у меня не дата-центр IP»). Это
реализует запасной путь D-016: клиентская часть бота работает с домашнего IP владельца.

1. Побитная точность физики держалась на математике glibc через std (D-004). На Windows std вызывает UCRT, и
   последние биты другие. Поэтому вводится **своя переносимая математика, побитно равная glibc** (sin/cos/atan/atan2/

   платформах, так что Linux и Windows считают одинаково. Доказательство — сверка с glibc на ≥ 10⁷ проб на функцию и
   полный паритет с оракулами.
2. Unix-специфичное (права 0600, `/proc`, пути, сигналы) заменяется переносимым или ветками `cfg`.
3. В CI добавляется сборка и тесты на `windows-latest`, в том числе золотые фикстуры физики.
4. Упаковка `.exe` и простой запуск на Windows — задача 5.5b. Веб бота на Windows слушает только 127.0.0.1; мост к
   сайту на VPS обсуждается там же.

Правила живой игры не меняются, где бы ни работал клиент: только разрешённые серверы, один бот, без чата, кик/бан —
стоп.

**D-050 — Защитные ограничения входа в игру (уточняет D-037)** (2026-09-29, по итогам инцидента на Swarfey и
задачи 2.3b). Причина инцидента: мод или прокси Swarfey на каждое приветствие отвечает `reconnect@ddnet.org`, а наш
клиент молча переподключался каждый раз с нового UDP-порта. Получилось 10 сессий за 35 с; правило «5 за 20 с» при этом
соблюдалось. Теперь:
1. Все переподключения и редиректы идут с одного локального порта, как у настоящего клиента (`client.cpp:3619`).
2. До первого входа в игру — **не больше 2 попыток подключения на запуск**, по любой причине: просьба сервера,
   «сервер полон», таймаут. Дальше — CLOSE и окончательная остановка.
3. Сторож входа: не в игре за 15 с — CLOSE и стоп. Пока идут куски карты, срок продлевается, но с абсолютным
   потолком. Повторное «connected» без явного решения о переподключении — тоже стоп.
4. Каждый шаг входа и каждый служебный пакет пишется в лог на уровне info.
5. Для записи наблюдателем после потери связи в игре весь бюджет восстановления — те же 15 с. Для будущего играющего
   бота (4.1) нужен отдельный бюджет «на один обрыв», его спроектировать там.
Остановка по этим правилам (код выхода 4) — повод разбираться, а не перезапускать.

**D-051 — Swarfey: админ разрешил, переподключение — ожидаемое поведение; Windows — только локальный веб**
(2026-09-29, ответы владельца).
1. Владелец спросил админа Swarfey. Тот «всё разрешил, делай что хочешь, просто переподключайся». Значит, просьба

**D-055 — Гибридный мозг: устройство и мелкие решения** (2026-09-29, задача 3.5, решения билдера). (1) Гибрид живёт в
`ddai-planner` (`hybrid::*`), не в новом крейте: поиск — это и есть планировщик (те же `evaluate`/`scoreTick`, щит, скрытое
состояние), всё это приватно; отдельный крейт заставил бы открыть внутренности ради одного потребителя. `FlyProposer` —
в `ddai-fly` (реализует `Proposer` из планировщика), чтобы планировщик не тянул зависимость от мухи. (2) Радиус угроз по
умолчанию — `380 + (2·2 + лаг)·15 px = 440 px`: длина хука плюс путь, который тушка проходит сама за два решения (15
px/тик — потолок `hook_drag_speed` на ось). (3) Робастный выбор — смесь `λ·худший + (1−λ)·ожидание` по комбинациям ответов
(`hold`/`react`) соперников, λ = 0,5: чистый max-min играет слишком осторожно против бота, который всегда атакует.
Ожидание взвешено онлайн-оценкой «соперник отвечает как скриптовый бот» (видимый ввод против двух предсказаний), вес
худшего случая падает, если соперник выглядит стоящим. Комбинации строятся только по соперникам, способным действовать
(замороженная или дальняя жертва не удваивает стоимость); при > 2 таких (1v3, 1v5) пересчёт пропускается — на 4 мс он
отнимал треть кандидатов и давал больше поражений.
(4) Расширение D-042 — правило явное и журналируется: флаги опасности (≥ 2 соперников в радиусе, фриз ближе 3 тайлов, нас
держат хуком) **и** выбранный план всё ещё заканчивается нашим выбыванием при каком-то ответе; тогда до 15 мс суммарно
добираются нерассмотренные кандидаты и CEM. (5) В `PlannerConfig` добавлен `enemy_landing_bonus` (0 во всех TS-пресетах,
3,0 у гибрида): бросок молотом кладёт жертву на дугу, которая приземляется за горизонтом 27 тиков, без этого слагаемого
поиск не видит выигрыша (T18: 0 → 40%). У гибрида включён и существующий `landing_cost` = 2,0 (то же прогноз для нас).
(6) Абсолютный прицел в плане — `ABS_AIM + угол` (`PlanStep.aim > 50`): относительный прицел CEM/книги не уходит дальше
нескольких радиан, TS-путь его никогда не порождает; хук в стену не должен «плыть» вслед за жертвой. (7) Общий код:
`PlanWorld::step_into` (без аллокаций; по умолчанию делегирует `step`), `PhysicsWorld::step` и `restore_state`/
`save_state_into` без аллокаций (`World::restore_from` вместо производного `clone_from`, которое строило новую копию мира
~105 КБ на каждый кандидат), `Planner`: `Rc` → `Arc` для полей опасности, `deterministic_thaw` (кэш `noThaw` не зависит от
порядка кандидатов и потока), `threats` (1vN, `None` на TS-пути). Паритет TS: 19 360 + 3 604 решений, 0 расхождений после
правок. (8) Дедлайн в арене — на **часах работы** (ти-тики физики × 2,2 мкс): на общей VM (load average 10–27) стенный дедлайн

остальные — в отчёте задачи 3.5 для 3.5b.

**D-063 — Бот: удержание решения до его тика, адаптивный `prediction_margin`, пощажённые тии как тела** (2026-10-01,

- **Удержание до намеченного тика.** Решение с `InputTag` ждёт в драйвере, пока следующий `NETMSG_INPUT` не станет для
  `tag.expected_tick`; до того уходит предыдущий ввод (его и предполагала модель «летящих» вводов бота). Опоздавшее решение
  уходит сразу, решение без тега — как раньше. Причина: слоты ввода стоят в постоянной фазе к снапшотам, а оценка времени
  решения (асимметричного, двугорбого: гибрид 6 мс, до 15 мс в опасности) раньше была сглаженным средним, и до 24% решений
  уходили на тик раньше, чем бот предсказал. Теперь «раньше» невозможно, и оценку можно делать консервативной: ошибка в
  большую сторону стоит максимум одного тика. Отвергнуто: слать готовое решение вне слота (сервер хранит ввод по
  `IntendedTick`; второй ввод на тот же тик — не предусмотренный клиентом случай, D-023).

    вытесненные до своего тика решения считаются (`superseded_decisions`).

    вытеснено и не ушло, не может «просочиться» в следующее значение счётчика (`CountInput` считает все нечётные между двумя
    вводами). Нажать может только принятое решение, а каждое решение прошло вето молотка на своём тике.

  p90 даёт больше попаданий в первый слот, p97 — больше точных попаданий в тик, но почти все решения идут во второй слот
  (цифры — `docs/formats.md` §21.6). Разброс прогонов на общей машине больше разницы между квантилями.
- **Адаптивный margin** (`ddai_client::timing::MarginController`, включён у `ddnet-ai play --bot`, если не задан
  `--prediction-margin-ms`, который остаётся фиксированным переопределением). Датчик — `time_left` из `NETMSG_INPUTTIMING`
  (D-023): скользящий p1 за 5 с, цель 2 мс запаса, зажим 3-20 мс. **Первая версия (+2 мс за каждое опоздание, 30 с
  удержания) на загруженной машине ползла к потолку 20 мс** (пауза потока даёт опоздание раз в ~10 с при любом margin) и
  сводила выигрыш к нулю; переработано: вверх только по оконному сигналу (>= 2 опоздавших ввода в окне или p1 < 2 мс при
  >= 100 отсчётах); «затык» — по задержке отправки `margin - time_left > 18 мс`, а не по сырому опозданию; отсчёты вводов,
  отправленных до последней смены, игнорируются; вниз не больше 1 мс за 3 с, при p1 >= 4 мс (гистерезис) и после 10 с без опоздавших; `StallWatch` предупреждает (раз в минуту, только доли), если затыки > 0,5% вводов. Сброс к 10 мс на новой карте и
  соединении. Чем меньше margin, тем позже после снапшота стоит слот ввода и тем больше времени у решения.
  Отвергнуто: фиксированный margin 4 по умолчанию (на реальном сервере зависит от RTT и джиттера, D-043).

**D-067 — Клипы, консольные команды без чата, выбор сервера только из разрешённых (задача 4.3, `ddai-clip`, `ddai-bot::{clipper,command,console,settings}`, `ddai-client::server_list`)** (2026-10-02; номер — следующий свободный

- **Формат клипа v1** (`docs/formats.md` §24): `magic + zstd(postcard)`, кольцо 750 кадров (30 с на 25 Гц) в фиксированных слотах — запись кадра не выделяет память. В кадре: наш тий, ближайшие семь, все связанные хуком (до 12), снаряды, **отправленные

  было с сырыми целыми и давало 28%: сервер шлёт ядро только когда клиентское предсказание расходится с ним, так что целые снапшота часто старше самого снапшота. - **События выводятся из снапшотов** (а не вшиты в `ActivityClock`): те же правила (точка удара `pos + dir·21`, 56 px), независимо от часов атрибуции; часы не тронуты.

- **Консоль и API:** `BotCommand` (enum) → `Bot::command` → `CommandReply`; шина `CommandBus`, поток `ddai-console`. **Строка без префикса не уходит никуда**, доказано тестами (она не доходит даже до шины; перебор 20 000 строк; в e2e — 0 чатов в аудите).

  готовы (D-052/D-053); запись Swarfey в файле владельца **не тронута**, то есть `auto` пока выбирает локальный. **Ворота `live_servers::check` (явный `--server`, `record`, драйвер) тоже требуют `ready = true`** (ревью F1) — это меняет прежнее поведение: запись в файле без `ready` больше не пускает.
- **Зависимости:** `ddai-bot` +`toml` (settings), `ddai-client` +`serde_json` (разбор мастера), `ddnet-ai` +`reqwest` (blocking, те же версия и признаки, что у `ddai-connectome`): новых пакетов в `Cargo.lock` нет, кроме нового крейта `ddai-clip` (`postcard`, `zstd`, `serde` уже в дереве).

**D-070 — Веб-управление ботом: модель безопасности канала управления (задача 5.6, `ddai-botctl`, `ddai-bot::control`, `ddai-web::http::bot`)** (2026-10-02; номер — следующий свободный на момент написания, при слиянии пересчитать; развивает D-007, D-036, D-051, D-067, D-068).
- **Канал.** Отдельный Unix-сокет `control.sock` (`0600` в каталоге `0700`) рядом с read-only мостом: мост остаётся только на чтение (D-036), управление — другой сокет, чтобы «читающий» путь не получил возможности писать. - **Типизированный закрытый словарь, а не строки.** По сокету идёт не текст консоли, а `ControlCommand` (JSON, `deny_unknown_fields`): режим, стоп/ход, вейблок, мозг, kill, клип, goto x y, spec/join, перечитать списки. Бот отображает его на `BotCommand` 4.3 `match`'ем без запасной ветки, так что новая команда требует решения.
  Чата нет **по построению** (ни одного варианта с текстом для сервера; заметка клипа уходит только в файл), как и `quit`, `target` по имени, подключения, смены сервера, allowlist и `ready`: сайт не пишет `live-servers.toml` и не может заставить бота подключиться. - **Списки идут не через канал.** Сайт правит `relations.json` (тот же код, что у бота: `ddai_botctl::relations`, одна свёртка D-021, точное совпадение), затем шлёт `reload_relations`; имена по сокету не ходят вовсе, поэтому не могут попасть ни в аудит, ни в журнал бота. Нечитаемый файл не перезаписывается ни сайтом, ни ботом (D-021).
  Файл теперь пишется с `0600` (в нём настоящие ники).
- **Лимит и аудит.** Одно ведро на сокет (8 пачкой, 2/с), считается каждая строка; не больше 4 соединений. **D-074 — Длительный прогон 4.4 и юнит бота** (2026-10-02; номер — следующий свободный на момент написания, при слиянии пересчитать).
- **Харнесс** `tools/e2e/soak.sh` (+ `soak.py`, `soak_analyze.py`): локальный сервер, наш бот `--brain hybrid`, три скриптовых бота (один живёт весь прогон, два приходят и уходят), отдельный веб-юнит на другом порту с WebSocket-зрителем, консоль, один перезапуск сервера, одна смена карты туда и обратно; журнал каждые 15 с (`~/aiddnet/data/logs/4.4/`, не в git). Критерии приёмки считает `soak_analyze.py`; `--selftest` строит синтетические прогоны и проверяет, что каждый критерий **может** упасть.
- **Критерии (как они считаются).** Рост памяти: медиана минуты 10 процесса против медианы его последней минуты, ≤ 10% (для каждого процесса, прожившего дольше минуты 10 плюс две минуты окна; сервер после перезапуска считается заново, от минуты 10 нового процесса); память — анонимная + swap, см. ниже. Потоки и fd: медиана конца ≤ медиана базы + max(2, 5%). p99 накладных расходов: медиана последних 30% прогона ≤ max(1,25 × медиана первых 30% после минуты 10; она + 150 мкс). `Cl_Kill`: интервал между подряд идущими ≥ 500 тиков, ≥ 100 для `WayBlockLying` (правило ВБ, `WB_KILL_COOLDOWN_TICKS`), счёт обнуляется при откате тика, смене карты и обрыве связи (как в боте). Клипы: автоматических ≤ 24, одного вида ≤ 16 (§24.4).
- **Память после смены карты (находка soak, исправлено конфигурацией).** С glibc по умолчанию бот после захода на карту 1244x667 (BlmapChill) остаётся на ~160 МиБ больше и на второй заход доходит до 261 МиБ (плато; утечки нет: 3-й и 4-й заходы не добавили ничего). Причина — динамический порог `mmap` glibc: после освобождения большого буфера порог растёт, и такие буферы дальше живут в куче. `MALLOC_MMAP_THRESHOLD_=131072` отдаёт их системе сразу (34 МиБ после возврата, 3 захода подряд). Кода это не меняет (нет `unsafe` и новых зависимостей): переменная стоит в юните и в стенде. У веба на таком заходе ступень +0,7…+1,0 МиБ (причина не проверялась); боевой веб-юнит не менялся.
- **Критерий роста памяти (решения лида: первый отчёт и ревью раунда 1): по каждому процессу `≤ max(10% базы, 1 МиБ)`, база — 25-я минута прогона, по анонимной памяти + swap (`RssAnon + VmSwap`) вместо голого RSS.** Рассуждение: ВМ общая, ядро выгружает анонимные страницы в swap и выбрасывает файловые страницы бинарника, голый RSS падает и растёт без единой аллокации (в прогоне A бот 37,7 → 26,5 МиБ за минуту). База на 25-й минуте — после заполнения 6 колец задержек (32 768 решений / 25 Гц ≈ 22 минуты, 768 КиБ: на минуте 10 заполнены на 46%, то есть ≈ 0,4 МиБ), в окне остаются ступени аллокатора (1-4 МиБ); 1 МиБ — размер одной ступени на 6-МиБ вебе, на ботах 10% шире. Первоначальные «≤ 4 МиБ» ревью отвергло: на вебе это +66%. Прогон короче 35 минут память не судит. Стенд: `ABS_MEM_TOL_MIB`, `WARMUP_S` (перезапуск сервера поставлен на 20% прогона, чтобы окно базы было тихим); `--selftest` покрывает ветку `anon_kb`: рост анонимной, рост только файловых страниц (проходит), рост, спрятанный в swap (ловится), порог 1 МиБ на 5-МиБ процессе. **Для многодневной работы без присмотра нужен прогон ≥ 6 часов:** окна по 10-16 минут не видят наклона ниже ≈ 0,5 МиБ/ч (≈ 67 МиБ в неделю при 0,4 МиБ/ч, ≈ 290 МиБ при 1,7); отдельная задача.
- **Стенд не трогает `~/aiddnet/data/bot` (ревью, F1).** В первой редакции режим `--unit` брал настоящий `data/bot` для бота и по окончании переносил его в каталог прогона; с 5.6 это боевое состояние (`relations.json` владельца, `control.sock`, `live.sock`, `ReadWritePaths` боевого веба: без каталога перезапуск веба даёт `226/NAMESPACE`). Теперь бот в обоих режимах получает частный каталог `<прогон>/botdata` (drop-in юнита: `--data-dir`, `--bridge`, `--control`, `--settings`, `--relations`, `ReadWritePaths` на него и на `data/run`; карты скачиваются в частный кэш), а в конце стенд сверяет `data/bot` (список, права, размеры, mtime) и пишет результат в вердикт. Прогоны B-E и ревьюера использовали и переносили настоящий каталог; они отмечены в E-009.
- **Причина отключения от сервера — свободный текст (ревью, остаточный риск).** Модератор мог вписать в неё ник. Клиентский слой пишет о причине только длину (`reason_len`); бот перед записью заменяет в тексте имена и кланы присутствующих игроков (`PlayerTable::redact`, без учёта регистра; имя из 1-2 символов только как целое слово) их тегами и добавляет длину оригинала. Не покрыты игроки, уже ушедшие из снапшота, и демонстрационный `play` без бота.
- **`status_message` больше не сортирует кольца задержек.** Три `Series::summary()` каждые 200 мс на потоке решений стоили ≈ 2,7 мс (0,9 мс на ряд) плюс шесть раз в 10 с строка лога. Теперь `Series` ведёт гистограмму окна (256 точных корзин до 256 мкс, 128 корзин на октаву выше, середина корзины: ошибка ≤ 0,4%), проценты — просмотр корзин, 6 мкс на три ряда; сообщение статуса не строится без читателей моста; точный `summary()` остался для итогового отчёта. - **Итог (E-009).** Четыре прогона по 60 минут (процесс и юнит, ВБ авто и выкл.): 0 паник, 0 чата, 0 ников в логе, `Cl_Kill` в кулдаунах, перезапуск сервера → в игре за 1,1-1,3 с, смена карты и ВБ-сброс, клипы ограничены, веб читает мост, потоки и fd не растут.   работают всё время, показывается живой, если его соединение **пригодно** (правильный `HELLO`), иначе демо, иначе ничего. Демо подключено всегда, поэтому уход бота даёт демо сразу, без паузы на подключение. Сокет, который не говорит по протоколу, ботом не считается.
  Альтернативы: подключать демо только когда бота нет (проще, но «вспышка» «нет источника» на каждое переключение и на каждое открытие страницы); реплеи Oracle B вместо демо (не показывают муху, нужен корпус).
- **Демо нельзя принять за бота (главное требование владельца).** События неактивного источника в хаб не идут; `STATUS` демо не становится статусом бота (его описание собирается из двух коротких строк: арена и имя весов, `docs/formats.md` §28); хаб при смене источника забывает всё прежнее;
  `GET /api/bot/status` — только живого бота (+ поле `source`); `POST /api/bot/command` при показанном демо — `503 demo_only` до разбора тела (после Origin, сессии, CSRF), ничего не уходит; у демо нет сокета управления, `control.sock` — бота. Список друзей (файл) правится, «перечитать» боту не шлётся. Кнопки выключены, плашка на трёх
  вкладках словами «Показ: муха на арене (не настоящая игра)». Безопасность 5.1-5.6 не менялась, кадры обоих источников проходят ту же проверку.
- **Демо рисует игру, а не только муху.** `fly watch` раньше слал мост только поток `DFLY`; теперь ещё `MAP` (настоящая карта по имени файла: у `clb-left` это Copy Love Box; у синтетических арен карты нет и «Игра» пуста), `PLAYERS` («муха», «соперник N»: слоты, ников нет), `FRAME` каждый тик (из `World<f32>` арены; наблюдатель только читает, побитное равенство решений с зрителем и без проверено тестом 7.4) и `STATUS` раз в секунду. Для этого у `ddai-env` появился `play_game_watched` (наблюдатель получает `&mut Sim`; `play_game_observed` — обёртка, поведение прежнее).
- **Пауза без зрителя: бит «сайт открыт» в подписке.** Простейшее («пауза, когда нет клиентов моста») не годится: веб подключён к демо всегда. «Зритель» — открытое WS-соединение (страница держит `sub live` всегда, а вкладка не меняет подписку); хаб считает их (`viewer()`), `BotSource` шлёт бит 1 маски подписки (аддитивно, бит 0 — муха из 7.4), `Bridge::watched()` — есть ли клиент с любым битом. `fly watch --pause-idle` (по умолчанию выключен: у тестов и ручного запуска зрителя нет) ставит игру на паузу и продолжает с того же тика.
  Живой бот бит читает и игнорирует, старый бот не знает его (по коду: он читает `маска & 1`), так что порядок выкладки веба и бота не важен. Недостаток: забытая вкладка держит демо играющим (~2,6% ядра) — цена принятой простоты (в сайте нет понятия «вкладка видна»).
  Запрос зрителей демо получает **только пока бот не пригоден** (затвор в `MuxSource`): с работающим ботом демо ни о чём не просят и оно стоит, чтобы не отбирать ядро у бота и 4.5.
- **Цена (замер, release, `nice -n 10`, общая ВМ, load average ~7):** без зрителей 0,05% ядра (юнит просыпается 10 раз в секунду); «Игра» открыта — 2,6%; «Игра» и «Муха» — 2,9%; RSS 18 МиБ, 2 потока. Ожидалось ~2%. Стоимость на стороне веба (кодирование 50 кадров в секунду и рассылка) отдельно не мерилась: это тот же путь, что у живого бота.
- **Юнит** `ddnet-ai-flydemo.service`: `Nice=10`, `IOSchedulingClass=idle`, без сети (`PrivateNetwork=true`, `AF_UNIX`, `IPAddressDeny=any`), пишет только `data/flydemo` (свой каталог `0700`, сокет `fly-demo.sock`), а весь `data/bot` недоступен (`InaccessiblePaths=…/data/bot` на каталог целиком, без `-`), `MALLOC_MMAP_THRESHOLD_` (D-074), `MemoryMax=512M`, `TasksMax=64`; проверен как временный юнит (запуск, кадры через сокет, чистая остановка с кодом 0, `systemd-analyze security` 2.2 OK).

Теперь у демо свой каталог `data/flydemo` (сокет `fly-demo.sock`, `ReadWritePaths` только он), а `data/bot` закрыт целиком; веб подключается к `fly-demo.sock` на чтение. Проверено временными системными юнитами тех же свойств на временных путях: при отсутствующих, при существующих и при пересозданных `live.sock`/`control.sock` демо не подключается, не удаляет, не занимает и не видит каталог, а свой сокет и вся игра в юните работают. Веса: `FLYDEMO_BUNDLE` (по умолчанию E-005 final), переопределяется необязательным `data/flydemo.env` для 8.2b без правки юнита. `WantedBy=multi-user.target` (в отличие от юнита бота: сети нет, играть на сервере он не умеет).

Кнопки на странице выключены по тому же правилу (по `control_socket` из статуса).

**D-076 — Скорость гибрида: горячий путь ускорен без смены решений, часы работы перекалиброваны на 1,25 мкс (задача 3.6, E-010; поправка к D-045, уточняет D-042 и D-055)** (2026-10-03; номер — следующий свободный на момент написания, лид перенумерует при слиянии).

**D-078 — Исключение из «никакого чата»: команда `/kill` как запасной путь** (2026-10-03, решение владельца:
«Разрешить /kill»; уточняет D-007).
- **Почему.** DDNet при `sv_kill_protection` (по умолчанию 20 мин) молча отбрасывает `Cl_Kill` после 20 минут жизни
  (`gamecontext.cpp:2998-3003`). Бот, замёрзший после этого, застревает: в репетиции 4.5 он сидел 93 минуты.
  Остаётся только серверная команда `/kill`. Её отправляют через `Cl_Say`, но другие игроки её не видят.
- **Что разрешено — ровно одна строка `/kill`**, и больше ничего. Тип в коде должен делать любой другой текст
  невозможным: отдельная типизированная команда, а не общий чат. Allowlist исходящих сообщений пропускает `Cl_Say`
  только с этим точным содержимым.
- **Когда.** Только как запасной путь: бот замёрз, решение о самоубийстве уже принято, `Cl_Kill` не дал смерти за
  разумное время. Кулдауны те же, что у самоубийства (D-058, 4.1). Аудит считает `/kill` отдельно.
- **Всё остальное без изменений.** Никаких сообщений, ответов, эмоций в чат — D-007 в силе.
- **Реализация (задача 4.6).** (а) **Тип:** `ddai_net::server_command::ServerCommand` с единственным вариантом `Kill`, константный текст `/kill`, `team = 0`; `encode_cl_say` остаётся `pub(crate)` и вызывается только оттуда; публичный путь — `Session::request_server_command` / `Client::server_command(ServerCommand)` (аргумента-строки нет). (б) **Список разрешённых** (`ddai-client::allowlist::check`): `Cl_Say` проходит, только если payload побайтно равен `ServerCommand::Kill.payload()`; остальные тексты, `/kill ` с пробелом, `/KILL`, NUL, длинная строка, тимчат — отказ (тесты). (в) **Аудит:** метка `Cl_Say(/kill)` отдельно от `Cl_Kill`; отчёт бота `kill_command_ticks`; «0 чата» в e2e и стенде стало «0 чата, кроме разрешённого `/kill`». **D-088 — SOCKS5 с UDP ASSOCIATE для Swarfey: прокси привязан к записи сервера, один путь датаграмм через трейт (задача 2.6; дополняет D-053, уточняет D-016/D-052/D-067)** (2026-10-03; номер — следующий свободный на момент написания, при слиянии пересчитать).
- **Зачем.** Выданный админом Swarfey прокси был только TCP (D-053), а VPS забанен как «VPN» (D-052). Следующий прокси, скорее всего, снова SOCKS5, и бот должен уметь им пользоваться сразу, как владелец его пришлёт. Всё сделано и проверено **только на loopback** (никаких подключений к Swarfey и к прокси владельца).
- **Правило D-053 не меняется, а закреплено в коде:** прокси допустим **только для сервера, чья запись в `live-servers.toml` называет его** (`proxy = "<имя>"`), и только по слову владельца, когда `ready = true` (D-067 без изменений). Файл прокси — `<data-dir>/secrets/<имя>-proxy.toml` (формат уже существующего `swarfey-proxy.toml`: `host`, `port`, `user`, `pass`; права строго без битов группы и остальных). Драйвер **перед каждой попыткой** (первой, переподключением, редиректом) сверяет пару «запись ↔ `ClientConfig::proxy`» в обе стороны и отказывает без единой датаграммы: прокси, которого запись не называет, не используется никогда; запись с `proxy` не подключается напрямую, даже если файл прокси потерялся (прямое соединение повторило бы бан D-052). Остальные серверы (TeeUnion, официальные DDNet) прокси получить не могут: способа указать его иначе, чем записью, нет. Привязку держит и сам файл: его `for_server` (как в настоящем `swarfey-proxy.toml`), если он есть, должен совпасть с адресом сервера, иначе прокси не загружается для него и драйвер отказывает (ревью F4: тестовый allow-list не направит прокси Swarfey на другой сервер). Это не меняет запрета обхода несанкционированных банов (D-016).
- **Транспорт.** Прежде драйвер использовал `UdpSocket` напрямую. Теперь это трейт `Transport` (`begin_attempt`, `reset_after_loss`, `send`, `recv`): `DirectUdp` — прежнее поведение без изменений (один сокет на весь `Client::connect`, тот же порт на переподключениях, D-050), `Socks5UdpTransport` — через прокси. Сессия (`Session`) не тронута. Разбор входящего от прокси строгий и не паникует (`proptest` на произвольных байтах): отбрасываются чужой источник, `FRAG ≠ 0`, битый заголовок, источник внутри не равен игровому серверу, пустые и слишком длинные данные; всё считается (`DropStats`), ничего не ошибка.
- **Ассоциация умирает с TCP** (RFC 1928 §6): управляющее соединение опрашивается на каждом `recv`; закрылось — это обрыв, дальше обычная политика (backoff, 5 за 20 с, два захода до входа по D-050, не больше 3 обрывов в игре за 600 с по D-058). Новое соединение с прокси открывается **не чаще одного на попытку, и только внутри попытки, уже занявшей слот** таблицы «5 за 20 с», так что переподключения к прокси входят в те же лимиты (тест: полная таблица — ни одного TCP к прокси). `reconnect@ddnet.org` и редирект сохраняют ассоциацию (тот же исходящий порт), потеря — нет.
- **Что останавливает повторы** (`GaveUp(ProxyRefused)`, код выхода бота **4**, который в `RestartPreventExitStatus` юнита: systemd не повторит вход, ревью F3; одно соединение с прокси и тишина): ответ `0x07` на `UDP ASSOCIATE` (`Socks5Error::UdpNotSupported`, «UDP not supported»), неверный пароль (повтор может заблокировать учётную запись), нет метода входа, отказ по набору правил, неразборчивый ответ. Сетевые ошибки и таймауты (каждый шаг ограничен, всё рукопожатие 10 с) — обычный обрыв.
- **Секреты.** `Secret` в `Debug`/`Display` всегда `<redacted>`; в нём хост, логин и пароль; `Debug` у `ProxyConfig` показывает только имя (значит и `ClientConfig`). Ошибки загрузки собраны из имён ключей и номеров строк, значений нет (текст ошибки TOML цитирует строку — не используется). Адрес прокси в журнал не пишется. Тесты проверяют это на каждом пути (файл, права, рукопожатие, `proxy-check`, `play`).
- **`ddnet-ai proxy-check --proxy <имя>`** — первым делом на новом прокси: TCP, вход, `UDP ASSOCIATE`, адрес ретранслятора, ничего игровому серверу. Выводит `ok` / `UDP not supported` (код 3) / `auth failed` (код 4), иначе код 1 с причиной; адрес и учётные данные не печатает.
- **Фильтр cgroup юнита бота пропускает адрес прокси, а не сервера** (`IPAddressAllow=<IP прокси>`; адрес Swarfey разрешать не нужно: ошибка в коде тогда не выпустит бота напрямую). Порядок переключения — `deploy/README.md`.
- **Осознанные границы.** (1) У TCP-соединения нет keepalive (стандартная библиотека не даёт его без `unsafe`/новой зависимости): прокси, который тихо перестал пересылать UDP при живом TCP, обнаруживается таймаутом DDNet (100 с по умолчанию), после чего ассоциация открывается заново. (2) Адрес ретранслятора из `BND` не принимается на веру (ревью F1): датаграммы идут всегда на IP самого прокси с объявленным портом, а объявленный чужой адрес (частный, NAT, loopback, IP игрового сервера: путь бана D-052) только подставляется и пишется в журнал; ответ принимается только с IP и порта ретранслятора, как требует спецификация задачи, поэтому прокси, отвечающий с другого порта, не заработает; `proxy-check` показывает, на той ли машине ретранслятор, но датаграмму не посылает, так что порт ответа он не проверяет. (3) Фрагменты (`FRAG ≠ 0`) не собираются (RFC позволяет). (4) Пароль в памяти не затирается (нет зависимости `zeroize`); буфер, в котором он уходит на провод, обнуляется. (5) Закрытие управляющего соединения при остановке откладывается на 100 мс, чтобы ретранслятор передал вежливый `CLOSE`. (6) Подключение к прокси блокирующее, до 10 с: `disconnect` в эти секунды заметит чуть позже.
- **Ревью, раунд 1.** F1 (доверие к `BND`) закрыт подстановкой IP прокси и отказом, если ретранслятор совпал с целью; F2 (прокси, отдающий ответ по байту, растягивал рукопожатие) — цикл `read` с пересчётом оставшегося времени; F3 (три перезапуска systemd) — категория `GaveUpCategory::ProxyRefused` → код 4; F4 — проверка `for_server`; F5 — версия байта ответа RFC 1929 игнорируется при успехе.
- **Проверено** (всё на loopback): модульные тесты и `proptest` разбора, рукопожатие против сервера-двойника с ретранслятором и инъекцией ошибок (без входа, логин, неверный пароль, `0x07`, другие отказы, `BND` `0.0.0.0`/домен/чужой/порт 0, зависание на каждом шаге, мусор, чужие/фрагментированные/битые/подмененные датаграммы, обрыв TCP); `Client::connect` через ретранслятор к игровому двойнику (сеанс идёт только через него, обрыв TCP → новая ассоциация, `reconnect@ddnet.org` сохраняет ассоциацию, `0x07`/пароль — стоп после одного соединения, привязка в обе стороны); `proxy-check` и `play` бинарником; e2e на настоящем локальном сервере (`tests/e2e_socks5.rs`, `#[ignore]` + `DDAI_E2E=1`): вход, движение, две смены карты, обрыв TCP-соединения с прокси, перезапуск сервера, аудит «0 чата». Формат — `docs/formats.md` §33.

**D-089 — Запуск бота с сайта: сайт только просит, проверяет и запускает отдельная root-программа (задача 5.9, `ddnet-ai launch`, `ddai-web::{launch, http::launch}`, `deploy/`)** (2026-10-04; номер — следующий свободный на момент написания, при слиянии пересчитать; развивает D-036, D-043, D-052/D-053/D-088, D-067, D-068, D-070, D-075, D-078).
- **Зачем.** Владелец хочет сам запускать и останавливать бота с сайта, выбирать мозг (гибрид / гибрид + муха / муха) и смотреть игру на вкладке «Игра». Сегодня Swarfey банит наш прокси как VPN (D-052), поэтому рабочая цель — локальный сервер `127.0.0.1:8303` со спарринг-ботами; Swarfey появляется в выборе сам, когда его запись в `live-servers.toml` получает `ready = true`.
- **Главное решение: сайт не получает никаких прав.** `ddnet-ai-web.service` остаётся `User=ubuntu`, `NoNewPrivileges`, `ProtectSystem=strict`, без systemctl, sudo, D-Bus и без запуска процессов. Он пишет **один маленький JSON** (`request.json`, атомарно: временный файл и `rename`) в **свой** каталог `~/aiddnet/data/launch/` (только он добавлен в `ReadWritePaths`, не `data/bot`) и читает оттуда `status.json`. Дальше работает root-юнит `ddnet-ai-launch.path` (`PathExists=` на файл запроса) → oneshot `ddnet-ai-launch.service` → `ddnet-ai launch apply`. Помощник запускает **корневую копию бинарника** (`/usr/local/libexec/ddnet-ai/ddnet-ai`, её кладёт `deploy/install-launcher.sh`): файл, который может переписать пользователь `ubuntu`, не должен исполняться от root.
- **Что делает `launch apply`.** Читает запрос как обычный файл ≤ 1 КиБ (`O_NOFOLLOW`: симлинк отвергается; `O_NONBLOCK`: FIFO не повесит) и **удаляет его до обработки** (запрос не повторится после перезагрузки). Разбор со строгой схемой (`deny_unknown_fields`, версия, id из 8–32 hex-цифр; у `stop` нет других полей, у `start` есть мозг, сервер и длительность). Каждое значение проверяется по фиксированным спискам: `action ∈ {start, stop}`, `brain ∈ {hybrid, hybrid-fly, fly}`, длительность `15m|60m|unlimited`, спарринг 0..3 и только на `local`, сервер — `"local"` либо **точный** `address` записи `live-servers.toml` с `ready = true` (не свободный адрес; ник, прокси и адрес, которые доходят до юнита, берутся из этой записи, а не из запроса; адрес записи должен быть `ip:порт` не-loopback, ник — 1–15 символов `[A-Za-z0-9_-]`). Путь к файлу мухи — из **корневого** конфига `/etc/ddnet-ai/launch.toml` (`fly_bundle`, по умолчанию `data/runs/E-005/e005-fly/checkpoints/final.bundle`), никогда из запроса; конфиг должен принадлежать root и не быть доступным на запись группе/остальным, путь — абсолютный, из `[A-Za-z0-9._/-]`, без `..`, `*.bundle`, обычный файл. Строка запроса не попадает ни в одну командную строку.
- **Что пишется для systemd.** (1) `/etc/ddnet-ai/bot-launch.env` (root, `KEY="значение"`, значения из закрытого набора символов: `BOT_SERVER`, `BOT_NAME`, `BOT_BRAIN`, `BOT_DURATION`, `BOT_FLY_ARGS`, `BOT_LAUNCH_ID`); `ddnet-ai-bot.service` берёт из него `--server --name --brain --duration` и (через `$BOT_FLY_ARGS`, пустая переменная — аргумент исчезает) `--fly-bundle`. Значения по умолчанию в самом юните — прежние (локальный сервер, hybrid, без лимита). `hybrid-fly` = `--brain hybrid --fly-bundle …`, `fly` = `--brain fly --fly-bundle …`. (2) Дроп-ин `…/ddnet-ai-bot.service.d/50-launch.conf` с `IPAddressAllow=` (сброс) + loopback, и **для сервера с `proxy`** — IP прокси из файла секретов (читается через `ddai-client::proxy`, с проверкой прав 0600, `for_server`, привязки записи; наружу выходят только IP, ни хост, ни логин, ни пароль не печатаются и не пишутся в статус), а для публичного сервера без прокси — IP самого сервера. Адрес Swarfey при прокси в фильтр не попадает (D-088).
- **Лимиты.** Не больше одного запуска в 30 с; после выхода бота с кодом 3 или 4 (кик, бан, отказ прокси, не вошёл) — запуск закрыт на 120 с; после 3/4 на **публичном** сервере сервер закрыт, пока владелец заново не откроет запись (правка `live-servers.toml` после бана: сравнивается mtime файла с моментом бана; рекомендация — оставлять `ready = false`, пока владелец не подтвердил). Память (последний запуск, выход, баны) — `/var/lib/ddnet-ai/launch-state.json` (root, 0600, под `flock`); нечитаемый файл **не перезаписывается**, и запуски закрыты (`state_unreadable`), пока владелец его не проверит. Свой лимит есть и у сайта (1 запрос в 3 с, `429`; ждущий необработанный запрос — `409`, устаревший старше 30 с можно заменить).
- **Бот ушёл → память и статус.** `ExecStopPost=-+…ddnet-ai launch exited` (от root, сбой хука юнит не валит): читает `$EXIT_CODE/$EXIT_STATUS`, пишет бан-память для публичного сервера (3/4), статус для сайта (`stopped`: `stopped_by_owner` / `finished`; `failed`: `kicked_or_banned` (3), `join_failed` (4), `crashed`) и после нормального конца (0, 3, 4, остановка владельцем) **удаляет одноразовый env-файл**, чтобы ручной `systemctl start` потом был обычным локальным по умолчанию (сбой перезапускается systemd с тем же окружением). Текст причины от сервера («VPN detected») в статус **не** попадает: бот не передаёт его (в журнал идёт только длина, D-067), а свободный текст чужого сервера на страницу не выносим; сайт показывает код выхода и смысл, текст — в `journalctl`.
- **Дополнительные запреты запуска** (статус `refused`, ничего не меняется): бот уже работает (`already_running`); локальный сервер не запущен (`local_server_down`); на юните бота есть **чужой drop-in** (`unit_overridden`: `systemctl show -p DropInPaths` должен перечислять только `50-launch.conf`; ручной `ExecStart=` с `swarfey.conf` обошёл бы проверенное окружение и фильтр). `deploy/install-launcher.sh --take-over` убирает такие drop-in в резервный каталог.
- **Спарринг** — шаблон `ddnet-ai-sparring@.service` (экземпляры 1..3): `play --brain scripted --name Spar%i --clan Spar`, случайный скин (по умолчанию), `--no-bridge --no-control --no-memory --no-settings --no-autoclip`, собственный `--data-dir data/sparring` (бот и секреты ему закрыты `InaccessiblePaths`), адрес `127.0.0.1:8303` зашит в юните, cgroup — только loopback, то же ужесточение. `BindsTo=ddnet-ai-bot.service`: уходят вместе с ботом (в том числе когда время вышло). Запускает и останавливает только помощник; на публичный сервер — никогда (`sparring_local_only`).
- **Интерфейс.** Карточка «Запуск» на вкладке «Бот» (`assets/launch.js`, `launch.css`, область `#launch-mount`): сервер (Локальный сервер / готовые записи списка), мозг (Гибрид / Гибрид + муха / Муха), длительность, спарринг 0–3 (только локально), «Запустить» / «Остановить», статус («В игре» из живого моста; «запущен, входит в игру»; ждёт обработки; остановлен; ошибка с причиной), имя запуска мухи (не путь). Маршруты `GET|POST /api/bot/launch`: сессия, строгий Origin, CSRF, JSON — как у остальных POST (D-070). Публичный сервер просит подтверждения в браузере.
- **Проверено.** Модульные тесты (схема и все отказы: лишнее поле, плохой мозг, свободный сервер, лимит размера, симлинк, публичный без `ready`, лимит запусков, остановка после бана, чтение конфига), интеграционный `launch apply` с поддельным `systemctl` (файл окружения, дроп-ин, точные команды, отсутствие секретов), тесты маршрутов (401/403/415, запрос пишется атомарно), и **настоящий e2e на этой машине, только локальный сервер**: реальные юниты, тестовый веб-экземпляр на порту 7789 (копия веб-юнита с тем же ужесточением), Playwright: гибрид + муха + 2 спарринга запущены с сайта, видны на «Игре» как «Живой бот», остановлены с сайта (`tools/e2e/launcher.spec.ts`).
- **Откат.** `deploy/install-launcher.sh --uninstall` (бот остановлен); прежний юнит бота лежит в `/var/backups/ddnet-ai-launcher/<метка>/`. Без запущенного пути-юнита сайт просто пишет файл, который никто не читает (интерфейс скажет об этом через 15 с).
- **Ревью 5.9, раунд 1 (поправки к D-089).** (F1) Хук остановки наследует `UMask=0077` юнита бота: статус создавался `0600 root` и сайт его не читал после самостоятельного конца бота. Теперь `write_atomic` ставит режим явно (`fchmod`), тест гонит всё под `umask 077`. (F2) Запрос теперь с `ts`; помощник отвергает и удаляет запрос старше 60 с (по `ts` и по mtime) и датированный будущим: запрос, написанный, пока путь-юнит не работал, не выполняется позже (`request_stale`); сайт удаляет свой устаревший запрос и показывает «запуск не отвечает». (F3) Сайт принимает не чаще одного запроса в 2 с и не больше 6 в минуту (у `ddnet-ai-launch.path` `TriggerLimitBurst=10`). (F4) Память фиксируется до записи файлов и запуска, а политика проверяется заново внутри замка на свежем состоянии: бан, записанный хуком после первого взгляда, не стирается и запуск отказывается. (F5) `status.json` пишется в `/run/ddnet-ai/` (root, 0755; `RuntimeDirectory=` юнита запуска, хук создаёт сам), а не в каталог, который пользователь может переименовать; в `data/launch` остался только запрос (помощник читает с `O_NOFOLLOW` и удаляет). (F6) Скрипт установки не копирует бинарник в резерв и хранит последние 3 каталога резервов; прежний юнит бота лежит навсегда в `original/`. (N1) IPv6 допустим в окружении. (N2) После остановки по запросу и нормального конца запуска помощник убирает env-файл и возвращает дроп-ин к одному loopback (после остановки по запросу делает `daemon-reload`; хук — без перезагрузки, она будет при следующем запуске); после сбоя, исчерпавшего `StartLimit`, одноразовое окружение остаётся до следующей остановки или запуска.
