# ddai-planner

Задача 3.2. Порт старого TS-планировщика блока (`src/plan/{planner,shield,seal,throwLines,memory,
livePlan}.ts`, BFS-поля из `planner.ts`, скриптовый бот и модели противника из `src/env/{scripted,
action}.ts`) в Rust, обобщённый по трейту `PlanWorld`, с двумя реализациями:

- `ts_adapter` (фича `ts-parity`) — над `ddai-tsworld::SimWorld`, побитовый паритет с настоящим
  TS-планировщиком (Node 24.21.0 / V8 13.6);
- `physics_adapter` (по умолчанию) — над `ddai_physics::World<f32>`, боевой/обучающий бэкенд
  (D-041): муха предлагает, этот поиск на настоящей физике DDNet проверяет и решает.

Вся числовая семантика JS (округление, `hypot`, тригонометрия, `Rng`) идёт через `ddai-jsmath`;
скоринг всегда в `f64` (критерий приёмки 2), даже когда сам мир считает в `f32`.

## Паритет с TS — результаты

Харнесс (`tools/ts-trace/gen-planner-dump.mjs` и `gen-planner-freerun.mjs`) гоняет настоящий,
неизменённый `src/plan/planner.ts` через Node 24 type-stripping (никогда не редактирует и не
копирует `src/`) и дампит JSON-lines с побитовыми (hex) `f64`.

**Способ 1 — teacher-forced, независимые решения** (`gen-planner-dump.mjs` +
`tests/parity_planner.rs`): для каждого случая — свежий `Planner` + `reset()` + свежий
`SimWorld` (`addTee(self)` затем `addTee(enemy)`, порядок как в `bot.ts`), состояние обоих ти
подставляется из диапазона позиций, собранных прогоном «скрипт против скрипта» на карте (чтобы
получить разнообразные позиции/скорости/фриз/хук), затем один вызов `decide()`. Поскольку
планировщик каждый раз свежий, сверять пришлось только вход (мир + `prevInput` + `enemyInput`) и
выход (решение + `lastInfo`) — всё скрытое между решениями состояние тут ещё не тестируется (см.
способ 2).

- **Прогон (2026-09-28, после fix round'а ревью раунда 2):** 4 карты (`arena`, `freeze` —

  **+** 6 файлов × 400 решений на Copy Love Box, E-000 левый холл, `--force-freeze-edge`
  (**shield-stress**-сценарий, F14, ниже) = **19 360 решений, 70 файлов, 0 расхождений**.

`restsInFreeze` брал состояния из органической траектории скриптовых ботов, которые сами
избегают опасности — «current dumps are ~all zeros». Теперь генератор дополнительно:

- дампит весь `hazardField`/`unfreezeField` (BFS-сетка) целиком — точное, поэлементное сравнение
  `Int32Array` против `Vec<i32>`;
- сэмплирует `touchesFreeze` на фриз-соседних и обычных тайлах;
- смещает 70% случаев `escapeExists`/`saferInput`/`sealedIn` на тайл вплотную к фризу (радиус 1)
  со скоростью в его сторону — вместо «почти всегда true» получается реальная смесь исходов.

|---|---|---|---|
| Copy Love Box (400 shield-кейсов, 1200 seal-кейсов) | 171/400 = 42.75% | 87/1200 = 7.25% | 0 |
| BlmapChill (400 shield-кейсов, 1200 seal-кейсов) | 131/400 = 32.75% | 474/1200 = 39.5% | 0 |

**F14, «Copy Love Box restsInFreeze dumps all zero» (было ровно так — 0/1200):** причина —
`restsInFreeze`'s собственный цикл выходит на тике 0, если тело УЖЕ стоит на земле
(`isSolid` под ним) и `vel.y >= 0` — до какого-либо перемещения. У CLB 38 из 84
фриз-соседних тайлов имеют ближайший фриз строго СБОКУ (`dy == 0` в направлении к фризу), то
есть внедрённая для них скорость чисто горизонтальна (`vel.y = 0`) — цикл обрывается мгновенно
и `restsInFreeze` возвращает `touchesFreeze` от НЕТРОНУТОЙ стартовой точки, что для стоячего,
не-фризового тайла почти всегда `false`. Исправление (`gen-component-dump.mjs`, только генератор
дампов — `src/plan/seal.ts` не тронут): `dy == 0` случаям добавлен небольшой скачок вверх
(`vel.y -= 4..8`, как будто тело только что подброшено — ровно так `restsInFreeze` и вызывается
по-настоящему в `planner.ts`/`bot.ts`, всегда на скорости ПОСЛЕ удара/броска, а не в покое), чтобы
баллистика вообще успела отработать; `dy != 0` случаи не тронуты (там уже есть настоящая
вертикальная компонента). Отдельный замер тем же пробником (`n=1200`, независимо от реального
корпуса): CLB 0/1200 → 269/1200 true; BlmapChill (для сравнения — уже была ненулевая, но
преимущественно за счёт органических тиков скриптовых ботов, не этого пробника: сам пробник в
изоляции давал лишь 3/1200) 3/1200 → 215/1200 true. В реальном корпусе (400 из 1200
seal-строк — именно этот пробник, остальное органика) это даёт итоговые 87/1200 (CLB) и рост
389→474/1200 (BlmapChill) в таблице выше — обе карты теперь дают настоящую смесь исходов, не
константу.

(Для сравнения: доля `shielded=true` в полном корпусе способа 1 — round 2: 193/16 960 ≈ 1.14% в
baseline+full после поднятия объёма/danger-bias (round 1: 79/12 960 = 0.61%); в выделенном
shield-stress-корпусе (способ 1, E-000 левый холл, гарантированный телепорт к фризу) — 117/2 400
≈ 4.9%. Ревью раунд 2, F14 просил ≥10% — этого не достигли: реальные игровые решения почти
никогда доходят до состояния, где щит нужен, потому что сам CEM-поиск уже хорошо избегает
опасности **даже когда `self` специально телепортирован к фризу** (round 1 уже пробовал скорости
8/10/12/14/16/18/24 — все в диапазоне 2–8.5%, не выше); выделенный дамп способа 3 (ниже) обходит
эту проблему по-другому — не пытаясь заставить полный `Planner::decide` дойти до `shielded=true`,
а вызывая `escapeExists`/`saferInput` напрямую на сконструированных состояниях.)

`frozenThrowLines` — тоже 0 расхождений на обеих картах (детали см. вывод теста).

## D-041: боевой режим с дедлайном — измерения

Ревью раунд 1, F1 (BLOCKER): у `Planner::decide`/`decide_once` нет и не будет настоящего
дедлайна — это TS-паритетный путь, `budgetMs`/`hardMs` там означают ровно то, что в TS (мягкий
"пропускай книгу, если долго" плюс жёсткий `overCap()`), и часы там принципиально не читаются
(D-017: детерминизм независимо от загрузки машины). Реальный боевой дедлайн — отдельный метод,
**`Planner::decide_production<C: Clock>(world, self_id, enemy_id, prev, enemy_input, &clock,
budget_ms)`**: тёплый старт (сдвинутый `warm`) → книга → CEM с итеративным уточнением, каждый

### F16 (ревью раунд 3, MAJOR): `prof` теперь по умолчанию выключен, память фиксированного размера

Ревью раунд 3 нашло то, что раунды 1-2 пропустили: все четыре метки `prof::mark` в
`decide_production` писались в растущий `Vec` БЕЗУСЛОВНО, и на боевом пути их никто не читал
(`take()` вызывают только тесты) — `Vec` рос без ограничения. Ревьюер (`zz_r3_leak.rs`): 3 000
вызовов `decide_production` без единого `take()` оставили **12 000 записей (480 Б)** — 160 Б на
решение, ≈29 МБ/ч на 50 решений/с, ≈430 МБ за 15-часовую боевую сессию, плюс периодическое
удвоение `Vec` даёт скачок задержки на том решении, где оно случилось.

**Исправление** (`src/prof.rs`, полностью переписан):
- новый флаг `enabled` (`thread_local`, по умолчанию `false`) — `inc_step`/`inc_escape`/`mark`
  теперь начинаются с проверки этого флага и, если выключен, **сразу возвращаются**: ни счётчик не
  трогается, ни аллокации. Выключенная стоимость — одна булева проверка, ничего больше;
- хранилище — **фиксированный массив на 4 слота** (`[Option<(Instant, u64, u64, u64)>; 4]`), не
  `Vec`: `mark(slot)` пишет НАПРЯМУЮ в `slot`, перезаписывая предыдущее решение — физически
  невозможно накопить больше 4 записей, независимо от того, сколько решений прошло без `take()`
  (в отличие от старого `Vec`, который переставал расти только потому, что тесты по факту звали

- вызывающие, которым нужны замеры (все существующие тесты, читающие метки), теперь явно зовут

### F17 (ревью раунд 3, MINOR): книжные/throw-сиды теперь участвуют в elites итерации 0

`decide_once` кладёт кандидатов книги (`seed_plans`), политики (`policy_seed_plans` — всегда пусто
в этом крейте, нет загруженной сети/политики) и приземлённых бросков (`landed_throws`) в ТОТ ЖЕ

так что первый `refit` видел только случайные CEM-семплы — книжные/throw-кандидаты влияли на
`best`/`best_stay` (выбор решения), но НЕ на форму распределения для следующей итерации.

**Исправление** (`planner.rs`): `scored` объявлен ДО тёплого старта/`seed_plans`/

цикл `'iters` больше не пересоздаёт `scored` на `it == 0` (использует то, что уже накоплено),
только `.clear()`-ит на `it > 0`. Тёплый старт (`self.warm`) **сознательно НЕ** добавлен в

`plan_margin` (см. «не перенесено» ниже), а `carry` в `decide_once` тоже держится отдельно от
`scored` и сравнивается с `best` только один раз, в самом конце, после всего поиска.

**Качество не хуже** — таблица `quality_vs_budget_report` (выше, у F13) уже перемерена ПОСЛЕ этого

### F18 (ревью раунд 3, MINOR): бюджет щита масштабируется по числу ти в сцене

Ревью намерило (`r3-phase.log`/`r3-phase-missed.log`, budget=4мс, n=1000/условие,
`shield_incomplete`):

| Арена | 2 ти | 6 ти |
|---|---|---|
| Весь Copy Love Box | 29-127 / 1000 | 330-493 / 1000 |
| E-000 левый холл | 2-12 / 1000 | 95-117 / 1000 |

Причина: `world.step()` тикает ВСЕ ти в мире, так что цена одного тика растёт с их числом — один
полный роллаут `escape_exists` (~126 тиков) стоит ~0.3 мс на 2 ти (`step_us` 2.35-3.7 мкс), но
~0.9 мс на 6 ти (`step_us` 6.99-7.15 мкс, ≈3×) — почти весь фиксированный резерв
`SHIELD_RESERVE_MS=1.0`, не оставляя времени на вторую попытку, если первый вариант побега не
подошёл.

**Исправление** (`planner.rs`): резерв теперь `SHIELD_RESERVE_MS_PER_TEE * world.all_tees().len()`
(константа `0.5` мс/ти подобрана так, чтобы при 2 ти — самом частом случае, self+один враг без
сторонних — формула давала РОВНО старую константу раунда 2, `0.5 * 2 = 1.0`, и линейно росла
дальше: `0.5 * 6 = 3.0` мс на 6 ти, ≈та же кратность, что и рост цены тика). Предельный колпак
D-042 (`SHIELD_DANGER_MAX_TOTAL_MS=15`) не тронут — общая работа по-прежнему ограничена.

**Порядок побегов внутри `escape_exists` (опциональная часть F18) — попробовано и ОТКАЧено
измерением:** ревью разрешило («you may») перебирать `escapes()` в порядке ожидаемой стоимости
ВНУТРИ `escape_exists` (не в `safer_input`, где порядок должен остаться TS-овским — первый
подошедший вариант там и есть результат). Гипотеза: побег через хук (самый решительный вариант,
`escapes()` кладёт его последним) чаще всего и есть тот, что срабатывает, так что перебор в
ОБРАТНОМ порядке должен сокращать среднее число полных роллаутов до ответа. Измерено
(`phase_breakdown`, budget=4мс, n=1000): на «весь Copy Love Box» действительно помогло, но на
**E-000 левом холле — специально построенном ревью раунда 2 сценарии максимального стресса щита —
СТАЛО ХУЖЕ**: `hall=true, 2 ти` `shield_incomplete` 12→30/1000, максимум шагов щита 1170→809, но
именно потому что хук-варианты в тесном коридоре чаще проваливаются только ПОСЛЕ полного
`SETTLE_TICKS` (не садятся на землю), тогда как обычный тормозной вариант (который TS пробует
первым) обычно решается быстро в любую сторону. Раз сценарий, которому стало хуже — это тот самый,
что ревью раунда 2 построило специально для стресса щита, обратный порядок **не применён** —
`escapes()` внутри `escape_exists` остаётся в исходном (TS) порядке, как и в `safer_input`.

**До/после, `shield_incomplete`** (budget=4мс, n=1000/условие, только масштабирование резерва, без
переупорядочивания; 2 прогона после фикса, машина разделена с другими агентами — см. «риски» у

## Адаптеры `Brain` (задача 8.1, `brains.rs`)

`ScriptedBrain`, `PlannerBrain` и `IdleBrain` (из `ddai-brain`) — то, чем арена `ddai-env` играет за игроков.

- Оба мозга **копируют** точный мир из `WorldView` в свой планировочный `PhysicsWorld` (`PhysicsWorld::sync_from`:
  `World::restore_from` без аллокаций + учёт присутствия и удерживаемых вводов) и мир вызывающего не трогают
  (тест `planner_brain_never_modifies_the_callers_world`). Без вида (`decide(obs)`, реплей) планировочный мир
  собирается из `Observation`, как `syncPlanningWorld` из снапшота.
- **`ScriptedBrain`**: `scriptedAction` как есть; RNG `Rng((seed * 7919 + 17) >>> 0)` из `ResetContext.seed` (как
  `ScriptedController` харнесса) — игра воспроизводится по сиду. Тест `scripted_brain_equals_scripted_action_on_the_same_world`.
- **`PlannerBrain`**: пресеты `normal`/`low`/`strong` (`preset_normal`/`preset_low_cpu`/`preset_strong_wb`), режимы
  `Fixed` (`Planner::decide`, детерминирован, TS-паритетный путь) и `Deadline { budget_ms }` (`decide_production`) с часами
  `Wall` или детерминированными `Step` (для тестов). `set_search_seed(ctx.seed)`. Ввод соперника — по
  **видимому** состоянию (`enemy_input_from_tee` = `enemyInputFromSnapshot`: направление, «хук выпущен», прицел), так что
  результат арены отражает то, что может знать живой бот. Лаг: мир прокручивается вперёд на `lag_ticks` шагов вводами
  `in_flight` (`syncPlanningWorld`). В 1vN замороженные соседи в 160 px передаются как `frozen bystanders`.
  `telemetry()` — накопительные счётчики (решения, поиск, выход по времени, щит, кандидаты).
- **Не перенесено** из `livePlan`/`bot.ts`: путевая цель `pathGoal`/`findRoute` (граф маршрутов придёт с `ddai-nav`) —
  в арене `travel_goal` не задаётся; на `pit`/`platform` при дальнем спавне это единственное отличие от харнесса E-000.

## `physics_adapter` — известные упрощения (НЕ параметр паритета, см. его doc-comment)

Бэкенд `ddai_physics::World<f32>` уже побитово точен с сервером DDNet (задача 1.6) — паритет
здесь не цель, цель — «достаточно правильно и быстро» для дообучения мухи и боевого режима:

- **Мёртвый ти остаётся видимым.** `ddai_physics::world::die()` полностью убирает `core` из
  `WorldCore`/`entity_order`, так что наивный `get_tee` после смерти вернул бы `None` — как будто
  ти исчез из мира, а не умер (в реальном DDNet и в `SimWorld` мёртвый ти виден с `alive:false`
  до респауна). Ревью раунд 1, F2: адаптер теперь кеширует последнее живое состояние
  (`last_known`) и отдаёт его с `alive:false`, если ядра больше нет — `scoreTick`'s `Death`-бонус
  срабатывает вместо симметричного, но неверного «противник исчез ⇒ −1000 каждый тик».
- **`remove_tee` действительно убирает персонажа из симуляции**, не только из своей книги
  учёта (`present`) — раньше «ушедший» ти оставался «призраком» в `WorldCore`/`entity_order` и
  продолжал тикаться каждый кадр `World::step()`, ломая `thawScratch`'у одиночную симуляцию
  (F3). `apply_tee_state` на отсутствующее ядро теперь возрождает персонажа
  (`spawn_character`) вместо тихого no-op'а — иначе после первой смерти любой `noThaw`-роллаут
  в кеш-мире был обречён навсегда решать «поймали».
- `step()` восстанавливает `WorldEvent::HammerHit`/`HammerFire` **выводом из наблюдаемого состояния**: у
  `World<f32>` нет списка событий (как у `SimWorld::step()`). Удар молотом виден по смене
  `attack_tick` (пишет только `fire_weapon`); попадание/промах — по `reload_timer` между
  `hammer_fire_delay_ms` (промах) и `hammer_hit_fire_delay_ms` (попадание); жертвы — по геометрии самого
  `fire_hammer`: все ти в радиусе 14 + 28 px от точки в `proximity * 0.75` впереди бьющего вдоль прицела, по
  позициям **до** шага (удар разрешается до тиков персонажей).
  **Исправлено в 8.1** (первая же проверка на настоящих ударах): раньше удар определялся условием
  `attack_tick == world.tick` уже после шага, а свежее нажатие обрабатывается **до** инкремента тика — так что
  выводились почти только удары из ветки «кнопка зажата, перезарядка кончилась»; жертву искали по позициям
  **после** шага (отброшенный ти уже дальше 42 px) и брали только ближайшего. Тест `tests/brains.rs` (попадание с
  отбросом, промах, стрельба из пистолета не считается ударом, два ти одним ударом) на старом коде падает.
  Последствие для прежних замеров: production-планировщик (`decide_production`, режим арены) до этого не видел
  большинства своих ударов ни как попадание, ни как штраф `wasted_hammer` — числа 3.2 (50 игр) сняты со старой
  моделью. TS-паритетный путь (`ts_adapter`) не затронут. Предложение на будущее — настоящий хук событий в
  `World::step` (см. отчёт 8.1): тогда вывод не нужен вовсе.
- `set_held_input` ведёт себя как `set_input` (не заводит отдельно `prevInput`/
  `latestPrevInput` для детекции фронта смены оружия) — не влияет на то, что реально читает
  ported-планировщик (только уровни direction/jump/hook/aim).
- **Фриз/анфриз читаются и с игрового, и с переднего слоя** (`front_tile(...) == TILE_FREEZE`),
  как в настоящем DDNet-сервере (`handle_tiles`) — TS-паритетный путь (`ts_adapter`) специально
  оставлен игровым-слоем-только (это осознанная особенность самого TS, F9), но production-бэкенд
  обязан видеть фриз там, где он реально есть (на BlmapChill — 161 передний фриз-тайл).
- `intersect_line` использует `Collision::intersect_line` — точный аналог TS `intersectLine`
  (ревью раунд 1, F7 — раньше здесь по ошибке стоял `intersect_no_laser`, лазерный примитив без
  буквального аналога). `intersect_line_hook` не менялся — `intersect_line_tele_hook(...,
  false)` уже был правильным аналогом TS `intersectLineHook`'а собственной tele-семантики.

### Как принимается решение

```text
setup      соперники в радиусе (1vN), флаги опасности, поля BFS, снимок решения для рабочих
пул        тёплый план -> предложения мухи -> книга -> броски -> техники   (порядок зависит от опасности)
стадия 1   все кандидаты при дешёвой модели (все соперники «держат ввод»)              [бюджет × (1 − f)]
CEM        выборки, уточнение по элите (как у планировщика; книга/предложения/броски идут в элиту итерации 0)
стадия 2   лучшие M заново при каждой комбинации ответов (hold/react)                     [бюджет × f]
расширение только если опасность и выбранный план всё ещё заканчивается нашим выбыванием (≤ 15 мс, D-042)
щит        escapeExists/saferInput со всеми соперниками, с их смоделированными вводами
```

Кандидат — план в кодировке планировщика (`docs/research/orig-plan.md` §1.1). Каждый оценивается тем же `evaluate`/`scoreTick`,
предложения и техники — **только кандидаты**, решает поиск; щит выполняется всегда. Кандидаты дедуплицируются (подпись
ходов + прицел с точностью 1/50 рад). Хвост-план после решения сохраняется как тёплый старт (абсолютные прицелы техник
переводятся в относительные — их усредняет `refit`).

### Модель угроз 1vN

* **Кто угроза.** Каждый свободный (жив, не заморожен) соперник в радиусе от нас, кроме жертвы (жертва — цель наступательных
  слагаемых `scoreTick`, но моделируется как угроза). Радиус по умолчанию `380 + (2·2 + лаг)·15 = 440 px`: длина хука плюс
  путь, который тушка проходит сама за два решения (15 px/тик — потолок `hook_drag_speed` на ось; решение каждые 2 тика).
  Настраивается (`threat_radius_px`). Замороженный сосед ≤ 160 px — «замороженный сторонний» планировщика, как в `PlannerBrain`.
* **Модели ответа** соперника: `hold` (ввод из его видимого состояния, `enemyInputFromSnapshot`) и `react` (`scriptedAction`,
  целится в нас); третья, «выученная», — расширение (место в комбинациях есть). Комбинации строятся только по тем, кто
  может действовать (свободная жертва в радиусе, затем ближайшие угрозы, ≤ 3): 1–2 таких — все подмножества (2 или 4),
  3 и больше — четыре (все держат / все реагируют / по одному из двух главных).
* **Защита по всем.** К `scoreTick(жертва)` добавляются слагаемые `threat_terms` для каждой другой угрозы: нас держит её хук,
  протяжка к ней через опасность (`drag_exposure`), запуск её молотом (`launch_exposure`, точный вариант близко). Самозамерзание
  и близость опасности — общие. Хук по чужой угрозе (не жертве) разрешается воротами хука.
* **Робастный выбор** (два этапа): стадия 1 — все кандидаты при дешёвой модели; стадия 2 — лучшие `top_m` (+ лучший «без
  разворота») при каждой комбинации; выбор по `λ·худший + (1−λ)·ожидание`, λ = 0,5 (документированная смесь; чистый max-min
  играет слишком осторожно против бота, который всегда атакует). **Ожидание взвешено вероятностью ответа** (`ReactBelief`):
  на каждом решении для каждого смоделированного соперника предсказывается «держит ввод» и «ответ скриптового бота», а
  через решение сравнивается с его видимым вводом (направление, хук); расхождение предсказаний — свидетельство, доверие
  плавает в [0,05; 0,95], а вес худшего случая умножается на `min(1, 2·среднее доверие)`: соперник, который стоит, не
  заставляет играть в страхе (T5: 36% → 72%, T10: 94% → 100%). Стадия 2 пропускается, если способных действовать
  соперников больше `max_relevant` (2): в 1v3/1v5 на 4 мс есть 6–9 кандидатов, и пересчёт съедал треть (измерено в E-003:
  без пропуска в 1v5 больше поражений). Выбирают только кандидаты с полным набором комбинаций (иначе смещение
  вверх); ничья — по индексу кандидата. Гистерезис `flipMargin` как в `decide_once`. Щит получает вводы **худшей** комбинации
  выбранного плана.
* **Флаги опасности** (D-042, явные, попадают в телеметрию): ≥ 2 соперников в радиусе, фриз ближе 3 тайлов (`EDGE_GAP_PX`), нас
  держит хук; плюс проба: тёплый план (или стойка) при «все реагируют» заканчивается нашим выбыванием — тогда защитные
  техники идут первыми и получают весь первый кусок стадии 1.
* **1v1-модель** (`threat_model = false`): моделируется только жертва, остальные держат ввод, слагаемые защиты и флаги по
  соперникам отключены — контроль для критерия «1vN лучше 1v1-модели».

### Дедлайн и адаптивный бюджет

`Deadline { budget_ms }`: итеративное углубление (пул → CEM), тёплый старт, лучший найденный, дедлайн внутри роллаута раз за шаг
плана, часы — внедряемые (`Clock`); фиксированный режим часов **не читает** (тест с паникующими часами). Бюджет поиска (по
умолчанию 4 мс) считается с конца предложений мухи (её ≈ 1 мс отдельно) и покрывает генерацию кандидатов. **Потолок решения без
расширения** (`decision_cap_ms` = 5 мс, по просьбе владельца «≤ 5 мс работы, жёсткий p99»): бюджет поиска =
`min(budget_ms, потолок − резерв щита)`, но не меньше 1 мс; резерв щита = `shield_reserve_ms_per_tee` (0,25 мс) × число ти в
мире. При 2 и 4 ти бюджет остаётся 4 мс, при 6 ти — 3,5 мс. Щит ограничен тем же резервом и, только при подтверждённой
опасности, — общим потолком расширения (15 мс). Если щит не уложился в резерв без опасности, решение помечается
`shield_incomplete` (доля — в таблице E-003). **Расширение** (`adaptive`, до
`max_total_ms` = 15 мс): флаги опасности **и** выбранный план заканчивается нашим выбыванием при каком-то ответе; тогда добираются
нерассмотренные кандидаты (защитные первыми) и CEM, пока план не станет безопасным или не выйдет время. Правило и его срабатывание
в телеметрии (`extended`, `danger`), доля решений — `totals.extended / totals.decisions`.

**Часы работы** (`work_clock_us_per_tick`, `clock = "work"` в арене, `hybrid::work`): дедлайн считается не по стенному времени, а
по числу смоделированных «ти-тиков» (тик физики одного ти; тик стоит тем дороже, чем больше ти в мире; луч якоря — два) ×
2,2 мкс (столько стоит ти-тик роллаута с оценкой на свободном ядре при 2, 4 и 6 ти), то есть «4 мс» — ≈ 1 800 ти-тиков:
900 тиков при 2 ти, 450 при 4, 300 при 6 — столько же, сколько даёт стенное время на свободной машине. На этой VM с паузами
хоста и соседними задачами (load average 10–27) стенный дедлайн даёт другой, более слабый поиск при каждом прогоне; на часах
работы режим дедлайна **воспроизводим побайтно** и не зависит от нагрузки и числа потоков арены (тест
`the_work_clock_makes_deadline_mode_reproducible_and_load_independent`; CLI: партии на 2 и 6 потоках — одинаковые хэши решений).
Только `workers = 1`. Стенные часы остаются для живой игры.

### Параллельные прогоны

`workers = N` — потоков оценки, включая вызывающий (`1` — потоки не создаются). Постоянный пул (`engine`): у каждого рабочего свой
`PhysicsWorld` и `Planner` только для `evaluate_impl`; снимок решения копируется `World::restore_from` (буферы переиспользуются),
кандидаты берутся с атомарного счётчика, результат кладётся в слот своей задачи, слияние по индексу кандидата. Оценка кандидата —
чистая функция снимка и плана (`deterministic_thaw`: кэш `noThaw` на оценку, сцена восстанавливается из снимка), поэтому в режиме
фиксированной работы решение **одинаково при N = 1, 2, 4** (тест `fixed_mode_decisions_are_identical_for_1_2_and_4_workers`,
24 решения 1v3). Без аллокаций (`tests/hybrid_alloc.rs`, счётчик `allocation_counter`): оценка кандидатов на рабочем мире — **0
аллокаций** в установившемся режиме; всё решение целиком не выделяет буфер размером с мир (пик живой памяти решения < 90 КБ против
~105 КБ мира), а мелкие векторы главного потока (списки кандидатов, книга, техники, телеметрия) — ≈ 260 аллокаций на решение
(измерено, не ноль). Найдено и исправлено попутно: `clone_from` у `World` строил новую копию мира на каждое `restore_state`
(3 аллокации на кандидата); теперь `World::restore_from`; щит выделял два снимка на вызов — теперь `ShieldBuffers`.

## Задача 8.2: учитель и мягкие цели

Аддитивный API для разметки, вне пути паритета (паритет 0 расхождений не менялся):

- `elite::EliteFirstStep` / `summarize_first_step` — частоты первого шага элиты последней итерации CEM: `left/stop/right`,
  `jump/hook/fire` (сырые доли, не сглаженные `0,1 + 0,8·f` из `refit`), круговое среднее и круговой разброс абсолютного
  прицела (в экранной конвенции планировщика). В `planner.rs` — одно поле `Planner::last_elite`, обнуляется в начале
  `decide_once` и заполняется рядом с `refit`; поиск его не читает. Для `decide_production` не заполняется.
- `teacher::TeacherPlanner` — фиксированные итерации, метка = действие + мягкая цель. Внутри — обёрнутый `PlannerBrain` в режиме `Fixed`,
  метка получается через его `decide_in` (мир, прокрутка по летящим входам, пощажённые — тот же код, планировщик в `Box`, как у
  `PlannerBrain`: 2 МБ стека потоков rayon), поэтому на одном состоянии и сиде решения равны по построению (тест). Для этого у
  `PlannerBrain` добавлены три `pub(crate)` метода доступа (`planner_mut`, `prev_input`, `set_prev_input`). Отличие для DAgger:
  `note_executed` подставляет в `prev` действие, которое **реально сыграно** (если играет ученик), иначе гистерезис поворота и логика
  хука читали бы «своё» прошлое действие.

## `Brain::set_live_context` (задача 4.1)

`PlannerBrain` реализует необязательный хук `ddai_brain::Brain::set_live_context(&LiveContext)`: живой бот передаёт
«пощажённых» (друзья, игнор, вне игры, AFK — `setSpareBystanders`) и путевую точку (`setTravelGoal`) перед каждым
`decide_in`. Арена этот метод не вызывает. `setThirdTees` не передаётся: живая конфигурация держит `thirdTeeExposure = 0`.
