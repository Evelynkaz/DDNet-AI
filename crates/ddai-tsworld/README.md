# ddai-tsworld

Задача 1.9. Буквальный, побитово точный (`f64` + `ddai-jsmath`) Rust-порт старого TS-мира
(`src/core/{vmath,tuning,types,collision,characterCore,projectile,world}.ts` +
`src/map/loadMap.ts`) старого бота `Wranked1/DDNet-AI` (GPL-3.0).

## Зачем это, если есть `ddai-physics` (решение D-035)

Это **не** рабочая физика бота. `ddai-physics` — побитово точная с C++-сервером DDNet, и в неё
эта задача НЕ добавляет ничего. `ddai-tsworld` существует только для одной цели: будущий
Rust-порт старого планировщика (`src/plan/*.ts`, фаза 3) должен доказуемо принимать **ровно те
же решения**, что и TS-планировщик, — а TS-планировщик считался на физике `SimWorld`, со всеми
её причудами V8 и TS-специфичными багами. Заносить эти причуды флагами в `ddai-physics::World` —
значит усложнять и рисковать главным кодом ради тестового паритета. Поэтому — отдельный,
одноразовый крейт: `crates/ddai-jsmath` (V8-точная математика, задача 3.1a) снизу, `ddai-tsworld`
сверху, оба не участвуют в игре бота. Подробности — `docs/DECISIONS.md` D-035, D-003, D-018,
D-020.

## Как читать этот крейт

Каждая функция — построчный порт TS-функции; doc-comment у неё цитирует `file:line` оригинала.
Вся числовая семантика JS идёт через `ddai_jsmath` (round/trunc/max/min/hypot/sin/cos/atan2/pow/
`|0`/`>>>0`) — **никогда** `f64::powf`/`f64::round` напрямую (см. `ddai-jsmath`'s README про
constant-folding `pow` с литеральным основанием — здесь это неактуально: `ddai_jsmath::pow` уже
защищён `black_box` внутри себя, так что этот крейт просит его вызывать «как обычно», без
собственных дополнительных мер).

**Отличие от TS не в математике, а в форме объектного графа.** В TS `CharacterCore`/
`Projectile`/`Laser` держат живую ссылку на свой `SimWorld` (`this.world`) и зовут её методы
(`allCores()`, `coreById()`, ...). Без `unsafe` (запрещён `CLAUDE.md`) и без `Rc<RefCell<_>>`
(проект их избегает) это не выразить полем структуры в Rust. Поэтому методы, которым это ДЕЙСТВИТЕЛЬНО
нужно (`tick`, `tickDeferred`, `move`, `setHookedPlayer`), перенесены в `SimWorld`
(`src/world.rs`) как методы, работающие по индексу тела в общем хранилище — см. doc-comment
`character_core.rs` и `world.rs`. Числа и порядок вычислений при этом не меняются ни на йоту;
поменялось только *где живёт код*, который их вычисляет.

## Известные причуды TS, воспроизведённые буквально (не исправленные)

Список — с `file:line`, откуда взято, и где именно в этом крейте это стоит:

1. **`order` — `unshift`, не `push`.** `addTee`/`respawnTee` кладут запись В НАЧАЛО массива
   (`world.ts:231`, `:717-718`). Каждый физический/оружейный цикл `step()` идёт по `order` в
   этом порядке («новые/только что респаунувшиеся — первые»). `byId` — ОТДЕЛЬНЫЙ массив,
   пересортировываемый целиком при каждом `addTee` (`world.ts:233`); `CharacterCore.tick`/
   `tickDeferred`/`move`'s «все остальные тела» — это `allCores()` (`world.ts:509-513`), то есть
   `byId`, НЕ `order`. `crates/.../src/world.rs`'s `TeeStorage`.
2. **`const order = this.order;` в `step()` — ссылка на ЖИВОЙ массив, взятая ПОСЛЕ цикла
   респаунов** (`world.ts:940`, после `world.ts:942-946`), а не снимок «на начало тика». Респаун
   этого же тика (`respawnTee`'s `unshift`) уже отражён в `order`, по которому идут все
   последующие циклы этого `step()`. **Реальный найденный баг порта (не TS-причуда сама по
   себе, но тонкость, которую легко упустить при переносе «ссылка → значение»):** первая версия
   этого порта клонировала `self.tees.order` ДО цикла респаунов — поймано настоящим
   расхождением трассы (`freeze`, эпизод с респауном и мгновенным захватом хука на том же тике,
   see «Найденные и исправленные баги порта» ниже). Исправлено: клон — после цикла респаунов.
3. **Повторный `addTee` с уже занятым id не убирает старую запись.** `this.tees.set(id, rec)` —
   `Map`, перезаписывает ТОЛЬКО связку id→запись; старая запись остаётся в `order`/`byId`
   осиротевшей — тикает, недостижима по id (`world.ts:224-234`). `TeeStorage::add_tee` никогда
   не выкидывает старый слот при добавлении, только `remove_tee` выкидывает ВСЕ записи с этим id
   (включая осиротевшие) — `world.ts:236-240`.
4. **`applyTeeState`/`restoreState` не трогают одни и те же поля.** `applyTeeState`
   (`world.ts:353-398`) НЕ трогает `queuedWeapon`, `weapons`, `teleCheckpoint`, `frozenLastTick` —
   `restoreState` трогает всё. См. `docs/research/orig-plan.md` §2.5.
5. **`coreById` фильтрует по `alive`, и это ломает `setHookedPlayer`'s очистку для мёртвых
   целей.** `coreById(id)` = `rec && rec.alive ? rec.core : undefined` (`world.ts:515-518`).
   `setHookedPlayer` (`characterCore.ts:436-448`) ищет предыдущую/новую цель именно через
   `coreById` — если тело, которое я хуком держал, УМЕРЛО, `coreById` не находит его, и
   `prev.attachedPlayers.delete(this.id)` просто не выполняется: `attachedPlayers` мёртвого тела
   хранит «память» о хуке до его возможного респауна (`core.reset()` очищает `attachedPlayers`).
   **Реальный найденный баг порта:** первая версия `set_hooked_player` искала предыдущую/новую
   цель через `self.tees.get_mut(id)` (без фильтра по `alive`) — поймано настоящим расхождением
   трассы (`freeze`, тело умерло с хуком на себе, затем хукающий отпустил хук).
6. **Три РАЗНЫХ, не унифицированных способа адресации тайла по пикселю** —
   [`collision::Collision::index_at`] (округление к ближнему + арифметический сдвиг `>>5`, то
   есть floor для отрицательных), `get_map_index`/`get_map_indices` (двойной `Math.trunc`, то
   есть truncate-к-нулю), `tele_at` (`roundToInt` + `Math.trunc`). Расходятся только для
   отрицательных/граничных пиксельных координат — инертно для любой карты этого корпуса
   (внешнее кольцо всегда solid). См. `collision.rs`'s doc comment.
7. **Тюнинг — `Math.trunc(v*100)/100` в `f64` при загрузке модуля**, не серверное `f32`-значение
   (`tuning.ts:5-7`).
8. **`pendingCoreInput`/`frozenInput` — мёртвое/чисто-тиковое поле**, не перенесены (см.
   `world.rs`'s doc comment на `TeeRecord` — `pendingCoreInput` проверено `grep -rn
   pendingCoreInput src/`: только записи, ноль чтений во всём `src/`).
9. **`allTees()` — не порядок `Map`.** См. таблицу выше; единственный вызывающий (`seal.ts:84`)
   не зависит от порядка.

## Найденные и исправленные баги порта (не TS-причуды — ошибки при переносе)

Реальный прогон трасс поймал 4 бага (все — расхождения между этим портом и TS, не сами TS-причуды);
ещё 2 нашлись при повторном построчном саморевью после того, как прогон стал зелёным (не через
mismatch, но того же рода — ошибки переноса, не TS-причуды):

1. **`CharacterCore.moveRestrictions` перепутан с `TeeRecord.moveRestrictions`** в
   `tickDeferred`'s хук-драге (`characterCore.ts:335,340` зовут `other.moveRestrictions`/
   `this.moveRestrictions`, где `other`/`this` — `CharacterCore`, не `TeeRecord` — это ДВА разных
   поля с одним именем, `characterCore.ts:71` и `world.ts:127`). Поймано трассой на `front`.
2. **Выбор цели хука** (`characterCore.ts:245-250`, `this.hookedPlayer === -1 || d < bestDistance`,
   `this.setHookedPlayer(other.id)` — мутация ВНУТРИ цикла сканирования, на каждой подходящей
   кандидатуре, не только на финальной). Раунд 1 ревью поймал трассой на `arena` (4 тела) первую,
   грубую версию: та откладывала мутацию `hooked_player` до конца цикла (собирала «лучшего
   кандидата», затем один раз звала `set_hooked_player` после цикла) и при этом сравнивала
   расстояния с немутировавшимся `core.hooked_player`, из-за чего побеждала ПОСЛЕДНЯЯ подходящая
   цель по `byId`, а не БЛИЖАЙШАЯ. **Это было исправлено, но неполно** — раунд 2 ревью (finding
   F3) нашёл, что тот самый «отложенный до конца цикла» фикс всё ещё расходился с TS в двух
   отдельных отношениях, которые «победитель — ближайший» тест не ловит: (a) если `hookedPlayer`
   уже был не `-1` ДО начала этого скана (недостижимо через обычную игру, но достижимо через
   `applyTeeState` с намеренно несогласованными `hookState`/`hookedPlayer`) — TS в этом тике вообще
   никого не захватывает (условие «первое свободное принятие» `d < bestDistance(0)` не может
   выполниться ни для одного настоящего `d >= 0`), а версия с отложенной мутацией всё равно хватала
   первого подходящего кандидата, потому что своё локальное «еще не нашли» она отслеживала через
   `best_distance`, а не через изначальное значение `hooked_player`; (b) TS зовёт полный
   attach/detach `setHookedPlayer` (`characterCore.ts:436-448`) на КАЖДОЙ принятой по ходу скана
   кандидатуре, не только на финальной — если кандидат A принят, а затем более близкий B его
   вытесняет, TS успевает и прицепить A, и снять его снова при переходе на B, так что `A`'s
   `attachedPlayers` корректно освобождается; версия с однократной мутацией после цикла звала
   `set_hooked_player` ровно один раз (на финальном победителе), пропуская промежуточные
   attach/detach. Исправлено полным переписыванием `core_tick_hook_flying`: `set_hooked_player`
   зовётся ВНУТРИ цикла, читает `hooked_player` живым на каждой итерации — буквально как в TS, без
   «сначала найти лучшего, потом мутировать» разделения. Регрессия закреплена TS-golden фикстурой
   `tests/fixtures/regression_f3_flying_with_hooked_player_never_grabs.jsonl` (случай (a) —
   `tests/parity_regressions.rs::regression_f3_flying_with_hooked_player_never_grabs`).
3. **`setHookedPlayer`'s очистка через живой, а не alive-фильтрованный поиск** — см. причуду 5
   выше.
4. **Клонирование `order` до цикла респаунов, а не после** — см. причуду 2 выше.
5. **`applyTeeState`'s `angle` лишний раз пропускался через `Math.trunc`** — TS делает простое
   присваивание `c.angle = st.angle;` (`world.ts:380-381`), без округления. На практике инертно
   (`st.angle` всегда уже целое — единственное место, где TS его ВЫЧИСЛЯЕТ, `core.tick()`, само
   всегда пишет `Math.trunc(...)`), но лишняя операция, которой в TS нет, — не то, что должен
   делать буквальный порт. Исправлено на прямое приведение типа.
6. **`reset()` обходил сырое хранилище слотов, а не текущую карту id→запись** — TS обходит
   `this.tees.values()` (`world.ts:418`), то есть ТЕКУЩУЮ карту id→запись (при повторном `addTee`
   с занятым id — только новую запись, старая осиротевшая недостижима через `Map`, см. причуду 3).
   Первая версия обходила `self.tees.slots` целиком — для осиротевшей записи это означало
   `reset()` на записи, которую TS вообще не видит с этой стороны, и двойной `reset()` на текущей
   записи того же id. Инертно для итогового состояния (`reset()` полностью перезаписывает КАЖДОЕ
   поле, так что двойной вызов на той же записи не отличим от одинарного), но неверно по
   конструкции — не то, что делает TS. Найдено саморевью, не трассой (`reset()` не вызывается ни
   из `src/plan`, ни из `src/env` — только юнит-тестами этого крейта).

Первые 4 найдены и исправлены через реальные mismatch-и `ts-diff`/массового прогона, не через
инспекцию кода — см. «Как проверялось».

### Раунд 2 ревью: findings F1-F9, N1 (2026-09-28)

Независимый ревьюер (opus-reviewer), с собственным адверсариальным харнессом (генератор `adv/gen.mjs`
+ отдельный Rust-бинарник `advrs`, оба вне этого репозитория, линкующие `ddai-tsworld` по пути) и
собственным построчным чтением `world.rs`, нашёл 9 находок (F1-F9) и один nit (N1) сверх раунда 1.
Все исправлены на корне; для каждой, где применимо, добавлена TS-сгенерированная golden/opscript
фикстура (`tests/fixtures/regression_*.jsonl`, скрипт `tools/ts-trace/gen-regression.mjs`) и Rust-тест
(`tests/parity_regressions.rs`), реплеящий её и (независимо от реплея) проверяющий по самим записям
ЭТОГО TS-оракула, что фикстура действительно упирается в описанную причуду:

- **F1 — `events`/`order`/`byId` не сравнивались.** До этого раунда `trace_ts`'s `diff_sim_state`
  сравнивал только `state`; `events` записывались как «диагностика», `order`/`byId` не сравнивались
  вовсе. Это оставляло дыру ровно там, где живут причуды 2, 3 и осиротевшая-запись-причуда (F4) —
  расхождение в порядке/составе `order`/`byId` или в списке событий тика не показывалось ни в одном
  прогоне, даже когда `state` (после дедупликации по id) совпадал. Исправлено: `diff_events` +
  `diff_id_list` в `trace_ts.rs`, оба генератора (`gen-episode.mjs`/`gen-opscript.mjs`) теперь пишут
  `events`/`order`/`byId` на КАЖДОЙ строке (не только на "step"), включая ранее пропущенный путь
  двух начальных `addTee` в `gen-opscript.mjs`. `docs/formats.md` §16.1/§16.3 исправлены (раньше там
  ошибочно было написано «events — не часть паритетной цели»).
- **F2 — `kill()`'s событие смерти терялось.** `step()` по ошибке делал `events.clear()` сразу после
  забора `pending_events` — реальный `world.ts:939` (`this.pendingEvents.splice(0)`) ничего не чистит
  повторно, событие должно выжить до следующего `step()`. Исправлено удалением лишнего `clear()`.
  Фикстура: `regression_f2_kill_event_survives.jsonl`.
- **F3 — выбор цели хука, вторая (более глубокая) причина** — см. исправленный пункт 2 выше.
  Фикстура: `regression_f3_flying_with_hooked_player_never_grabs.jsonl`.
- **F4 — повторный `addTee` с занятым id: осиротевшая запись видна в `order`/`byId`, но тикалась
  неверно.** Причуда 3 (осиротевшая запись продолжает тикать) была реализована с id-based
  разрешением «себя» (`this`) во внутренних методах — `core_tick_hook_flying`/`core_tick_deferred`/
  `core_move`/`fire_weapon` и т.д. брали `self.tees.get(id)` (текущая по id запись), а не операцию
  на конкретном СЛОТЕ, который им передали. Для осиротевшей записи это тихо перенаправляло всю её
  физику на ТЕКУЩУЮ запись того же id — ровно противоположность того, что делает TS (`other === this`
  в TS — равенство ССЫЛОК на объект, `characterCore.ts:240,312`, а не совпадение `.id`). Исправлено
  большим скоординированным рефакторингом: внутренние методы принимают `slot: usize` для «себя»;
  `alive_slots_by_id_into` (было `alive_ids_by_id_into`) отдаёт СЛОТЫ, не дедуплицированные id — у
  осиротевшей записи есть свой слот, отдельный от текущей. Фикстура:
  `regression_f4_duplicate_addtee_orphan_still_ticks.jsonl` (id 1 дважды в `order`/`byId` после 20
  тиков, ровно один раз в `state.tees`).
- **F5 — респаун не снимал хук со старой цели.** `respawn_tee` вызывал `core.reset()` (который в TS,
  `characterCore.ts:100,110`, САМ первым делом зовёт `setHookedPlayer(-1)`), но порт не звал
  `self.set_hooked_player(slot, -1)` до `reset()`, так что цель, за которую держался респаунящийся,
  оставляла в своём `attachedPlayers` устаревшую запись навечно (до её собственного респауна/новой
  причуды F4). Исправлено добавлением явного `set_hooked_player(slot, -1)` перед `reset()`. Фикстура:
  `regression_f5_respawn_detaches_from_old_hook_target.jsonl`.
- **F6 — `getMapIndices` собирал индекс `0` на первом сэмпле пути.** Порт добавлял `i == 0.0 ||` к
  условию `last_index != index`, которого нет в TS (`collision.ts:468`: `lastIndex` инициализирован
  в `0`, так что первый сэмпл с РЕАЛЬНЫМ индексом `0` — не собирается, `0 !== 0` ложно). На карте с
  фриз-тайлом на индексе `0` порт ложно замораживал тело на первом же сэмпле пути. Исправлено
  удалением добавки. Юнит-тест (не через TS-оракул — коллизия чистая/детерминированная функция без
  побочек, не нуждается в TS-подтверждении сверх самого TS-кода коллизии, который уже процитирован
  file:line в fix'е): `collision.rs::get_map_indices_does_not_collect_index_zero_on_the_first_sample`.
- **F7 — `saveState(into)` не чистил устаревшие записи.** TS обходит ТЕКУЩИЕ id, обновляя/добавляя в
  `into.tees`, но никогда не удаляет запись для id, который был жив на момент ПРЕДЫДУЩЕГО
  `saveState(into)` в тот же `into`, но уже не жив сейчас (`world.ts:292-298`) — призрачная запись
  остаётся в `into` и может быть восстановлена на НОВОЕ тело с тем же id (`removeTee`+`addTee`).
  `save_state_into` уже был реализован верно (обновление на месте, без предварительной очистки) —
  находка F7 была в том, что это НЕ проверялось никаким тестом/трассой (ни `gen-opscript.mjs`, ни
  `trace_ts.rs`'s опскрипт-реплеер вообще не поддерживали операцию `saveInto`: реплеер падал с
  `unknown op "saveInto"`). Исправлено: `OpLine.slot` + обработчик `"saveInto"` в
  `replay_opscript_with_map_bytes`, и — для полноты покрытия случайного корпуса, не только
  фикстуры — сам `gen-opscript.mjs` теперь включает `saveInto` в взвешенный список операций (F8).
  Фикстура: `regression_f7_save_into_keeps_stale_entries.jsonl` (после `removeTee`+`addTee` того же
  id, `restoreState` возвращает СТАРУЮ, призрачную позицию, не позицию нового тела).
- **F8 — масштаб/покрытие корпуса.** Случайный генератор (`gen-opscript.mjs`) никогда не создавал
  повторный/переиспользованный id (только монотонно растущий `nextId`), никогда не гонял
  `noWeakHook`/`svHit:false`/`infiniteAmmo:false`/`respawnDelayTicks:0` (все флаги были захардкожены
  в «всё включено» на момент раунда 1), и не включал `reset`/`saveInto` в свой взвешенный список
  операций вовсе — то есть весь bulk-корпус до этого раунда проверял ОДНУ комбинацию опций и никогда
  не касался F4/F7's причуд иначе как через ручные фикстуры. Исправлено: оба генератора получили
  CLI-флаги `--respawn-delay`/`--infinite-ammo`/`--sv-hit`/`--all-weapons`/`--no-weak-hook`;
  `gen-opscript.mjs`'s `OPS` получил `reset`/`saveInto`; `addTee` с вероятностью 1/5 переиспользует
  ранее использованный id; `tools/ts-trace/run-corpus.sh` переписан на потоковый
  генерация→diff-одного-файла→удаление и варьирует три production-реалистичные комбинации опций по
  всем картам/скриптам (см. §16.6 build report'а задачи за итоговыми числами). При скейлинге найден
  и отдельный, не-Rust баг — см. следующий пункт.
- **Баг генератора, найденный при скейлинге F8 (не в Rust-порте).** `gen-opscript.mjs`'s
  `"restoreState"` со случаем «нет сохранённых состояний» откатывался на настоящий `world.step()`,
  но ВЫБРАСЫВАЛ его возвращаемое значение, записывая `events: []`, даже если в этот тик реально
  случилось событие (например, смерть от ранее отложенного `kill()`) — ложный «mismatch» против
  Rust, который на том же (корректно помеченном) `"step"`-опе честно вычислял то же самое реальное
  событие. Подтверждено прямым запуском той же последовательности операций напрямую через
  `SimWorld` вне генератора. Исправлено: этот путь теперь пишет `record.events` так же, как основной
  `"step"`-кейс.
- **F9 — лишние аллокации на хот-пасе.** `fire_weapon`'s удар молотом клонировал `self.tees.order`
  на каждый удар (не переиспользуемый `Vec`); `step()` тоже клонировал `order` на каждый тик.
  Исправлено: оба используют `scratch_order` (переиспользуемый скретч-буфер на `SimWorld`),
  выделяемый один раз. См. также обновлённый раздел «Аллокации» ниже.
- **N1 — `tuning()` пересчитывался на каждый вызов.** `Tuning` — 40 полей `f64`, каждое через
  `js::trunc`; вызывался до `O(n²)` раз на тик из `core_tick_deferred`'s парного цикла. Значение
  детерминированное и не меняется в рантайме — исправлено кэшированием в `OnceLock` (`tuning.rs`).

### Раунд 3 ревью: findings F10, F11 (2026-09-28)

- **F10 — масштаб ≥1000×1000 достигнут только на синтетических картах.** AC 4a называет конкретные
  карты (arena, freeze, Copy Love Box, один настоящий block-map), а прогон раунда 2 давал настоящим
  картам только 40 эпизодов × 500 тиков — риск-механики (заморозка, смерти, респауны) там почти не
  встречались (BlmapChill: 2 смерти, 0 респаунов; Copy Love Box: 4 удара молотом суммарно).
  Исправлено: `run-corpus.sh`'s `REAL_EPISODES_PER_MAP`/`REAL_TICKS` дефолты подняты с 40/500 до
  1000/1000 (тот же масштаб, что у синтетических карт, теперь и по-карточно, не только в сумме);
  добавлен флаг `--real-only` (гоняет только настоящие карты на полном масштабе, без пересборки уже
  подтверждённых синтетических/opscript частей). Актуальные цифры — в «Паритет: результаты» ниже.
- **F11 — освобождённые слоты тел никогда не переиспользовались.** `TeeStorage::add_tee` всегда
  делал `push` в `slots`, `remove_tee` только отвязывал ссылки (`id_index`/`order`/`by_id`), сам
  `Vec<TeeRecord>` рос без границ на каждый add/remove-цикл. Измерено ревьюером: после 200k и 400k
  циклов add/remove на одном и том же id `clone()` шёл 1.9 мкс → 75 мс → 164 мс, до 365 МБ RSS —
  churn планировщика (`syncOthers`/`thawScratch`) бьёт по этому на долгой сессии. Исправлено:
  `TeeStorage` получил `free_slots: Vec<usize>` — `remove_tee` кладёт туда именно те слоты,
  которые реально вычистило из `order`/`by_id` (то же множество слотов с данным id, живых или
  осиротевших через F4 — TS фильтрует по значению `core.id`, а не по ссылке, так что дубликат-
  осиротевшая запись сметается вместе с текущей), `add_tee` сначала пробует `free_slots.pop()` и
  переиспользует индекс перед тем, как расти. Наблюдаемое TS-поведение не меняется: каждое внешнее
  чтение идёт через `id_index` или обходом `order`/`by_id` по id, а не по сырому индексу слота —
  какой физический слот `Vec`'а хранит данные тела, не часть паритетной цели. Дубликат-осиротевшая
  запись (F4) НЕ освобождается преждевременно — проверено отдельным тестом
  (`duplicate_orphan_slot_is_not_freed_until_remove_tee_sweeps_its_id`). Регрессия
  (`remove_tee_frees_the_slot_so_repeated_add_remove_cycles_stay_bounded`, `world.rs`): 400k
  add/remove циклов на одном id, `slots.len()` остаётся ровно `1` на каждой итерации, `clone()`
  после всех циклов — под 50 мс (щедрый порог, не тайминг-бенчмарк); falsifiability-проверено
  (временно откатил переиспользование слота — тест упал на первой же итерации: `left: 2, right: 1`
  — вернул фикс, тест снова зелёный). Существующие TS-паритетные фикстуры (золотые + регрессионные)
  и адверсариальный прогон ревьюера (`adv/batch.sh`, пересобран против исправленного крейта) не
  задеты — см. «Паритет: результаты».

## Аллокации

`step()` переиспользует скретч-буферы (`scratch_slots` — слоты живых тел по `byId`,
`scratch_tile_indices` — список индексов тайлов на пути тела, `scratch_other_snapshots` —
позиции/флаги других тел для развёртки столкновений в `move()`, `scratch_order` — копия
`self.tees.order` для `step()`'s собственного цикла и для `fire_weapon`'s удара молотом,
`scratch_targets` — цели `releaseHooked`); после стабилизации количества тел и длины пути ни одна
из них больше не аллоцирует. До review finding F9 (раунд 2) `step()` и `fire_weapon`'s hammer-удар
каждый клонировали `self.tees.order` заново (на тик и на удар молотом соответственно) вместо
переиспользования буфера — исправлено переводом обоих на `scratch_order`. Неизбежные аллокации:
`tick_entities()` временно забирает `projectiles_list`/`lasers_list` через `mem::take` и кладёт
назад — сама операция не аллоцирует, но `Vec::remove(i)` на маркированных-для-удаления элементах
сдвигает хвост (O(n) на удаление, не аллокация).

## Загрузка карт (`map_load.rs`)

Использует `ddai-map` (готовый, проверенный against C++ загрузчик реальный ридер `.map`), не
переписывает парсинг датафайла — см. `map_load.rs`'s doc comment. Тайлы/tele/speedup/front
переливаются из `ddai_map::LoadedMap` в аргументы `Collision::new` напрямую (без обращения к
типу `ddai_physics::map::MapData` по имени — крейт формально зависит только от `ddai-jsmath` и
`ddai-map`, как требует спека, хотя `ddai-map`'s `LoadedMap.data` физически имеет тип из
`ddai_physics::map`). `sv_no_weak_hook` парсится из `Settings`-строк, которые уже разбил на
NUL-строки `ddai-map` (`readMapSettings`, `loadMap.ts:81-106`) — известное расхождение: `ddai-map`
декодирует UTF-8 lossy, TS — `latin1`; совпадает байт-в-байт для ASCII (всё, что реально есть в
`sv_no_weak_hook <0|1>` и любой другой команде настроек в этом корпусе).

### Синтетические карты как настоящие `.map`-файлы

В отличие от `crates/ddai-trace`'s "rawmap v1" (свой формат для сверки Rust/C++), паритету с TS
нужен файл, который реальный `loadMap.ts` умеет открыть. Поэтому даже синтетические рецепты
(`arena`/`freeze`/`front`/`tele-speedup`, `ddai_trace::synthetic`) здесь пишутся как настоящий
DDNet datafile v4 (`examples/gen_fixture_maps.rs`, дев-only, `cargo run --example gen_fixture_maps
-- <out-dir>`) — тот же файл открывают TS (`loadMapCollision`) и Rust (`load_map_bytes`). Важная
деталь: front-слой НИКОГДА не кодируется tile-skip (`ddai-map` отклоняет эту комбинацию, как и
настоящий DDNet), поэтому game-слой — `item_version: 4` (RLE), front/tele/speedup —
`item_version: 3` (по клетке) в одном файле. См. `docs/formats.md` §16.4.

## `trace-ts v1` и генератор (`tools/ts-trace/`)

Полный формат — `docs/formats.md` §16 (новый раздел, по-русски). Коротко: JSON-lines, первая
строка — метаданные (версия, `mapPath`/`mapSha256`, seed, tees, node/v8, `tsCoreCommit` —
закреплённая константа `TS_CORE_COMMIT` в `tools/ts-trace/lib.mjs` — раньше `git log -1 --format=%H -- src/core src/map`; после переноса в `tools/ts-reference` (5.4) значение то же), далее — по строке на тик (`kind: "episode"`)
или на API-операцию (`kind: "opscript"`). Каждый `f64` — 16 hex-символов бит (`f64::to_bits`).
Генератор — `tools/ts-trace/gen-episode.mjs`/`gen-opscript.mjs`, запускает РЕАЛЬНЫЙ
`tools/ts-reference/src/core/world.ts`/`…/src/map/loadMap.ts` (до задачи 5.4 — `src/core/…`) через Node 24 type stripping (без копий).
Детерминизм: два запуска с одним seed → побайтово одинаковый файл (проверено вручную — `sha256sum`
двух прогонов `gen-episode.mjs` с одним seed совпадает).

Сравнение — `crates/ddai-tsworld/src/trace_ts.rs` (`replay_episode`/`replay_opscript` +
`diff_sim_state` — первое несовпадающее поле, бит-в-бит для `f64`) и бинарник `ts-diff`
(`ts-diff <trace.jsonl>` — один файл; `ts-diff --corpus <dir>` — весь корпус рекурсивно +
агрегированное покрытие).

`cargo test`; каждый тест дополнительно (не только через реплей) проверяет по самим записям
TS-оракула, что фикстура действительно упирается в описанную причуду (например, F3: `hookState`
у TS остаётся `HOOK_FLYING`, не `HOOK_GRABBED`). Отдельно, F11 (слоты тел) проверен не через
TS-оракул (чистая внутренняя структура данных, не TS-причуда) — юнит-тестами в `world.rs`, см.
«Раунд 3 ревью» выше.

## Производительность

`cargo bench -p ddai-tsworld --bench step` (Copy Love Box, 2 тела, ходьба+джамп+хук на 80-тиковый
цикл) — требует локальный незакоммиченный `~/aiddnet/data/maps/copy-love-box/...`, иначе бенч сам
себя пропускает с понятным сообщением, не проваливая `cargo bench`.

| | Rust (`criterion`, release, `lto=thin`) | Node 24.21.0 (тот же сценарий, `tools/ts-trace/bench-node.mjs`, 2M прогревочных + 2M замеряемых) |
|---|---|---|
| `step()`, 2 тела | ≈213 нс/вызов (≈4.7M/с) | ≈186 нс/вызов (≈5.4M/с) |
| `saveState`/`save_state` | ≈308 нс | ≈1216 нс |
| `restoreState`/`restore_state` | ≈93 нс | ≈655 нс |

**Честно:** `step()` в Rust НЕ быстрее V8 после прогрева на этом сценарии — вероятная причина:
дизайн этого крейта ищет тело по id через `HashMap` (`TeeStorage::get`/`get_mut`) на каждый
маленький подшаг (`core_tick`, `fire_weapon`, `handle_tile`, ...), тогда как TS просто держит
живую ссылку на объект. `save_state`/`restore_state` — Rust быстрее в 4-7 раз (без аллокаций
объектов/`Map`, которые каждый вызов делает в V8) — то, что важнее всего для бюджета планировщика
(частые сохранения/восстановления состояния при поиске по дереву решений). Оптимизация
`step()`'s id-lookup (кэшировать slot-индекс на всё время одного вызова вместо повторных
HashMap-поисков) — не сделана в этой задаче (не входит в критерии приёмки, задача явно говорит
«для оценки бюджета планировщика», не «быстрее TS быть обязано»), зафиксирована как открытый
риск/возможность для будущей задачи.

## Аллокации на не-hot-path операциях

`fire_weapon`'s удар молотом клонирует `order` (маленький `Vec<usize>`) — единственная
не-scratch-буферизуемая аллокация на удар (не на тик простого движения).
