# ddai-fly

Инференс-движок мухи (задача 7.1) плюс обратный проход и обучение (задача 7.2) плюс лучевой
кодировщик входа / декодер действий / голова «модели мира» / `FlyBrain` (задача 7.3): грузит
скомпилированный подграф коннектома (`.flyg` v1, крейт `ddai-flyg`) плюс обучаемые параметры,
гонит continuous-time rate-модель (`docs/FLY.md` §3.1, §4, в корне репозитория) вперёд в реальном
времени, обучает её вручную написанным truncated BPTT + Adam + батчами по `rayon` (7.2), и (7.3)
превращает игровое наблюдение (`ddai_brain::Observation`) в токи через реальные VPN/AN-нейроны и
частоты DN — обратно в действие (`ddai_brain::Action`), с полной дифференцируемостью
энкодер→муха→декодер+«модель мира» через один вызов `brain_train::brain_train_step`.

Задача 7.1 прошла один раунд ревью (см. «Что изменилось после ревью» ниже): исправлены прогрев,
целостность чекпоинтов, метрика «мухи не мёртвой» и производительность. Задача 7.2 (обратный
проход, обучение) описана в разделе «Обратный проход и обучение (задача 7.2)» ниже. Задача 7.3
(энкодер/декодер/модель мира/`FlyBrain`) — в разделе «Задача 7.3» в конце файла.

## Модель (FLY.md §4)

```
τ_T · dV_i/dt = −V_i + b_T + Σ_j w_ij · f(V_j) + e_i(t)
w_ij = σ_j · α_{T(i),T(j)} · N_ij / Z_i,   α = softplus(a) ≥ 0,   Z_i = max(1, N_i^in)^γ
f(V) = r_max · tanh(relu(V) / r_max)
```

Дискретизация — экспоненциальный Эйлер: `V ← V + (1 − e^{−Δ/τ_T})·(V_∞ − V)`, безусловно
устойчив. По умолчанию `Δ = 10 мс`, 4 подшага на решение (= 40 мс = игровой тик 25 Гц), `γ = 1.0`,
`r_max = 10`, `τ = Δ + softplus(θ)` клипуется на `τ_max = 1.0 с`. Знак `σ_j` и топология
(`N_ij`, пары типов) — фиксированы, из `.flyg`; обучаются `a` (на пару типов, точнее на
`shared_param_id` — см. `docs/formats.md` §8), `b`/`θ` (на тип).

## API

- `FlyConfig` — гиперпараметры (`Δ`, подшагов на решение, `γ`, `r_max`, `τ_max`, `warmup_cap_ms`,
  `warmup_epsilon`). `FlyConfig::default()` — значения выше.
- `FlyParams { a, b, theta }` — обучаемые параметры, `f32`. `FlyParams::init_default(flyg,
  config, seed)` — детерминированная инициализация (см. «Подбор инициализации» ниже);
  `init_default_with_alpha(.., alpha_init)` — то же с явным `α_init` (использовалось для подбора
  константы, см. таблицу ниже, и переиспользуется `tests/stability.rs`'s `alpha_sweep_experiment`
  для его воспроизведения). `validate_shape` проверяет длины против конкретного `.flyg` (иначе
  понятная ошибка вместо паники в `set_params`).
- `FlyModel::new(flyg, config, params)` — грузит граф + считает все производные массивы (веса
  `w_ij`, bias и decay на нейрон, `1/Z_i`, `u16`-копию `pre_index` — см. «Производительность»),
  один раз. `set_params` пересчитывает веса/bias/decay (`O(nnz + N)`), не трогая топологию;
  вызывать только при смене параметров, не на каждом шаге. `memory_footprint_bytes()`,
  `output_slot_for_neuron()` (индекс DN-нейрона → позиция в `DecisionOutput::dn_rates`, зацепка
  для декодера 7.3).
- `FlyState` — состояние (`V` на нейрон) + скретч-буферы, выделяются один раз в `FlyState::new`.
  `step_decision(model, inputs)` — горячий путь, **ноль аллокаций** (проверено
  `tests/no_alloc.rs` поточным счётным аллокатором; поддерживает инвариант `r_buf == f(v)` между вызовами,
  так что первый подшаг решения не пересчитывает `f(V)` заново — см. «Производительность»).
  `set_v(model, v)` — прямая установка `V` (обновляет и `r_buf`, поэтому требует `&FlyModel`).
  `warm_up(model) -> WarmUpReport` / `reset_to_rest(model)` — прогрев до сходимости и возврат к
  закэшированному покою (см. «Прогрев до сходимости» ниже).
- `DecisionOutput { dn_rates, per_type_mean_rate }` — заимствует буферы `state` (тот же
  жизненный цикл, что и заимствование `&mut state` в `step_decision`), поэтому нужно скопировать
  значения, если после вызова снова понадобится трогать `state` в этом же выражении (см. doc
  comment `step_decision`).
- `TrajectoryRecorder` — опциональный, заранее выделенный буфер `V`/`r` по подшагам
  (`step_decision_recording`) — зацепка для будущего backward (7.2); не используется горячим
  путём по умолчанию. Точное правило пары `(V, r)`: подшаг `k` хранит `(V после обновления k, r =
  f(V после обновления k−1))` — `r`, который **привёл** к этому `V`, не результат от него; финальный
  `r` решения нигде не хранится (пересчитывается из `v_at(последний_подшаг)` при необходимости) —
  см. doc comment `TrajectoryRecorder`.
- `checkpoint` — `postcard`+`zstd` (с включённой контрольной суммой содержимого) + отдельный
  sha256 payload'а, версия формата + `sha256` того `.flyg`, для которого собраны параметры
  (`load_checkpoint_for_flyg` явно проверяет совпадение и возвращает `FlygMismatch`, а не тихо
  индексирует чужими `shared_param_id`/`type_index`). Порченые/обрезанные файлы — `Err`, не
  паника; каждый из 2000 выборочных однобитовых флипов на реальном (S-масштаб, ~23 КБ,
  высокоэнтропийном) чекпоинте отклоняется (см. «Целостность чекпоинтов» ниже).

### Порядок входов/выходов

`inputs[k]` в `step_decision` — ток k-го входного нейрона в порядке возрастания плотного индекса
среди нейронов с ролью `InputVisual`/`InputAscending` (`FlyModel::input_neuron_indices()`).
`DecisionOutput::dn_rates` — тот же принцип для роли `Output` (`output_neuron_indices()`) —
**не** порядок `flyg().output_groups` (это отдельная, ролевая по действиям структура для будущего
декодера; `output_slot_for_neuron` переводит из одного в другое).

### Почему `step_decision` берёт `&FlyModel` явно

Буквальная сигнатура в спеке — `step_decision(&mut state, inputs)`. Здесь она —
`state.step_decision(&model, inputs)`: несколько независимых `FlyState` могут работать против
одного `FlyModel` (параллельные эпизоды на будущем ES/self-play), а `set_params` (`&mut
FlyModel`) не должен воевать с чужими заимствованиями. Замыкание модели внутри состояния
потребовало бы `Rc<RefCell<_>>` (аллокация + рантайм-проверка заимствования) без явной выгоды.

## Прогрев до сходимости (ревью, раунд 1, F1)

Первая версия `warm_up` гоняла фиксированные 400 мс и кэшировала результат как «покой» без
проверки, что состояние действительно устоялось. Ревьюер показал: на реальных графах с исходной
инициализацией (`α_init = 5.0`) `max|V − V*|` после 400 мс составлял ещё 11.1 (M) — то есть 60-с
прогон стабильности на 97% состоял из переходного процесса, а не установившейся активности.

Теперь `warm_up(model) -> WarmUpReport` гоняет решения с нулевым входом от `V = 0`, пока
`max|ΔV|` между двумя последовательными решениями не упадёт ниже `config.warmup_epsilon`
(по умолчанию `0.01`), с потолком `config.warmup_cap_ms` (по умолчанию 5000 мс) — и **явно
сообщает**, сошёлся ли прогрев (`#[must_use]`, так что вызывающий код не может тихо закэшировать
несошедшееся состояние как «покой»). `tests/stability.rs` и `ddnet-ai fly bench` печатают этот
отчёт и (для теста) падают, если сходимости не было.

муху от почти мёртвой, см. ниже), и (4) **проверяет левый/правый шаговый отклик** как основной
критерий «не мёртвая». Реальные числа при `α_init = 2.3`:

несвязанного шума». Левый/правый шаговый отклик — прямая проверка направленности, которую слабая
сеть не проходит (см. таблицу подбора `α_init`: при `α_init = 0.5` доля сдвинувшихся DN — только
11-12%, за порогом 15%, используемым в тесте).

## Целостность чекпоинтов (ревью, раунд 1, F2)

Первая версия не имела никакой проверки целостности за пределами «удалось ли decode»: фаззинг
ревьюера (400 однобитовых флипов реального чекпоинта) — 389 из 400 «успешно» загрузились с
незаметно другими параметрами. Формат на диске теперь: `[32 байта: sha256 postcard-байт]
++ [zstd-поток с включённой контрольной суммой содержимого (include_checksum(true))]`. Два
независимых уровня проверки (не один): zstd сам проверяет свою контрольную сумму при
распаковке; explicit sha256 над распакованными байтами проверяется в `load_checkpoint` до
попытки декодировать их как `Checkpoint`. `tests::every_sampled_bit_flip_on_a_high_entropy_payload_is_rejected`
воспроизводит методику ревьюера (S-масштаб: 5368 `a` + 432×2 `b`/`theta`, случайные
высокоэнтропийные значения — ~22.8 КБ, близко к «21,851 байт» у ревьюера) и требует, чтобы
**все** 2000 выборочных однобитовых флипа были отклонены — подтверждено.

## SIMD/perf (acceptance criterion 5)

Осталось на плоском скалярном коде (8 независимых аккумуляторов на строку CSR через
`as_chunks::<8>()`, `src/kernel.rs`), **без** `unsafe` во всём крейте и в его тестах (счётный
аллокатор для `tests/no_alloc*.rs` даёт dev-зависимость `allocation-counter`, задача 1.10b).
Пробовали и отклонили: `f32::mul_add` без гарантированной таргет-фичи `fma`
лишится аппаратного FMA и упадёт на софтверный вызов `fmaf` — медленнее плюс-умножения; а
рантайм-диспетчеризуемая `#[target_feature(enable = "fma")]`-версия (с одним `unsafe`-вызовом
после `is_x86_feature_detected!`) на реальном графе M **замедлила** цикл (медиана ~4.3 мс против
~3.7 мс скалярного до остальных оптимизаций ниже) — вероятно, из-за потери инлайнинга через
границу вызова таргет-фича-функции на горячем пути (вызывается на каждую строку CSR, а строк —
десятки тысяч, по ~30 рёбер на строку). Совпадает с находкой фазы 0
(`docs/research/rust-stack.md` §4): ручной SIMD не нужен для B=1 на этом железе/форме нагрузки.

## Производительность (ревью, раунд 1, F3 — переизмерено)

Ревьюер нашёл оба целевых p99 непройденными, и что S-цель осталась незамеченной. Применены три
оптимизации, все с сохранённой корректностью (полный набор тестов зелёный после каждой):
1. **Кэш `r` между решениями** (`FlyState`'s инвариант `r_buf == f(v)`): исходный код
   пересчитывал `f(V)` на входе каждого подшага **и** ещё раз после последнего подшага (5 проходов
   на 4 подшага) — пятый проход избыточен, это ровно то же самое, что первый проход *следующего*
   решения. Теперь ровно 4 прохода на решение.
2. **`u16`-индексы `pre_index`** вместо `u32` из формата `.flyg` (оба реальных графа — S/M —
   укладываются в 65536 нейронов): половина трафика на выборку. `FlyModel::new` строит `u16`-копию
   один раз (топология не меняется `set_params`); откат на `u32`, если граф не влезает.
3. **`activation`** пропускает вызов `tanh` целиком при `V <= 0` (математически то же самое —
   `relu(V) = 0`, `tanh(0) = 0` — просто без вызова трансцендентной функции).
4. **`as_chunks::<8>()`** вместо ручной индексации `base + k` (даёт компилятору чанк
   статически-известного размера, а не арифметику индекса, которую надо доказывать раз за разом
   безопасной).

**Criterion** (чистый цикл `step_decision`, без сна между вызовами; load average ≈ 1–4):

| Граф | median до | median после | Δ | `set_params` после |
|---|---|---|---|---|
| S (49.7k рёбер) | 830 мкс | **361 мкс** | −57% | 374 мкс |
| M (426k рёбер) | 3.78 мс | **3.00 мс** | −21% | 3.91 мс |

**`ddnet-ai fly bench`** (реалистичный цикл 25 Гц: решение → сон до тика 40 мс → повтор, 500
решений — методика фазы 0, `docs/research/rust-stack.md` §4), несколько прогонов, load average
0.6–4.2 (конкурентные сборки других задач, `CARGO_BUILD_JOBS=4`):

| Граф | median | p99 (диапазон по прогонам) | max | >5 мс |
|---|---|---|---|---|
| S | 0.47–0.48 мс | **1.0–1.2 мс** (цель ≤1 мс) | 1.1–1.5 мс | 0/500 |
| M | 3.0–3.2 мс | **4.5–10.2 мс**, большинство прогонов ≤5–6.4 мс (цель ≤5 мс) | 5.0–15.4 мс | 0–49/500 |

**Статус целей после оптимизации:** median у обоих графов комфортно укладывается и совпадает с
criterion. p99 у S теперь на уровне цели (было 1.3–1.5 мс, стало 1.0–1.2 мс) — иногда чуть выше
1 мс. p99 у M **чаще укладывается в 5 мс, чем нет** (было стабильно 5.2–8.3+ мс, стало по
большинству прогонов 4.5–6.4 мс, редкие выбросы до 10 мс на одном прогоне из ~8 приload
average 2.7 — вероятно шум хоста, а не наш код: чистый criterion-замер даёт стабильные 2.9–3.1
мс). Известный риск для дальнейшей работы: p99 у M не гарантированно ≤5 мс на каждом прогоне при
фоновой нагрузке; если это станет жёстким блокером, следующий кандидат по измерениям
ревьюера — быстрая рациональная аппроксимация `tanh` (не пробовали: раунд оптимизаций выше уже

## Обратный проход и обучение (задача 7.2)

*(В этом разделе «ревью раунда 1»/«review round 1» и метки F1–F7 — это отдельный, свой раунд ревью
задачи 7.2, не тот же самый «раунд 1» задачи 7.1 из более раннего раздела этого файла; метки F1–F8
там и F1–F7 здесь пересекаются по номерам, но относятся к разным находкам разных задач.)*

### Как читается обратный проход (`src/backward.rs`)

Плоская цепочка из `t_decisions * substeps_per_decision` подшагов (граница «решение» влияет только
на то, какой вход держится и когда снимается `dn_rates`, но не на саму рекуррентность — тот же
экспоненциальный Эйлер работает сквозняком через все подшаги, включая переход между решениями,
поскольку `r`, которым питается первый подшаг решения `t+1`, — это ровно тот `r`, который дал
последний подшаг решения `t`, тот же инвариант `r_buf == f(V)`, что и в 7.1).

Траектория собирается без нового кода на прямом проходе: `TrajectoryRecorder` дополнен третьим
буфером `V_∞` (`v_inf_at`, рядом с существовавшими `V`/`r`) — обратному проходу нужно `V_∞ − V_prev`
для градиента по `τ`, а хранить его явно точнее, чем восстанавливать делением `(V_new − V_prev) /
decay` (decay может быть ~0.01 у τ около `τ_max`, деление на такое усиливает шум округления `V` в
~100 раз). `step_decision_recording` вызывается `T` раз подряд без `reset()` между решениями — это
уже работало в 7.1, обратный проход просто использует это свойство.

Дальше — стандартный BPTT назад по подшагам: подхватить прямой градиент из `dn_rates` (0.5 на
подшаг `S−1` решения, 0.5 на подшаг `S−2` — единственный неочевидный случай: при `substeps == 1`
подшаг `S−2` решения `t=0` — это виртуальный `l = −1`, то есть `v_init`, а не записанный подшаг; в
коде это единственная явная граничная проверка, не размазанная по всему циклу) и опциональные
`ExtraRateGrad` (критерий 1: «градиент по частоте любого нейрона на любом подшаге» — для будущих
вспомогательных голов/регуляризатора активности), пропустить через субградиент `f'(V)` (ровно 0 при
`V <= 0` — та же конвенция, что и у самого `relu`, задокументирована в
`activation::activation_derivative`), разложить на вклад в `b`/`θ` (тот же субградиент-0 у
клипа `τ`, когда клип активен) и в `V_∞`. `grad_a` накапливается post-major проходом по рёбрам (тот
же порядок, что у прямого прохода) — точный требуемый смысл: каждое ребро добавляет свой вклад в
`a[shared_param_id]` этого ребра, так что несколько рёбер одной пары типов корректно суммируются в
один параметр. Перенос градиента к `r_prev` (то, что фидбэк-петля должна протолкнуть в предыдущий
подшаг) — явно через **транспонированный (pre-major) CSR** (критерий 1 требует это явно):
`BackwardIndex::build` один раз считает обратный индекс (топология, не зависит от параметров) плюс
`sign·N_ij/Z_i` на ребро (тоже топология+`γ`, не `α`) — так что сам `backward()` на каждом подшаге
делает только гатеры/скаттеры в уже готовые массивы, без пересчёта `type_pairs`/`sign`/`inv_z` по
ребру (первая версия это делала и обходилась в ~2 раза дороже — см. «Производительность обучения»
ниже).

### Корректность градиента (критерий 2)

- **(2a/2b)** `tests/backward_correctness.rs`: независимый **плотный `f64`**-референс (прямой +
  обратный проход, `mod dense`, без единого вызова в код крейта — только те же формулы FLY.md §4)
  проверен против центральных конечных разностей (`h = 1e-5`, `rel_tol = 1e-6`, `abs_tol = 1e-10`
  — ровно критерий 2a, «relative error < 1e-6»: ревью раунда 1, F2, ужесточено с `1e-5`/`1e-8`) —
  это 2a. Настоящий разрежённый `f32`-обратный проход крейта сверен с этим (уже подтверждённым)
  плотным `f64`-референсом — `rel_tol = 1e-4`, `abs_tol = 1e-6` (как предлагает критерий) — это 2b.
  По каждой группе параметров (`a`, `b`, `θ`, `grad_inputs` на решение, `grad_v_init`), на 7 ручных
  графов (смешанные знаки, общий `shared_param_id` на двух разных рёбрах, несколько решений/
  подшагов с переходом состояния через границу решения, `substeps == 1` с попаданием градиента в
  виртуальный `v_init`, вспомогательный `ExtraRateGrad`-тэп на скрытом нейроне, 9-рёберный fan-in
  для основного цикла `as_chunks::<8>()`).
- **(2c)** `randomized_property_test_over_many_tiny_graphs_and_sequences` — 150 случайных графов
  (3–12 нейронов, случайные знаки/веса/`τ`/`γ`/число решений/подшагов), обе проверки выше на
  каждом; прогонялось вручную на 2000 испытаний при ужесточённом (F2) `rel_tol=1e-6` без единого
  расхождения перед тем, как урезано до 150 для обычного прогона.
- **(2d)** `tests/backward_real_graph.rs` (`#[ignore]`, реальный S) — **два независимых способа**
  (ревью раунда 1, F3: исходная версия сэмплировала индексы чисто случайно, и на графе этого
  размера большинство `a`/`θ`-градиентов у случайного зонда близки к нулю, так что бо́льшая часть
  из «20 случайных» проверок молча проходила против фактического нуля):
  - **FD** (сама формулировка критерия): половина проверяемых индексов — с наибольшим `|аналитический
    градиент|` (заведомо нетривиальная проверка), половина — случайные (по-прежнему покрывает
    «маленький/нулевой градиент», но не только это); `abs_tol` теперь масштабируется на
    `1e-2 × max|аналитический градиент|` группы (не фиксированная константа, которую группа с малыми
    значениями тривиально прошла бы) — `1e-3`, предложенный ревьюером как отправная точка, оказался
    туже собственного шума округления `f32`-FD на этом графе (эмпирически ~`1e-5`); `h = 2e-2` (не
    `5e-3`) по той же причине. Все 80 проверок (20×4 группы) проходят.
  - **(dual)** точная **forward-mode dual-number** референс-реализация (`mod dual`, `f64`,
    независима от `crate::backward`/`model`/`state` — та же дисциплина, что у `mod dense`): без
    шага `h` вообще, производная точна до обычного округления `f64`. По 5 параметров на группу,
    `rel_tol = 1e-4`, `abs_tol = 1e-6` (как 2b — здесь нет погрешности усечения FD, которую можно
    было бы прощать). Все 20 проверок проходят.
  - `spot_check_with_a_deliberately_zeroed_gradient_is_caught` — доказывает, что проверка не
    тавтологична: намеренно занулённый `grad_a` (крупнейший по модулю) **не** проходит тот же
    допуск, которым проверяются настоящие градиенты.

**Единственная известная точка, где конечные разности не могут совпасть с аналитикой:** ровно в
`V == 0` (излом `relu`) центральная разность видит примерно половину правого наклона, а субградиент
здесь определён как 0 — это математически ожидаемо, не баг; тестовые фикстуры явно избегают
приземления `V`/`v_init` точно на 0.0 (см. `nine_fan_in_edges_of_the_same_type_pair`'s комментарий).

### Обучающие утилиты (критерий 3, `src/optim.rs`)

Adam с раздельными lr на `a`/`b`/`θ` (по умолчанию `2e-4`, диапазон fly-lit.md §7.9), `β₁=0.9`,
`β₂=0.999`, `ε=1e-8`; `clip_grad_norm` — глобальная норма по всем трём группам вместе (масштаб один
общий, не по группам), no-op на уже-нефинитной норме; `add_l2_pull_to_a` — опциональное
`weight·(a − a_init)`, добавляемое прямо в градиент («не уходить далеко от коннектома»);
`activity_regularizer_rate_grad` — flyvis-style штраф за средний по типу rate вне `[low, high]`
(квадратичный hinge на обе стороны, не только «к целевому значению», как у flyvis) — даёт плотный
градиент по частоте, который подаётся как `ExtraRateGrad` на последнем подшаге решения.

**NaN/inf-guard (ревью раунда 1, F1 — переделан).** Первая версия проверяла только
`ParamGradients::all_finite()` *на входе* и вызывала `adam_step` напрямую — это ловит нефинитный
градиент, но НЕ ловит финитный градиент с достаточно большим lr, который сам оверфлоит **параметры**
до NaN/inf (проверка входного градиента ничего не знает о результате обновления). Ревьюер
воспроизвёл это на `lr = 1e38`: `applied=[true,false,false,...]`, застревало навсегда.

Настоящий guard — `optim::guarded_adam_step` (обёртка над `adam_step`, а не сам `adam_step`, у
которого никакой защиты нет и не должно быть — это осознанно «голое» обновление): снимок
`params`/`AdamState` → тентативный `adam_step` (с `lr`, умноженным на `GuardedAdamState::lr_scale`)
→ если результат нефинитен **или** вызывающий closure-валидатор (`validate: FnOnce(&FlyParams) ->
bool`, типично — применить кандидат к живой `FlyModel` и прогнать один дешёвый forward-проход,
проверив, что выход конечен) вернул `false` → откат к снимку и `lr_scale *= backoff_factor` (по
умолчанию `0.5`, с полом `min_lr_scale`). `demo::run_direction_demo` реально использует это (не
просто существующая-но-неиспользуемая функция): closure применяет кандидата к модели через
`set_params` и гоняет один probe-decision. `tests/train_demo.rs`'s
`run_direction_demo_survives_an_absurd_learning_rate` воспроизводит ревьюерский `lr = 1e38` целиком
через демку и проверяет: параметры модели никогда не становятся нефинитными, происходит минимум
один откат, `lr_scale` в итоге падает ниже 1.0 (backoff действительно применился).

### Батчи и параллелизм (критерий 4, `src/train.rs`)

`train_step(model, index, sequences, memory_cap_bytes)` — `sequences.par_iter().map(...)` по
`rayon`, каждая последовательность на своём воркере считает forward-с-записью + `backward`
независимо (свой `FlyState`/`TrajectoryRecorder`/`BpttScratch`), редукция — **последовательная**,
по уже упорядоченному `rayon`-результату (`.collect::<Vec<_>>()` сохраняет порядок независимо от
того, какой воркер что и когда закончил) — значит суммарный градиент побитово одинаков **при любом
числе потоков**, не только «при том же числе потоков» (тест
`batch_gradient_is_bit_identical_across_thread_counts`, 1 против 4 потоков). Память —
`sequence_memory_bytes` = `T · substeps · N · 3 слова · 4 байта` (`V`/`r`/`V_∞` в
`TrajectoryRecorder`), `batch_memory_bytes` суммирует по батчу; `train_step` отказывает
(`MemoryCapExceeded`) *до* аллокации, если сумма превышает `memory_cap_bytes`.

**Консервативность оценки памяти (ревью раунда 1, F7c).** `batch_memory_bytes` — сумма по *всем*
последовательностям батча, но `rayon`'s work-stealing держит живым не больше одного рекордера на
активный воркер одновременно (каждый освобождает свой перед тем, как взять следующий) — реальный
пик заметно меньше: ревьюер измерил ~65 МиБ RSS на S при `B=64`/8 потоках, тогда как
`batch_memory_bytes` даёт оценку в ~4 раза больше. `train_step`'s собственная проверка cap
намеренно оставлена на этой (безопасной, просто пессимистичной) оценке — это не баг, задокументировано
в doc comment `batch_memory_bytes`; добавлена `concurrent_batch_memory_bytes(model, sequences,
num_threads)` — та же формула, но по `num_threads` **крупнейшим** последовательностям (не по всем),
для вызывающего кода, которому нужна более точная оценка (например, перед выбором cap для
конкретного размера пула).

**Производительность обучения.** Первая версия `grad_a`-прохода пересчитывала `type_pairs[..]`/
знак/`synapse_count`/`inv_z` на каждое ребро на каждом подшаге (то же самое, что `FlyModel::
recompute` делает **один раз** на смену параметров) — `BackwardIndex` теперь кэширует
`edge_alpha_coeff`/`edge_shared_id` на ребро один раз при постройке (топология + `γ`, не зависит от
`a`), и `grad_a`-проход на подшаге — это гатер+скаттер, без пересчёта. Замер (`ddnet-ai`-независимый
`cargo test --release --test train_throughput -- --ignored --nocapture`, `B=64`, `T=32`, load
average в момент замера — см. таблицу; машина делила ядра с параллельными задачами других агентов,
`CARGO_BUILD_JOBS=4`):

| Граф | рёбер | потоков | sample-steps/с | peak RSS | load avg (1м) |
|---|---|---|---|---|---|
| S | 49 741 | 1 | 571 | 34.3 МиБ | 2.40 |
| S | 49 741 | 6 | 3 390 | 56.0 МиБ | 2.16 |
| S | 49 741 | 8 | 4 599 | 70.2 МиБ | 2.47 |

Приведён последний (наиболее тихий, load avg 1м ≈ 1.8–3.6) прогон — ревью раунда 1 (F4) поймало,
что более ранний прогон в это же окно замера дал у S на 8 потоках 2322 (медленнее 6 потоков), что
не воспроизвелось у ревьюера (у него 8 потоков дали 4646). Перезамерено в отдельном, спокойном окне
— здесь 8 потоков **быстрее** 6, как и должно быть при честном масштабировании (571→3390→4599 для

замера (другие процессы гостя делили vCPU в тот момент), не свойством кода. Числа до оптимизации
`grad_a`-прохода (см. выше) на **той более ранней, зашумлённой** серии замеров были: S 1/6 потоков
468/2312, M 1/6 потоков 25/156 — прямое сравнение «до/после» с этой (текущей, чистой) таблицей
было бы нечестным (разные условия хоста), поэтому не приводится повторно; сам факт ускорения после
оптимизации подтверждён отдельно (раздел выше, числа сняты в одном и том же, тогда зашумлённом,
окне до/после — корректное сравнение).

**Сравнение с прогнозом фазы 0** (`docs/research/rust-stack.md` §4: «≈13–18k sample-steps/с при
0.5М синапсов на 8 потоках; ~43k при 0.2М») — **числа заметно ниже** (M на 8 потоках даёт 454, не
13–18k; S на 8 потоках даёт 4599, хотя граф меньше даже 0.2М-случая, где прогноз ~43k). Это не
скрытая регрессия — это другая архитектура параллелизма. Фаза-0 замеряла **батч-SIMD** backward:
один поток держит состояние `[N][B]` и векторизует B=64 сэмплов *внутри* одного прохода по рёбрам —
каждый вес/индекс CSR читается из памяти **один раз** и используется для всех 64 сэмплов сразу
(амортизация трафика памяти на батч). `train_step` здесь параллелит **по потокам, не по SIMD-
дорожкам**: каждая из 64 последовательностей — это полноценный, независимый B=1-проход по всему
`nnz` на своём rayon-воркере; при 8 потоках это 8 полных, не амортизированных проходов по CSR на
поток, каждый заново читающий веса/индексы из памяти. Корректная, честная реализация транспонированного
CSR (критерий 1 явно требует именно его для δ) и полная детерминированность редукции даются здесь
дешевле по сложности и риску для корректности, чем батч-SIMD-переписывание внутреннего цикла
`backward()` — которое было бы уместнее как отдельная последующая задача по производительности, а
не втиснуто в эту (риск внести тонкую ошибку в самый критичный по корректности код задачи —
неприемлем без отдельного раунда ревью именно на это). **Ревью раунда 1 (F6) подтвердило: этот
разрыв — не для этого раунда**, он выделен в отдельную будущую задачу (7.2b, сделана — см. «Задача 7.2b» в конце файла: батч-SIMD
`[N][B]`-состояние с отдельным раундом ревью градиентов именно для этого переписывания).

### Демки обучения (критерий 5, `src/demo.rs`)

Задача — во обоих размерах: «включена левая или правая половина входных нейронов» ->
«одна из двух именованных групп выходных нейронов должна читаться высоко, другая — низко» (FLY.md
§6: `LC10a -> AOTU019/025 -> DNa02` — тот же пример). Лосс — MSE только по слотам двух именованных
групп (остальные выходы — без градиента); он же (через `2·(pred−target)/count`) даёт `grad_dn` для
`train_step`.

- **(5a)** `tests/train_demo.rs`, крохотный граф (`in{0,1} -> hid{0,1} -> out{0,1}`, без
  перекрёстных рёбер — они пробовались первыми и отклонены: `hid_t` по закону Дейла всегда
  возбуждающий, значит перекрёстное ребро может только *добавлять* активность второму выходу,
  никогда не убирать её, а придушить его до нуля означает гнать `softplus(a) -> 0`, чей градиент
  (`sigmoid(a)`) сам затухает при этом — реальный, но не относящийся к цели этой демки случай
  затухающего градиента). loss упал **~1223×** (18.49 → 0.015 за 1500 шагов Adam, `lr=3e-2`,
  `clip_norm=1.0`), итоговая точность классификации обоих (детерминированных) паттернов — 100%.
  Важная деталь: лосс считается только на *последних* `readout_decisions` подшагах решения (по
  умолчанию 2 из 4) — самое первое решение окна детерминированно одинаково для обоих паттернов
  (общий `v_init`, сигнал ещё не успел дойти), и его включение в лосс создаёт неубираемый пол —
  без этого урезания тот же граф застревал на ~3.3 (падение всего ×5–6), это не баг обучения, а
  артефакт неправильно поставленной задачи.
- **(5b)** `tests/train_demo_real_graph.rs` (`#[ignore]`, реальный S): «левый/правый» вход —

### Чекпоинт: версия 2 (критерий 6, `src/checkpoint.rs`)

`FLY_CHECKPOINT_FORMAT_VERSION` — 2 (было 1): добавлено поле `Checkpoint::optimizer:
Option<optim::AdamState>` (моменты Adam + счётчик шага). `None` — чекпоинт до первого шага
обучения; `Some` — можно продолжить обучение без «холодного старта» оптимизатора. Старый (v1) файл
не декодируется v2-читателем — явная `CheckpointFormatVersionMismatch` по заголовку, не путаная
ошибка postcard (та же конвенция review round 1's F6). Тест
`resuming_training_from_a_checkpoint_reproduces_the_same_next_step`: 3 шага Adam → сохранить
чекпоинт (с состоянием оптимизатора) → 2 шага дальше *без* сохранения — параллельно: загрузить
чекпоинт → те же 2 шага — параметры и состояние Adam **побитово** совпадают между двумя путями.
Фаззинг однобитовых флипов (`every_sampled_bit_flip_on_a_high_entropy_payload_is_rejected`) обновлён
— теперь включает реалистичное состояние Adam в пейлоад (энтропия/размер представительны для
настоящего чекпоинта посреди обучения), все 2000 выборочных флипов всё ещё отклоняются.

**Проверка формы optimizer/params при загрузке (ревью раунда 1, F7d).** `load_checkpoint` раньше
декодировало `Checkpoint` и отдавало его как есть, не проверяя, что `optimizer` (если `Some`)
согласован по длине со своими же `params` — рассинхрон (например, руками отредактированный или
частично побитый, но всё ещё проходящий sha256/`format_version` файл) не паниковал бы тут же, а
только позже, внутри `adam_step`, при первом же продолжении обучения. Теперь `load_checkpoint`
сам вызывает `AdamState::matches_shape` и возвращает понятную `FlyError::OptimizerShapeMismatch`,
не давая такому файлу тихо «загрузиться». Тест
`load_checkpoint_rejects_an_optimizer_that_does_not_shape_match_its_own_params` строит такой файл
напрямую (минуя `save_checkpoint`, которое всегда строит согласованную пару) и проверяет отказ.

## Задача 7.3: лучевой энкодер, декодер действий, голова «модели мира», `FlyBrain`

Соединяет игру с мухой (`docs/FLY.md` §5-§7, §10): `crate::encoder` — лучевая сетка «глаз» +
проприоцепция → токи в реальные VPN/AN-нейроны из `.flyg`; `crate::decoder` — частоты DN →
действие через замороженную калибровку + небольшие головы; `crate::world_model` — линейная
голова предсказания физики + отдельный (без backprop) ridge-пробник; `crate::brain::FlyBrain` —
`ddai_brain::Brain`, который играет через всё это; `crate::brain_train::brain_train_step` — одна
функция «encode → шаги мухи → decode + модель мира → лоссы → backward», дающая градиенты по всем
четырём обучаемым группам за один вызов.

### Энкодер (`encoder.rs`)

Лучевая сетка: 48 направлений × 4 дальностных бина (конфигурируемо, `RayGridConfig`), максимум
20 тайлов, **настоящий** Amanatides-Woo DDA-марш по тайловой сетке (`RayGridFeatures::cast_ray`,
точное расстояние до входа в каждый тайл) — стены/no-hook останавливают луч (окклюзия), фриз/
deep-фриз/смерть (game **и** front-слой) — нет, только запоминают ближайшее попадание.
**Ревью раунд 1, F7 (подтверждено, major):** раньше это был march с фиксированным шагом в 1 тайл,
а не DDA, вопреки doc comment/README (0.19% лучей на реальной карте Copy Love Box «видели» сквозь
стену, 0.23% перелетали дальше тайла) — переписано на честный DDA, проверено против
brute-force-эталона на нерегулярной карте (`cast_ray_matches_a_brute_force_reference_on_an_
irregular_map`) и на тонкой диагональной стене
(`cast_ray_does_not_see_through_a_thin_diagonal_wall`). Объектные каналы (соперник/его хук/другие игроки) — не по лучам, а гауссовым «бликом»
по углу и дистанции (`place_point_feature`) в ту же 48×4-сетку. `opponent_approach` (looming) —
`2·r·v_closing/d²`, насыщенное `x/(x+K)` вместо экспоненты (см. doc comment
`compute_looming_feature`). **Единицы (ревью раунд 1, F3/F4, подтверждено, блокер+major):** `v` —
**пиксели за тик сервера** (`CharacterObservation::vel`, не пиксели/с — раньше doc comment
ошибочно говорил «px/s-ish» и `looming_k=400.0` был подобран под это, из-за чего признак насыщался
практически в 0 при любом реалистичном сближении: `v=10 px/tick` в упор с 3 тайлов давало
`2rv/d²≈0.03`, то есть `0.03/400≈7.5e-5`). Новые значения по умолчанию — `looming_k=0.03`
(то же сближение теперь даёт `≈0.5`), `velocity_norm_scale=30.0` (тоже px/tick, `3×` дефолтной
скорости бега); `configs/fly/{S,M}-brain.toml` явно перечисляют оба значения, совпадающие с
кодовым дефолтом. Собственная скорость (vx/vy) — не по сетке, а через RF-азимут/
элевацию каждого нейрона как знаковый направляющий фактор (`sin(azimuth)`/`sin(elevation)`) —
это одновременно и физиологически осмысленный выбор (реальные HS/VS клетки направленно
селективны по своему ретинотопическому положению), и то единственное решение, при котором вся
цепочка остаётся зеркально-симметричной (см. ниже).

**Угловая конвенция** (ринг-угол θ, 0 = экран +x, π/2 = вверх/дорсально): единая функция
`ring_angle_from_screen_delta(dx, dy) = atan2(-dy, dx)` — и для луча, и для пеленга на соперника,
и для РП-центра нейрона (азимут/элевация RP folds через `sin(az), sin(el)` в тот же ринг). Из
этого следует (и проверено тестом `mirroring_azimuth_sign_gives_pi_minus_theta`): отражение
азимута (ровно то, что связывает L/R-гомологов в `.flyg`) даёт `θ -> π - θ` — ровно то же
преобразование, которому подчиняется зеркально отражённый пеленг/луч. `num_directions` обязано
быть чётным — иначе `π` не попадает точно на другое направление сетки, и зеркальная проверка
структурно не смогла бы пройти.

**Ревью раунд 1, F1 (блокер, подтверждено):** элевация была инвертирована — дорсальные клетки
реагировали на то, что *внизу*, а не вверху (положительная элевация — «дорсально/вверх» по
FLY.md §5, а «вверх» в этой конвенции — *отрицательный* экранный `dy`). Исправлено: элевация
подставляется в `ring_angle_from_screen_delta` со знаком минус. Баг был сам по себе
зеркально-симметричен (отражение одной азимуты по-прежнему давало `θ -> π-θ`), поэтому старый
тест на зеркальность его не ловил — понадобился отдельный «соперник строго сверху» тест
(`opponent_above_drives_dorsal_cells_more_than_ventral_ones`).

**Ревью раунд 1, F9 (подтверждено, minor):** ни одна реальная РП S-графа даже близко не смотрит
строго вверх/вниз — максимум `|elevation_deg|` по всем 1290 визуальным РП равен `47.06°` (медиана
`16.41°`), так что при простом `atan2(sin(el), sin(az))` **все 100%** РП попадали в пределы `±60°`
от горизонтали — прямо-вверх/вниз-зрение практически не представлено. `RayGridConfig::
elevation_gain` (по умолчанию `2.0`) домножает `sin(elevation)` перед `atan2`: та же реальная
выборка при этом даёт медианное отклонение от горизонтали `41.1°` (было `23.5°`) и долю «всё ещё
в пределах ±60°» `87.7%` (было `100%`) — заметное улучшение без чрезмерного (`gain=4.0` даёт
`~50%`, но за счёт более сильного сжатия азимутального разрешения). Зеркальная симметрия держится
при любом `gain` (элевация не участвует в отражении по азимуту). Числа — из
`encoder::tests::dump_real_s_elevation_and_ring_angle_distribution` (`#[ignore]`d диагностика).

**Канал → тип, по факту на реальных графах** (task 6.3's `.flyg`; проверено реальным прогоном
`ddnet-ai fly brain-demo` на S — см. «Демо обучения» ниже):

| `opponent_position` | LC10a | LC10a, LC10d, LC9 | Б |
| `opponent_approach` | LC4, LPLC2 | LC4, LPLC2 | Б |

**Выбор соперника (ревью раунд 1, F13, подтверждено):** `opponent_position`/`opponent_approach`/
`opponent_hook` строятся из `Observation::target_or_nearest()` (`ddai-brain`) — явно выбранный
`target_id`, если он есть и всё ещё присутствует среди `others`, иначе ближайший по расстоянию.
Раньше это молча был `obs.others.first()` (индекс `0`), при том что doc comment самого поля
`others` прямо говорит: «порядок не имеет значения» — производитель `Observation`, вернувший
`others` в, скажем, порядке по дистанции, незаметно подсовывал бы то одного, то другого соперника
в зависимости от случайного порядка. `other_players` теперь получает всех, кроме именно
выбранного (не «кроме первого»).

S: 3 канала из 10 без единого нейрона (`opponent_hook`, `no_hook_tiles`, `self_velocity_flow`) —
подтверждено реальным запуском (`EncoderModel::visual_channels_with_no_neurons()`, лог CLI: 28
(type, channel)-параметров на S). M закрывает все 10 (только через типы, отсутствующие в S:
LC15/LC24/LC26/LLPC1-3). **Обратная находка** (не «канал без нейронов», а «нейрон без канала»):
и в S, и в M тип `H2` присутствует среди `visual_types`, но не упомянут ни в одном
`[[input_channels]]` — такие нейроны всегда получают `I = 0` (нет ни одного терма); аналогично
`LC9` в S. Это не баг этого крейта (маппинг типов на каналы взят из `configs/fly/{S,M}.toml`,
задача 6.3, не трогается здесь) — зафиксировано как открытый вопрос ниже. Число параметров
энкодера у M — 67 по конфигу (не прогонялось на реальном графе M в рамках этой задачи, только S;
формула `Σ channels per VPN type + Σ AN types` проверена на S, где она даёт ровно измеренные 28).

### Проприоцепция → AN (label П, `ProprioceptionConfig`)

AN-типы MaleCNS v1.0 не несут функционального имени (`docs/formats.md` §8) — в отличие от VPN,
`.flyg` вообще не хранит для них канальную карту. `configs/fly/{S,M}-brain.toml`'s `[proprioception]`
— **детерминированный round-robin** по отсортированным по имени реальным AN-типам графа через 6
каналов (`grounded`/`airborne`/`own_hook`/`jumps_left`/`freeze_timer`/`speed`), метка **П**
всюду (не «Walk/Rest AN» из FLY.md §5 — этих функциональных имён у данных нет). `EncoderModel::new`
проверяет каждое имя типа: существует ли, действительно `InputAscending`, не назначено ли двум
разным каналам одновременно.

### Декодер (`decoder.rs`)

Калибровка — **одна** документированная функция, `crate::calibrate_from_rest` (ревью раунд 1, F10:
раньше это было прозой в doc comment здесь и *другим*, недокументированным рецептом внутри CLI):
прогреть, затем собрать 64 `dn_rates`-снимка при почти-нулевом входе с небольшим джиттером
(`±0.025`), `DnCalibration::fit` — среднее/std по каждому DN-слоту, `σ` не ниже `min_sigma`.
`z = clip((r-μ)/σ, ±10)`. И CLI (`ddnet-ai fly brain-demo`), и тесты, и
`tests/brain_demo_generalization.rs` зовут ровно эту функцию — нет второго места, где протокол
мог бы незаметно разойтись.

**Джиттер — общий на тип, не на нейрон (ревью раунд 2, F19, подтверждено).** Раньше джиттер
рисовался независимо для каждого входного нейрона — у зеркальных `L`/`R`-гомологов набегала
разная `mu` (~1e-3) за 64 семпла, а поскольку `sigma` в этом протоколе покоя всегда садится на
`min_sigma` (это ожидаемое свойство калибровки *от покоя*, не то, что джиттер якобы предотвращает
— более ранняя версия doc comment здесь ошибочно утверждала обратное), эта разница в `mu`
превращалась в `z`-сдвиг `0.02–0.04` между гомологами — достаточно, чтобы сломать
action-level зеркальную симметрию декодера через саму калибровку (`3.7e-2` до фикса против `6.5e-7`
после, на точно симметричном графе). Теперь джиттер один и тот же для всех входных нейронов
одного типа независимо от стороны — `tests/brain_mirror.rs`'s action-level тест идёт через
настоящий `calibrate_from_rest` (не через руками заданные `mu=0, sigma=1`), плюс отдельный
прицельный тест `decoder::tests::calibrate_from_rest_gives_l_r_homologs_the_same_mu_and_sigma`.

**Зеркально-симметричные головы, привязка весов (ревью раунд 1, F6, критерий 8).** Раньше `W_dec`
был плотной, ничем не связанной матрицей — ни одно архитектурное ограничение не заставляло вес
«левой» DN-группы совпадать с весом «правой», в отличие от `a`/`b`/`theta`, которые `.flyg`'s
`shared_param_id`/`type_index` жёстко разделяют между L/R. Теперь каждая голова строится один раз
в `DecoderModel::new` из настоящих `output_groups` графа (задача 6.3) и `side` каждого члена:

- **`direction_left`/`direction_right`** — по одному весу `w_lr[type]` + общий `b_lr` на **тип**,
  присутствующий в обеих группах (на реальных S/M — каждый тип: `DNa01`/`DNa02`/`DNg13`/`DNp09`,
  один `L`-инстанс в `direction_left`, один `R`-инстанс в `direction_right`); `right_logit(z) ==
  left_logit(mirror(z))` ровно по построению (обе стороны считаются одной и той же формулой).
  Тип, встретившийся только в одной из групп — явная ошибка `DirectionTypeNotOnBothSides`, не
  тихо пропущенный член.
- **`direction_stop`/`jump`/`hook`/`fire`** — по одному весу на **тип**, но приложенному к
  среднему по **обеим сторонам вместе** (пул `L+R`) — у этих действий нет «левого»/«правого»
  варианта (скриптовый учитель никогда не просит «прыгнуть влево»), пуллинг даёт инвариантность
  к перестановке L/R автоматически (среднему всё равно, какое конкретное значение с какой стороны
  пришло).
- **Прицел** — популяционный вектор (не смесь фон Мизес): члены каждого типа с обеих сторон
  спариваются позиционно (по возрастанию dense-индекса); у пары свободен только `θ_L`, `θ_R =
  π - θ_L` **выводится**, никогда не хранится. `C = Σ_pairs (z_L-z_R)cosθ + Σ_unpaired z cosθ`,
  `S = Σ_pairs (z_L+z_R)sinθ + Σ_unpaired z sinθ`, `μ=atan2(S,C)`; под перестановкой `z_L<->z_R`
  внутри пары `C` меняет знак, `S` не меняется — ровно то же преобразование, которому подчиняется
  зеркально отражённый пеленг. Член без парного (`side=M`/`Unknown`, либо разное число `L`/`R` в
  типе — ни то ни другое не встречается на реальных S/M, но код этого не предполагает) получает
  свой независимый угол (метка **П**) — он **не** гарантированно зеркально-симметричен сам по
  себе (нет противоположной стороны, с которой его можно было бы поменять местами); на реальных
  S/M таких членов нет вовсе (см. «Проверка градиента» ниже — `aim_unpaired_theta` там 0 записей).
  Обучаются только `θ` (FLY.md §6 называет обучаемыми именно предпочтительные углы, не
  концентрацию); лосс — фон Мизес NLL `-κ·cos(target-μ)` с **фиксированной** `κ`
  (`DecoderConfig::aim_kappa`, по умолчанию 4.0) — раз `κ` не обучается, `log(2π·I0(κ))` не даёт
  градиента и просто отбрасывается (не нужен рукописный `d log I0(κ)/dκ`). Вырожденная точка
  `(C,S)=(0,0)` — градиент 0 (та же конвенция «излом → 0», что и у relu в этом крейте).
- **L1 на `W`** — отдельная функция `add_l1_penalty` + `l1_penalty_value` (не внутри
  `decoder_loss_and_grad`, как `crate::optim::add_l2_pull_to_a`), но теперь и правда **вызываемая**
  из `brain_train_step` (ревью раунд 1, F12: раньше `add_l1_penalty` существовала, но не звалась
  ниоткуда — `DecoderConfig::l1_weight` был мёртвым полем).

**Проверка формы/конечности при загрузке (ревью раунд 1, F11).** `DecoderModel::
validate_params_shape`/`DnCalibration::validate_shape`/`WorldModelHead::validate_params_shape` —
каждая голова/калибровка проверяется на длину (совпадает ли с тем, что ждёт *текущая* модель,
построенная из *текущих* `.flyg`+brain-config) и на `NaN`/`inf`, а не молча переинтерпретируется.
`crate::brain_checkpoint::BrainCheckpoint` получил `brain_config_sha256` (sha256 самого
`configs/fly/{S,M}-brain.toml`, не только `.flyg`) — правка конфига, меняющая размер какой-либо
головы (число участников `output_groups`, `neuron_subset`), раньше молча переинтерпретировала бы
старый чекпоинт под новую форму; теперь `load_brain_checkpoint_for_flyg` ловит несовпадающий
конфиг явной ошибкой, а `validate_brain_checkpoint_shapes` — несовпадающую форму/`NaN` после того,
как оба хеша совпали.

### Голова «модели мира» (`world_model.rs`)

Линейный readout из `f(V)` подмножества (по умолчанию — все `Hidden`), 3 горизонта {1,5,10}: 8
непрерывных целей (Δpos/Δvel себя+соперника) + 3 бинарных (фриз/касание земли/попадание хука).
`fit_ridge_probe` — **отдельная**, без backprop, замкнутая ridge-регрессия (нормальные уравнения,
Gauss-Jordan с частичным выбором ведущего элемента, вручную — без внешней линал-библиотеки);
`RidgeProbe::r_squared` — метрика FLY.md §7. Проверено на точно восстановимой линейной
зависимости (R² > 0.999 на отложенных точках) и на вырожденной (ранг-1) матрице (аккуратный
`None`, не паника/деление на 0). `fit_ridge_probe`'s `O(d³)`-предел зондирования всей M-популяции
разом — см. «Открытые вопросы» ниже (ревью раунд 1, F17).

**Вес лосса модели мира теперь действительно применяется (ревью раунд 1, F5, подтверждено,
major).** `WorldModelConfig::loss_weight` (FLY.md §7: «0.1–0.3 от основного лосса») раньше
вычислялся, но нигде не умножался — `brain_train_step` складывал лосс/градиенты модели мира с
весом `1.0` независимо от конфига, так что крупная по масштабу MSE-регрессия могла заглушить
градиент действия в общих параметрах энкодера/мухи. Теперь `WorldModelHead` хранит свой
`loss_weight` и `brain_train_step` домножает на него и лосс, и `WorldModelGradients`, и
`grad_r`-тэп в `backward` — единообразно, в одном месте.

### Сквозная дифференцируемость (`brain_train.rs`, критерий 6)

`brain_train_step` — один вызов: кодирует каждое наблюдение окна, прогоняет
`step_decision_recording` по всем decisions, восстанавливает `dn_rates` (то же усреднение
`0.5·(r_до-последнего + r_последний)`, что и `DecisionOutput`, но по записанной траектории — без
повторного `step_decision`), считает лоссы декодера/модели мира, зовёт `crate::backward::backward`
**один раз** (с `grad_dn_rates` от декодера и `ExtraRateGrad`-тэпом от модели мира на последнем
подшаге), затем прокатывает `grad_inputs` через `EncoderModel::backward`. Возвращает градиенты по
всем четырём группам (`encoder.g/c`, `fly.a/b/theta`, `decoder.*`, `world_model.*`) одним вызовом.

**Проверка градиента.** Крохотные графы (`brain_train::tests`, `encoder::tests`,
`decoder::tests`, `world_model::tests`): аналитика vs. центральные конечные разности,
`rel < 1e-3` **или** `abs < 2e-4` (комбинированный допуск — чистая относительная планка слишком
жёсткая у мелких по модулю градиентов рядом с собственным `f32`-шумом округления центральной
разности; поймано и обосновано числами при подборе — см. doc comments тестов). **Ревью раунд 1,
F14 (подтверждено):** раньше эти crate-внутренние проверки покрывали только 4 группы и пропускали
`enc.c`, `fly.b`, `fly.θ`, `jump`/`hook`/`fire`/`aim` в реальном S-тесте — теперь
`tests/gradcheck_brain.rs` перебирает **все 7** полей декодера (`direction_lr_w`,
`direction_stop_w`, `jump_w`, `hook_w`, `fire_w`, `aim_pair_theta`, `aim_unpaired_theta`), допуск
`abs < max(1e-2 × max|g|, floor)` для каждой группы отдельно (тот же урок ревью задачи 7.2 —
«сэмплировать самые большие, допуск от максимума группы»; floor поднят до `5e-5` только для
декодера — у `direction_stop_w` на реальном S сам `max|g|` крохотный, `~1e-3`, и `1%` от него
садится прямо на шум конечной разности при `h=5e-3`) — **все проходят**:


(`aim_unpaired_theta`'s 0 записей подтверждает то, что уже сказано выше в «Декодер»: на реальном S
нет ни одного непарного члена прицела.)

**`tests/dualcheck_brain.rs` — независимая dual-number проверка (ревью раунд 1, F14, часть про
«dual-number reference», подтверждено).** Конечные разности (даже в `f64`) всё равно несут
truncation error, зависящий от шага `h`; dual-числа (forward-mode autodiff) дают **точную**
производную (единственная погрешность — округление `f64`), собственная реализация (не копия
скретч-инструмента ревьюера), написанная заново для этого файла. Покрывает **декодер** (все 12
скалярных параметров: `direction_lr_w/b`, `direction_stop_w/b`, `jump_w/b`, `hook_w/b`, `fire_w/b`,
`aim_pair_theta`, `aim_unpaired_theta` — на крохотном графе с ровно той же формой связывания, что
и на реальном S: 1 tied-пара direction, пуловые `stop`/`jump`/`hook`/`fire`, 1 tied aim-пара + 1
непарный член) и **модель мира** (все 44 параметра горизонта 0: `w_reg`/`b_reg`/`w_bin`/`b_bin`).
Допуск `rel<1e-5`/`abs<1e-6` — не уступка (dual-сторона точна), а просто пол собственной точности
`f32`, в котором аналитика (`decoder_loss_and_grad`/`world_model_loss_and_grad`) считается целиком
(наблюдаемое расхождение ~1e-7, ровно `f32`-epsilon); тест «намеренно занулённый градиент ловится»
— тот же урок ревью задачи 7.2, теперь и через dual-числа, не только через конечные разности.

**Почему не все 4 группы через dual-числа** (сознательное сужение объёма, не пропущенное):
коннектомные `a`/`b`/`theta` уже имеют dual-number проверку (`tests/backward_real_graph.rs`,
задача 7.2, не тронуто) — ровно через настоящую нелинейную рекуррентную динамику (exponential
Euler, `tanh`/`relu`), которую decoder/world-model проверкам заново выводить не нужно (их параметры
влияют только на *чтение* `dn_rates`/`r_full`, не на саму рекуррентность). Энкодерные `g`/`c` —
`EncoderModel::forward`'s формула (FLY.md §5) **линейна** по `g`/`c` при фиксированном наблюдении
(`I_i = Σ feature·g + c`, без единой нелинейности) — центральная конечная разность линейной функции
не имеет truncation error вовсе ни при каком `h` (член ряда Тейлора, который `h` контролирует,
тождественно ноль при нулевой второй производной), так что уже существующие FD-проверки
(`encoder::tests::backward_matches_finite_differences_of_forward`, `tests/gradcheck_brain.rs`'s
`encoder.g`) настолько же точны, насколько была бы и dual-number проверка — переписывать
энкодерное гауссово взвешивание по лучам ещё раз здесь не добавило бы строгости, только код.

Тест «намеренно занулённый градиент не проходит ту же проверку» — во всех трёх модулях
(`encoder`/`decoder`/`brain_train`), тот же урок ревью задачи 7.2.

Найденный (и исправленный) в процессе бага реальный баг: направление-голова изначально смешивала
«из какой DN-группы физически пришёл этот `z`» с «для какого класса сейчас считаем логит» —
градиент по `z` терял 2 из 3 слагаемых (полная плотная матрица `W`, не блочно-диагональная).
Поймано ровно finite-difference-проверкой на игрушечном графе, не на глаз.

### Зеркальная симметрия (критерий 8, `tests/brain_mirror.rs`, реальный S)

Отражение `Observation` через `ddai_brain::Observation::mirror_x()` (карта **и** позиции — одна
ось) должно давать отражённую активность, потому что L/R-копии типа делят параметры (FLY.md §4).
Проверено на **среднем по (тип, сторона)**, не по конкретному нейрону (параметры общие именно на
уровне типа, канонической 1:1 привязки нейрона к гомологу через `group_id` для этого не нужно и
местами неоднозначно): для каждого типа с нейронами на обеих сторонах, `mean_rate(type, L, obs)`
против `mean_rate(type, R, mirror(obs))` и наоборот.

```
$ cargo test -p ddai-fly --test brain_mirror --release -- --ignored --nocapture

worst deviation by role: {"AN": 0.0129, "DN": 0.1186, "Hidden": 0.1057, "VPN": 0.1090}
```

Максимальное отклонение — **0.119 из `r_max=10`** (≈1.2%), проверено допуском `< 0.15` (число
слегка выросло после F1's правки знака elevation — реальные признаки, которые раньше вычислялись
по неверной формуле, теперь корректно ненулевые, так что зеркальная пара сравнивает настоящую,
а не почти-плоскую активность; всё ещё комфортно внутри допуска).

**Декодер — теперь тоже проверяется на зеркальность, действие целиком** (ревью раунд 1, F6:
раньше это было открытым вопросом — у `W_dec` не было структурной привязки). Два теста:
`crate::decoder::tests::mirroring_z_gives_the_mirrored_decoded_action` — синтетический `z` напрямую
в декодер (изолированно от энкодера/коннектома); `tests/brain_mirror.rs`'s
`action_level_mirror_symmetry_on_a_synthetic_l_r_symmetric_graph` — **целиком** энкодер → коннектом
→ декодер на маленьком, вручную построенном, точно L/R-симметричном графе с ненулевыми
(асимметричными) весами декодера (нулевые веса прошли бы тривиально, спрятав именно тот класс
багов, который тест должен ловить) **и через настоящую `calibrate_from_rest`** (ревью раунд 2,
F19 — раньше здесь стояли руками заданные `mu=0, sigma=1`, так что калибровка сама никогда не
проверялась на зеркальность; она ломала её, см. «Декодер» выше, до F19's фикса):

```
$ cargo test -p ddai-fly --test brain_mirror -- --nocapture
action-level mirror symmetry (synthetic graph): left/right=0.00e0 right/left=0.00e0 stop=0.00e0 jump=0.00e0 hook=0.00e0 fire=0.00e0 (max=0.00e0)
```

Точное совпадение (`0.00e0`, не просто «в пределах допуска») — ожидаемо для маленького

архитектурно** (проверено, не только заявлено): та же синтетическая проверка руками задаёт
несимметричные веса `w_reg` и печатает `regression[0]` до/после отражения — совпадение в этом
конкретном фикстуре происходит только потому, что его `Hidden`-подмножество не различает стороны,
а не потому, что это где-либо гарантировано; никакого архитектурного требования «Δx меняет знак при
зеркале» здесь нет и не подразумевается (задача 7.3's критерий 5 этого не просит — только
критерий 8 про *действие*).


(диапазон из нескольких прогонов подряд, не одно число — машина делится с параллельными задачами

корректно, честно и глубоко внутри бюджета.

### Демо обучения (критерий 9, `ddai_fly::demo_brain`, `ddnet-ai fly brain-demo`)

Синтетика: случайный спавн на открытом тайле реальной карты (`ddai-map`), соперник на случайном
относительном смещении/скорости. Скриптовый учитель — **только** `direction`/`jump`/`hook`
(FLY.md/задание не описывают учителя для `fire`/`aim` в этом сценарии — нет ни оружия, ни цели,
поэтому эти две головы в демо не обучаются и не оцениваются, это осознанное сужение, не забытое).
Обучение: `guarded_adam_step` (7.2) — мухины `a`/`b`/`theta`; `flat_adam::step_guarded` (ревью
раунд 1, F12: раньше был обычный, негвардированный `step` — один нефинитный градиент навсегда
портил Adam-моменты этой группы, независимо от того, что делал гвардированный шаг мухи) — энкодер
`g`/`c`, декодер `W`/`b`, каждая из 13 групп по отдельности.

**Честная оценка (ревью раунд 1, F2, критично)** — раньше отчёт печатал голую accuracy против
захардкоженного «chance» (`1/3`, `1/2`), молча предполагая сбалансированные классы; на реальном
учителе `jump` — редкое событие (~1.5% позитивных на случайной выборке), и предиктор «никогда не
прыгать» набирал обманчиво высокую accuracy, при этом почти не имея сигнала для обучения. Теперь:

- `HeadMetrics`/`BinaryMetrics`/`DirectionMetrics` — у каждой головы своя распространённость
  класса, **настоящий** majority-baseline (посчитанный из распространённости, не константа),
  recall по каждому классу, **balanced accuracy** (среднее recall — метрика, которую константный
  предиктор не может задрать), **AUROC** (бинарные головы) и **95%-й интервал Уилсона** на
  accuracy.
- `sample_scenario_stratified` — rejection-sampling `jump` к 30–50% позитивных (и в обучающих
  батчах, и в held-out наборе), чтобы редчайшая голова не тонула в одном классе.
- `evaluate_fly`/`evaluate_mlp` — публичные функции (не замыкание внутри `run_brain_demo`), поэтому
  один и тот же прогон можно честно оценить и на картах/сидах, которых обучение не видело —
  `tests/brain_demo_generalization.rs`.
- Ревью раунд 1, F15: `evaluate_fly` теперь читает `DecisionOutput::dn_rates` (усреднение
  `0.5·(r_до-последнего+r_последний)`) — тот же readout, что и обучение/`FlyBrain::decide`; раньше
  оценка бралась из `state.v()` напрямую (`r_последний` в одиночку), незаметно другой readout, чем
  тот, для которого декодер обучался.

**Протокол (ревью раунд 1's F2, скорректированный ревью раунда 2's F20)**: 3 сида × обучение на
одной карте, оценка на семи (реальный S, `batch=16, t_decisions=4, steps=200` —
`tests/brain_demo_generalization.rs`, `#[ignore]`d, ~177с на 3 сида):


результат не меняется. **Вывод, прямо: голова `hook` мухи на естественном распределении и на
новых картах работает около шанса — это открытый исследовательский вопрос для фазы 8 (возможно,
`hook`'у нужно больше степеней свободы, дольше обучение, другой lr декодера, или само задание
слишком завязано на близость по прямой линии, которую скриптовый учитель не всегда отражает
правильно через `line_of_sight_clear`), а не дефект кода этой задачи.**

Правдоподобная (не доказанная контролируемой абляцией — не хватило времени на неё в рамках этой
задачи) причина разрыва с MLP в целом: декодерные головы `jump`/`hook` устроены как **один общий
скаляр-вес на тип** (пул L+R, ревью F6) — очень мало степеней свободы (5–8 весов на голову на
реальном S, см. `tests/gradcheck_brain.rs`'s вывод) против плотного per-feature слоя у MLP; плюс
мухин `g`/`c` энкодер разделён по (тип, канал), а не по входному признаку — гораздо более сжатое
представление, которое к тому же должно одновременно обслуживать все головы через один и тот же
рекуррентный `V`, тогда как у MLP `direction`/`jump`/`hook` читают общий скрытый слой, но не делят
между собой ничего архитектурно навязанного сверх этого. Это цена биологической привязки к
настоящему коннектому, а не баг — но и не повод скрывать разрыв.

**Параметрный паритет MLP — не точный** (открытый вопрос): у мухи параметры структурно разделены
(один `a` на пару типов, не на входной признак), у MLP — плотные per-feature веса; при входной
размерности ~1372 (реальный лучевой грид) точное совпадение суммарного числа параметров означает
либо урезать MLP до нескольких скрытых юнитов (сделано — подобрано формулой, реально получилось
сравнимо), либо раздувать его далеко за пределы мухи. Оба числа честно напечатаны и сохранены —
решение не подгонять напоказ.

## Задача 8.2: что добавлено в `ddai-fly`

Обучение мухи живёт в `ddai-train` (см. его README); здесь — только то, что оно потребовало от самой мухи. Всё аддитивно:
поведение 7.1–7.3 и их тесты не менялись.

- **`bc`** — лосс поведенческого клонирования в пространстве логитов, общий для мухи и контролей (`ddai-controls`): 3-way
  direction (softmax), jump/hook/fire (sigmoid, вес положительного класса), aim (фон Мизес `-κ·cos(y-μ)`, `μ = atan2(S, C)`);
  **мягкие цели** (частоты элиты CEM, `soft_mix`), веса голов, маски голов (прицел — только когда хук или выстрел
  задуманы), вес шага (`0` = прогрев без лосса).
- **`decoder::decoder_logits` / `decoder_bc_loss_and_grad`** — привязанный по L/R декодер в логитах: прямой проход совпадает
  с `decoder_forward` (тест), а при жёстких метках и единичных весах градиенты совпадают с `decoder_loss_and_grad`.
- **`brain_bc`** — окно решений: энкодер → муха (запись) → декодер → лосс → `backward` → градиенты энкодера; регуляризатор
  активности (полоса на средний ритм типа) через `ExtraRateGrad`; переиспользуемые буферы (`BcWorkspace`); отдельный
  проход вперёд для оценки. Сверка с конечными разностями на реальном S — `tests/bc_step_real_graph.rs`.
- **`calibration`** — калибровка DN по реальным сценам вместо покоя (σ покоя всегда садится на `min_sigma`), с усреднением
  гомологов L/R (иначе ломается точная зеркальная симметрия декодера).
- **`bundle`** — один файл с мухой целиком (параметры мухи, энкодера и декодера, калибровка, **текст** brain-конфига,
  sha256 `.flyg`, **пороги решений jump/hook/fire** — формат v2, **`HookView`** — формат v3 (8.2b: `MaskedForHookHead` — голова хука видит наблюдение без собственного состояния хука; модель играется в два вида); файлы v1/v2 читаются) и `FlyBrainTemplate` (загрузить
  один раз, по мозгу на партию; тёплый покой считается один раз). `HeadThresholds` (`bc.rs`) использует `FlyBrain` при выборе argmax
  (`set_thresholds`); пороги подбирает `ddai-train` на валидации (по частоте нажатий учителя; у хука — по частоте старта). `EncoderParams::validate_shape(num_params,
  num_bins)` требует ровно `num_params × num_bins` усилений корзин.
  `brain_checkpoint.rs` (7.3) проверен: он не хранит параметры самой мухи (`a`/`b`/`theta` лежат в `checkpoint.rs`) и опирается на
  файл конфига по хэшу, поэтому для арены нужен единый файл.
- **Усиления по дальностным корзинам** (`RayGridConfig::learn_distance_gains`, `EncoderParams::bin_gain`, выключено по
  умолчанию = энкодер 7.3 бит в бит). Причина — разбор хука (E-005): энкодер 7.3 складывает четыре дальностные корзины луча с
  равными весами, а гауссовы корзины разбивают дальность (их сумма почти постоянна), поэтому «стена/фриз/соперник в 1 тайле»
  и «в 20 тайлах» неразличимы. Теперь у каждой пары (тип, канал) обучаемый вес на корзину (`backward_with_params`).
## Задача 3.5: `FlyProposer` — муха как предлагающая половина гибрида (`src/proposer.rs`)

`FlyProposer` реализует трейт `Proposer` гибридного мозга (`ddai_planner::hybrid`, D-041): один `decide()` `FlyBrain`
(≈ 0,6 мс на S, необученная) даёт распределение действий решения (`FlyBrain::last_decoded()` — вероятности голов направления,
прыжка, хука, огня и угол прицела), а `ddai_planner::hybrid::plans_from_distribution` превращает его в `K` планов в кодировке
планировщика (`docs/research/orig-plan.md` §1.1): первый — argmax-план (самое вероятное направление на весь план, прыжок на
первом шаге, хук на две трети плана, молот со второго шага, абсолютный прицел), остальные — выборки тех же голов шаг за шагом
с удержанием ответа на три шага. Знак угла — из кольцевой конвенции энкодера `(cos a, −sin a)` в углы планировщика
`atan2(dy, dx)` (y вниз). Предложение — только кандидат: поиск оценивает его точным роллаутом наравне с остальными и берёт
только если он лучше. `untrained_fly_brain(flyg, brain_config, seed)` строит муху с параметрами по умолчанию (состояние до
обучения фазы 8); CLI-арена использует её для `hybrid = { proposer = "fly" }` (`configs/arena/e003-fly.toml`) — проводка и
цена, **силы у необученной мухи нет**. Зависимость `ddai-fly → ddai-planner` односторонняя (планировщик мухи не знает).

**Задача 3.7a (D-080): цена предложения.** `Proposer::work_units` у `FlyProposer` — цена одного `propose` на часах работы арены в ти-тиках: `proposal_tee_ticks` = `nnz × substeps × FLY_TEE_TICKS_PER_MEGA_SYNAPSE_STEP / 10⁶` (граф S: 500 ти-тиков ≈ 0,63 мс при 1,25 мкс); живой бот считает стенное время и цену не читает. Метод замера и таблица — `tests/fly_proposal_cost.rs` и E-012 §1 (`cargo test -p ddai-fly --release --test fly_proposal_cost -- --ignored --nocapture`), предварительно (load average 18–28, тихое ядро — после 8.2b).

## Задача 7.2b: батчевый бэкенд обучения (`src/batched/`, `src/brain_bc_batched.rs`)

7.2 параллелит обучение **по последовательностям**: каждая из B последовательностей на каждом подшаге заново читает весь CSR
(индексы и веса), и на M это даёт ≈ 330–450 sample-steps/с на 8 потоках — M необучаема. Здесь состояние всего батча лежит как
`[N][NB]` ячеек по 8 линий (`NB = ⌈B/8⌉`), поэтому индекс и вес каждого ребра читаются **один раз за подшаг на все линии**, а
умножения-сложения идут по линиям векторным кодом. Потоки делят **нейроны** (последовательные блоки строк — «чанки»), а не
последовательности (барьер на каждый подшаг: 256 параллельных регионов на шаг обучения). 7.2 остаётся эталоном: `train_step`, инференс 7.1 и результаты по одной последовательности не менялись.

Единица измерения везде — как в 7.2: **sample-step = одно решение одной последовательности** (4 подшага), вперёд + назад.
(В «13–18 тыс.» фазы 0 считались *подшаги*; в решениях это 3,3–4,5 тыс. на 0,5M рёбер. **Цель 7.2b — «M ≥ 5 тыс. решений/с на 8 потоках»**, то есть выше прогноза самой фазы 0; D-064.)

### Устройство

- **Раскладка.** `[N][NB][8]` — `f32`-ячейки по 8 линий (`[f32; 8]`, цикл по константной длине: LLVM векторизует сам — SSE2 на
  штатной цели, AVX2 под `-C target-cpu=x86-64-v3`; **ни `unsafe`, ни интринсиков, ни target-фич**). Буферы выровнены по
  64 байтам (смещение выбирается по адресу аллокации). Ядра берут по `G = 8` ячеек (64 линии) за проход, остаток — 4, 2, 1;
  `G` ячеек-аккумуляторов живут в регистрах, пока цикл идёт по рёбрам нейрона.
- **Чанки.** Строки режутся на смежные блоки одинаковой «стоимости» (рёбра входящие + исходящие + 8 на строку,
  `DEFAULT_CHUNK_COST = 8192`: M ≈ 116 чанков, S ≈ 15). Каждый чанк владеет своими строками и своими частичными суммами
  (`b`, `θ`, `a` и градиента входов); частичные суммы складываются **в порядке чанков**. Границы зависят только от графа →
  результат побитово один и тот же при любом числе потоков.
  (Пробовал резать батч ещё и на независимые «колонки» по 8 линий, чтобы поток, ждущий барьер одной колонки, брал чанк другой,
  — на загруженной машине выигрыш не воспроизвёлся: при чередовании A/B одна колонка выиграла 3 пары из 4, а процессорное время
  у колонок было вдвое больше; убрано.)
- **Перенумерация нейронов.** Внутри плана нейроны идут в порядке `(тип, исходный индекс)` — нейроны одного типа подключены
  похоже, и строки, из которых гатерит чанк, пересекаются сильнее: на M различных пресинаптических строк на чанк 38 % от числа
  рёбер вместо 64 % (≈ −25 % процессорного времени на шаг). Всё, что пересекает API (начальные состояния, входы, выходы, краны
  `ExtraRateGrad`, средние по типам), отображается на границе; порядок нейронов внутри типа — исходный, поэтому суммы по типу
  идут в прежнем порядке.
- **Что пишется при прямом проходе.** Для обратного нужны `r` (ритм, который вёл подшаг — для `dL/dα`) и `X = V∞ − V_prev`
  (для `dL/dτ`): два `f32` на нейрон, линию и подшаг (до 7.2c было три: ещё и `f'(V)`, см. «Задача 7.2c»). `V` — одно катящееся
  состояние, а не запись (у 7.2 пишутся `V`, `r`, `V∞`); `f'(V)` обратный проход **пересчитывает из `r`**
  (`1 − (r/r_max)²`), а точные значения для глубокого насыщения прямой проход пишет в разреженный список.
- **Обратный проход.** По строке `j` (транспонированный CSR): `dL/dr_j` — гатер `δ` следующего подшага по исходящим рёбрам `j`,
  плюс краны (`dn_rates` читаются с весом 0,5 в двух подшагах решения — ровно как в 7.2, плюс `ExtraRateGrad`), затем цепное
  правило и адъюнкты `b`/`θ`/входов. **`dL/dα` подшага `l+1` копится прямо тут**, из тех же строк `δ` (они только что
  прочитаны, лежат в L1) против `r_j` — второго случайного гатера по пресинаптическим ритмам, который есть у постмажорного
  прохода по рёбрам, нет. `dL/dα` подшага 0 (против `f(V_init)`) считает проход «перед первым подшагом», он же даёт `dL/dV_init`.
  Суммы по линиям `dL/dα` берутся один раз в конце (по линиям копятся векторы).
- **`tanh` и `1/cosh²`.** libm-овские `tanhf`/`coshf` скалярные и по стоимости сравнимы со всей работой по рёбрам. Вместо них —
  нечётная рациональная аппроксимация 13/6 (коэффициенты как в Eigen/TensorFlow; максимальная относительная ошибка `1,3·10⁻⁷`,
  ≈ 1 ulp) для `f`, и `f' = (1−t)(1+t)`, `t = r/r_max` (с 7.2c — из записанного `r`, а не из того же `tanh`); ячейки с
  `V/r_max > 1,5` (глубокое насыщение, редко) прямой проход досчитывает через `4q/(1+q)²`, `q = e^{−2x}` — без вычитания близких
  чисел, как просило ревью F7a задачи 7.2 — и записывает как «заплатки» (`kernels::PatchStore`), которые обратный проход
  накладывает поверх пересчитанного `f'`. Измерено против `f64` по плотной сетке (`f'` пересчитан из `r`, заплатки наложены):
  `f` — `3,5·10⁻⁷`, `f'` — `≤ 2,6·10⁻⁶` относительно; NaN остаётся NaN, `V ≤ 0` даёт ровно 0
  (`src/batched/lanes.rs`, тесты там же).
- **Субнормалы.** Адъюнкты затухают геометрически; без защиты они уходят в субнормальный диапазон, где каждая векторная
  инструкция идёт через микрокод. Адъюнкты `< 1e-30` по модулю обнуляются (на 7 порядков ниже шума `f32` любого значимого
  градиента). В прямом проходе субнормалов в записях не наблюдалось (проверено счётом на M со случайными входами).
- **FMA — только если сборка его включила.** `lanes::fma` = `f32::mul_add` при `cfg(target_feature = "fma")` и `a*b+c`
  иначе (без фичи `mul_add` — вызов libm, на порядок медленнее). Битовая воспроизводимость — в пределах одной конфигурации сборки.
- **Ассемблерные тонкости (почему часть функций `#[inline(never)]`).** LLVM векторизует аккумуляторы, зависящие через
  итерации цикла (`gather_acc`, `lane_dot_n`, `lane_sum`, `axpy8`), только если их потребители тоже векторизуемы; встроенные в
  длинную функцию с ветвями (вход, краны) они остались скалярными (`mulss`/`addss`, 8·G регистров) — вынос за границу вызова
  вернул векторный код. Элементные участки (`fwd_row_elementwise`, `bwd_row_elementwise`) — циклы по плоским `f32`-срезам;
  форма селектов важна (вложенное `if v<=0 {0} else if v.is_nan() {v} else {x}` для двух выходов заставляло LLVM оставить цикл
  скалярным).

### API

- `BatchedEngine::new(&model)` (или `with_plan(BatchedPlan::new(&model).with_parallel_threshold(..))`), `forward(&model, &[BatchedSeqInput], &BatchedForwardOptions)
  -> Result<(), MemoryCapExceeded>`, затем `dn_rates(b, t, out)` / `type_mean_rates(b, t, out)`, затем
  `backward(&model, &[BatchedSeqGrad], want_v_init_grad) -> BatchedGradients { grad: ParamGradients, grad_inputs[b][t][k],
  grad_v_init[b] }`. Последовательности могут быть разной длины (короче — без лосса после конца). Параметры модели между
  `forward` и `backward` менять нельзя.
- `train_step_batched(&model, &mut engine, &[Sequence], cap)` — вставка вместо `train_step` (те же `Sequence`/`BatchGradients`).
- `brain_bc_batched_step` (`src/brain_bc_batched.rs`) — батч окон BC: энкодер → муха (пакетом) → декодер → лосс →
  пакетный BPTT → градиенты энкодера; всё, что делает `brain_bc_step`, включая регуляризатор активности. Градиент мухи уже
  суммирован по батчу, градиенты энкодера/декодера — по окнам (вызывающий сам складывает в нужном порядке).
- `TrainBackend::{PerSequence, Batched}` (serde `"per-seq"` / `"batched"`).

### Память и чанки окна BPTT (критерий 4)

Записи — `T·S·N·B·2·4` байт (до 7.2c — `·3·4`, с `f'(V)`): M, B = 64, T = 32, S = 4 → **0,84 ГБ** (измерено после 7.2c: пик RSS
975 МиБ против 1 366–1 430 до неё; B = 128 в 7.2b → 2,70–2,76 ГиБ; S, B = 64 → 0,31 ГиБ в 7.2b). `BatchedForwardOptions::memory_cap_bytes` ограничивает то, что движок **держит** после вызова `forward` и следующего за ним
`backward`: буферы рабочего набора (записи, адъюнкты, входы, краны, контрольные точки) и копии чисел модели, **не** план
(индексы/веса графа, `memory_bytes()` их включает) и **не** то, что выделяет вызывающий (закодированные признаки, возвращаемые
`grad_inputs`, логиты). `estimate_memory` считает набор для данной формы батча на *свежем* движке заранее, до аллокаций, и
отказывает `MemoryCapExceeded`, если не помещается даже сегмент в одно решение; `forward` учитывает ещё и то, что движок уже
держит от более крупного вызова: если оставшиеся буферы вместе с набором этого вызова превысили бы лимит, они освобождаются
(и выделяются заново нужного размера), иначе переиспользуются (в тренере форма батча постоянна — переаллокаций нет). Без лимита
буферы только растут. При росте буфера старый освобождается до выделения нового. Сегмент подбирается сокращением
(`seg - 1` или `¾·seg`) до первого, при котором набор помещается, — он может быть короче максимально возможного (до ¼);
поиска точного максимума нет. Если окно целиком не влезает,
BPTT режется по времени **точно** (градиентный чекпойнтинг): прямой проход хранит `V` только на границах сегментов, обратный
пересчитывает запись каждого более раннего сегмента прямо перед тем, как она понадобится, перенося адъюнкты через границу.
Градиенты **побитово равны** неразрезанным (повторяется то же самое в том же порядке; тест `chunked_bptt_segments_give_bitwise_identical_gradients`
и на реальных S/M), цена — один лишний прямой проход по всем сегментам, кроме последнего.

(≈ 6,4 на ядро при 8 ядрах), ≈ 68 ГБ/с случайного операнд-трафика из L2/L3 (≈ 8,5 ГБ/с на ядро) и ≈ 9 ГБ/с записей в DRAM.

ребро·линию, 26 нс на «посещение» ребра сразу для 64 линий), v3 ≈ 770 = 7,9 Гфлоп/с и 10,5 ГБ/с. Для сравнения, микробенчмарк
одного голого гатера (`gather_acc` на случайном графе того же размера, B = 64) даёт ≈ 0,26 нс/ребро·линию (≈ 15 ГБ/с), то есть
ядро работает на ≈ 43 % (штатная сборка) – 70 % (v3) от потолка чистого гатера; остальное — элементные части
(активация, цепное правило), скалярное произведение `dL/dα` и записи. DRAM-потолок записей не лимитирует: измеренный `STREAM triad` на этой машине (под
нагрузкой) — 7,8 ГБ/с на 1 поток и 47 ГБ/с на 8 (с учётом `write-allocate` ×1,33), записям нужно ≈ 9 ГБ/с. Вывод: упор —
случайный доступ к L2/L3 (латентность/пропускная способность на ядро) и число свободных ядер, а не арифметика (≈ 7–25 % пика
ядра по флопам) и не DRAM.

**Что ещё пробовалось (все варианты с замерами на M, 1 поток, процессорное время).** Группы по `G` ячеек: `G = 8` на ≈ 12 %
быстрее `G = 4`, `G = 2` заметно хуже (мало ячеек на ребро — накладные расходы на индекс). Перенумерация нейронов по типу:
≈ −25 % CPU (различных строк на чанк 38 % от рёбер вместо 64 %; RCM — 51 %, хуже). `tanh` и `1/cosh²` через `exp`: заменены рациональной формой (активация была ≈ 44 % прямого прохода на S). Вынос `dL/dα` в проход по рёбрам post-major
(как в 7.2) против слияния с транспонированным гатером: слияние убирает второй случайный гатер (`dL/dα` была ≈ 50 % обратного
прохода). Принудительная префетч-инструкция недоступна без `unsafe` (`_mm_prefetch` небезопасна даже на базовой x86-64).

### Ассемблер горячих циклов (критерий 1)

Проверять надо **собранный бинарник**, а не `--emit asm` библиотеки: релиз идёт с `-C linker-plugin-lto`, и ассемблер крейта
до ThinLTO — не тот код, что в итоге выполняется (в нём векторизации ещё нет). `objdump -d -C target/release/deps/batched_throughput-*`,
счёт packed (`*ps`) и scalar (`*ss`) FP-инструкций в функции:

| функция | штатная сборка (SSE2): packed / scalar | v3 (AVX2+FMA) |
|---|---|---|
| `gather_acc::<u16, 8>` (цикл по рёбрам, прямой и обратный гатер) | 16 `mulps` + 16 `addps` / 0 | 8 `vfmadd231ps ymm` / 0 |
| `lane_dot_n::<4>` (`dL/dα`, 4 ребра за раз) | 128 / 0 | 64 / 0 |
| `lane_sum`, `axpy8` | 16 / 0 и 4 / 0 | 8 / 0 и 1 / 0 |
| `fwd_row_elementwise` (обновление `V`, `tanh`; без `f'` с 7.2c) | 52 / 14 (было 63 / 19 с `f'`) | 228 / 14 (пересчитано в 7.2c, иначе, чем 124 в 7.2b) |
| `bwd_row_elementwise` (цепное правило) | 5 / 5 | 40 / 5 |

(`scalar` в элементных функциях — эпилог цикла для хвоста, не кратного вектору; в `saturated_derivatives` — редкий путь,
в `bwd_chunk` — краны выходных нейронов.) Внутренний цикл `gather_acc::<u16, 8>`, штатная сборка: 16 × (`movups` → `mulps` →
`addps`) на ребро плюс индексная арифметика; из-за 16 аккумуляторов-`xmm` (регистров ровно 16) аллокатор гоняет их `movaps`-ами
между регистрами — на счёт CPU-времени `G = 8` всё равно ≈ 12 % лучше `G = 4`, у которого цикл чистый. Под v3 цикл чистый:

```asm
movzwl (%rdi,%rbx,2),%eax ; imul %r11,%rax ; lea ...        ; индекс строки * NB + g0, две проверки границ (cmp/ja)
shl    $0x5,%rax
vbroadcastss (%rdx,%rbx,4),%ymm8                              ; вес ребра на все линии
vfmadd231ps  (%r8,%rax,1),%ymm8,%ymm0                         ; 8 ячеек × 8 линий = 64 линии, 8 независимых цепочек
vfmadd231ps  0x20(%r8,%rax,1),%ymm8,%ymm1
...                                                           ; (ymm2 … ymm6)
vfmadd231ps  0xe0(%r8,%rax,1),%ymm8,%ymm7
inc %rbx ; cmp %rbx,%rsi ; jne <начало цикла>
```

Хрупкость векторизации (почему код написан так): LLVM векторизует аккумуляторы, зависящие через итерации цикла, только если
их потребители векторизуемы — встроенные в длинную функцию они остались скалярными, поэтому `gather_acc`, `lane_dot_n`,
`lane_sum`, `axpy8` — `#[inline(never)]`; форма `select` в активации и три-четыре массива в одном цикле тоже решали (см. комментарии
в `lanes.rs`). Регрессию скалярного кода ловит страховка (D-064):
`cargo test --release -p ddai-fly --lib vectorisation_guard` — ядра `gather_acc::<u16, 4>`/`<u16, 8>` и `lane_dot_n::<4>` против
строго последовательных (без fast-math — компилятор не вправе переставлять и векторизовать) скалярных сумм на тех же данных
в том же процессе; сравниваются лучшие из 31 коротких замеров (отношение, а не абсолютное время — устойчиво к загрузке
машины; до 3 попыток на тест). Измерено на штатной сборке: `G = 4` ≈ 2,9–3,0× (порог 1,8×), `lane_dot_n` ≈ 3,2× (порог 1,8×),
`G = 8` ≈ 1,4–1,5× (16 аккумуляторов занимают все регистры `xmm`; порог 1,0× ловит только «медленнее скалярного»); под v3 —
≈ 5× / 7× / 4×. Проверено на «мутанте» (поэлементный `black_box` в `gather_acc`: оба теста `gather_acc` падают, 0,49× и 0,23×).
**С 7.2c тесты идут в обычном `cargo test` и в CI**: `[profile.dev.package.ddai-fly] opt-level = 3` в корневом `Cargo.toml`
(как у `ddai-jsmath`; `opt-level` не меняет значений float; под opt-level 0–1 циклы не векторизуются и тесты бы упали) и
сняты `cfg_attr(debug_assertions, ignore)`. В dev-профиле: `G = 4` — 2,7×, `G = 8` — 1,7×, `lane_dot_n` — 3,1×; с выключенными
векторизаторами (`RUSTFLAGS="-C llvm-args=-vectorize-slp=false -C llvm-args=-vectorize-loops=false"`) падают все три. Вручную
в release и с `objdump` — `tools/vectorisation/check.sh` (те же тесты + `objdump` тестового бинаря: в `gather_acc` обязаны быть упакованные
`mulps`/`addps`/`vfmadd*ps` и ≤ ¼ скалярных; штатная сборка — 16 и 32 упакованных на `G = 4`/`8`, v3 — 4 и 8 `vfmadd231ps ymm`, 0 скалярных).

### Обучающая сборка под x86-64-v3 (опционально, D-064)

`tools/train-v3-build.sh` собирает `ddnet-ai` с `RUSTFLAGS="-C target-cpu=x86-64-v3"` в **отдельном** каталоге
(`target/train-v3`, переопределяется `TRAIN_V3_TARGET_DIR`) и кладёт бинарь `ddnet-ai-train-v3`: ×1,45 на ядро на ядре
батчевого обучения (выше). Это **только обучение**: по умолчанию остаётся обычная сборка, `target-cpu` нигде не закоммичен;
бинарь v3 отказывается выполнять всё, кроме `train` и `fly` (проверка `TRAIN_ONLY_BUILD` по `cfg!(target_feature = "avx2")` в
`ddnet-ai/src/main.rs` со списком разрешённых команд — `play`, `record`, `web`, арена, трассы по умолчанию запрещены, как и любая
будущая команда); скрипт сам проверяет AVX2+FMA в `/proc/cpuinfo` (иначе SIGILL). **Побитовая воспроизводимость — только
внутри одной конфигурации сборки**: FMA меняет округление, так что v3 и базовая сборка дают результаты, отличающиеся на уровне
допуска «батч против 7.2» (демо S, 300 шагов: итоговый лосс 0,7891 у v3 против 0,7869; отрыв 3,9990 против 4,0016). Возобновлять
прогон нужно той же сборкой, которой он начат. Чекпойнты читаются любой сборкой (инференс 7.1 батчевый путь не использует).

### Что не проверено и риски

- Цель по M (≥ 5 тыс. на 8 потоках) на этой машине не достигнута и не измерена в тихих условиях (см. выше: свободных ядер 1,2–4);
  оценки для 8 свободных ядер — проекция по процессорному времени одного ядра.
- Обучаемость M целиком (кривая BC до осмысленной точности) не проверялась — дымовой прогон только проверяет проводку и память.
- Эквивалентность и чанки BPTT проверены на реальных S/M; `f64`-эталон — на случайных входах, а не на входах реального энкодера
  (окна BC сверены с путём 7.2 через `brain_bc_step`).
- Тонкое место — векторизация (см. выше): изменение формы горячих циклов или смена тулчейна может вернуть скалярный код.
  Страховка (`vectorisation_guard`) с 7.2c идёт в CI (`cargo test`, dev-профиль ddai-fly на opt-level 3), `tools/vectorisation/check.sh` —
  вручную в release с `objdump`; порог для `G = 8` на штатной сборке слабый (1,0×).
- **Масштабирование по потокам зависит от свободных ядер.** Подшаг — рандеву всех потоков пула (256 регионов на шаг обучения);
  когда машина насыщена, рандеву стоит миллисекунд и 8 потоков дают столько же, сколько 1 (последний прогон при load 12–13:
  M, B = 64, T = 16, потоки 1/2/4/8 — 392/454/425/373 sample-steps/с, CPU-время шага 2,2–2,4 с во всех случаях). Выбирайте
  `threads` по числу реально свободных ядер. 7.2 в этом смысле устойчивее (окна независимы, барьеров нет), но на порядок менее
  эффективен по CPU. Пробный (не вошедший) эксперимент: восемь независимых односячеечных движков по одному на поток, без
  барьеров, на M при load ≈ 8 дали 860–1 010 sample-steps/с против 578 у деления по нейронам, ценой ×2 процессорного
  времени; пробная реализация «колонок» внутри одного пула rayon (вложенный параллелизм) была хуже одной колонки.
  Если машина останется такой загруженной, это следующий кандидат.

## Задача 8.2b: вид собственного хука (`bc::HookView`)

Копирование состояния (ревью 8.2, F2): голова хука, у которой на входе `own_hook`, учит «хук ⇔ мой хук уже выпущен». `HookView::MaskedForHookHead` в чекпоинте v3 значит: голова хука
обучена и играет на наблюдении с собственным состоянием хука, скрытым (`bc::mask_own_hook`: `hook_state = IDLE`; больше ничто в энкодере его не читает), остальные головы — на полном;
`bc::combine_hook_view` берёт `hook` из второго прохода, остальное из первого. Играет это `ddai_fly::two_view::TwoViewBrain` (две мухи, два состояния; автономный мозг — `FlyBrainTemplate::instantiate_played`); предлагателем гибрида такая муха ставится через
`FlyProposer::from_template` (вероятность хука — из второго вида). Арена и живой бот (`--fly-bundle`) идут одним путём; одним видом такой чекпоинт играть нельзя (F1 ревью 8.2b). Множитель `StepTargets::hook_scale` усиливает лосс только головы хука на отдельных решениях (старт/отпускание).

## Задача 7.2c: ещё быстрее батчевое обучение, хвосты 7.2b (`src/batched/{kernels,lanes,mod,split,cores}.rs`)

Что сделано и как измерено — в `docs/EXPERIMENTS.md`, E-013; решение — D-081. Здесь — устройство и команды.
**Путь по умолчанию не менялся**: `train_step` (7.2) и инференс 7.1 побитно те же, что в `main` (хэш выходов `step_decision` и градиентов
`train_step` на S и M до/после — совпал); батчевые градиенты на S/M (B = 24 / 16, случайные входы) побитно совпали с батчевыми
`main` (при малых ритмах `1 − t²` из пересчитанного `t` округляется в тот же `f32`; при больших активностях побитового совпадения
нет, только допуск 7.2b ниже); результаты побитно не зависят от числа потоков.

- **Страховка векторизации в CI.** `[profile.dev.package.ddai-fly] opt-level = 3` и снятый `ignore` с `vectorisation_guard` (см. выше
  «Ассемблер горячих циклов»); путь в докомментарии `kernels.rs` исправлен на `tools/vectorisation/check.sh`. Пересборка ddai-fly на
  opt-level 3 — ≈ 20 с (load 30); под opt-level 1 два из трёх тестов падают (`G = 4` и `lane_dot_n`) — страховка работает, а не
  проходит вхолостую.
- **`f'(V)` не пишется** (`PatchStore`, `derivative_from_rate_row`, `saturated_derivatives`). Запись на нейрон, линию и подшаг:
  `r` и `X` (было ещё `f'`): −⅓ записи (M, B = 64, T = 32: 1,25 → 0,84 ГБ; пик RSS 1 366 → 975 МиБ). Обратный проход считает
  `f' = (1 − t)(1 + t)`, `t = r/r_max`, из записанного `r` (ровно 0 там, где `r = 0`), а для глубокого насыщения (`V/r_max > 1,5`),
  где эта формула теряет малые производные на вычитании, прямой проход пишет **точные** `4q/(1+q)²` в разреженный список «заплаток»
  на чанк (ключ — плоский индекс линии, порядок обхода тот же, что у обратного прохода, потому он читается курсором). На типичных
  данных список пуст; слот заплаток хранится разреженно, пока заплатано не больше половины его линий, и плотно (весь `f'` слота,
  пересчитанный из `r` с наложенными заплатками) иначе — то есть ≤ 4 Б на линию и слот, как прежний плотный массив, даже когда всё
  насыщено. Эта граница входит в `estimate_memory` (`patch_bytes`) и в лимит `memory_cap_bytes` (оценка шага M B = 64 T = 32
  остаётся 1,25 ГБ, фактически держится 0,84 на типичных данных); излишек ёмкости `Vec` после роста возвращается (`trim`), а
  вызов с меньшим лимитом освобождает хранилища вместе с остальными буферами. Тест
  `fully_saturated_worst_case_stays_within_the_memory_cap` (400 нейронов, B = 64, T = 16, S = 4, всё насыщено: держит ≤ лимита;
  мутации «без плотного перехода» и «плотный слот без заплаток» краснят его и `deep_saturation_…`). Допуск 7.2b сохранён: таблицы `batched_real_graph` на S и M воспроизвелись
  (S: `a` 1,6·10⁻⁶ / 2,3·10⁻⁶ / 1,2·10⁻⁶ от масштаба группы против 7.2 / `f64` / 7.2 против `f64`; M — 9,8·10⁻⁷ / 5,1·10⁻⁷ /
  9,8·10⁻⁷), `f'` на сетке против `f64` — `≤ 2,6·10⁻⁶` относительно. Новые тесты (`batched_equivalence.rs`):
  `saturated_regime_…` (24 графа, 5–95 % состояний насыщено, в одном 8-линейном окне есть и насыщенные, и нет) и
  `deep_saturation_derivatives_are_exact` (всё на `V/r_max` 4–8, градиенты ×10⁵) — мутация «заплатки не накладываются» красит
  второй (первый к ним нечувствителен по построению: малые `f'` не влияют на сумму), сдвиг ключа заплаток красит оба.
  **Скорость**: ≈ 0 % на штатной сборке (медиана 4 218 → 4 191 мс CPU на шаг, 18 пар) и 3–9 % на v3 (3 095 → 3 016 медиана,
  2 943 → 2 680 минимум); главное — память (см. E-013).
- **Перестановка нейронов для локальности — не принята.** Перебраны семь семейств порядков (барицентр и minhash внутри типа и глобально,
  порядок самих типов) и k-means-подобное перераспределение нейронов по чанкам (число различных строк-источников на чанк на M:
  42,6 % → 34,1 % от числа рёбер, приёмников 36,7 → 29,7 %, чанки при этом перекошены). Внутри типа порядок ничего не меняет
  (42,6 %), а любой «глобальный» порядок хуже (50–65 %). Реальное время k-means-раскладки (отдельный план, рёбра в строке в прежнем
  порядке, поэтому по линиям результат тот же): 1 поток, M, B = 64, T = 8, 30 пар — медиана CPU 947 против 960 мс (в пределах
  шума ±10 % при load 10–33), минимум 743 против 790; вариант с рёбрами по физическому порядку — то же (24 тройки, 1 035 против
  1 062). То есть выигрыш ≤ 2–3 % и не отличим от шума, а побитово-тождественным он быть не может: чанки определяют группировку
  сумм `dL/d{a,b,θ}`, при другом составе чанков они суммируются иначе. Код не оставлен (см. E-013).
- **Стоп-градиент burn-in (опционально, по умолчанию выключен).** `BatchedForwardOptions::no_grad_decisions = n`: первые `n` решений каждой
  последовательности идут только вперёд (без записи, `forward_prefix`), состояние на решении `n` — константа; градиентов через них нет
  (параметры не получают градиент от их подшагов, `grad_inputs` там нули, `grad_v_init` нули; `grad_dn`/`extra_taps` этих решений
  игнорируются), `dn_rates`/средние по типам для них считаются. Запись, обратный проход и пересчёт сегментов покрывают только
  `[n, T)`. Для обучения: `[fly] batched_stop_grad_decisions = n` (ставить равным `[train] burn_in`; `brain_bc_batched_step` читает его
  у движка, `BatchedEngine::with_stop_grad_decisions`) — первые `n` решений **каждого** окна считаются небитыми целями (без потерь,
  градиента декодера и регуляризатора активности), в том числе в окне, начинающемся с начала последовательности (там при полном
  BPTT эти решения оценивались). Семантика градиента меняется: в энкодер и коннектом ничего не течёт из burn-in через состояние.
  Тесты: градиент равен 7.2 BPTT хвоста от состояния после префикса, посчитанного путём 7.2 (24 графа × 4 длины префикса, включая
  префикс ≥ длины); побитово воспроизводимо (потоки, сегменты); прямая сторона шага BC побитово та же (потери, логиты, градиент
  декодера на реальном S); тренер на S. Скорость (M, B = 64, T = 32, 1 поток, burn-in 6 из 32): −10 % CPU штатная сборка (3 788 против 4 191 мс
  медиана; минимум 3 475 против 3 800), −15 % на v3 (2 550 против 3 016); burn-in 8: −16 % (штатная, 8 пар, load 11–33); пик RSS
  975 → 827 (6) / 777 МиБ (8).
- **K независимых под-движков** (`BatchedEngine::with_subengines(k)`, `[fly] batched_subengines = K`, `batched/split.rs`). Батч режется
  на `K` групп из целых 8-линейных ячеек; у каждой группы свой `BatchedEngine` и свой пул rayon из `threads / K` потоков (размер
  берётся из пула, в котором вызван `forward`), группы идут одновременно без барьера между ними; градиенты складываются по
  группам по порядку. По линиям (`dn_rates`, средние, `grad_inputs`, `grad_v_init`) — побитово то же, что у одного движка;
  `dL/d{a,b,θ}` отличаются порядком суммирования f32 и зависят от `K`, но не от числа потоков (тест `subengines_are_bitwise_…`).
  Лимит памяти делится поровну. Групп не больше потоков вызывающего пула: при `K` больше числа потоков группы делят `threads`
  однопоточных пулов по кругу (результат тот же, он зависит только от `K`). **Возобновление**: `K`, `backend` и стоп-градиент меняют
  градиент, поэтому `train run` отказывается возобновлять прогон с другими значениями, чем в `config.toml` каталога (флага
  `--allow-config-change` в этой базе нет; тест в `ddai-train/tests/runner.rs` и юнит-тесты `resume_checks`); `fly cores` напоминает об этом.
  Цена — ЦП: каждое ребро читается на `K` раз чаще. Таблица (M, B = 64, T = 32, штатная сборка,
  потоки × K; load 11–18):

  |---|---|---|
  | 1 × 1 | 464 | 3,90 |
  | 3 × 1 | 616 | 4,44 |
  | 4 × 1 | 628 | 4,05 |
  | 4 × 2 | 724 | 4,34 |
  | 4 × 4 | 904 | 4,89 |
  | 8 × 1 | 503 | 3,97 |
  | 8 × 2 | 592 | 4,61 |
  | 8 × 4 | 821 | 5,54 |
  | 8 × 8 | 914 | 7,80 |

  Другой набор (T = 16, load 16–30): 4 × 2 — 892, 4 × 4 — 906, 3 × 1 — 661, 8 × 1 — 606, 8 × 8 — 978. На загруженной машине группы выигрывают
  в 1,2–1,8 раза по стене (при 1,1–2× ЦП); на машине, где потокам хватает ядер, выигрыша нет, а ЦП растёт — по умолчанию K = 1.
- **Выбор `threads`.** `ddnet-ai fly cores` (`ddai_fly::batched::cores`): две пробы `/proc/stat` с окном 1 с → число свободных ядер;
  рекомендация (`advise`) — тихая машина (≥ 6 свободных): один движок, `threads` = свободные ядра, не больше 6 (потолок `train`); загруженная:
  `threads` = свободные ядра, округлённые вверх до чётного (минимум 2, не больше 6), `batched_subengines = threads / 2` (по два потока
  на группу — по CPU выгоднее, чем по потоку на группу, которая быстрее по стене, но платит ×1,25–2 ЦП). Запускать до обучения. Свободные ядра — **хоста** (счётчики и число CPU из одного `/proc/stat`); число CPU процесса
  (`available_parallelism`: affinity/cgroup) только ограничивает рекомендацию. Без
  `fly cores`: `threads` = число свободных ядер (смотреть `uptime`/`top`: «8 − load average», но не меньше 2); больше — не быстрее,
  барьер подшага ждёт самого медленного потока.

  только v3 + стоп-градиент (оба опциональны); измерить на 8 свободных ядрах не удалось (load average машины 7–39 весь сеанс).

  `cargo test -p ddai-train --release --test fly_batched`; замеры — `batched_throughput` с `FLY_BENCH_SUBENGINES=1,4`,
  `FLY_BENCH_STOPGRAD=0,6`, `FLY_BENCH_CHUNK_COST=…` (список через запятую; в строке вывода `sub=` и `nograd=`); `ddnet-ai fly cores`.
- **Что не проверено и риски 7.2c.** (1) Все замеры — на машине с load average 7–39 (свободных ядер 1–4), поэтому числа — медианы и минимумы
  по чередующимся парам, разброс ±5–10 %; на 8 свободных ядрах ничего не мерено (проекция). (2) Заплатки `f'` теперь в
  `estimate_memory`/лимите (≤ 4 Б на линию и слот), но оценка шага остаётся такой же консервативной, как до 7.2c: экономия 0,84 против
  1,25 ГБ видна в факте (RSS), не в оценке. (3) Стоп-градиент меняет градиент (не только скорость) — включать осознанно; влияние на качество обучения не
  исследовалось. (4) Под-движки: порядок суммирования зависит от `K` — возобновлять прогон с тем же `K` (как и с той же сборкой).
  (5) `advise` откалиброван по замерам этой машины (8 vCPU EPYC-Rome); правило «два потока на группу» — компромисс между стеной и ЦП.
  (6) Слияние с 8.2b: `brain_bc_batched_step` читает `engine.stop_grad_decisions()` — если 8.2b добавит свой вызов, пройти
  мимо этого нельзя (но own-hook через батчевый путь пока не поддержан, см. D-064).

## Поток для веб-панели (задача 7.4)

`viz.rs` — бинарный кадр `DFLY` на решение (групповые частоты по нейропилю и типу, лучевая сетка «глаза» по каналам, z-оценки DN,
логиты и действие, флаг «предложение мухи сыграно») и JSON-описание его раскладки; формат — `docs/formats.md` §27.

- **Без зрителя — ноль работы.** `FlyBrain::decide` про поток не знает: он оставляет `last_*`, а кадр строит `Brain::viz_frame(tick)`
  (`FlyBrain::viz_frame_with` для гибрида), которую драйвер зовёт **только пока кто-то смотрит**. Единственное, что добавлено в
  `decide`, — запись выбранного действия и счётчик решений (два сохранения). Решения от потока не зависят: тест
  `pulling_frames_never_changes_a_decision` (60 решений с сэмплированием, каждое с кадром: действия, частоты DN, вероятности и
  **всё состояние `V`** равны побитно) и целая игра на арене (`ddnet-ai/tests/fly_watch.rs`: хэш решений мухи и результат равны у
  `fly` и у `hybrid:fly` в детерминированном режиме).
- **Аллокации.** `tests/no_alloc_brain.rs`: `decide` + кадр на каждое решение (и через `dyn Brain`, с прореживанием) — 0 аллокаций.
  Буфер кадра выделяется в `FlyBrain::new`.
- **Стоимость, замер** (`tests/viz_overhead.rs`, `--release`, граф S, четыре одинаковые мухи, одно и то же решение времится на
  каждой подряд в меняющемся порядке; машина общая и занята, три прогона по 12 000 решений на режим):
  `decide` ≈ 670–710 мкс (медиана); «поток включён, зрителя нет» (`if watched { viz_frame }` с `watched = false`, как у бота) —
  **+0,19 / −0,35 / −0,02 %** к медиане при шуме двух одинаковых режимов −0,44…+0,11 %; «зритель смотрит, кадр на каждое решение»
  (худший случай; бот строит по одному на два решения) — **+0,7…+1,0 %**, то есть 5–7 мкс на кадр. Кадр S — 1524 байта (≈ 19 КБ/с при 12,5 Гц).
- Группы: `VizLayout::build` (классификация по роли, суперклассу и префиксу имени типа; тест на реальных именах MaleCNS).
  Имя и хэш весов (`FlyBrainTemplate::load` запоминает `<запуск>/<файл>` и sha256 файла) показываются в панели, пути — нет.
- `FlyProposer` отдаёт тот же кадр с вердиктом поиска (`ProposalOutcome`: сыграно ли предложение, сколько раз и сколько всего решений).

CLI: `ddnet-ai fly watch --bundle <b> --arena <a> [--hybrid] [--opponent scripted] [--opponents 1] [--speed 1] [--games 0]` играет
арену в реальном времени с обученной мухой и отдаёт поток на сокет моста (`--bridge`, по умолчанию
`~/aiddnet/data/bot/fly-watch.sock`); `ddnet-ai web --bot-socket <он>` показывает его во вкладке «Муха».
