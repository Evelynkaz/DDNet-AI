# ddai-env

Задача 8.1. **Офлайн-арена оценки**: N игроков играют в «блок» на побитно точном мире сервера
(`ddai_physics::World<f32>`), каждый игрок — любой `ddai_brain::Brain` (скриптовый бот, планировщик, муха, позже гибрид
D-041). Арена — линейка для всего остального: поиска D-041 (1v1…1v5), обучения мухи (BC/DAgger, вехи F1–F3 в
`docs/PLAN.md` §0) и регрессий. Результаты **воспроизводимы** (тот же конфиг и сид — те же числа), **статистически
честны** (W:L:D:T и 95% ДИ Уилсона) и **быстры** (rayon по играм).

Команды (из корня репозитория, `source ~/.cargo/env`):

```bash
cargo build --release -p ddnet-ai
ddnet-ai arena list                                                       # арены и число «стоячих» клеток
ddnet-ai arena run --config configs/arena/smoke.toml --out /tmp/arena     # JSONL + summary.json + summary.md
ddnet-ai arena scenarios --check-reference                                # эталонные решения T1–T18
ddnet-ai arena scenarios --config configs/arena/scenarios.toml            # успех по мозгам
ddnet-ai arena scenarios --trace T9 --trace-brain planner                 # покадровая трасса + ввод как [[reference]]
```

## Модули

| Модуль | Что внутри |
|---|---|
| `arena` | `ArenaDef` (TOML) → `Arena`: карта (синтетическая из кода или файл с проверкой sha256), шаблонный `World<f32>`, «стоячие» клетки, спавн из сида; тег `train`/`holdout` |
| `sim` | общий цикл тика: решения по каденции, лаг ввода на клиента, счётчик нажатий `fire`, хэш решений, замер времени, один шаг физики |
| `game` | правила одной партии (порт `runGame` харнесса), 1vN, `GameReport` (одна строка JSONL) |
| `run` | партии условия параллельно (rayon), сид партии `g` = `base_seed + g`, раскладка 4-way: позиции меняются на нечётных партиях, порядок спавна обращается на партиях `g % 4 ≥ 2` |
| `report` | `ConditionSummary`, `RunSummary`, база пауз ВМ (D-045), русская markdown-таблица |
| `output` | прогон всего конфига: `<условие>.jsonl`, `summary.json`, `summary.md`; коммит git |
| `scenario` | сценарии техник T1–T18: стартовые состояния, горизонт, предикаты успеха, эталонные решения |
| `brains` | `TimelineBrain` (вводы по таймлайну), `RecordingBrain` (запись решений в `[[reference]]`) |
| `observe` | `Observation` из `World<f32>` (то же отображение полей, что в `ddai-world::live_world`) |
| `config`, `stats` | TOML прогона, фабрика мозгов, Уилсон, перцентили |

## Правила (как в стенде фазы 0, `lib.mjs:320-420`, `orig-run.md` §3)

- Тик мира — 50 Гц. Мозги решают каждые `decide_every` = 2 тика, все по одному и тому же состоянию до шага. Решение,
  принятое на тике `T` при лаге `L`, действует со шага на тике `T + L` (очередь как в `lib.mjs`; `L = 0` — сразу).
- Ти «выбыл» (*out*), если мёртв или заморожен (`freeze_time > 0`); *onset* — тик, на котором он выбыл.
- **1v1.** Партию решает первый тик с onset: только B → `W`, только A → `L`, оба → `D`; 1500 тиков без onset → `T`.
- **1vN** (A против B1..Bk, k ≥ 2): `W`, когда какой-то Bi выбыл **с зачётом A**; `L`, когда выбыл A; `D` — оба на одном
  тике; `T` на 1500. Bi без зачёта A только записывается (`bystander_outs`), партия идёт дальше. Переопределяется
  `rules.credit_required`.
- **credited**: жертву хукал или била молотом победитель ≤ 50 тиков до onset. **held**: играется ещё 150 тиков; жертва
  всё ещё out, победитель за окно ни разу не был out (проверяется состояние на каждом тике окна, как в харнессе).
- Зачёт молота — `HammerHit` из `PhysicsWorld::step` (адаптер планировщика, задача 3.2; в 8.1 он исправлен и получил
  тесты на настоящих ударах, см. README `ddai-planner`); зачёт хука — `hooked_player` хукающего на каждом тике.
  Толчок телом зачётом **не** считается (как в спецификации).
- Мёртвый ти не опрашивается: его клиент повторяет предыдущий ввод (как `prevInput` харнесса); `held` проигрыша в 1vN без
  зачтённого победителя требует, чтобы за окно ни один соперник не был out (F5).
- Метрики: самозаморозки A/мин (onset A до решающего тика / сыгранные минуты), блоки A/мин, время до первого блока,
  выживание A (цензурированное на решающем тике), решение p50/p99.

**Главная метрика (D-059) — доля игр, выигранных собственным засчитанным блоком** (`credited_win_rate` в `summary.json` и колонка
«credited-побед» в `summary.md`: `credited_w / все игры` с 95% ДИ Уилсона, таймауты считаются против игрока), рядом блоки/мин и
самозаморозки/мин. Победа без credit — это соперник сам замёрз; её набирает и бездействие (`idle` выигрывает 74% на `chillblock5-ruler`,
E-005), поэтому `W/(W+L+D)` (`PLAN.md` §0) остаётся **вторичной** колонкой (с ДИ Уилсона; рядом `W/все`, таймауты против игрока).
Каждая таблица арены публикуется с базовыми линиями `idle` и scripted-против-scripted. Поле `credited_win_rate` добавлено в
`summary.json` аддитивно: старые сводки читаются как раньше, а для них значение пересчитывается из `credited_w` и `games`.

**Удержанный блок (задача 3.10, поправка к D-059, E-021).** Все прежние замеры силы — доля *первых заморозок*: партия кончается на
первом onset. На Copy Love Box заморозка у потолка зала роняет жертву на пол, и через 150 тиков (`sv_freeze_delay` 3 с) она
оттаивает: на тех же играх `held` (150 тиков) держится у ≈ 50% побед. Поэтому добавлено:
- `rules.after_ticks = 250` (5 с, больше `sv_freeze_delay`) — окно «удержания»; помощник `Rules::held_block_window()` (константа
  `HELD_BLOCK_TICKS`). Умолчание `after_ticks` осталось 150, чтобы не менять прежние прогоны.
- **`held_block`** в строке игры: жертва была out (заморожена или мертва) на **каждом** тике окна (в отличие от `held`, где важно только
  состояние в конце и что победитель не выбывал); `escape_tick` — первый тик окна, когда жертва снова свободна; `victim_out_ticks` —
  сколько тиков окна она была out (градуированный вариант для наград).
- В `summary.json`/`summary.md`: `held_block_w` — победы **собственным засчитанным блоком** с удержанной жертвой (`credited && held_block`; соперник, который
  сам замёрз в яму, — не блок: ловушка D-059), `held_block_w_any` — то же без условия credited (сырое число), `held_block_l`, «held W:L», «held среди решённых» =
  held W / (held W + held L) (жертва при проигрыше — сам A), «held-побед/все» = held W / все игры, «удержано из W», все с ДИ Уилсона.
- `docs/research/held-block/heldcompare.py` — те же числа из JSONL и **парное** сравнение двух плеч (точный McNemar по «held W»,
  знаковый тест по `held W − held L`).
- **Для обучения мухи** (`ddai-train`): `Rules::held_block_window()` проигрывает эпизод дальше первой заморозки, `collect_game_held` отдаёт `(Episode, HeldOutcome)`
  (формат `Episode` не менялся). Факты `HeldOutcome`: `result`, `credited`, `held_block` (жертва out на каждом тике окна; верно для **любой** жертвы), `escape_tick`,
  `victim_out_ticks`, `winner_out_in_window`, `focal_out_in_window`. **Собственный удержанный блок A** — `strict_held_win()` = `W && credited && held_block &&
  !focal_out_in_window`; ровно это считает `EpisodeOutcome::held_block` задачи 8.5a, поэтому 8.5a может взять из `HeldOutcome` `credited`, `focal_out_in_window`,
  `held_block`, `victim_out_ticks`, `escape_tick` вместо своего `from_records`. `held_return()` совпадает с наградой **`RewardConfig::post_freeze`** 8.5a (не `full_game`, которая добавляет ещё +0,3 за засчитанную первую заморозку, −1 за проигрыш и −0,5 за ничью и таймаут): **+1** за строгий
  удержанный блок, **−1**, если A был out в окне (проигрыш — тоже), **0** за остальное (в том числе блок, который оттаял, и заморозку, за которую A не credited).
  **Только дуэль:** 8.5a считает удержанным блоком лишь победу с жертвой в слоте 1 (`victim_slot == Some(1)`); у `HeldOutcome` нет номера слота жертвы, и в толпе (1vN) `strict_held_win` засчитает и жертву другого слота, поэтому для обучения в толпе берите слот жертвы из `GameReport::victim`.
  `arena_eval` по-прежнему играет 150 тиков после заморозки; окно 250 и поля `held_block_*` — в `arena_eval_held` (opt-in).
- `rules.hold_target = true` — правило цели фокусного игрока «не бросать замороженную цель, пока точный прогноз
  (`ddai_planner::forecast::passive_forecast`) не скажет, что она останется out на всё окно» (`sim::HoldTarget`; умолчание
  `default_target` берёт свободного соперника первым и поэтому в толпе бросает жертву сразу). Аналог правила цели живого бота
  `--finish target`.

Диагностика: `cargo run --release -p ddai-env --example held_diag` проигрывает партии из JSONL и пишет траекторию жертвы после
решающего тика (`docs/research/held-block.md`); `--example map_ascii` рисует окно тайлов настоящей карты.

**ВБ-удержание (задача 3.18, E-033).** `wb = true` в описании игрока оборачивает мозг в `WbHintBrain`: пока тий в зале удерживаемой стороны, мозг получает те же `LiveContext::wb`, что от
живого бота (`in_hall`, `band`, `wall_dir`); роль верхней/нижней полки — как у `WbRole` бота: «нижняя» после 25 тиков на ≥ 3 тайла ниже первого спота (друг на полосе в арене
не моделируется), в ней `wall_dir` = 0. Гибрид читает подсказку только с `hybrid.wb_hold = true` (иначе тождественно прежнему: проверено на 400 играх по хэшам решений). Набор сценариев удержания —
`configs/scenarios-wb/` (W1–W8, обе стороны; замороженная до 150 тиков жертва лежит или падает, успех = вне боя все 250 тиков окна), прогон `configs/arena/e033-scenarios-{left,right}.toml`; подтверждение в
играх — `configs/arena/e033-confirm-{clb-left,clb-right,joni}.toml`. Разбор клипа: `cargo run --release -p ddai-env --example wb_clip_diag -- <карта> <клип>…`;
`held_diag` строит игроков так же, как прогон (`run::setups`: `wb = true` учитывается).

**Порядок спавна тоже симметрия (раунд 1 ревью, F1).** Слот 0 всегда имеет client id 0 и спавнится первым; ти, спавнившийся
последним, обрабатывается в тике первым и держит «сильный» хук (`m_StrongWeakId`). Обмен позиций (`swap`) этого не
компенсирует: скриптовый vs скриптовый в зале CLB на 4000 партиях давал 55,7% [53,8; 57,5] при обычном порядке и 46,2%
[44,3; 48,1] при обратном. Поэтому раскладка партии — 4-way: позиции (`swap`, нечётные `g`) × порядок спавна
(`reverse_order`, `g % 4 ≥ 2`); в каждом блоке из четырёх партий все четыре ячейки по разу, а `summary.json`/`summary.md`
дают разбивку `splits` (порядок обычный/обратный, позиции как выпали/обменяны). Для честного ДИ число партий кратно 4.
Партии 0 и 1 (первые в блоке) совпадают с харнессом. Клиентские id всегда равны слоту.

Спавн — **буквальный порт** харнесса (для двух игроков): RNG `Rng(seed * 2654435761 >>> 0)`, две равномерные выборки из списка стоячих клеток на
попытку, отбраковка по расстоянию. Для 1vN (F2) каждый следующий ти — в `[min, max]` тайлов от игрока 0 **и** не ближе `min` к любому
уже поставленному (два соперника не стартуют на одной клетке; если не хватает места, раскладка вытягивается заново — для двух
игроков этого не бывает). Тест `spawns_match_the_ts_harness` сверяет позиции с самим харнессом (сид 1..200 × 4
арены, фикстура `tests/fixtures/harness_spawns.json`, генератор рядом): 800 совпадений.

**Обоснование бокса ChillBlock5.** Карта огромна (943×1075) и почти пуста. Бот DDNet++ для ChillBlock5
(`data/research/block/ddnetpp/chillblock5_blocker.cpp`) называет место боя «ruler area» и охраняет его границами: вход
из туннеля при x ≥ 415, точка вейблока около x = 427, «слишком далеко вправо в ruler area» при x > 469, «фриз-бассейн под
областью» при y > 222. Отрисовка игрового слоя показывает ровно один зал внутри этих границ: потолок из фриза/no-hook
(строки 199–200), левая стена x = 415, воздух строк 201–212, пол строки 213 из no-hook-блоков с ямами фриза
(x 429..435, 440..449, 451..457) и приподнятым уступом (x 449..457). Бокс — воздух этого зала; стоят на no-hook блоках
пола (27 клеток). Это тот же тип места, что зал Copy Love Box (плоский блочный пол над фризом), но другой карты и
почти без хукаемой геометрии — честный отложенный тест переноса. Карту ChillBlock5 нужно положить в
`~/aiddnet/data/maps/chillblock5/` (копия из `data/ddnet-server/maps/`); в репозиторий карты не попадают.

## Конфиг прогона

```toml
name = "E-002 baselines"
base_seed = 1          # партия g -> сид base_seed + g
games = 200            # по умолчанию на условие
[rules]                # необязательно; значения по умолчанию = правила выше
[[condition]]
name = "clb-left planner vs 3 scripted"
arena = "clb-left"
players = [{ brain = "planner", mode = "deadline", budget_ms = 4.0, lag = 0 },
           { brain = "scripted", count = 3 }]
```

Толпы (задача 3.5b): `[rules] crowd_from = 2` — ти со слота 2 и дальше появляются где угодно на стоячих клетках арены (не обязательно
рядом с фокусным игроком), не ближе `crowd_spacing` тайлов (по умолчанию `min_tiles` = 3; для 12–15 ти берём 1,0 — плотный хаб)
друг от друга и от уже поставленных; без `crowd_from` правило E-002 прежнее (все в 3–12 тайлах от игрока 0). Условия с
`{ brain = "idle", count = 13 }` дают «простаивающих зевак», `{ brain = "scripted", count = 14 }` — толпу атакующих.

На ВБ-арене партии не меняются сторонами (`swap` выключен: слот 0 всегда держит спот), чередуется только порядок спавна.

`wb = true` (задача 4.2) — игроку сообщают то, что бот-ВБ сообщает планировщику в зале (`WB_PLAN_OVERRIDES`, полоса; `wb_strong` — `STRONG_WB`); только на арене с `[wayblock]`; сценарии — `configs/arena/wb-hold.toml`.

`brain` = `idle` / `scripted` / `planner` (`preset` normal|low|strong, `mode` fixed|deadline, `budget_ms`,
`clock` wall|step) / `hybrid` (гибридный мозг D-041, задача 3.5; те же `preset`/`mode`/`budget_ms`/`clock` плюс таблица
`hybrid = { … }`: `proposer` none|scripted|fly, `proposals`, `workers`, `techniques`, `threat_model`, `robust`, `lambda`,
`top_m`, `adaptive`, `max_total_ms`, `stage2_fraction`, `anchors`, `throw_cap`, `threat_radius_px`, `enemy_landing_bonus`,
`landing_cost`, `debug_dump`; `fly_config` и `model = <.flyg>` для `proposer = "fly"`, фабрика — в CLI `ddnet-ai`, муха
пока необученная: только проводка и цена). Слот 0 — фокусный игрок A. Любой другой `Brain` подключается через
`BrainFactory` (библиотека). Телеметрия гибрида (`players[].telemetry`) — счётчики за партию (`totals`: решения, доля
расширения D-042, кандидаты по источникам, выбранные техники, тики физики по фазам) и последнее решение (`last`).

  `telemetry`) и `timing` (`decide_us_p50/p99` по игрокам — **единственная** недетерминированная часть).
- `hash` — первые 16 hex SHA-1 потока решений (`orig-run.md` §9): `"{тик}:{dir},{jump},{hook},{fire},{tx},{ty},{wanted};"`
  по проводным значениям.
- `summary.json` (`meta`: хэш эффективного конфига, коммит + признак правок, сид, потоки, карты с sha256, база пауз;
  `conditions[]`) и `summary.md` — русская таблица W:L:D:T, винрейт с ДИ, credited/held, блоки/мин, самозаморозки/мин,
  время до первого блока, решение p50/p99, игр/с.

## Воспроизводимость

Условие `rules` в конфиге — переопределение поверх `[rules]` прогона (поля, которых нет, наследуются, F4). В `summary.json`
`meta.git_commit` — коммит исходников, из которых собран бинарник (`build.rs`), а не каталога запуска; `git_dirty = true`,
если в дереве исходников есть правки, оно ушло на другой коммит или его нет рядом (F6).

Партия — чистая функция `(base_seed, g, условие)`; результаты собираются в порядке индексов, поэтому JSONL **побайтно
одинаков** при любом числе потоков (кроме `timing`), а `ConditionSummary::deterministic_view()` двух прогонов равен.
Тесты: `jsonl_is_identical_at_1_and_6_threads` (скриптовый, планировщик в фиксированном режиме, 1v2 с лагом),
`different_base_seeds_give_different_games`. **Оговорка:** режим планировщика с дедлайном по стенным часам зависит от
загрузки машины и не воспроизводим; для тестов есть `clock = "step"`.

## Отличия от харнесса E-000 (TS) и что они значат

- **Физика — настоящий DDNet** (`World<f32>`, 0 расхождений с C++ на оракулах), а не TS-мир; числа E-000 и E-002
  сравнивать как «та же игра, другой мир». Планировщик один и тот же (порт с паритетом), но `World<f32>` даёт
  другие отбросы, инерцию, порядок тика и фриз-механику.
- Нет `pathGoal`/`findRoute` планировщика (см. README `ddai-planner`); карты `pit`/`platform` при дальнем спавне без него.
- Ввод соперника для планировщика — по видимому состоянию, как в харнессе (`snapshot`-режим), но окружение — настоящий мир.
- Зачёт молота исправлен (см. выше); раньше его вывод в Rust-адаптере почти не работал.
- `Observation.jumps_left` — оставшиеся прыжки (`ddai_brain::jumps_left`, правила HUD `hud.cpp:868-889`), а не ёмкость
  `core.jumps` (F3, тот же хелпер использует `ddai-world`).

## Скорость и память

Скриптовая партия ≈ 3 мс (60 игр/с на 1 потоке, 305 игр/с на 6; ограничение — таймаут в 1500 тиков), партия
планировщика 1–7 с (0,7 игр/с на 1 потоке, 3,2–3,9 на 6; p50 решения 8–12 мс). Память процесса при 6 потоках ~60–100 МБ (мир копируется из шаблона, карта — общая `Arc`).
Числа E-002 — `docs/EXPERIMENTS.md`.

## Предложение: настоящий хук событий в `World::step`

Зачёт молота в арене выводится из состояния (`PhysicsWorld::step`, README `ddai-planner`). Надёжнее — событие из самой
физики: в `fire_hammer` (`world.rs`) в момент попадания положить `(from, to, tick)` в предвыделенный буфер
`World::events` (очистка в начале `step`, без аллокаций), а `HammerFire { from, hits }` — по числу целей. Это не меняет
физику (запись рядом с существующим кодом), убирает вывод по `reload_timer` и геометрии и заодно даёт события `Freeze`/
`Death` с причиной для награды D-030. Не делалось в этой задаче: `ddai-physics` сейчас правит задача 1.10b.

## Мозги из файлов (задача 8.2)

`models::ModelBrains` — фабрика мозгов с файлами: `{ brain = "fly", model = "<чекпоинт>" }` в конфиге или `--brain
fly:<чекпоинт>` / `mlp:<...>` / `gru:<...>` в `ddnet-ai arena run|scenarios` (слот 0 всех условий заменяется). Чекпоинт
загружается и проверяется **один раз** (кэш по пути), на каждую партию строится свежий мозг (`FlyBrainTemplate::instantiate`,
`ControlTemplate::instantiate`); тёплое состояние покоя мухи считается один раз. Остальные имена идут в `builtin_brain`.
Гибридный мозг (3.5) собирается там же: `--brain hybrid:fly:<чекпоинт>` (или `{ brain = "hybrid", hybrid = { proposer = "fly",
fly_model = "<чекпоинт>" } }`) — гибрид, у которого `FlyProposer` предлагает планы **обученной** мухой из чекпоинта 8.2; `hybrid = {
proposer = "fly" }` с `model = <.flyg>` — необученная муха (проводка и цена). Так в гибридной арене можно сравнить обученного и
необученного предлагателя. Пороги решений jump/hook/fire берутся из чекпоинта (v1 — 0,5).
`arena scenarios --brain <спецификация> --trials N` добавляет мозг в таблицу T1–T18.

## Дуэль как вживую: вид мира, правила раунда F-DDrace (задача 3.19, E-034, D-116; `docs/research/duel-3.19.md`, `docs/formats.md` §49)

* `liveview` — мозг видит мир, как живой бот: `ServerView` (память пересчёта сервера `m_SendCore`/`m_ReckoningTick`, снапшот раз в `decide_every` тиков) → `LiveSeat` (`LiveWorld`, неподтверждённые вводы, прогон на лаг, `LiveContext { duel: true }`). Проверено: пересобранный мир побитно равен истинному на каждом снапшоте, прогноз нашего тия через вводы в полёте — 0 px (`tests/duel.rs`).
* `duel` — правила раунда (`RoundWatch`, `play_duel_watched`): отсчёт 150 тиков, проигрыш лежащего во фриз-тайле на земле без движения > 50 тиков, взаимная заморозка и раунд без касания — без очка. Включается условием `duel = { … }` (`[condition.duel]`); без таблицы все игры прежние, хэш конфига не меняется.

* Примеры `clip_json` (клип → JSONL) и `pm_counterfactual` (контрфакты разбора дуэли 07.10, `docs/research/duel-2026-10-07.md` §5) перенесены из ветки разбора.
* Главный результат: нехватка поиска вживую (14 кандидатов на решение против 28 в арене) объясняет разрыв по молоту; откалиброванная арена — часы работы 2,1 мкс/ти-тик.
