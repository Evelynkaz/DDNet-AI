# ddai-bot

Задача 4.1. **Живой бот** вокруг мозга: всё, что происходит между «пришёл снапшот» и «ушёл ввод». Запуск — `ddnet-ai play
--brain planner|scripted|hybrid|fly` (или `--bot --brain idle`) против локального сервера DDNet 20.1 (D-043: на публичные
серверы пока нельзя). Бот **никогда не пишет в чат** (D-007: в клиентском API нет вызова, принимающего текст, а кик-разгон — это
сообщение протокола `Cl_Kill`) — **за одним исключением, разрешённым владельцем (D-078, задача 4.6): серверная команда `/kill`** как запасной путь, когда DDNet отбрасывает `Cl_Kill` (`sv_kill_protection`, жизнь старше 20 минут). Это типизированная команда `ddai_net::server_command::ServerCommand::Kill` с константным текстом, список разрешённых исходящих (`ddai-client::allowlist`) пропускает `Cl_Say` только с побайтно тем же содержимым; ничего другого в чат уйти не может. Правила — `killfallback` и `docs/formats.md` §21.8. Бот **никогда не обходит кики и баны** (D-016/D-037: кик, бан или неизвестная причина — стоп
с кодом выхода 3/4 и сообщением, без переподключения).

Подробный формат (мост к вебу, `relations.json`, тайминг предсказания, замеры) — `docs/formats.md` §21.

**Задача 4.3** добавляет к боту: запись клипов (`clipper`, крейт `ddai-clip`), консольные команды (`command`, `console`, `Bot::command`; строка без `!`/`?` не уходит никуда), `settings` и выбор сервера
(`ddai_client::server_list`, `--server auto` — только из разрешённых). См. `docs/formats.md` §24.

## Конвейер одного снапшота (`bot::Bot::on_snapshot`, `orig-bot.md` §4.2)

Снапшоты, пришедшие пачкой, **схлопываются** (`runner`): решается только самый новый, пропущенные считаются
(`collapsed`). Один снапшот — одно решение, 25 Гц.

1. карта загружена и свой id известен (иначе ничего не делаем);
2. игровой тик пошёл назад — `onTickReset` (рестарт карты): чистятся все зависящие от тика состояния;
3. **LiveWorld** (`ddai-world`) обновляется из снапшота со своими «летящими» вводами и снарядами (`SnapshotInput`);
4. таблица игроков (`players`), плоский вид тиев (`tees`), **часы активности и атрибуция** (`activity`);
5. своего ти нет / мёртв — нейтральный ввод; в спектаторах — просьба войти в игру (`Cl_SetTeam(0)`, не чаще раза в 3 с,
   не больше 10 попыток **за весь запуск**, успех счётчик не обнуляет). Если бот уже играл на карте, а теперь он в
   спектаторах, — это сигнал модерации: **не просится обратно, запуск останавливается** (код 3, как при кике);
6. первый кадр жизни: `Brain::reset`, таймеры блуждания, навигатор. Начинается и после **своего** `Sv_KillMsg`
   (после `Cl_Kill` сервер возрождает сразу, пустого снапшота может не быть), смерть считается один раз;
7. **unstick** (`unstick`): константы `maybeUnstick` один в один, но убийство — `Cl_Kill`;
8. режим: `hold` — стоим; хук навигатора (4.2) может взять снапшот на себя; иначе **выбор цели** (`target`);
9. цели нет — **блуждание** (`wander`) через щит; цель есть — **предсказание** до PredTick по ближним тям, **мозг**
   (`decide_in`), затем **постфильтры**: щит (`guard`) для мозгов без своего щита (scripted, fly), **вето хука** и
   **вето молотка** на «пощажённых» (друзья, игнор, вне игры, AFK; вето молотка проверяет **эффективное** оружие — первые
   1-3 тика после спавна снапшот ещё показывает пистолет). Пощажённые тии передаются мозгу как `LiveContext::spares`
   (позиции) и `spare_ids`; ближайшие **3** в пределах **200 px** остаются в мире мозга **физическими телами**
   (отдельно от `max_local_others`), но только для мозгов, соблюдающих `spare_ids` (`BrainKind::honours_spare_ids`: planner и гибрид), остальным пощажённые не попадают в мир, если не связаны верёвкой;
   решение целится в слот ввода по **p95** недавних времён решения (`DecisionEstimator`), а драйвер **удерживает** его до
   тика `expected_tick` (`docs/formats.md` §21.1): раньше предсказанного оно не уходит;
10. **кодирование ввода** (`input`): счётчик огня, молот по умолчанию, никаких флагов табло.

## Решения и отличия от TS (D-021)

- **Точное совпадение списков.** `listed()` в TS искала подстроку: короткий ник в friend/war задевал всех с похожим именем.
  Теперь: обрезка, сжатие пробелов, нижний регистр, снятие префикса дубликата `^\(\d+\)` — и сравнение целиком. Списки
  лежат в `~/aiddnet/data/bot/relations.json` (не в git). Повреждённый файл — отказ стартовать, а не «друзей нет».
- **Порядок при равном счёте.** TS брал первого в порядке вставки в `Map`; здесь тии обходятся по возрастанию client id,
  заменяет только строго больший счёт: побеждает наименьший id. Детерминированно и не зависит от порядка входа.
- **`FlagScoreboard` не портирован.** Раз в секунду на один снапшот TS включал флаг «табло открыто» (`bot.ts:4843`).
  Зачем — в коде не сказано; это выглядит как имитация активности для AFK-детектора сервера, поэтому не переносится.
  `player_flags` всегда `PLAYING`; тест проверяет, что флаг табло не уходит ни на одном тике.
- **Лаг — точный, а не оценка.** Вместо `echoLagTicks`/`pingLagTicks` (0..6 тиков по эху прицела или пингу) драйвер
  сообщает тик последнего отправленного ввода (`pred_tick`), а `sent` превращает `InputSent`/`InputTiming` в ввод,
  который сервер применит на каждом тике (поздний ввод сдвигается вперёд на `ceil(опоздание/20 мс)`, как делает сервер
  20.1). Мир предсказывается до `pred_tick`, действие мозга применяется на следующем шаге: `WorldView { lag_ticks: 0 }`.
- **Мозгу — только нужные тии.** Цель + те, кто связан с нами хуком + ближайшие 5 в радиусе 900 px. Остальные
  вырезаются из предсказанного мира (`LiveWorld::predict_local`): поиск на 8+ тях разваливается (ревью 3.5, F2).
- **Пощажённые идут планировщику** через `Brain::set_live_context` (`LiveContext.spares`, `setSpareBystanders`);
  замороженные соседи уже берутся планировщиком из мира. `setThirdTees` не передаётся: в живой конфигурации
  `thirdTeeExposure = 0`, он бы игнорировался.
- **Достижимость.** `findRoute` TS — граф ходьбы/падения/прыжка/хука на 984 строки — это навигация (4.2). Здесь тот же кэш
  (25 тиков, по тайлам «откуда/куда») и тот же бюджет «low-cpu» (один свежий поиск на снапшот, остальные — из кэша или
  оптимистично `true`), а сам поиск — `RouteFinder`; по умолчанию заливка по воздуху без фриза (`throughFreeze: false`,
  `nearTiles: 3`, 20 000 узлов). Это верхняя граница настоящего поиска: цель, запертая стеной или фризом, остаётся
  недостижимой.
- **Не портировано** (DROP по ТЗ и D-021): чат, авточат, LLM, дамми, партнёр, спасение друга, эмоции, дуэль-авто через
  `/accept`. **Вынесено:** goto/seek/trek/home, вейблок и память фризов сделаны в 4.2 (`nav_hooks`); клипы и команды консоли — 4.3.

## ВБ по релизу апстрима 2026-10-02 (задача 4.8)

Что бот делает иначе после порта `af49dfb` (полная таблица решений — `docs/research/upstream-2026-10-02.md`, решение D-092):

- **ВБ на любой копии карты с тем же залом.** `wayblock_for` ищет зал по тайлам (`ddai-nav`), поэтому на Swarfey (Copy Love Box
  468×255) и на копиях с залом в другом месте ВБ включается; в логе `WB: this map has one (Copy Love Box hall at +0,+0)`. Прежнее
  «версия карты другая» остаётся только для карты с тем же именем, у которой зала в тайлах нет.
- **Гард** (`wb_guard`, `nav_hooks/wb_extra.rs`): первый спот — левый (правый) край верхней полки; на месте бот стоит неподвижно
  (`WanderHint::still`); замороженного на нижней полке бросают из точки `job`, того, кто мешает в коридоре за стеной, ловят
  первым (`WbFilter::corridor`, +5000), падающих мимо зала не берут; роль нижней полки берёт тот, у кого на верхней друг.
  **Не перенесено (3.8):** броски планировщика в стеновой фриз (`wallDir`, `airChain`) и пассивная проверка запечатанности.
- **Путь в зал.** После 2 неудачных заходов переход идёт «маршрутом 2» через стену прохода (`Navigator::wall_route`); по дороге
  бот дерётся только с войной из списка, с тем, кто у трубы действует против него, и с тем, кто заморозил его 3 раза за 3 мин
  (`WayBlock::foe_target`, `Navigator::blocked_by`); у трубы с двумя и больше врагами не дерётся, а проходит. Перезагрузка той
  же карты не сбрасывает паузу ВБ после смертей.
- **Не только ВБ:** игрок в `/spec` / `/pause` с тием на карте — цель (кроме комнаты AFK); вернувшийся из наблюдателей не AFK;
  удержанная клавиша при движении — активность; блуждание тормозит заранее перед фризом с учётом лага; навигатор на цели на бегу
  тормозит против опасности за ней.
- Переменные окружения (как в TS, для сравнений): `DDAI_WB_GUARD=0` — прежние споты и без гарда, `DDAI_WB_ROUTE2=0` — без
  «маршрута 2», `DDAI_WB_ROUTE2_CROWD=1` — маршрут 2 и от толпы у трубы.
- **Живая проверка на своём сервере** (`tests/e2e_wb_versions.rs`, `DDAI_E2E_SERVER=127.0.0.1:<порт>` приватного сервера,
  `DDAI_E2E_MAP=<карта сервера>`): гибрид в режиме ВБ `auto` против скриптовых; раз в секунду тайл тия, затем «в зале» и «на споте».
  Результаты — E-018 (`docs/EXPERIMENTS.md`).

- **Закрытая арена на той же карте (задача 3.14, D-105).** На joniTee в карте есть копия зала, но мини-игра `/1vs1` от неё отгорожена: ходьба к ВБ шла «через фриз» с `/kill`, который в мини-игре возвращает в арену, и бот замерзал по дороге.
  Теперь `walk_to_wb` снаружи зала закрывает ходьбу на 10 с (`WB_CLOSED_TICKS`, серверный тик, забывается при смене карты), **только если и тий, и начало его последней жизни** (`respawned` → первая позиция в `poll`) лежат в открытых тайлах, отрезанных пешком (без фриза и `/kill`)
  от всего ВБ (старты переходов, места, выходы); пока жизнь не записана, работает прежняя ходьба. Метки компонент (`nav_hooks/foot.rs`) считаются при загрузке карты (`Core::on_map`, не на пути снапшота) заливкой по `NavGrid::free` с объединением компонент по телепортам (4 мс на CLB, 21 мс на joni), ответ — поиск в таблице; возврат из серверной паузы (`/pause`, `/spec`) стирает запомненную жизнь (`Navigator::resumed`: тий не респаунился), и работает прежняя ходьба; нижняя граница достижимости
  (верёвка через полосу фриза не учитывается), поэтому условие про респаун обязательно: `/kill` на обычной CLB возвращает на спаун с дорогой к трубе, и там ходьба прежняя. В журнал `WB left: walled off from its crossings at (x,y) (an arena?); the fight is here, not walking`.
  Тесты на настоящих картах (пропускаются без файлов): `no_walk_to_the_wb_from_a_walled_off_arena_after_a_respawn_in_it`, `on_copy_love_box_a_tee_on_the_floor_below_the_hall_still_walks_to_the_wb`, `a_map_change_forgets_the_walled_off_state`, и через весь `Bot` — `tests/wb_pause_resume.rs` (пауза → возврат); заливка, включая телепорты, — модульные тесты `foot.rs` на синтетической карте.

## Задержка (D-042)

`Bot::latency()` — кольца по 32 768 значений: `total` (снапшот в потоке бота -> `set_input` вернулся), `brain` (только
`decide_in`), `overhead = total - brain` (цель D-042: p99 <= 0,5 мс), `queue` (поток драйвера -> поток бота) и `wire`
(драйвер: снапшот пришёл -> первый `NETMSG_INPUT` с этим решением ушёл в сокет; включает каденс сессии — один ввод на
предсказанный тик, до 20 мс, — который скоростью бота не сократить). Замеры — в `docs/formats.md` §21.6 и отчёте билда.

Цена `sealedIn` и щита вынесена из накладных расходов: проверка sealed считается лениво (только там, где вердикт
`settled` может измениться — первый кадр заморозки, «добиваемая» цель, свободная цель у фриза) и на отдельном потоке;
щит для мозгов без своего (scripted, fly) относится к доле мозга и пропускается, когда в 12 тайлах нет фриза/смерти;
«sealed»-ответ живёт до 30 тиков, пока тий заморожен на том же тайле. Если решение мозга не успевает к ближайшему вводу
сессии (`next_input_in`), мир предсказывается на тик дальше (§21.1).

**4.1b (D-063): попадание в слот.** Оценка времени решения — скользящий p90 (`DecisionEstimator`), не среднее, зажатая
ниже периода снапшота; драйвер **удерживает** решение с `InputTag` до `NETMSG_INPUT` для `expected_tick` (раньше предсказанного
оно не уходит, «раньше» = 0 по построению; опоздавшее уходит сразу; вытесненные до своего тика считаются), и пересчитывает
счётчик огня от последнего **отправленного** ввода (нажатие вытесненного решения не просачивается); **адаптивный
`prediction_margin`** (`ddai_client::timing::MarginController`: p1 `time_left` за 5 с, цель 2 мс, зажим 3-20 мс; вверх только по
оконному сигналу — 2 опоздавших ввода в окне или p1 < 2 мс при >= 100 отсчётах, один опоздавший ввод margin не поднимает;
«затык» определяется по задержке отправки `margin - time_left`; отсчёты вводов, отправленных до смены margin, игнорируются;
вниз не больше 1 мс за 3 с и только после 10 с без опоздавших) сдвигает слот ввода после снапшота позже, пока опозданий нет;
`--prediction-margin-ms` задаёт фиксированный margin. Горизонт предсказания следует за RTT (`pred_tick - tick + 3`, не больше
75 тиков), `PredictionClamped` предупреждает, если и этого мало. Проверка: `adaptive_margin_through_a_delay_and_jitter_relay`
(UDP-реле на 127.0.0.1) и `adaptive_margin_long_acceptance_run_under_load` (10 минут на загруженной машине) в e2e.

Аллокации: путь бота (LiveWorld, таблица игроков, часы, выбор цели, ключи, предсказание, наблюдение, кодирование) **не
аллоцирует** на снапшот в устоявшемся режиме — тест `a_steady_state_snapshot_allocates_nothing_in_the_bots_own_code`
(`allocation-counter`, 7 тиев, 200 снапшотов, 0 аллокаций). Вне этого пути остаются помощники `ddai-planner` (проверка
sealed для замороженных кандидатов, щит, вето хука) и сам мозг.

## Тайминг ввода (задача 3.11, E-024, D-101; `docs/research/live-timing.md`)

- **Фазы решения** (`LatencyStats`, в `ddnet-ai bot --report` — `latency_detail_us`): `update` (LiveWorld, игроки, тии, часы блоков), `nav`
  (навигация до выбора цели), `predict` (прогноз мира до тика решения), `post` (щит и вето), `finish` (отложенные команды, запасной `/kill`),

  (насколько тиков вперёд предсказан мир мозга); слоты считаются отдельно для решений мозга (`brain_*` в `slots`).
- **`BotConfig::kind_estimate`** (умолчание библиотеки `false`; `ddnet-ai bot`/`play` включают по умолчанию, `--live-timing precise,kind`): решение, которое сейчас пойдёт в мозг, целится во

- **`BotConfig::driver_pickup`** (2 мс; раннер ставит 0,3 мс при `ClientConfig::precise_wakeups`): сколько драйвер добавляет между отдачей решения и проводом.

## Чат владельца с сайта (задача 4.9, D-094)

Единственный чат бота — типизированный запасной `/kill` (D-078, `killfallback`) и строка, набранная владельцем на сайте. Автоматического нет: ни автоответов, ни LLM, ни периодических сообщений, ни приказов из игрового чата; консоль (`!say`, строка без префикса) по-прежнему ничего не говорит.

- Путь: сайт (`POST /api/bot/say`) -> `control.sock` (`ControlCommand::Say { team, text }`) -> `BotCommand::Say { team, text: OwnerText }` -> `OwnerChat::submit` в раннере -> `OwnerChat::poll` каждый проход цикла -> `Client::owner_say` -> `Session::request_owner_say` (одноразовое разрешение в списке разрешённых, метка аудита `Cl_Say(owner)`). `Bot::command` строку не применяет (у него нет ни часов, ни клиента): отвечает отказом.
- «Только сайт» — гарантия типов: `OwnerText::new` требует способность `OwnerChannel` (один раз на процесс, её забирает `ControlServer::start` и кладёт в `Dispatcher`), а `tests/owner_chat_census.rs` сканирует исходники и падает, если конструкторы и отправители строки встретились в рабочем коде вне короткого списка файлов. Текст проверяется трижды: сайт (`OwnerText::check`, значения не делает), `ControlRequest::validate` и `OwnerText::new` в диспетчере.
- Аварийный выключатель только чата, «в закрытую»: `--no-owner-chat` у `ddnet-ai play`, `owner_chat = false` или неизвестный ключ / нечитаемый файл в `settings.toml`, либо файл-метка `data/bot/owner-chat.off` (переживает `launch apply`) — канал сжигается (`control::forgo_owner_chat`), `say` -> отказ `chat_disabled`, остальное в канале работает. `--report` пишет `owner_chat` (accepted, sent, refused, dropped); `sent` — передано клиенту, на проводе `Cl_Say(owner)` не больше `sent` (`tools/e2e/soak_analyze.py` сверяет это). Лимиты бота и причины отказов — `src/ownerchat.rs`, `docs/formats.md` §21.9. `RunReport::owner_chat` — принято / сказано / отказано / отброшено при выходе из игры.
- Дуэль `/1vs1` вручную (D-102, задача 4.11; с 4.12 дуэль ещё и определяется сама, см. раздел ниже; с 5.15 флаг принимает и форму `--no-selfkill=true|false` для юнита запуска с сайта, голый флаг — как раньше): `--no-selfkill` или файл-метка `data/bot/selfkill.off` (перепроверяется раз в секунду; ошибка чтения метки, кроме «не найдена», считается «метка есть») — бот сам себя не убивает: ни unstick `Cl_Kill`, ни `/kill` D-078, ни маршрутов и trek с шагом-убийством (такие маршруты не строятся); консольный `!kill` (с его запасным `/kill`) и строки владельца остаются. В STATUS поле `selfkill`. В журнал: `self-kill: off (flag|marker)`. Модуль `src/selfkill.rs`.
- Приватность: в журнале «owner chat sent (len N)» и «owner chat refused» с причиной, текста нет; в аудите канала — `say:all` / `say:team`.
- Тесты: `ownerchat::tests` (9: 3 с, очередь 3, длинная строка, двухминутный затор, вне игры, ответы без текста), `control::tests`, `tests/commands.rs` (консоль не может сделать `Say`); e2e на частном сервере — `crates/ddnet-ai/tests/e2e_owner_chat.rs`.

## Умное самоубийство и автоопределение дуэли (задача 4.12, D-108)

Бот убивает себя только тогда, когда это действительно нужно, и никогда — в дуэли F-DDrace `/1vs1`. Две независимые части.

**1. Дуэль определяется сама** (`src/duel.rs`, по умолчанию включено при любой политике). Структурный сигнал: наша команда DDRace (`Sv_TeamsState`, поле `teams` снапшота) не 0 и не 64 и в ней **ровно один другой** присутствующий игрок — так F-DDrace собирает дуэль (`CArenas::StartFight`: `SetForceCharacterTeam(…, первая свободная команда)` и `SetTeamLock`). **Одной команды мало** (двое в команде бывают и на обычном DDNet: `/team`, `set_team_ddr`; и в карточной игре Durak F-DDrace): команда считается, только если в этой сессии есть **признак F-DDrace**: системная строка мини-игры `/1vs1` (`client_id` −1, английский текст из `arenas.cpp`): «You have been invited to a fight by '…'», «You have accepted the invite by '…'», «'…' has accepted your invite» — **или команда дуэли, которую владелец отправил с сайта** (`/duel`, `/1vs1`, список — `duel_commands` в `settings.toml`; на joniTee команда `/duel`, её нет в исходнике F-DDrace; строку отправил сам бот, игрок её подделать не может; в журнал — `duel evidence: owner command (len N)`, без текста). Признак живёт 20 минут после последнего (команда без новых признаков дольше отпускается) и расходуется, когда дуэль действительно кончилась (100 тиков без считающейся команды или строка конца; один снапшот без команды бой не обрывает: на F-DDrace номера команд частично декоративны). Переподключение и перезагрузка той же карты признак сохраняют (код таймаута возвращает бота в команду боя), другая карта — нет; свой номер 64 («супер-команда» радужного ника) при живом признаке — «неизвестно», дуэль не прерывается, пока противник не покажет номер 0 или не уйдёт (F9: радужный номер — 1..63, не 0). Строки «accepted» ещё и сами включают определитель на 60 с, пока не пришла команда; конец боя — ровно «'A' won a 1vs1 round against 'B'! Final scores: n - m» или «'A' left a 1vs1 round against 'B'! Current scores: n - m» с нашим ником на месте A или B (хвост из двух чисел, больше ничего: строку с чужим текстом не подделать). Строки читаются и забываются (не хранятся, не логируются). Пока дуэль есть, бот ведёт себя как при `--no-selfkill` (D-102): ни unstick, ни `/kill` D-078, ни маршрутов и trek с убийством; остаются консольный `!kill` владельца и его строки. Дуэль заканчивается через 2 с после того, как команда перестала быть «двое»; смена карты и выключение определителя забывают всё; переподключение и перезагрузка той же карты оставляют признак (не дольше 150 с отсутствия: после более долгого боя уже нет, F11), команду — нет. **Выключатель:** `--no-duel-detect` или файл-метка `data/bot/duel-detect.off` (перепроверяется раз в секунду, как `selfkill.off`; ошибка чтения, кроме «не найдена», считается «метка есть»), журнал `duel detection: off (flag|marker)`. Журнал дуэли: `duel: an F-DDrace 1vs1 is on: … by="team"|"chat"` (warn) и `duel: the 1vs1 is over`. STATUS моста (аддитивно): `duel` (bool), `selfkill` = `"off"` и в дуэли; `selfkill_policy`.

**2. Политика `--selfkill-policy legacy|smart`** (по умолчанию `legacy`: таймеры D-058 без изменений). `smart` (`src/smartkill.rs`, `unstick.rs`): замёрзший бот убивает себя, только если ожидание дороже убийства. Цена убийства — respawn (25 тиков) плюс дорога назад от ближайшего спауна (расстояние / 6 px за тик). Прогноз — точная физика нашего тия одного, без ввода (`ddai_planner::forecast::passive_forecast`, тот же, что у «удержанного блока»; ≤ 0,25 мс, только пока бот заморожен ≥ 25 тиков).

- **не убивает:** друг хукает нас (до верхней границы 1500 тиков, как раньше); друг («помощник»: списки friend, ignored, clan friend; не AFK, не замёрзший) просто в радиусе хука 380 px — короткая отсрочка 200 тиков (время начать хукать; legacy ждёт помощника в 140 px все 1500); нас хукает чужой (до 400); прогноз «оттает за ≤ max(цена, 100 тиков)» или «умрёт сам»; свободный застрявший бот, пока держит свой блок (`ActivityClock::holding_block`);
- **убивает:** глубокий фриз (прогноза «оттает» нет), покой на тайле фриза (выхода нет), «мёртвая зона» навигатора (после оттаивания всё равно нужен respawn), оттаивание позже цены убийства — после `SMART_MIN_FROZEN_TICKS` = 50 тиков заморозки (запрос вейблока — по своим 25);
- **верхние границы:** заморозка ≥ 400 тиков убивает независимо от прогноза (прогноз не видит других тиев); друг, который хукает, держит не дольше 1500; кулдаун 500 тиков и обучение защиты от убийств D-078 (`killfallback`) не тронуты;
- **навигация:** `Router::find_route_kill_last` / `Navigator::set_kill_last` / `Trek::start_with_policy`: маршрут пешком (идти, падать, прыгать, хук), и только без него — шаг-убийство (цена 60 в поиске больше не перевешивает дальний пеший путь).

Лог: `unstick: Cl_Kill (smart) why=…`, `self-kill skipped … why=…` (не чаще раза в 100 тиков), при старте `self-kill policy: smart`. STATUS: `selfkill_policy`.

**Измерения.** Сценарии `tests/selfkill_policy.rs` (оттаивание скоро, глубокий фриз, яма, друг рядом / хукает, дуэль), реплей клипов `ddnet-ai clip selfkill <клипы>` (по каждому записанному `Cl_Kill`: то же / раньше / пропуск, у пропуска — что стало с тием дальше на реальной физике с записанным окружением), точность прогноза `ddnet-ai clip forecast`, сквозной тест дуэли на частном сервере `tools/e2e/duel-team-e2e.sh`. Цифры и предложение переключить умолчание — D-108.

## Код защиты от таймаута `/timeout` (задача 4.10, D-100)

Третий, и последний, чат бота: стандартная команда DDNet `/timeout <код>` один раз за вход в игру, как у официального клиента 20.1 (решение владельца 2026-10-06). Ничего в боте для неё не менялось:
семя читает `ddnet-ai play` (`<data-dir>/bot/timeout-seed`), отправляет сессия `ddai-client` (`Session::maybe_send_timeout_code`), раннер видит её только в аудите (`RunReport::outgoing["Cl_Say(/timeout)"]`).
Чат владельца `/timeout` отвергает целиком (любая строка с `/` и словом `timeout`, в любом регистре, в том числе `/spec;timeout x`), `tests/owner_chat_census.rs` держит места вызова коротким списком файлов.
Пока рядом призрак с нашим именем (после быстрого входа заново), та же команда повторяется каждые 30 с, не более 35 раз (D-100). Выключатель — `ddnet-ai play --no-timeout-code`. Что это даёт и чего нет (старое соединение должно уже быть «мёртвым» для сервера) — D-100, «Граница»; формат — `docs/formats.md` §39.

## Поток мухи для сайта (задача 7.4, D-073)

Мост (`bridge.rs`) получил два вида сообщений — `FLYMETA` (6) и `FLY` (7) — и **единственное, что бот читает от клиента**: подписку
`u32 len | u8 1 | u8 маска` (бит 0 — муха; всё прочее читается и отбрасывается, длиннее 16 байт — клиент отключается, сокет остаётся
только на чтение по смыслу, управления нет). Раннер зовёт `Bot::viz_frame` **только при `Bridge::fly_wanted()`**; без зрителя мозг
для потока ничего не делает. Кадр отдаётся, только если мозг решал **именно этот** снапшот (`Bot::viz_frame` проверяет `brain_decisions`; у гибрида ещё `viz_fresh`: предлагающий был спрошен в этом решении), чтобы подписавшийся позже не получил кадр прошлого решения с чужим вердиктом. Очередь клиента, который не читает, ограничена `MAX_PENDING` при каждом опросе. Описание потока (`Bot::viz_meta`) уходит в мост на старте и после каждой смены мозга
(`brain_generation`), подписчику — сразу при подписке. `--fly-bundle <файл>` (`BrainOptions::fly_bundle`): `--brain fly` играет весами
bundle, `--brain hybrid` получает муху предлагающим (`hybrid:fly`); без него муха необучена, у гибрида нет предлагающего и потока нет.
Формат — `docs/formats.md` §21.2 и §27; тесты — `bridge::tests` (подписка, метаописание, отписка, закрытый клиент, чужие и
слишком длинные сообщения).

## Долгий прогон и юнит (задача 4.4)

`tools/e2e/soak.sh` гонит бота час на локальном сервере (гибрид, три скриптовых бота с приходами и уходами, веб-юнит на другом порту,
консоль, перезапуск сервера, смена карты туда и обратно), пишет журнал каждые 15 с и проверяет приёмку; результаты — `docs/EXPERIMENTS.md`
E-009, systemd-юнит бота и его установка — `deploy/README.md`. Для этого бот пишет раз в 10 с в лог строки `bot status` (задержки и счётчики) и
`input margin` (поздние вводы, адаптивный margin), `play --duration 0` — без лимита времени, `starting the bot` называет режим ВБ.
**Статус и лог без сортировки.** Проценты в сообщении моста и в строке лога раз в 10 с берутся из гистограммы кольца (`Series::quick_summary`: просмотр корзин, ошибка ≤ 0,4%, 6 мкс на три ряда); точный `summary()` (сортировка копии) — только для итогового отчёта.
**Память.** После смены карты на большую (1244x667 тайлов) бот с glibc-аллокатором по умолчанию остаётся на 160 МиБ больше, хотя
ничего не держит: переменная `MALLOC_MMAP_THRESHOLD_=131072` отдаёт память системе сразу (юнит и soak выставляют её; ручной запуск —
`MALLOC_MMAP_THRESHOLD_=131072 ddnet-ai play ...`; без неё бот при старте пишет одно предупреждение).


## Удержанный блок (задача 3.10, E-021, D-097): `--finish off|target|full`

Живой разбор (`docs/research/held-block.md`): через 1 с после нашего блока бот уже сменил цель в 63% случаев (68 блоков, 6 сессий Swarfey), а заморозка у
потолка зала роняет жертву на пол, где она оттаивает через 150 тиков, если её не затащить обратно во фриз. Всё новое — **opt-in**, умолчание прежнее:
- **Слежение (всегда включено, на решения не влияет).** `ActivityClock` ведёт каждый наш блок 250 тиков: жертва ни разу не разморозилась (или умерла) — `block held`,
  стала свободной раньше — `block escaped after=<тики>`; сообщение `Kill` о жертве внутри окна (kill-тайл, её собственный `/kill`) — `block held died=true`
  сразу (жертва уже на ногах в следующем снапшоте). Жертва, пропавшая из снапшота **без** сообщения `Kill` (вне зоны видимости, в наблюдателях), вердикта не получает. Строки в журнале, события `BotEvent::{BlockHeld, BlockEscaped}`, счётчики `held` (из них `died`) и `escaped`
  в итоговой строке и в `--report` (`blocks`). Без аллокаций (8 слежений в массиве). Диагностика: `DDAI_DIAG_BLOCK_CLIPS=1` — когда судьба блока известна,
  кольцо сохраняется клипом `manual-<тик>-held|escaped-<тик>` (не больше 12 за запуск), читать `ddnet-ai clip held --track`.
- **Цель (`BotConfig::finish`, `TargetPicker::set_finish`).** Замороженная **текущая** цель не бросается как «устроенная» через 150 тиков или вне 2 тайлов от фриза
  (правило порта), а остаётся целью до `FINISH_MAX_HOLD_TICKS` = 600 тиков после заморозки, пока точный прогноз не скажет, что она **останется out ещё 250 тиков**
  (`PlanScratch::sealed_or_held` → `ddai_planner::forecast::passive_forecast`: жертва одна в мире, ввода нет, на реальной физике; в живом боте — на потоке
  `seal_worker`, как и прежняя проверка). Бонус удержания `FINISH_HOLD_SCORE` = 600 в радиусе 420 px (в порте `blockHoldScore` = 0). Прочие замороженные игроки — по-прежнему «устроены» сразу.
- **Гибрид (`BrainOptions::hybrid_finish` → `HybridConfig::with_finish`).** См. README `ddai-planner`: подтягивание замороженной жертвы к фризу (`frozen_drag_weight`)
  и наступательные техники против замороженной жертвы (`finish_families`).
- Включается ключом `ddnet-ai play --bot … --finish off|target|full` (умолчание `off`: на людях не проверено; `on` = `full`, старое написание). **`target`** — только правило цели бота (`BotConfig::finish`, `TargetPicker::set_finish`): часть с последовательными данными (в арене-толпе held W 259 → 342), **кандидат на живую A/B-проверку**. **`full`** добавляет подтягивание замороженной жертвы в оценке гибрида (`BrainOptions::hybrid_finish`, `HybridConfig::with_finish`): на дуэли прирост не подтвердился при ревью (E-021 §3), по умолчанию не рекомендуется. Живая проверка на приватном сервере (127.0.0.1:8483, свои скриптовые
  соперники) — E-021 §6.

## Copy Love Box: цели и сторона ВБ под `--wb-smart` (задача 3.12, D-103)

Выключено по умолчанию (`--wb-smart off`; `NavConfig::wb_smart`): без переключателя бот ведёт себя как раньше, байт в байт.

- **Почему «выбирает одних и не трогает других».** Простаивающий игрок (нет смены ввода 10 с или флаг AFK сервера: `awayInGame`) пропускался
  `pickTarget` до всех остальных проверок; на живой сессии 2026-10-06 такие игроки стояли на нижней полке обоих залов. Тест на настоящей карте
  и настоящих хуках — `target::tests::diagnosis_the_idle_tee_…`.
- **AFK — только если на пути** (`--wb-smart on`): в зале удерживаемой стороны (зона + 3 тайла), рядом (≤ 64 px) или на маршруте
  ходьбы (в 2 тайлах от ближайших 12 шагов и не дальше 256 px от нас). Друг, `ignore`, `/spec`-игрок и комната AFK — никогда. Ходьба
  отсекается («found a game on the way») ради такого игрока, только если он рядом (≤ 64 px; текущая цель держится до 96 px).
- **Сторона ВБ** — где больше блокируемых целей, при равенстве случайно (сид один на процесс; `NavConfig::seed` в тестах), с гистерезисом и
  памятью о провалах трубы (`crates/ddai-nav/README.md`). «Блокируемый»: жив, не друг / `ignore`, играет, не припаркован замороженным, в зале
  стороны (бодрый — и в её зоне / подходе); AFK считается только внутри зала.
- **Бой в нашем зале** (`fighting_here`; пока он идёт, принятая смена зала ждёт): крюк в любую сторону, наша текущая цель (какой её видело наведение
  последние 25 тиков) в 128 px или игрок, бивший по нам за последние 150 тиков. Свободный бодрый игрок, просто стоящий в 420 px, боем не считается
  (ревью 3.12 раунд 2, F8).
- Команда: `ddnet-ai play --brain hybrid --wb auto --finish target --wb-smart on …`. Через сайт («Запуск») переключатель пока не передаётся.
- **Переходы труб (задача 3.12b, D-104), тоже под `--wb-smart on`:** вне зала при удерживаемом ВБ тий после возрождения стоит на месте и идёт к залу сразу (**только первая попытка жизни**, `fresh_life`: дальше снова `WB_RETURN_TICKS`, ревью F12) (`wb_wander_hint`, `wb_return_ticks`: без этого свободный `wander` секунду ходил по ступеньке и падал в камеру); `Navigator::smart = CrossSmart { others, unblock }` (`ddai-nav`, README).

## Модель ввода соперника в окне лага (задача 3.17, D-111): `--window-model <файл>`

Выключено по умолчанию: без флага и без ключа `window_model` в `settings.toml` бот решает побитно как раньше (тест `off_is_the_default_and_a_killed_model_decides_exactly_like_no_model`, весь прежний набор).

- **Что делает.** Гибрид решает на мире, который бот предсказал до тика, куда ляжет наш ввод (окно лага ≈ 3–5 тиков), а соперник в этом броске «держит то, что показывает снапшот». С моделью (`ddai-oppnet`, `m1.oppnet`, вне git) цель в этом броске
  играет **предсказанные моделью** вводы (`LiveWorld::predict_local_observation_with`); дальше всё как раньше. Работает только при `--brain hybrid` и грузится только при старте (позднее `!brain hybrid` модель не подгрузит). Замороженная на всё окно цель не предсказывается (`skipped_frozen`). Шаги: `Bot::decide` — после выбора цели `observe` (каждый снапшот с целью кормит историю признаков), в ветке мозга `predict` вместо `predict_local_observation`.
- **Флаги.** `--window-model <файл>` или `window_model = "<путь>"` в `settings.toml` (флаг сильнее; ключ в `KNOWN_KEYS`). Файл читается при старте, sha256 — в журнал бота и в STATUS; не загрузился — бот не стартует. Маркер `<data-dir>/bot/window-model.off` выключает модель (читается раз в секунду, вне пути решения; пока есть — модель не вызывается и журнал не пишется).
- **Предохранитель** (`ddai_oppnet::live::guard`): сравнивает прогноз модели и «держит» с тем, что соперник показал в следующих снапшотах (направление, хук, прицел); при проигрыше > 5% на 250 окнах окно отдаётся «держит», модель оценивается в тени и возвращается не раньше чем через 500 окон и только если не хуже. Смены состояния — в журнал бота и в журнал модели.
- **STATUS** (аддитивно): `window_model` (`off`/`on`/`hold`/`killed`), `window_guard` (числа предохранителя). **Журнал** `bot/oppnet-live.jsonl` (≤ 8 МиБ × 4, поток; без ников); разбор `ddnet-ai oppnet-live report`. Формат — `docs/formats.md` §44; как ставить A/B — `docs/research/opponent-predictor-live.md` §7.
- **Тесты.** `tests/window_model.rs` (тождественность «выкл» / маркер, влияние на мир мозга, предохранитель, маркер, журнал без ников, 0 аллокаций), юнит-тесты `oppnet`, `ddai-oppnet::live`, `ddai-world` (`tests/live_bot_api.rs`), равенство признаков `ddai-env/tests/live_features.rs`, e2e на приватном сервере со скриптовым соперником
  `crates/ddai-bot/tests/e2e_window_model.rs` (`DDAI_E2E=1 cargo test -p ddai-bot --test e2e_window_model -- --ignored --nocapture --test-threads=1`).
