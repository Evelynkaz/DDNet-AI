# ddai-libm

Задача 5.5a (D-047, D-127). Листовой крейт без зависимостей и без `unsafe`: **переносимые, побитно точные порты математики glibc 2.39**.
Linux и Windows считают одни и те же числа.

## Зачем

Физика `ddai-physics` совпадает с сервером DDNet 20.1 побитно, потому что сервер на Linux зовёт glibc (`sinf`, `cosf`, `atanf`, `atan2f`,
`powf` и в `double` — `atan2`, `log`), а Rust на `linux-gnu` зовёт через `std` ту же glibc (D-004). На Windows `std` идёт в UCRT, у которой
последние биты другие: физика, поиск и предсказание молча разошлись бы с сервером. Крейт `libm` не выход (его `powf` расходится с glibc в 9,7%
проб, D-004), поэтому здесь порты алгоритмов самой glibc, и **все платформы пользуются ими**.

Порты сделаны с файлов glibc 2.39, а не с исходного проекта ARM (оттуда алгоритмы и таблицы: у ARM первые ревизии под Apache-2.0, с 2018-11-12
MIT, с 2022-02-10 «MIT OR Apache-2.0 WITH LLVM-exception»; все совместимы с GPL-3). Поэтому и лицензия у них glibc: LGPL-2.1+. Раздел 3 LGPL 2.1
позволяет применить к своей копии обычную GNU GPL вместо LGPL при одном условии: уведомления, которые ссылаются на LGPL, заменены на ссылающиеся
на GPL. В заголовке каждого такого файла это сделано (строки авторских прав FSF/IBM сохранены, абзацы о правах — из GPL, версия 3 или любая
более поздняя, пометка «Altered» с датой 2026-10-09), DDNet-AI целиком под GPL-3.0. Подробнее — `NOTICE`. `softfma.rs` и `selftest.rs` написаны
для DDNet-AI с нуля.

Использование: `ddai_libm::sinf(x)`, `ddai_libm::pow(x, y)` и т. д. Сигнатуры как у C.

## Какой именно glibc и откуда `fma`

Эталон — glibc 2.39 (Ubuntu 24.04) **на x86-64 с FMA3 и AVX2**: на таких CPU (все x86 за последнее десятилетие) загрузчик glibc (`ifunc`) выбирает
варианты `__sinf_fma`, `__powf_fma`, `__log_fma`, `__ieee754_atan2_fma`, `__pow_fma`. В них GCC слил `a + b * c` в fma, а код ARM для `log`/`pow`
идёт по веткам `__FP_FAST_FMA`. От варианта на чистом SSE2 результат отличается в последнем бите у малой доли входов (у `log` — 549 проб из 10⁷),
поэтому порты повторяют **именно слитые операции**: явные вызовы `fma` ровно в тех местах, где они есть в машинном коде `libm.so.6`
(найдено по дизассемблированию и подтверждено пробами). Правило GCC такое: умножение, результат которого входит только в сложения/вычитания
того же базового блока, сливается с первым из них; умножение за ветвлением (`EADD`/`ESUB` у `atan2`) не сливается — на этом правиле
потрескались бы два места из 11,6 млн проб, пока его не нашли.

Нужен `fma` с одним, правильным округлением. Какой именно запускается, решает `ddai_libm::fma_mode()` один раз за процесс:

1. сборка с `-C target-feature=+fma` — команда процессора (без проверок, порты на уровне скорости glibc);
2. `linux-gnu` на процессоре с FMA (определяется в рантайме средствами `std`) — `fma` из glibc, но только после сверки с собственным `soft_fma`
   крейта на ≈ 41 тыс. наборах угловых случаев (переполнение, потеря значимости, субнормальные, сокращение, ничьи, нули разных знаков);
3. везде иначе (Windows, musl, macOS, процессор без FMA, признак `force-soft-fma`) — `soft_fma`: точный `fma` на 128-битных целых, один раз
   округляет, написан с нуля, без `unsafe`.

Зачем: `fma` в glibc правильный, в mingw-w64 известно неверный на углах (Rust #140515, mingw-w64 bug 848), а программная ветка `fma` MSVC UCRT
(процессоры без FMA3) никем не проверена, и CI на `windows-latest` (FMA есть) её не покажет. Сам `fma` UCRT неверным **не признан**: первый прогон CI
выглядел так, будто он неверен, но причиной был вход самопроверки, посчитанный `exp2` платформы (исправлено). Поэтому чужим библиотекам C не верим:
это сознательный запас надёжности (≈ 7 % на `World::step`), а не доказанная необходимость.
Результат функций от выбора не зависит (проверено: `soft_fma` против команды процессора, 10⁹ наборов, 0 расхождений; все пробы и хэши с
`--features force-soft-fma`). `ddai_libm::self_test()` проверяет то же на машине пользователя (`fma` и по 20 тыс. проб на функцию против
хэшей из glibc, несколько миллисекунд); бот вызывает её перед игрой и отказывается играть, если она не прошла. Более быстрый путь на Windows
(копии функций с `#[target_feature(enable = "fma")]` и запуск после `is_x86_feature_detected!`) требует `unsafe`, которого в крейте нет; для
процессоров, заведомо имеющих FMA, можно собрать с `-C target-feature=+fma`.

Цена: без `+fma` в `RUSTFLAGS` (политика репозитория не кладёт `target-cpu` в конфиг, D-001) на Linux каждый `fma` — вызов `fma` из glibc, и порты медленнее
glibc (таблица ниже); на Windows и на CPU без FMA — ещё медленнее (`soft_fma` ≈ 54 нс на вызов, `sinf`/`cosf` ≈ 14×, `powf`/`pow`/`log` ≈ 26–39× медленнее glibc, то есть 0,2–1 мкс на вызов). На результат это не влияет.

## Проверка

`tests/glibc_probe.rs` (только Linux: сравнивает с glibc через `std`, побитно, включая полезную нагрузку и знак NaN):

- `cargo test -p ddai-libm` — набор для CI: списки особых значений (±0, субнормальные, ±inf, NaN всех сортов, степени двойки и соседи,
  пороги каждой ветки) и по 10⁵ проб на функцию;
- `cargo test --release -p ddai-libm --test glibc_probe -- --ignored` — по 10⁷ проб (`LIBM_PROBES=n` меняет число);
- `… -- --ignored exhaustive` — **все 2³² входа** `f32` для `sinf`, `cosf`, `atanf` (3 потока, 2,5 мин на пару sin/cos);
- `… -- --ignored atan2_every_integer_aim_vector` — все целые векторы прицела в окне ±4096 (`LIBM_AIM=n`) для `atan2(int, int)`, как в
  `CCharacterCore::Tick`.

`tests/golden.rs` (**любая платформа**): фиксированная детерминированная последовательность проб (генераторы в `tests/common/mod.rs` используют
только целочисленную арифметику и базовые операции IEEE, без libm), результаты считаются здесь, хэши FNV по блокам по 4096 результатов лежат в
`tests/golden/hashes.txt` и записаны с самой glibc (`cargo test --release -p ddai-libm --test golden -- --ignored regenerate`). Это тест, ради
которого заведена Windows-задача CI: числа с Linux должны совпасть на Windows бит в бит.

Таблицы (`src/tables.rs`) порождает `tools/libm-tables/gen_tables.py` из исходников glibc 2.39 (`~/aiddnet/ref/glibc-2.39`).

## Скорость

`cargo run --release -p ddai-libm --example speed` (нс на вызов, лучшая из 5; пропускная способность — независимые вызовы, задержка — каждый
вызов ждёт предыдущий). Цифры и сравнение со сборкой `+fma` — в записи D-127 (`docs/DECISIONS.md`).
