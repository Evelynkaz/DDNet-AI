# ddai-brain

Задача 7.3. Общий интерфейс «мозга» бота: `Brain` — то, что реализует любой принимающий решения
модуль (планировщик, скриптовый бот, муха `ddai-fly::FlyBrain`, позже — воспроизведение записей
людей), плюс общее пространство наблюдения/действия (`Observation`/`Action`), через которое живой
бот или арена общаются с текущим «мозгом», не зная, какая конкретно реализация сейчас за рулём.

Крейт не тяжёлый: единственная зависимость — `ddai-physics` (сама без зависимостей) — тайлы карты
(`ddai_physics::map::MapData`) и формат провода (`PlayerInput`/`CNetObj_PlayerInput`).

## `Observation`

Плоские данные, `Clone`, без ссылок в живой мир (можно клонировать в буфер обучения, передавать
между потоками): `map: Arc<MapData>` (общий хендл — не клонируется по значению на каждый тик),
`tick`, `self_state: CharacterObservation`, `others: Vec<CharacterObservation>` (порядок не имеет
значения), `target_id: Option<i32>`, `tuning: TuningParams` (весь набор тюнинга целиком — он уже
маленький и `Copy`, так что не нужно урезать поля вручную под «то, что нужно сейчас»).

**`target_id`/`target_or_nearest` (ревью раунд 1 задачи 7.3, F13, подтверждено):** какого из
`others` выбрала внешняя логика выбора цели (вне этого крейта). `Observation::target_or_nearest()`
резолвит его в реальный `CharacterObservation` — выбранный по `id`, если он `Some` и всё ещё
присутствует среди `others` (устаревший id, скажем, отключившегося игрока, не «залипает» на
`None`), иначе ближайший по прямому расстоянию до `self_state.pos`. Раньше единственным
потребителем (`ddai-fly::encoder`) молча использовался `others[0]` — вопреки собственному doc
comment у `others`, что порядок не значит ничего; `others.iter().min_by(...)` через
`ddai_physics::vmath::length_squared` — единственная реальная логика выбора «ближайшего»,
живущая здесь, а не дублируемая у каждого потребителя.

`CharacterObservation` — одна и та же структура для себя и для других персонажей (задание прямо
просит «other characters (same fields + id/team)»): позиция/скорость, состояние/позиция хука и
`hooked_player` (`-1` = никого, тот же нуль-конвенция, что у `CharacterCore::hooked_player()`),
фриз/deep-фриз/live-фриз и оставшиеся тики до оттаивания, прыжки (осталось/использовано),
`grounded`, оружие, направление. Константы `HOOK_IDLE`/`HOOK_FLYING`/`HOOK_GRABBED`/... —
реэкспорт `ddai_physics::core`'s, чтобы не тащить вторую зависимость на `ddai-physics` только за
ними.

## `Action`

`direction` (`-1/0/1`), `jump`/`hook`/`fire` (булевы — **уровень**, не грань нажатия), `target:
IVec2` (целочисленный вектор прицела относительно ти, конвенция DDNet), `wanted_weapon:
Option<i32>`. Свой `IVec2` (не `ddai_physics::vmath::Vec2<R>`, который параметризован только
`Real` — `f32`/`f64`, не `i32`).

`to_player_input()`/`from_player_input()` конвертируют в/из `ddai_physics::core::PlayerInput`
(проводной формат `CNetObj_PlayerInput` DDNet 20.1) — **разница уровня/грани нажатия** (задание
прямо разрешает оставить это на вызывающего, но требует задокументировать): `jump`/`hook` физика
ядра читает как обычный булев «держится сейчас» (`Input().m_Jump != 0`), а `fire` в проводном
формате — счётчик нажатий (младший бит = «нажато сейчас») — `to_player_input` всегда отдаёт
`0`/`1` (то есть «только что нажато» при каждом вызове, если `fire == true`); клиенту, который
хочет корректную семантику удержания огня для автоматического оружия, нужно самому вести счётчик
переходов 0→1 между вызовами. `target == (0, 0)` заменяется на `(0, -1)`: провод DDNet никогда не
хранит нулевой вектор прицела (`docs/formats.md` §2). `wanted_weapon`: провод `0` = «не менять»,
`N` (`1`-based) = «слот `N-1`» — конвертация `+1`/`-1` спрятана здесь, `Action::wanted_weapon`
остаётся простым `0`-based индексом.

`mirror_x()` — X-отражение (`direction`/`target.x` меняют знак, остальное не трогается).

## Зеркалирование (`mirror.rs`, задача 8's mirror-symmetry test)

Одно отражение через вертикальную ось **карты** (`x -> width_px - x`) применяется **и к тайлам, и
к позициям персонажей вместе** — не только к персонажам: у реальной (не собранной вручную)
карты, если отразить только персонажей, лучевая кассета/декодер будет «видеть» геометрию, не
соответствующую никакому настоящему миру. `mirror_map_data` реально переворачивает только
`game`/`front` (единственные слои, которые читает лучевой кодировщик, `ddai-fly::encoder`) —
`tele`/`speedup`/`switch`/`tune` в отражённой копии отсутствуют (`None`): корректно отразить
номер телепорта или направление свитч-двери — вне рамок того, что сейчас нужно любому потребителю
отражённого `Observation`.

## Тесты

`cargo test -p ddai-brain` — 15 юнит-тестов: круговой обход `Action` <-> `PlayerInput` (включая
грань `fire`, `target == (0,0)`, `wanted_weapon`), `mirror_x()` дважды возвращает исходное
значение, `mirror_map_data` реально переставляет столбцы (проверено на **несимметричной** карте —
симметричная карта прошла бы тест и при сломанной реализации), `Observation::other_by_id`
исключает собственный id, `Observation::target_or_nearest` (предпочитает явный `target_id`,
откатывается к ближайшему при `None`/устаревшем id, `None` при пустых `others`).
