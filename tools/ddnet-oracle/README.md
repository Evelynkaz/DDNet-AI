# Oracle A — C++-эталон физики DDNet (core-уровень)

Собирает и запускает реальные `gamecore.cpp`/`collision.cpp`/`layers.cpp`/`teamscore.cpp`/
`prng.cpp` из исходников DDNet 20.1 (тег `20.1`, коммит
`c9d208138f85755521f16a0096b6fe036c5c8698`) против сценария (карта + вводы), core-уровень
только: `CCharacterCore::Tick`/`TickDeferred`/`Move`/`Quantize`, без DDRace-логики персонажа
(без фриза, тайловых эффектов, оружия — это Oracle B, будущая задача). Пишет побайтово
детерминированный трейс (`docs/formats.md`, раздел 6). Задача 1.3 (Rust-порт
`CCharacterCore`/`CCollision`) должен совпасть с этими трейсами без единого расхождения.

Исходники DDNet **не коммитятся** в этот репозиторий — `fetch.sh` каждый раз скачивает их в
`build/` (в `.gitignore`). Файлы этого каталога (`oracle_core.cpp`, `sha256.h`, `*.sh`, `*.py`)
— наш собственный код (GPL-3.0-only, как весь репозиторий); ни строчки DDNet сюда не
скопировано, только вызовы через заголовки после сборки объектных файлов из скачанного дерева.

## Использование

```bash
cd tools/ddnet-oracle
./fetch.sh                 # один раз (и повторно — идемпотентно, если коммит уже верный)
./build.sh                 # собирает build/oracle_core

# Карту и сценарий готовит Rust CLI (crates/ddnet-ai), не оракул:
../../target/release/ddnet-ai trace export-map --recipe arena --out /tmp/arena.rawmap
../../target/release/ddnet-ai trace gen-scenario --recipe arena --seed 1 --ticks 3000 --chars 3 --out /tmp/s.scn

build/oracle_core /tmp/arena.rawmap /tmp/s.scn /tmp/out.trace --generator random-v1 --seed 1
# stderr: "oracle_core: N ticks, M characters, K tee-ticks/s, wrote ... (... bytes)"

../../target/release/ddnet-ai trace diff /tmp/out.trace /tmp/out2.trace
../../target/release/ddnet-ai trace hashes /tmp/out.trace --out /tmp/hashes.json

# no_weak_hook / tuning-переопределения — отдельные флаги gen-scenario (не параметры
# random-v1, см. docs/formats.md §2): один сценарий может задать оба сразу, хотя bulk_run.sh
# (ниже) прогоняет их как два отдельных слайса, не смешивая (раунд 2, находка F11).
../../target/release/ddnet-ai trace gen-scenario --recipe arena --seed 1 --ticks 3000 --chars 3 \
    --no-weak-hook --tune gravity=40 --out /tmp/s_nwh.scn

./selftest.sh               # полная проверка детерминизма + throughput
./gen_fixtures.sh           # пересборка золотых фикстур (после изменения генератора/оракула)
./bulk_run.sh                # ≥ 240 сценариев в ~/aiddnet/data/traces/oracle-a/v1/
```

`--generator`/`--seed` у `oracle_core` — необязательная аннотация в JSON-метаданных трейса
(`docs/formats.md` §6.1), сама симуляция от них не зависит: оракул воспроизводит ровно то, что
записано в файле сценария (и проверяет его `map_sha256` перед запуском).

## Почему так собрано

- **Не патчим DDNet.** `m_MoveRestrictions` у `CCharacterCore` приватное и без геттера — вместо
  патча заголовка оракул повторяет тот же (чистый, `const`) запрос к `CCollision` в нужный
  момент тика (см. `docs/formats.md` §5.5) и получает то же самое значение доказуемо, а не
  предположительно.
- **Флаги сборки** — `-std=c++20 -O2 -fno-fast-math -ffp-contract=off -fsigned-char`, без
  `-march`: тот же набор, что и в прототипе фазы 0
  (`data/research/physics-scratch/run.sh`) и что подтверждено экспериментом
  (`docs/research/ddnet-physics.md` §4) не давать FMA-контракции на x86-64 без `-march`, что
  важно для побитового совпадения с Rust `f32`.
- **Список компилируемых `.cpp`** — `gamecore`, `collision`, `layers`, `teamscore`, `prng`;
  `mapitems.cpp` не компилируется (её свободные функции не вызываются ни из одного из
  вышеперечисленных файлов — проверено `grep`); `prng.cpp` нужен, даже когда `CWorldCore::m_pPrng
  == nullptr` (что здесь всегда так — оракул никогда не вызывает `InitSwitchers`/не задаёт PRNG):
  `CWorldCore::RandomOr0` — не шаблон, содержит вызов `m_pPrng->RandomBits()` под `if`, поэтому
  символ нужен линкеру независимо от того, выполнится ли эта ветка в рантайме.
- **`CTuningParams` без раунд-трипа через float.** Переопределения тюнинга применяются через
  `NetworkArray()[index] = value_x100` в обход `CTuningParams::Set(name, float)` — тот сам умножает
  на 100, а обратное деление/умножение float может не восстановить исходное целое (см.
  `docs/formats.md` §2).
- **Явный zero-init `CCharacterCore`.** `Reset()` не трогает `m_ActiveWeapon`/`m_Colliding`/
  `m_LeftWall`/`m_MoveRestrictions`/`m_Id` — на реальном сервере их устанавливает код вокруг
  `CCharacter`, которого здесь нет. `std::vector<CCharacterCore>(N)` (value-initialization)
  гарантирует, что все они стартуют с `0`/`false` — см. `docs/formats.md` §5.6, это часть
  контракта для задачи 1.3.
- **Валидация id/`aim_slot` (раунд 1, находка F5).** `ParseScenario` отклоняет `id >=
  MAX_CLIENTS` (реальная константа DDNet — **128**, `engine/shared/protocol.h`; черновик
  находки F5 в отчёте ревью называл 64 — это `LEGACY_MAX_CLIENTS`, не тот предел, который тут
  важен, см. build report), дублирующиеся `id`, и `aim_slot` вне `-1..characters.size()` — до
  того, как эти значения дошли бы до `World.m_apCharacters[Id]` (реальный размер массива).
- **`resolve_input`/`aim_slot` (раунд 1, находка F3).** Оракул разрешает «прицел» персонажа
  заново каждый тик, читая `Cores[k].m_Pos` (целочисленное после `Quantize()`) в `int32_t`
  арифметике — см. `docs/formats.md` §2.1 для полного алгоритма; здесь важно только то, что это
  ОТДЕЛЬНАЯ от Rust-реализации (`crates/ddai-trace/src/scenario.rs::resolve_input`), но
  алгоритмически идентичная копия — обе стороны специфицированы одним и тем же текстом в
  `docs/formats.md`, а не одна вызывает другую.

## Известные ограничения (вне охвата этой задачи)

Нет weapons/freeze/tiles/switch-дверей/tune-зон — это `CCharacter`-уровень (Oracle B). Свитчеры
(`switch`-слой) в этом харнессе всегда неактивны (`m_vSwitchers` не заполняется) — двери не
работают, но `STOP`/`STOPS`/`STOPA` из front/game-слоя от свитчеров не зависят и проверяются
рецептом `front` напрямую.

## `map2raw` (задача 1.4) — чтение настоящих `.map`-файлов

Отдельный от `oracle_core` инструмент: читает настоящий DDNet `.map` (datafile v3/v4) через
РЕАЛЬНЫЙ, не переписанный код DDNet (`engine/shared/datafile.cpp` + `engine/shared/map.cpp` +
`game/layers.cpp`, из тех же скачанных `fetch.sh` исходников) и пишет физические слои
(game/front/tele/speedup/switch/tune, обрезанные до размера game-слоя — как это фактически
делает `CCollision::Init`) + Settings в формате rawmap v1 (`docs/formats.md` §1) — то же самое,
что производит `ddnet-ai trace export-map --map <file> --out <file.rawmap>` (крейт `ddai-map`).
Задача 1.4: `crates/ddai-map/src/loader.rs` должен совпасть с этим побайтово на всём корпусе карт.

```bash
./build.sh                      # собирает build/map2raw вместе с build/oracle_core
build/map2raw input.map out.rawmap

# Паритет на корпусе (см. tools/ddnet-oracle/map-corpus-check.sh):
cd ../.. && cargo build --release -p ddnet-ai && cd tools/ddnet-oracle
./map-corpus-check.sh ~/aiddnet/data/research/proto-scratch/ddnet-maps \
    ~/aiddnet/data/maps/copy-love-box ~/aiddnet/data/research/physics-scratch/maps

# Дифференциальный мутационный фаззинг (раунд 1 ревью — настоящие карты в корпусе выше все
# ПРИНИМАЮТСЯ обеими сторонами, так что сам корпус не проверяет паритет на ОТКЛОНЕНИЕ; этот режим
# портит случайные поля внутри LAYER-item'ов настоящей карты и сравнивает результат):
./map-corpus-check.sh --mutate ~/aiddnet/data/research/physics-scratch/maps/BlockField.map \
    --seed 42 --iterations-per-map 1000
```

### Песочница по памяти/времени (раунд 2 ревью, находка F7)

И `map-corpus-check.sh`, и `map_mutation_fuzz.py` запускают **оба** инструмента — `build/map2raw`
И `../../target/release/ddnet-ai trace export-map --map` — под жёстким лимитом виртуальной памяти
и таймаутом: `prlimit --as=2147483648` (2 ГиБ) + `timeout --signal=KILL 20s`. Причина: `map2raw`
линкует настоящий, немодифицированный код DDNet, у которого (как и у самого DDNet) нет гарантий
ограниченной памяти — намеренно испорченная (мутационным фаззером) карта может попросить у
`ReadSettings`/`std::vector` сотни миллионов записей и упасть в `std::bad_alloc`/`abort()` (реальный
инцидент раунда 1: ~6.8 ГиБ RSS на карте с испорченной v4 declared-size таблицей для Settings-блоба,
`settings_bomb_256m.map` в отчёте о билде). Классификация кода выхода под лимитом: `0` — приняла,
`1` — собственный чистый отказ инструмента (`Fail()`/код ошибки `ddai-map`), что угодно другое
(`124`/`137` от `timeout`, `128+сигнал` от `prlimit`) — инструмент упёрся в СВОЙ лимит, а не дал
осмысленный ответ. Для `map2raw` это репортится отдельно (`cpp (map2raw) resource-limited`) и НЕ
считается расхождением — ожидаемая, документированная форма (`ddai-map`'s bounded reads, критерий
приёмки №2 задачи 1.4, — именно то, чего у real-DDNet-кода нет). Для `ddnet-ai`/`ddai-map` тот же
код выхода — это всегда баг (`RUST/ddai-map crashed`) и всегда проваливает прогон: критерий №2
обязывает `ddai-map` никогда не падать и никогда не выделять память пропорционально заявленному
(а не реальному) размеру данных, так что сам Rust-инструмент не должен упираться в этот лимит на
файле любого размера, каким бы испорченным он ни был.

`map2raw.cpp` — своя (не DDNet) обвязка: минимальный `IStorage` (открывает путь к файлу напрямую
через `io_open`, без реальной подсистемы хранения), заглушки для `g_UuidManager`/`CUuid` (все
типы карточных item'ов, которые нас интересуют — VERSION/INFO/GROUP/LAYER — намного меньше
`OFFSET_UUID`, так что реальный код `g_UuidManager` никогда не вызывается для них, см. комментарий
в файле) и `log_log`/`log_log_color` (не нужен вывод DDNet, ошибки видны через код возврата
`CMap::Load`). Компилирует РЕАЛЬНЫЕ `base/{str,mem,io,hash_libtomcrypt,bytes,unicode/tolower*}.cpp`
— не переизобретает их — подробности и обоснование каждой заглушки в шапке `map2raw.cpp`.

`map2raw` повторяет «ленивый» `nullptr`-фолбэк DDNet (`CCollision::Init` оставляет указатель
`nullptr`, если данные КОНКРЕТНОГО не-game физического слоя не декомпрессировались, — карта всё
равно загружается, этот слой просто отсутствует) — `GetGameLayerData` (жёсткий отказ, как у
настоящего `CMap::Load` для game-слоя) отдельно от `GetOptionalPhysicsLayerData` (мягкий, как у
`CCollision::Init`, для всех остальных). `ddai-map`'s единственный оставшийся bounded-allocation
предел сверх собственных проверок DDNet — см. `crates/ddai-map/src/lib.rs`'s top-level doc
comment, `docs/formats.md` §10.2 и отчёт о билде задачи 1.4.

## `demo2json` (задача 8.4b) — чтение настоящих `.demo`-файлов

Отдельный от `oracle_core`/`map2raw` инструмент: читает настоящий `.demo` через РЕАЛЬНЫЙ,
неизменённый код DDNet (`engine/shared/demo.cpp` + `snapshot.cpp` + `compression.cpp` +
`huffman.cpp`) и пишет per-tick JSON-строки с элементами полностью раскрытого снапшота (ключ +
сырые `i32`-данные, в порядке файла) — подробный разбор формата и всех заглушек этого файла
(`CNetBase::Compress`/`Decompress` против собственного `CHuffman`, статические размеры типов
через `sizeof`, минимальный `IStorage` и т.д.) — в шапке `demo2json.cpp` и `docs/formats.md`
§18.5. То же самое, только на Rust, делает `ddnet-ai demo dump --raw` (крейт `ddai-demo`,
задача 8.4b) — оба должны совпасть байт-в-байт на любом реальном `.demo`.

```bash
./build.sh                        # собирает build/demo2json вместе с остальными
build/demo2json input.demo out.jsonl

# Паритет на корпусе (нужен и build/demo2json, и release-сборка ddnet-ai):
cd ../.. && cargo build --release -p ddnet-ai && cd tools/ddnet-oracle
./parity_check_demo.sh ~/aiddnet/data/demos/chillerdragon/block-06 ~/aiddnet/data/demos/public-samples
```

Тот же принцип песочницы, что и у `map2raw` (см. выше): `parity_check_demo.sh` гоняет оба
инструмента под `prlimit --as=2147483648` + `timeout --signal=KILL 60s` (демки крупнее карт —
таймаут больше), `demo2json`-упор-в-лимит репортится отдельно и не считается расхождением,
`ddnet-ai`-упор-в-лимит — всегда баг. Результаты полного прогона — `docs/formats.md` §18.7 и
отчёт о билде задачи 8.4b.

# Oracle B — полный сервер DDNet (задача 1.5)

В отличие от Oracle A (только `CCharacterCore`/`CCollision`), Oracle B гоняет **настоящий,
немодифицированный** игровой код сервера DDNet 20.1 — `CGameContext`/`CGameWorld`/`CCharacter`/
контроллер/команды, т. е. 100% серверной игровой логики: фриз (обычный/deep/live), разморозку,
смерть, телепорты, спидапы, стопперы, switch-слой/двери, tune-зоны, endless-хук, jump-тайлы,
NPC/NPH/HIT-тайлы, solo/команды, молоток и другое оружие, пикапы, респавн — тик за тиком, без
сети, под управлением входов из сценария (те же rawmap/scenario, что и Oracle A) или собственного
харнесс-генератора для настоящих `.map`-файлов. Пишет trace-b v1 (`docs/formats.md` §11) —
отдельный, более полный формат, НЕ версия trace v1 Oracle A (тот зафиксирован под задачу 1.3 и не
меняется).

Подробности — `docs/formats.md` §11-9 (форматы, точная схема, бутстрап/цикл тика с ссылками
file:line, харнесс-генератор для настоящих карт, детерминизм PRNG, техника доступа к приватным
полям). Здесь — только сборка/запуск и известные ограничения.

## Сборка и запуск

```bash
cd tools/ddnet-oracle
./build-server-oracle.sh          # тянет отдельную копию DDNet 20.1, собирает build/ddai_oracle_server
                                   # (~/aiddnet/build/oracle-b/ — НЕ трогает ~/aiddnet/build/ddnet-20.1,
                                   # на котором держится ddnet-local.service)

# режим 1: рецепт/rawmap + сценарий v2 (тот же формат, что видит Oracle A — без изменений)
../../target/release/ddnet-ai trace export-map --recipe arena --out /tmp/arena.rawmap
../../target/release/ddnet-ai trace gen-scenario --recipe arena --seed 1 --ticks 3000 --chars 3 --out /tmp/s.scn
BIN=~/aiddnet/build/oracle-b/build/ddai_oracle_server
$BIN --storage-dir /tmp/storage --rawmap /tmp/arena.rawmap --scenario /tmp/s.scn \
     --seed 1 --out /tmp/out.trb

# режим 2: настоящий .map-файл, харнесс сам генерирует спавны/вводы (docs/formats.md §12.3);
# --emit-scenario-v3 пишет рядом (rawmap + scenario v3), которые воспроизводят этот же трейс
# побайтово БЕЗ .map-файла и без харнесс-генератора (docs/formats.md §12.6, находка F5)
$BIN --storage-dir /tmp/storage2 --real-map /path/to/map.map \
     --seed 42 --ticks 3000 --chars 3 --out /tmp/out2.trb \
     --coverage-out /tmp/cov.json --emit-scenario-v3 /tmp/replay.scn

# воспроизведение из scenario v3 (тот же --rawmap/--scenario путь, версия читается автоматически)
$BIN --storage-dir /tmp/storage2b --rawmap /tmp/replay.rawmap --scenario /tmp/replay.scn \
     --seed 42 --out /tmp/out2_replayed.trb
cmp /tmp/out2.trb /tmp/out2_replayed.trb   # идентичны после metadata JSON (разная только provenance-аннотация)

# консольные команды (sv_*, tune/tune_zone) — выполняются ДВАЖДЫ (до и после OnInit, см.
# docs/formats.md §12.1 шаг 8 — находка F1: tune/tune_zone теряются, если выполнить только один
# раз до OnInit) — до первого тика; назначение DDRace-команды напрямую
$BIN --storage-dir /tmp/storage3 --real-map /path/to/map.map --seed 1 --ticks 100 --chars 2 \
     --cfg /path/to/commands.cfg --team 0=5 --team 1=5 --out /tmp/out3.trb

# сверка с Oracle A (тот же файл сценария, что и у Oracle A) на 27 из 28 core-полей

$BIN --storage-dir /tmp/storage4 --rawmap /tmp/arena.rawmap --scenario /tmp/s.scn --seed 1 \
     --out /tmp/out4.trb --compare-oracle-a /tmp/oracle_a_out.trace

../../parity_check_b.sh 20      # ≥ 20 сценариев, агрегированный отчёт
../../bulk_run_server.sh        # полный корпус ≥ 500 сценариев
```

### Сверка вторым методом (раунд 3 — весь корпус, не один файл)

Раунд 2 сверял вторым методом (независимый Python-декодер, читающий ТОЛЬКО документированный
байтовый макет trace-b, без обращения к живым переменным харнесса) один файл. Раунд 3 гоняет тот
же принцип декодера на **ВСЕХ 650 файлах корпуса** и суммирует — сильнее проверка (покрывает
100% корпуса, не образец): **20 из 23 счётчиков совпали ТОЧНО** (все, кроме трёх — список ниже)
— `character_ticks`, `frozen_ticks`, `deep_frozen_ticks`, `live_frozen_ticks`, `freeze_entries`,
`freeze_exits`, `stopper_ticks`, `tune_zone_ticks`, `hammer_swings`, `hook_grabs`,
`switch_toggles`, `solo_ticks`, `jetpack_ticks`, `endless_jump_ticks`, `super_ticks`,
`collision_disabled_ticks`, `hook_hit_disabled_ticks`, `nonzero_team_ticks`, `died`,
`respawned`. Три счётчика намеренно НЕ сверены этим методом (та же причина, что и
раунд 2 их тоже не сверял): `teleport_ticks`/`speedup_ticks` (нужен живой `CCollision` —
тайл-в-позиции — которого у чистого байтового декодера нет) и `hammer_hits` (нужна формула
`FireWeapon()` с учётом тюн-зоны конкретного персонажа) — эти три проверены иначе: реальными
прогонами на настоящих картах с логом (`teleport_ticks` — см. таблицу выше, ненулевой и
пропорциональный на 6 картах, честный 0 на `Blockdale`), и через сам факт, что `hammer_hits` ≤
`hammer_swings` везде и в разумной пропорции (48-60%), что уже проверялось построчно против
`FireWeapon()`'s формулы в раунде 2 (не заново в раунде 3, код этой формулы не менялся).

### Известное, честно задокументированное свойство: `recipe_tele-speedup` — 0 телепортов

Синтетический рецепт `tele-speedup` (task 1.2, `crates/ddai-trace/src/synthetic.rs`, вне охвата
этой задачи — не трогали) кладёт свой ряд тайлов-телепортов на `y=5` в открытой карте 34×20 с
полом на `y=17` — персонажу нужно подняться на ~11 клеток над полом, чтобы вообще коснуться
этого ряда. `random-v1` (Rust-генератор, тоже вне охвата) — ненаправленное блуждание с
прыжками/хуком, не «целится» в конкретные тайлы. Проверено напрямую: те же самые 40 seed'ов/4
персонажа/3000 тиков, что и в самом корпусе, дают `teleport_ticks=0` КАЖДЫЙ раз (детерминированно,
не один неудачный прогон) — при этом ТОТ ЖЕ детектор даёт уверенно ненулевые, пропорциональные
числа на 6 из 7 настоящих карт (25-397 на карту, таблица выше), так что это не дефект детектора
(F13), а структурное свойство ЭТОГО рецепта + ЭТОГО генератора движения, оставленное как есть
(вне охвата задачи 1.5 — правка синтетических рецептов/генератора `random-v1` — задача 1.2).

## Известные ограничения (обоснованы фактами, не предположениями)

- **Оставшиеся нулевые счётчики покрытия — обоснованы сканированием тайлов, не угадыванием.**
  Прогнав `--emit-scenario-v3` на 1 тик по каждой из 7 настоящих карт и просканировав
  получившиеся rawmap-файлы на конкретные индексы тайлов:
  - `TILE_JETPACK_ENABLE`(106)/`TILE_UNLIMITED_JUMPS_ENABLE`(105) **есть** на `BlmapChill`, но
    `jetpack_ticks`/`endless_jump_ticks` всё равно 0 — тайлы существуют, но ни рецепт, ни
    харнесс-генератор не целятся в них специально, и случайное блуждание/подсчёт свободных
    клеток не привёл персонажа на эту конкретную клетку за 70 сценариев на этой карте.
    Не «невозможно», а «не задета этим прогоном» — честно отражено, не подделано.
  - `TILE_NPC_DISABLE`(88)/`TILE_NPH_DISABLE`(91) (единственные тайлы, способные ВЫСТАВИТЬ
    `collision_disabled`/`hook_hit_disabled` в `true` — `character.cpp:1713-1734`) **отсутствуют

    лишь СНИМАЮТ уже включённый флаг — без своего `_DISABLE` включить их не через что). Реально
    недостижимо на этом наборе карт, не ограничение харнесса.
  - `TILE_LFREEZE`(144)/`TILE_LUNFREEZE`(145) (`live_frozen`) **отсутствуют на всех 7 картах** —
    подтверждено тем же сканированием. Сама механика в trace-b дампится и реально устанавливается
    настоящим кодом сервера (`character.cpp:1675-1681`, проверено построчно) — просто нет тайла,
    который бы её включил, ни на одной из карт, которые есть в этом проекте.
  - `super`/`invincible` — устанавливаются ТОЛЬКО через `CCharacterCore::ReadDDNet()` (сетевой
    снапшот `CNetObj_DDNetCharacter`, `game/gamecore.cpp`) или через тестовые rcon-команды
    (`ddracecommands.cpp`, `CMDFLAG_TEST`) — этот харнесс никогда не открывает сеть и не
    выполняет команды такого уровня доступа, так что структурно недостижимо этим харнессом,
    независимо от карты (задокументировано и в docs/formats.md §11.3 списком «сознательно не
    включено в сверку», по аналогии с тем, как это же для Oracle A отмечено в §5.6).
- **Свитчеры (switch-двери) в trace-b — ИСПРАВЛЕНО раундом 3 (находка F14).** Раньше дампилась
  только команда 0 (`TEAM_FLOCK`); теперь — каждая DDRace-команда, реально присутствующая среди
  персонажей прогона (список — в заголовке файла, `docs/formats.md` §11/§11.2). Остаточное
  ограничение: команда, заданная позже самим сценарием на лету (этот харнесс такого не делает —
  команда персонажа фиксирована на весь прогон) не была бы отражена, но такого сценария в этом
  корпусе нет.
- **Карта-фикстуры (двери/тягачи/тросы/турели/свет) — ЧАСТИЧНО ИСПРАВЛЕНО раундом 3 (находка
  F6).** Раньше не дампились вовсе; теперь дампятся как `EntityRecord` kind 2-6 — но только
  позиция (`CEntity::m_Pos`, публичное поле у всех), и для `CLight` — ещё несколько его
  собственных публичных полей. Их остальное состояние (направление/сила/фриз/explosive/кого
  тащит тягач) лежит в неявно-приватной секции этих классов в этой сборке DDNet — `#define
  private public` (текстовая подстановка токена) не может его достать без правки заголовков
  DDNet, чего этот харнесс сознательно не делает (см. `docs/formats.md` §11.2/§12.5 для полного
  разбора, по классу). Их СИМУЛЯЦИОННО значимое состояние (открыта/закрыта дверь, номер свитча)
  уже покрыто дампом свитчеров, не завязано на этот пробел.
- **Харнесс-генератор для настоящих карт** (`--real-map`) — своя, отдельная от Rust
  (`crates/ddai-trace`) реализация SplitMix64 и алгоритма спавна/ввода (`docs/formats.md` §12.3);
  НЕ сверялась побитово с Rust-генератором `random-v1` (разные генераторы по построению —
  настоящие карты против синтетических рецептов), только специфицирована тем же текстом
  алгоритма.
- **Сетевой доступ, честно (находка F9).** `pServer->RegisterCommands()` (нужен для регистрации
  `tune`/`sv_*`-команд, которые исполняет `--cfg`) вызывает `CServerBan::InitServerBan()` →
  `CNetBan::Init()`, которая делает `net_host_lookup("localhost", ...)` — однократный DNS-запрос
  за именем «localhost» (подтверждено `strace`: UDP-пакет на `127.0.0.53:53`, локальный
  stub-резолвер systemd-resolved, никогда не покидает машину). Это НЕ слушающий сокет, не
  подключение куда-либо вовне, не регистрация на мастер-сервере — но и не буквально «вообще нет
  сокетов». Нетривиально избежать без переизобретения `RegisterCommands()` целиком (~1000 строк
  регистрации команд DDNet) — оставлено как есть, задокументировано честно вместо формулировки
  «сокетов нет совсем». `pEngineHttp->Init()` (как и в `gameworld_test.cpp`) — тоже только
  инициализация клиентской библиотеки curl, ни одного HTTP-запроса харнесс не выполняет.
- **Оружейные/ниндзя/фризовые поля из-за которых Oracle A не сравнивался с Oracle B напрямую**
  — единственное намеренно исключённое из сверки поле — `active_weapon` (см. `docs/formats.md`
  §12.4); остальные 27 core-полей сравниваются как есть.
- **Синтетические рецепты (`arena`/`freeze`/`front`/`tele-speedup`) не имеют тайлов-спавнов**
  (`ENTITY_OFFSET`+`SPAWN`) — у них его никогда и не было, они предназначены для Oracle A
  (core-only, без смерти/респавна вовсе). Первый спавн каждого персонажа в любом случае идёт
  через `ForceSpawn` (позиция из сценария, тайл-спавн не нужен), но если персонаж умирает
  (например, наступив на `TILE_DEATH` в рецепте `freeze`) — он **не респавнится**: контроллер не
  находит точку спавна. **Раунд 3 (находка F12) сузил область действия политики
  «самоубийство при затяжной заморозке» до ТОЛЬКО `--real-map`** (`docs/formats.md` §12.3/§12.6 —
  бит `kill` физически не существует у scenario v2, на котором построены все 4 синтетических
  рецепта в этом корпусе) — так что рецепты теперь НИКОГДА не инициируют такое убийство сами; в
  `recipe_freeze` персонаж может всё ещё умереть от `TILE_DEATH` и не респавниться (структурное,
  ожидаемое поведение — то же случилось бы и на настоящем сервере с такой же картой), но не от
  политики харнесса. На настоящих картах (все 7 содержат тайлы спавна — `ChooseSpawns`,
  `docs/formats.md` §12.3, ни разу не свалился с ошибкой на этом корпусе) `kill`→`Respawn()`
  работает штатно.
