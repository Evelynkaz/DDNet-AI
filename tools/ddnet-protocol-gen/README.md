# ddnet-protocol-gen — генератор Rust из протокольного описания DDNet

Читает `datasrc/network.py` + `datasrc/datatypes.py` настоящего дерева исходников DDNet 20.1
(пиннутый коммит `c9d208138f85755521f16a0096b6fe036c5c8698`) и печатает Rust-код в
`crates/ddai-net/src/generated/` — константы/enum/флаги, все объекты снапшота (`NETOBJTYPE_*`/
`NETEVENTTYPE_*`) и игровые сообщения (`Sv_*`/`Cl_*`) с их упаковкой/валидацией, имена UUID
расширенных (`ex`) типов. Байтовые раскладки и то, как это устроено, — `docs/formats.md` §13.

Исходники DDNet **не коммитятся** в этот репозиторий — путь к ним передаётся аргументом; сам
`generate.py` (наш код, GPL-3.0-only) ни строчки DDNet не копирует, только читает два файла как
Python-модули (оба — только stdlib, без сторонних зависимостей, ровно как `datasrc/compile.py`
самого DDNet).

## Файлы

| Файл | Назначение |
|---|---|
| `generate.py` | Сам генератор: `importlib`-импорт `datasrc/{datatypes,network}.py`, таблица символов для диапазонов (`MAX_CLIENTS`, `NUM_WEAPONS`, `TuneZone::*`, …), построчная печать четырёх файлов `generated/{mod,enums,objects,messages}.rs`, форматирование через `rustfmt` в конце. |

## Использование

```bash
python3 tools/ddnet-protocol-gen/generate.py ~/aiddnet/build/ddnet-20.1/src
```

Путь — корень дерева исходников DDNet (папка, где лежит `datasrc/`, не сама `datasrc/`). Пишет в
`crates/ddai-net/src/generated/` (переопределяется `--out`). Форматирует результат `rustfmt`, если
он есть в `PATH` (иначе печатает предупреждение — результат всё ещё валидный Rust, просто не
побайтово совпадёт с закоммиченным).

**Повторный запуск против того же пиннутого коммита воспроизводит закоммиченные файлы
побайтово** — это и есть тест «генератор соответствует коммиту» (собственный CI-раннер не может
гонять этот скрипт — ему нужно дерево DDNet, которое не коммитится; см.
`crates/ddai-net/tests/`, где обычные `cargo test` проверяют уже сгенерированный результат, а не
сам процесс генерации).

## Почему `importlib`, а не текстовый парсинг

`datasrc/network.py` и `datasrc/datatypes.py` — обычные Python-модули (`network.py` импортирует
только `datatypes`, тот — вовсе без сторонних импортов), которые сам `datasrc/compile.py` DDNet
запускает точно так же (импортирует и обходит `network.Objects`/`network.Messages` как живые
Python-объекты). Прямой импорт даёт нам ровно тот же порядок полей, дефолты, наследование
(`Character:CharacterCore`) и разрешение диапазонов (например, `len(Emotes)` — реальное
Python-выражение, вычисляемое при импорте), какие получает сам генератор DDNet — без риска
разойтись с ним из-за неточностей регекспового парсинга при следующем обновлении DDNet.

## Что генератор **не** трогает

- Системные сообщения (`NETMSG_*` из `protocol.h`) — у DDNet они не описаны в `datasrc/` вовсе
  (заведены руками), поэтому и у нас это hand-written `crates/ddai-net/src/sysmsg.rs` +
  `ExSysMsg` в `src/message.rs`, не генератор.
- Диапазоны, использующие символы вне жёсткой таблицы `SYMBOLS` в `generate.py`: генератор
  бросает `ValueError` при запуске, а не тихо угадывает значение — если DDNet добавит новый
  символ в `datasrc/`, это надо будет явно вписать в таблицу (с цитатой источника).
